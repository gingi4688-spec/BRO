# Data Engineering and Pipelines worked examples

## English

### Example A — Duplicate-after-retry + freshness contract

**Prompt.** A daily orders pipeline duplicates rows after an Airflow retry. Diagnose it and make it safe, with a freshness contract.

**Senior answer.** Diagnosis: the extract is **at-least-once** and the sink **appends** by partition date with no merge key, so a retry re-emits the already-landed rows — classic non-idempotent append. Fix: define a deterministic **idempotency key** = `order_id + source_updated_at`; write to a staging partition and **MERGE** into the target on that key, so the task is rerunnable for the same date with no extra rows. Do **not** promise exactly-once here — the source is at-least-once; the correct claim is at-least-once delivery made safe by an idempotent sink. **Freshness contract:** source close 02:00 UTC, expected warehouse availability 02:30, allowed lateness 20 min, completeness threshold ≥99%, owner = DE on-call, alert route = on-call channel; notify consumers only if completeness < 99%. **Backfill** (if a prior day must be re-run): write `orders_v2_backfill_YYYYMMDD`, run uniqueness on `order_id` and a revenue reconciliation against source, then swap the serving view.

**Why this passes.** It names the actual cause — at-least-once extract into an appending sink — instead of "add a dedupe step," so the fix targets the mechanism. The idempotency key is deterministic (`order_id + source_updated_at`) and the write becomes a MERGE on that key, which is exactly what makes the retry safe; a vaguer "use a unique constraint" would not survive a source that re-sends the same row with a new load timestamp. It refuses the exactly-once trap: the source is at-least-once, so the honest guarantee is at-least-once + idempotent sink, not a marketing claim. The freshness contract is a real contract — arrival time, allowed lateness, a completeness threshold, an owner, and an alert route — not "the dashboard looked slow." And the backfill writes to a versioned output and reconciles revenue before the swap, so a bad reprocess cannot silently corrupt live numbers.

### Example B — ELT pipeline with streaming aggregate and DLQ

**Prompt.** Design an ELT pipeline for order events into a warehouse, with a near-real-time orders-per-hour metric. Handle bad records and schema evolution.

**Senior answer.** **Ingest (E+L):** stream order events via **log-based CDC** (preserves commit order, captures deletes) into a landing topic serialized as **Avro** against a schema registry in **BACKWARD** compatibility mode, so consumers can be upgraded ahead of producers. Land raw, partitioned by ingest date, into the warehouse raw zone — **no transform yet**, preserving full lineage. Landing write uses idempotency key `order_id + source_updated_at` via MERGE. **Bad records:** unparseable/schema-invalid messages route to a **DLQ** topic carrying the raw payload, the error, the source offset, and the timestamp; a transient source error retries with backoff (separate from poison). Alert on the DLQ rate; replay after fixing the parser by re-ingesting through the same idempotent MERGE. **Transform (T, in-warehouse):** run cleaning/conforming/aggregation as versioned SQL models over the immutable raw partitions — a logic fix is a re-run, not a re-extract (this is *why* ELT, not ETL). **Streaming metric:** orders-per-hour as a **tumbling** 1-hour event-time window with a watermark and allowed-lateness of 15 min; allowed-late events correct the window, past-lateness events go to the side-output/DLQ. **Quality gate before serving:** row-count vs source within tolerance, uniqueness on `order_id`, null-rate bounds on required fields, and a **revenue reconciliation** (sum of `amount` matches source within tolerance) — a failure blocks promotion. **Schema evolution:** new optional fields are BACKWARD-compatible (add with a default); a breaking change (drop/retype a required field) requires a new version, the consumer list, and a deprecation window. **Freshness contract & verify-live:** arrival 02:30, allowed lateness 20 min, completeness ≥99%, owner = DE on-call; done means the reconciliation passed and freshness met in the running warehouse, not that the DAG turned green.

**Why this passes.** It is genuinely ELT and says *why*: raw is landed untransformed so transforms are versioned, in-warehouse, and replayable, which turns a transform-logic fix into a re-run instead of a re-extract — the defining ELT payoff. Log-based CDC is chosen for the right reason (order + deletes), not by default. The serialization layer is taught, not referenced: Avro + registry in BACKWARD mode, with the upgrade-consumers-first consequence stated. Bad records are quarantined to a DLQ with diagnostic context and a replay path, and transient failures are separated from poison so retries do not loop forever — nothing is silently dropped and one bad record cannot halt the stream. The streaming metric names the window **type** (tumbling), the watermark, and the allowed-lateness with an explicit late-event path, so late data is corrected or quarantined, never silently wrong. The quality gate actually *blocks* on a revenue reconciliation, and "done" is tied to that reconciliation in the running warehouse rather than a green DAG.

### Example C — Schema evolution under a registry

**Prompt.** A producer wants to remove a field and rename another on a high-traffic event consumed by four teams. We use Avro + a schema registry. How do we ship this without breaking consumers?

**Senior answer.** Treat both changes against the registry's compatibility mode. **Renaming** a field is, at the wire level, a **remove + add** — under BACKWARD compatibility you cannot simply drop the old field if consumers still read it. Sequence: (1) **Add** the new field (BACKWARD-safe: new optional field with a default) and have the producer dual-write old + new for a deprecation window. (2) Migrate the four consumers to read the new field; track each team's cutover. (3) Once all four have cut over and the registry+consumers confirm, the old field becomes removable — **removing a field with a default is BACKWARD-compatible**, so drop it as a new version. The straight remove-and-rename in one shot is a **breaking** change and the registry in BACKWARD mode should reject it. Document the version bump, the consumer list with cutover status, the deprecation window, and the rollback (re-point to the prior schema version). Never reuse the removed field's position/tag for a new meaning.

**Why this passes.** It refuses the one-shot breaking change and decomposes the rename into the only safe sequence under a BACKWARD registry — add-with-default, dual-write, migrate consumers, then remove — so no consumer ever reads a schema it cannot parse. It uses the registry's compatibility mode as the actual gate (the registry rejects the breaking version), not as decoration. It tracks the four consumers' cutover explicitly, because "compatible at the registry" still requires every consumer to have migrated before the old field is dropped. And it closes with the version, deprecation window, and rollback, and the do-not-reuse-the-tag rule that prevents a future silent corruption.

### Example D — stream-stream join & out-of-order enrichment

**Prompt.** Enrich a stream of `click` events with a stream of `impression` events (join on `ad_id`) to compute click-through, but clicks and impressions arrive out of order from different producers with independent lag. A naive join drops half the matches. Design it.

**Senior answer.** The bug is treating a **stream-stream join** like a batch join. Two independent streams have **independent event-time skew** — a click can arrive before its impression is processed, or long after — so you join on **event time within a bounded window**, hold state for that window, and handle **watermarks and late data** explicitly.

1. **Join on event time, not processing time.** Key both streams by `ad_id` and join where `click.event_time` falls within an **interval** of `impression.event_time` (e.g. click within `[impression, impression + 1h]` — the max plausible click delay). A processing-time join silently misses matches whenever the two streams' lag differs, which is always.
2. **Bounded state + window.** The engine buffers each side's events (keyed by `ad_id`) for the window duration and emits the joined row when the match arrives inside it. State is **bounded by the window and TTL'd**, or it grows forever — unbounded stream-join state is the classic OOM.
3. **Watermarks — per stream, independent.** Each stream carries its **own watermark** (event-time progress = "no more events older than T expected"). The join advances only when *both* watermarks pass the window end, so it neither emits incomplete results nor evicts state too early. Because the streams are independent, a slow impression stream must not make the join drop clicks that are still legitimately waiting — the watermark encodes exactly how long to wait.
4. **Late data — an explicit policy, not silence.** An event arriving later than its watermark allows is **late**. Decide, don't drop silently: (a) a bounded **allowed-lateness** grace that still updates the result, then (b) route anything beyond it to a **side-output / DLQ** for reprocessing or metrics, so you *know* the late-drop rate instead of it being invisible. A silent late-drop is exactly the "half the matches disappear" bug.
5. **Semantics + idempotency.** Emit with at-least-once + an idempotency key (`ad_id` + `click_id`) so a retried/duplicated join output does not double-count click-through downstream.

**Why this passes.** It names the real failure — a **stream-stream join is not a batch join**; the two streams have **independent event-time skew**, so joining on processing time silently drops matches whenever their lag differs. It joins on **event time within a bounded interval window** with **bounded, TTL'd state** (no unbounded-join OOM), uses **independent per-stream watermarks** so the join waits exactly as long as each stream's lateness requires before emitting/evicting, and — the piece the naive version omits — it makes **late data an explicit policy** (allowed-lateness grace, then side-output/DLQ with a measured late-drop rate) instead of silence, which is the exact cause of "half the matches vanish." It closes with idempotent output so a replay does not double-count. Every mechanism maps to the out-of-order reality the prompt describes; nothing invented.

### Օրինակ B — ELT pipeline streaming aggregate-ով և DLQ-ով

**Prompt.** Նախագծիր ELT pipeline order event-երի համար warehouse, near-real-time orders-per-hour metric-ով։ Մշակիր bad record-ները և schema evolution-ը։

**Ինչու է անցնում gate-ը.** Այն իսկապես ELT է և ասում է *ինչու*․ raw-ը land է լինում առանց transform-ի, ուստի transform-ները version-ավորված, in-warehouse և replayable են, ինչը transform-logic fix-ը դարձնում է re-run, ոչ re-extract — ELT-ի սահմանող օգուտը։ Log-based CDC-ն ընտրված է ճիշտ պատճառով (order + deletes), ոչ լռելյայն։ Serialization շերտը սովորեցված է, ոչ հղված․ Avro + registry BACKWARD mode-ով, upgrade-consumers-first հետևանքը նշված։ Bad record-ները quarantine-ված են DLQ՝ diagnostic context-ով և replay path-ով, և transient failure-ները բաժանված են poison-ից, որ retry-ները հավերժ չ-loop անեն — ոչինչ լուռ չի drop-վում և մեկ bad record-ը չի կարող կանգնեցնել stream-ը։ Streaming metric-ը անվանում է window-ի **տեսակը** (tumbling), watermark-ը և allowed-lateness-ը՝ բացահայտ late-event path-ով, ուստի ուշ data-ն ուղղվում է կամ quarantine-վում, երբեք լուռ սխալ չէ։ Quality gate-ը իրականում *block* է անում revenue reconciliation-ի վրա, և «done»-ը կապված է այդ reconciliation-ին running warehouse-ում, ոչ green DAG-ի։

### Օրինակ C — Schema evolution registry-ի տակ

**Prompt.** Producer-ը ուզում է field հանել և մեկ ուրիշը rename անել high-traffic event-ի վրա, որ սպառում են չորս թիմ։ Օգտագործում ենք Avro + schema registry։ Ոնց ship անենք առանց consumer-ներին կոտրելու։

**Senior պատասխան.** Երկու change-ն էլ վերցրու registry-ի compatibility mode-ի դեմ։ Field-ի **rename**-ը, wire մակարդակում, **remove + add** է — BACKWARD compatibility-ի տակ չես կարող պարզապես drop անել հին field-ը, եթե consumer-ները դեռ կարդում են այն։ Հերթականություն․ (1) **Ավելացրու** նոր field-ը (BACKWARD-safe՝ նոր optional field default-ով) և producer-ին տուր dual-write հին + նոր deprecation window-ի համար։ (2) Migrate արա չորս consumer-ները նոր field-ը կարդալու. track արա ամեն թիմի cutover-ը։ (3) Երբ չորսն էլ cut over են արել, և registry+consumer-ները հաստատում են, հին field-ը դառնում է removable — **default-ով field հանելը BACKWARD-compatible է**, ուստի drop արա այն որպես նոր version։ Ուղիղ remove-and-rename-ը մեկ հարվածով **breaking** change է, և registry-ն BACKWARD mode-ում պետք է մերժի այն։ Փաստաթղթավորիր version bump-ը, consumer list-ը cutover status-ով, deprecation window-ը և rollback-ը (re-point նախորդ schema version-ին)։ Երբեք մի՛ reuse արա հանված field-ի position/tag-ը նոր իմաստի համար։

**Ինչու է անցնում gate-ը.** Այն հրաժարվում է one-shot breaking change-ից և rename-ը քայքայում է BACKWARD registry-ի տակ միակ ապահով հերթականության — add-with-default, dual-write, migrate consumers, հետո remove — ուստի ոչ մի consumer երբեք չի կարդում schema, որ չի կարող parse անել։ Այն օգտագործում է registry-ի compatibility mode-ը որպես իրական gate (registry-ն մերժում է breaking version-ը), ոչ որպես դեկորացիա։ Այն track է անում չորս consumer-ի cutover-ը բացահայտ, որովհետև «registry-ում compatible»-ը դեռ պահանջում է, որ ամեն consumer migrate-վի մինչև հին field-ի drop-ը։ Եվ այն փակում է version-ով, deprecation window-ով և rollback-ով, plus do-not-reuse-the-tag կանոնով, որ կանխում է ապագա լուռ corruption։

### Օրինակ D — stream-stream join & out-of-order enrichment

**Prompt.** Enrich արա `click` event-ների stream-ը `impression` event-ների stream-ով (join `ad_id`-ով)՝ click-through հաշվելու, բայց click-երն ու impression-ները գալիս են out of order տարբեր producer-ներից independent lag-ով։ Naive join-ը կորցնում է match-երի կեսը։ Նախագծիր այն։

**Senior պատասխան.** Bug-ը **stream-stream join**-ը batch join-ի պես վերաբերվելն է։ Երկու independent stream ունեն **independent event-time skew** — click-ը կարող է գա իր impression-ի մշակվելուց առաջ, կամ շատ ուշ — ուստի join ես անում **event time-ով bounded window-ի ներսում**, state պահում այդ window-ի համար, և **watermark-ներն ու late data-ն** բացահայտ մշակում։

1. **Join արա event time-ով, ոչ processing time-ով.** Key արա երկու stream-ը `ad_id`-ով և join արա, որտեղ `click.event_time`-ը ընկնում է `impression.event_time`-ի **interval**-ի ներսում (օր.՝ click `[impression, impression + 1h]`-ում — max հավանական click delay-ը)։ Processing-time join-ը լուռ բաց է թողնում match-երը, երբ երկու stream-ի lag-ը տարբեր է, ինչը միշտ է։
2. **Bounded state + window.** Engine-ը buffer է անում ամեն կողմի event-ները (`ad_id`-ով keyed) window-ի տևողության համար և emit joined row-ը, երբ match-ը գալիս է ներսում։ State-ը **bounded է window-ով և TTL'd**, թե չէ աճում է ընդմիշտ — unbounded stream-join state-ը classic OOM-ն է։
3. **Watermark-ներ — per stream, independent.** Ամեն stream կրում է իր **սեփական watermark**-ը (event-time progress = «T-ից հին event այլևս չի սպասվում»)։ Join-ը առաջ է շարժվում միայն, երբ *երկու* watermark-ն էլ անցնում են window-ի վերջը, ուստի ոչ incomplete result է emit անում, ոչ state շատ շուտ evict։ Քանի որ stream-ները independent են, դանդաղ impression stream-ը չպետք է ստիպի join-ին drop անել click-երը, որ դեռ legitimate սպասում են — watermark-ը կոդավորում է հենց, թե որքան սպասել։
4. **Late data — բացահայտ policy, ոչ լռություն.** Event, որ գալիս է իր watermark-ի թույլատրածից ուշ, **late** է։ Որոշիր, մի՛ drop արա լուռ․ (ա) bounded **allowed-lateness** grace, որ դեռ update է անում result-ը, հետո (բ) route արա դրանից անդին ամեն ինչ **side-output / DLQ**՝ reprocess-ի կամ metrics-ի, որ *գիտենաս* late-drop rate-ը, ոչ թե անտեսանելի լինի։ Silent late-drop-ը հենց «match-երի կեսը անհետանում է» bug-ն է։
5. **Semantics + idempotency.** Emit արա at-least-once + idempotency key-ով (`ad_id` + `click_id`), որ retried/duplicated join output-ը click-through-ը downstream double-count չանի։

**Ինչու է անցնում gate-ը.** Այն անվանում է իրական failure-ը — **stream-stream join-ը batch join չէ**. երկու stream ունեն **independent event-time skew**, ուստի processing time-ով join անելը լուռ drop է անում match-երը, երբ lag-ը տարբեր է։ Այն join է անում **event time-ով bounded interval window-ում** **bounded, TTL'd state-ով** (ոչ unbounded-join OOM), օգտագործում **independent per-stream watermark-ներ**, ուստի join-ը սպասում է հենց այնքան, որքան ամեն stream-ի lateness-ը պահանջում է, նախքան emit/evict անելը, և — կտորը, որ naive տարբերակը բաց է թողնում — **late data-ն դարձնում է բացահայտ policy** (allowed-lateness grace, հետո side-output/DLQ չափված late-drop rate-ով)՝ լռության փոխարեն, ինչը հենց «match-երի կեսը անհետանում է»-ի պատճառն է։ Այն փակում է idempotent output-ով, որ replay-ը double-count չանի։ Ամեն մեխանիզմ map է անում out-of-order իրականությանը, որ prompt-ը նկարագրում է. ոչինչ հորինված չէ։
