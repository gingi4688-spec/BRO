# Data Engineering and Pipelines manual

## English

### Operating principle

Senior data-engineering work is decision-grade only when it converts a vague pipeline picture into explicit, auditable guarantees — and refuses to inherit a guarantee the underlying system cannot keep. The deliverable is one of a few shapes: a pipeline design, a freshness/SLA contract, a backfill runbook, a streaming-semantics review, or a schema-evolution plan. The single discipline that governs all of them is honesty about the end-to-end guarantee. A streaming engine can advertise exactly-once, but the guarantee a user actually gets is bounded by the weakest link — usually the sink. If the sink cannot dedupe or commit transactionally, the real guarantee is at-least-once with idempotent writes, and saying "exactly-once" is a lie that surfaces as duplicate revenue rows three weeks later. So the first move is always to trace the guarantee to where it actually holds: the idempotency key, the sink merge condition, the watermark and lateness policy, the DLQ path. Reliability in data is not "the DAG turned green"; it is data that is fresh, complete, deduplicated, schema-valid, and reconciled — with every one of those properties tied to a mechanism a reviewer can check.

### Mechanism reference

- **Delivery semantics: exactly-once vs at-least-once** — At-least-once means every record is processed one or more times; duplicates are possible and must be absorbed by the sink. Exactly-once means each record affects the result once. In practice end-to-end exactly-once is `at-least-once processing + an idempotent or transactional sink`, not a single engine flag. Kafka transactions and Flink checkpoints make a *processing stage* consistent (atomic offset+state commit), but end-to-end correctness still depends on the sink: deduplication keys, transactional writes, and replay behavior. If the sink only appends, retries duplicate — full stop. The honest design names the processing guarantee, the sink's dedupe/transaction mechanism, and what a replay does.
- **Idempotency and keys** — A pipeline is idempotent when re-running it for the same input produces the same output with no extra rows. Achieve it with a deterministic key (natural key, or a surrogate built from stable fields like `source_id + source_updated_at`) and an upsert/MERGE on that key, never a blind append. The key is the contract that makes retries and backfills safe.
- **Event time vs processing time, watermarks, and allowed lateness** — Event time is when the business event happened; processing time is when the system saw it. They diverge under network delay, batching, and outages. A **watermark** is the engine's estimate of "event time has progressed to T; events older than T are probably all here" — it lets event-time windows decide when to close. **Allowed lateness** extends how long after the watermark a late event can still update an already-emitted window result. Past allowed lateness, the event is dropped *or* routed to a side-output/DLQ. Windowing with no watermark-and-lateness policy silently drops or mis-buckets real late data.
- **Window types** — **Tumbling**: fixed-size, non-overlapping, contiguous buckets; each event lands in exactly one window (e.g. hourly order counts). Use when buckets must not overlap and every event counts once. **Sliding**: fixed-size windows that advance by a step smaller than the size, so windows overlap and each event lands in several (e.g. a 5-minute average emitted every 1 minute). Use for smooth moving aggregates; do *not* use when an event must be counted once. **Session**: variable-length windows bounded by a gap of inactivity; a new event within the gap extends the session, a longer silence closes it (e.g. user activity sessions). Use when the natural unit is a burst of activity, not a clock interval; do *not* use when you need aligned, comparable fixed buckets.
- **CDC (change data capture)** — Log-based CDC reads the database's write-ahead/binlog, preserves commit order, and captures deletes; it is the default for correctness. Query-based CDC polls an `updated_at`/version column; it is simpler but misses hard deletes and clock-skewed updates, and needs an overlap window plus a monotonic key. High-watermark incremental loads need a monotonic cursor, an overlap to avoid boundary misses, and an idempotent merge so the overlap does not duplicate.
- **Serialization and the schema-registry layer (Avro vs Protobuf)** — Schemas must be enforced, not implied. **Avro** stores its schema with (or alongside) the data and pairs natively with a schema registry; its reader/writer-schema resolution makes it the common choice for evolving streaming records. **Protobuf** is a compact, strongly-typed, cross-language contract with explicit numbered field tags; you never reuse or renumber a tag. A **schema registry** holds versioned schemas and enforces a **compatibility mode** on every new version: **BACKWARD** (new schema can read data written by the previous schema — safe to add optional fields / remove fields with defaults; lets you upgrade consumers first), **FORWARD** (old schema can read data written by the new schema — lets you upgrade producers first), **FULL** (both directions), and **NONE** (no check — drift risk). The mode is the contract: choose it deliberately and let the registry reject incompatible changes before they reach production.
- **Dead-letter queue (DLQ) handling** — A poison message (unparseable, schema-invalid, or repeatedly failing) must neither be silently dropped nor allowed to block the stream. Route it to a DLQ — a separate topic/queue/table — carrying enough to diagnose: the raw payload, the error/exception, the source offset or key, and the timestamp. Track a quarantine count and alert on its rate. Provide a documented **replay** path: fix the cause (parser, schema, downstream), then re-ingest the DLQ records through the normal idempotent path so they are not lost and not double-counted. Distinguish transient failures (retry with backoff) from poison (route to DLQ) so retries do not loop forever on a record that will never succeed.
- **Orchestration and idempotent backfill** — A DAG task must be rerunnable: it declares its input partition, output partition, idempotency key, dependencies, retry policy, a backfill command, and data-quality tests. A backfill must never overwrite production in place. Write to a versioned/partitioned output (e.g. `target_backfill_YYYYMMDD`), run uniqueness and source-to-target reconciliation, then atomically swap the serving view/pointer so rollback is one step. Backfills are idempotent by partition: re-running the same partition yields the same result.
- **Freshness contracts and data-quality gates** — A freshness contract names expected arrival time, allowed lateness, a completeness threshold, the owner, and the alert route — not "the dashboard loaded". A quality gate runs assertions between source and serving that *block* release on failure: freshness, volume/row-count vs expectation, schema conformance, uniqueness (no dup keys), null-rate bounds, and source-to-target reconciliation (counts/sums match within tolerance).

### Decision rules

1. Resolve any "exactly-once" request at the sink: name the processing guarantee, the sink's dedupe/transaction mechanism, and replay behavior; if the sink cannot dedupe or commit atomically, promise at-least-once + idempotency key, not exactly-once.
2. Make every retryable pipeline idempotent: a deterministic key + upsert/MERGE, never a blind append; a retry that duplicates is a design defect.
3. On event-time streaming, require a watermark strategy and an explicit allowed-lateness policy, and state the late-event path (drop, side-output, or DLQ).
4. Name the window type and justify it: tumbling for non-overlapping fixed buckets, sliding for overlapping moving aggregates, session for inactivity-gap-bounded activity; state the size/step/gap.
5. Choose ETL vs ELT on where compute and governance live: ELT to keep raw lineage and replayable in-warehouse transforms; ETL when you must mask/validate before landing; state which and why.
6. Classify schema change compatibility (backward/forward/full/breaking) against the registry mode, list consumers, and bump the version or migrate; never ship a producer change with the consumer impact unnamed.
7. Pin the serialization format and its compatibility rules: Avro for registry-driven streaming evolution, Protobuf for compact cross-language contracts with stable field tags; never leave records schemaless.
8. Default CDC to log-based; use query-based only with stated missed-delete handling, an overlap window, and a monotonic key.
9. Route bad records to a DLQ with diagnostic context (raw payload, error, offset/key, timestamp) and a documented replay path; never silently drop, never let one record block the stream; separate transient (retry) from poison (DLQ).
10. Backfill to a versioned/partitioned output, reconcile, then atomically swap; keep it idempotent per partition and reversible in one step; never overwrite production in place.
11. Write a freshness contract (arrival, allowed lateness, completeness threshold, owner, alert route); freshness is not dashboard load time.
12. Gate every release on data-quality assertions (freshness, volume, schema, uniqueness, null-rate, reconciliation) that block on failure; "it ran" is not a gate.
13. Never treat a green DAG run as verification; check the real downstream metric/contract (fresh, complete, reconciled) before declaring done.
14. Gate irreversible/data-loss steps (destructive backfill, in-place overwrite, schema field drop in production) behind explicit human approval with a stated rollback/backup.

### Failure-repair playbook

1. **Exactly-once promised on a non-dedupe sink** → re-state the real guarantee as at-least-once + idempotent sink; add the deterministic key and the upsert/MERGE, and correct the claim.
2. **Duplicate rows after a retry** → trace replay vs transform-nondeterminism vs sink-append; if the sink appends, convert to upsert on a deterministic key; if no natural key, build a surrogate from stable fields.
3. **Late events silently dropped** → add a watermark strategy and an allowed-lateness policy, and route past-lateness events to a side-output/DLQ instead of vanishing them.
4. **Wrong window type** → re-derive from the requirement: count-once → tumbling; overlapping moving aggregate → sliding; inactivity-bounded → session; state size/step/gap explicitly.
5. **Schema drift breaks consumers** → run the registry compatibility check, classify the change, list consumers, and either bump the version (BACKWARD/FORWARD/FULL) or run a versioned migration with rollback.
6. **Schemaless / mixed formats** → pin a format and registry now (Avro for streaming evolution, Protobuf for typed cross-language), set the compatibility mode, and stop accepting unschema'd records.
7. **Query-based CDC missing deletes** → add hard-delete handling (tombstones / log-based source), an overlap window, a monotonic cursor, and a periodic source-to-target reconciliation to catch divergence.
8. **Poison message kills or is lost** → add a DLQ with full diagnostic context, separate transient retries from poison routing, alert on quarantine rate, and document the fix-and-replay path through the idempotent ingest.
9. **Backfill overwrites history in place** → redirect it to a versioned/partitioned output, reconcile counts/sums, then swap the serving pointer; make it idempotent per partition so reruns are safe.
10. **Freshness defined as dashboard load time** → replace with a contract: expected arrival, allowed lateness, completeness threshold, owner, alert route; alert on arrival + completeness, not on chart render.
11. **No data-quality gate** → insert blocking assertions (freshness/volume/schema/uniqueness/null/reconciliation) between source and serving; a failing assertion must stop promotion, not warn-and-continue.
12. **"Done" on a green DAG** → before closing, check the real downstream metric/contract: is the data fresh, complete, deduplicated, and reconciled against source? A green run is necessary, not sufficient.

### Worked ELT pipeline (mechanism walkthrough)

Build an **ELT** order-events pipeline feeding a warehouse, end to end:

1. **Extract / ingest (E + L).** Stream order events from the source via **log-based CDC** (preserves order, captures deletes) into a landing topic, serialized as **Avro** against a schema registry in **BACKWARD** compatibility mode so consumers can be upgraded first. Land the raw records partitioned by ingest date into the warehouse's raw zone — *no transform yet*; this preserves full lineage and lets you replay transforms later. Bad/unparseable records route to a **DLQ** topic with payload + error + offset; a transient source error retries with backoff.
2. **Idempotency at landing.** Write raw with an idempotency key `order_id + source_updated_at` via MERGE, so a CDC replay or consumer retry cannot duplicate landed rows.
3. **Transform (T, in-warehouse).** Run the cleaning/conforming/aggregation as SQL/transform models *inside* the warehouse against the raw zone — versioned and replayable. Because transforms read from immutable raw partitions, a logic fix is a re-run, not a re-extract.
4. **Streaming aggregate (if a live metric is needed).** For a near-real-time orders-per-hour metric, use a **tumbling** 1-hour event-time window with a watermark and an allowed-lateness of, say, 15 minutes; late-but-allowed events correct the window, past-lateness events go to the side-output/DLQ — counts are never silently wrong.
5. **Quality gate.** Before promoting the transformed model to serving, run blocking assertions: row-count vs source within tolerance, uniqueness on `order_id`, null-rate bounds on required fields, and source-to-target **revenue reconciliation** (sum of `amount` matches source within tolerance). A failure blocks promotion.
6. **Backfill (when transform logic changes).** Reprocess into `orders_fact_backfill_YYYYMMDD` from the immutable raw zone, run the same quality+reconciliation gate, then **atomically swap** the serving view to the backfill output — rollback is re-pointing the view. Idempotent per partition.
7. **Freshness contract & verify-live.** Contract: source close 02:00 UTC, expected serving availability 02:30, allowed lateness 20 min, completeness ≥ 99%, owner = DE on-call, alert on breach. Done means the **reconciliation passed and freshness/completeness met in the running warehouse** — not that the DAG turned green.

This is ELT (load raw, transform in-warehouse) precisely because we want immutable raw lineage and replayable transforms; an ETL design would transform before landing and lose the cheap re-run.

## Հայերեն

### Գործառնական սկզբունք

Ավագ data-engineering աշխատանքը decision-grade է միայն այն ժամանակ, երբ pipeline-ի մշուշոտ պատկերը վերածում է հստակ, auditable երաշխիքների — և հրաժարվում է ժառանգել երաշխիք, որ հիմքում ընկած system-ը չի կարող պահել։ Deliverable-ը մի քանի ձևից մեկն է՝ pipeline design, freshness/SLA contract, backfill runbook, streaming-semantics review կամ schema-evolution plan։ Բոլորը կառավարող միակ կարգապահությունը end-to-end երաշխիքի մասին ազնվությունն է։ Streaming engine-ը կարող է գովազդել exactly-once, բայց երաշխիքը, որ user-ն իրականում ստանում է, սահմանափակված է ամենաթույլ օղակով — սովորաբար sink-ով։ Եթե sink-ը չի կարող dedupe անել կամ transactional commit անել, իրական երաշխիքը at-least-once է idempotent write-երով, և «exactly-once» ասելը սուտ է, որ դուրս է գալիս որպես duplicate revenue row-եր երեք շաբաթ անց։ Ուստի առաջին քայլը միշտ երաշխիքը հետագծելն է այնտեղ, որտեղ այն իրականում պահվում է՝ idempotency key-ը, sink-ի merge condition-ը, watermark-ը և lateness policy-ն, DLQ path-ը։ Data-ում հուսալիությունը «DAG-ը green դարձավ»-ը չէ. այն data է, որ fresh, complete, deduplicated, schema-valid և reconciled է — և այս հատկություններից յուրաքանչյուրը կապված է mechanism-ի հետ, որ reviewer-ը կարող է ստուգել։

### Մեխանիզմների տեղեկագիր

- **Delivery semantics․ exactly-once ընդդեմ at-least-once-ի** — At-least-once-ը նշանակում է, որ ամեն record-ը մշակվում է մեկ կամ ավելի անգամ. duplicate-ը հնարավոր է և պետք է կլանվի sink-ի կողմից։ Exactly-once-ը նշանակում է, որ ամեն record-ը result-ի վրա ազդում է մեկ անգամ։ Գործնականում end-to-end exactly-once-ը `at-least-once processing + idempotent կամ transactional sink` է, ոչ թե մեկ engine flag։ Kafka transaction-ը և Flink checkpoint-ը *processing stage*-ը consistent են դարձնում (atomic offset+state commit), բայց end-to-end correctness-ը դեռ կախված է sink-ից՝ dedupe key-ից, transactional write-ից և replay behavior-ից։ Եթե sink-ը միայն append է անում, retry-ն duplicate է անում՝ վերջ։ Ազնիվ design-ը անվանում է processing guarantee-ն, sink-ի dedupe/transaction մեխանիզմը և ինչ է անում replay-ը։
- **Idempotency և key-եր** — Pipeline-ը idempotent է, երբ նույն input-ի համար re-run-ը նույն output-ն է տալիս՝ առանց ավելորդ row-երի։ Հասիր դրան դետերմինիստիկ key-ով (natural key, կամ surrogate՝ կառուցված stable field-երից, ինչպես `source_id + source_updated_at`) և upsert/MERGE-ով այդ key-ի վրա, երբեք blind append-ով։ Key-ն այն contract-ն է, որ retry-ն և backfill-ը ապահով է դարձնում։
- **Event time ընդդեմ processing time-ի, watermark և allowed lateness** — Event time-ը business event-ի տեղի ունենալու ժամանակն է. processing time-ը՝ երբ system-ը տեսավ այն։ Դրանք շեղվում են network delay-ի, batching-ի և outage-ի դեպքում։ **Watermark**-ը engine-ի estimate-ն է՝ «event time-ը հասել է T-ի. T-ից հին event-ները հավանաբար բոլորն այստեղ են» — այն թույլ է տալիս event-time window-ին որոշել, թե երբ փակվել։ **Allowed lateness**-ը երկարացնում է, թե watermark-ից որքան հետո ուշ event-ը կարող է դեռ update անել արդեն emit-ված window result-ը։ Allowed lateness-ից հետո event-ը drop է լինում *կամ* ուղղորդվում side-output/DLQ։ Windowing-ը առանց watermark-and-lateness policy-ի լուռ drop կամ սխալ-bucket է անում իրական ուշ data-ն։
- **Window-ի տեսակներ** — **Tumbling**․ ֆիքսված չափի, չհատվող, հարակից bucket. ամեն event-ը land է լինում ճիշտ մեկ window-ում (օր.՝ ժամային order count)։ Օգտագործիր, երբ bucket-ները չպետք է հատվեն և ամեն event-ը հաշվվում է մեկ անգամ։ **Sliding**․ ֆիքսված չափի window, որ առաջ է շարժվում չափից փոքր step-ով, ուստի window-ները հատվում են և ամեն event-ը land է լինում մի քանիսում (օր.՝ 5-րոպեանոց միջին, emit-ված ամեն 1 րոպեն)։ Օգտագործիր հարթ շարժվող aggregate-ի համար. *մի՛* օգտագործիր, երբ event-ը պետք է մեկ անգամ հաշվվի։ **Session**․ փոփոխական երկարության window՝ սահմանված inactivity gap-ով. gap-ի ներսում նոր event-ը երկարացնում է session-ը, ավելի երկար լռությունը փակում է այն (օր.՝ user-ի ակտիվության session)։ Օգտագործիր, երբ բնական միավորը ակտիվության պոռթկում է, ոչ ժամացույցի interval. *մի՛* օգտագործիր, երբ պետք են համահունչ, համեմատելի ֆիքսված bucket-ներ։
- **CDC (change data capture)** — Log-based CDC-ն կարդում է database-ի write-ahead/binlog-ը, պահում commit order-ը և բռնում delete-երը. այն լռելյայն ընտրությունն է correctness-ի համար։ Query-based CDC-ն polling է անում `updated_at`/version սյունով. այն ավելի պարզ է, բայց բաց է թողնում hard delete-երը և clock-skewed update-երը, և պետք ունի overlap window plus monotonic key։ High-watermark incremental load-ին պետք են monotonic cursor, overlap՝ boundary-ի բացթողումից խուսափելու, և idempotent merge, որ overlap-ը չ-duplicate անի։
- **Serialization և schema-registry շերտ (Avro ընդդեմ Protobuf-ի)** — Schema-ները պետք է enforce-ված լինեն, ոչ ենթադրված։ **Avro**-ն իր schema-ն պահում է data-ի հետ (կամ կողքին) և native զուգվում է schema registry-ի հետ. իր reader/writer-schema resolution-ը այն դարձնում է ընդհանուր ընտրությունը evolving streaming record-ների համար։ **Protobuf**-ը compact, ուժեղ-տիպավորված, cross-language contract է՝ բացահայտ համարակալված field tag-երով. tag-ը երբեք չես reuse կամ renumber անում։ **Schema registry**-ն պահում է version-ավորված schema-ներ և enforce է անում **compatibility mode** ամեն նոր version-ի վրա․ **BACKWARD** (նոր schema-ն կարող է կարդալ նախորդ schema-ով գրված data — ապահով է optional field ավելացնելը / default-ով field հանելը. թույլ է տալիս նախ consumer-ները upgrade անել), **FORWARD** (հին schema-ն կարող է կարդալ նոր schema-ով գրված data — թույլ է տալիս նախ producer-ները upgrade անել), **FULL** (երկու ուղղություն), և **NONE** (check չկա — drift risk)։ Mode-ը contract-ն է. ընտրիր այն գիտակցորեն և թող registry-ն մերժի incompatible change-երը նախքան production հասնելը։
- **Dead-letter queue (DLQ) մշակում** — Poison message-ը (չ-parse-վող, schema-invalid, կամ կրկնակի fail-վող) պետք է ո՛չ լուռ drop լինի, ո՛չ թույլ տրվի stream-ը block անել։ Ուղղորդիր այն DLQ՝ առանձին topic/queue/table՝ diagnose-ի բավարարով՝ raw payload, error/exception, source offset կամ key, և timestamp։ Հաշվիր quarantine count և alert արա իր rate-ի վրա։ Տրամադրիր փաստաթղթավորված **replay** path․ ուղղիր պատճառը (parser, schema, downstream), հետո re-ingest արա DLQ record-ները նորմալ idempotent path-ով, որ չկորեն և չ-double-count լինեն։ Տարբերիր transient failure-ները (retry՝ backoff-ով) poison-ից (route DLQ), որ retry-ները հավերժ չ-loop անեն երբեք-չ-հաջողվող record-ի վրա։
- **Orchestration և idempotent backfill** — DAG task-ը պետք է rerunnable լինի․ այն հայտարարում է իր input partition-ը, output partition-ը, idempotency key-ը, dependency-ները, retry policy-ն, backfill command-ը և data-quality test-երը։ Backfill-ը երբեք production-ը տեղում չպետք է overwrite անի։ Գրիր versioned/partitioned output (օր.՝ `target_backfill_YYYYMMDD`), գործարկիր uniqueness և source-to-target reconciliation, հետո atomic-ով swap արա serving view-ը/pointer-ը, որ rollback-ը մեկ քայլ լինի։ Backfill-ները idempotent են ըստ partition-ի․ նույն partition-ի re-run-ը նույն result-ն է տալիս։
- **Freshness contract և data-quality gate** — Freshness contract-ը անվանում է expected arrival time, allowed lateness, completeness threshold, owner և alert route — ոչ թե «dashboard-ը load եղավ»։ Quality gate-ը գործարկում է assertion-ներ source-ի և serving-ի միջև, որ fail-ի դեպքում *block* են անում release-ը՝ freshness, volume/row-count ընդդեմ սպասվածի, schema conformance, uniqueness (dup key չկա), null-rate սահման, և source-to-target reconciliation (count/sum համընկնում tolerance-ի ներսում)։

### Որոշման կանոններ

1. Լուծիր ցանկացած «exactly-once» հարցում sink-ի վրա․ անվանի՛ր processing guarantee-ն, sink-ի dedupe/transaction մեխանիզմը և replay behavior-ը. եթե sink-ը չի կարող dedupe կամ atomic commit անել, խոստացիր at-least-once + idempotency key, ոչ exactly-once։
2. Ամեն retry-ունակ pipeline դարձրու idempotent․ դետերմինիստիկ key + upsert/MERGE, երբեք blind append. retry-ն, որ duplicate է անում, դիզայնի թերություն է։
3. Event-time streaming-ի վրա պահանջիր watermark strategy և հստակ allowed-lateness policy, և նշի՛ր late-event path-ը (drop, side-output, թե DLQ)։
4. Անվանի՛ր window-ի տեսակը և հիմնավորիր․ tumbling՝ չհատվող ֆիքսված bucket-ի, sliding՝ հատվող շարժվող aggregate-ի, session՝ inactivity-gap-ով սահմանված ակտիվության. նշի՛ր size/step/gap-ը։
5. Ընտրիր ETL ընդդեմ ELT-ի ըստ այն, թե որտեղ են compute-ն ու governance-ը․ ELT՝ raw lineage և replayable in-warehouse transform պահելու համար. ETL՝ երբ պետք է mask/validate անես նախքան land-ը. նշի՛ր որը և ինչու։
6. Classify արա schema change compatibility-ն (backward/forward/full/breaking) registry mode-ի դեմ, գրիր consumer-ները և bump արա version-ը կամ migrate արա. երբեք producer change մի՛ ship արա առանց consumer-ի impact-ը անվանելու։
7. Pin արա serialization format-ը և իր compatibility rule-ները․ Avro՝ registry-driven streaming evolution-ի, Protobuf՝ compact cross-language contract-ի համար՝ stable field tag-երով. record-ները schemaless մի՛ թող։
8. CDC-ն լռելյայն դարձրու log-based. query-based օգտագործիր միայն նշված missed-delete-ի մշակմամբ, overlap window-ով և monotonic key-ով։
9. Bad record-ները ուղղորդիր DLQ՝ diagnostic context-ով (raw payload, error, offset/key, timestamp) և փաստաթղթավորված replay path-ով. երբեք լուռ մի՛ drop արա, երբեք մի՛ թող մեկ record-ը block անի stream-ը. բաժանիր transient-ը (retry) poison-ից (DLQ)։
10. Backfill արա versioned/partitioned output, reconcile արա, հետո atomic swap. պահիր idempotent ըստ partition-ի և մեկ քայլով հետշրջելի. երբեք production-ը տեղում մի՛ overwrite արա։
11. Գրիր freshness contract (arrival, allowed lateness, completeness threshold, owner, alert route). freshness-ը dashboard load time չէ։
12. Gate արա ամեն release data-quality assertion-ով (freshness, volume, schema, uniqueness, null-rate, reconciliation), որ fail-ի դեպքում block է անում. «աշխատեց»-ը gate չէ։
13. Երբեք green DAG run-ը verification մի՛ համարիր. ստուգիր իրական downstream metric-ը/contract-ը (fresh, complete, reconciled) մինչև done ասելը։
14. Gate արա անդառնալի/data-loss step-երը (destructive backfill, in-place overwrite, production-ում schema field drop) հստակ մարդկային approval-ի և նշված rollback/backup-ի հետևում։

### Վերականգնման խաղագիրք

1. **Exactly-once խոստացված non-dedupe sink-ի վրա** → վերա-նշիր իրական երաշխիքը որպես at-least-once + idempotent sink. ավելացրու դետերմինիստիկ key-ը և upsert/MERGE-ը, և ուղղիր պնդումը։
2. **Duplicate row-եր retry-ից հետո** → trace արա replay ընդդեմ transform-nondeterminism-ի ընդդեմ sink-append-ի. եթե sink-ը append է անում, փոխիր upsert-ի դետերմինիստիկ key-ի վրա. եթե natural key չկա, կառուցիր surrogate stable field-երից։
3. **Ուշ event-ները լուռ drop-ված** → ավելացրու watermark strategy և allowed-lateness policy, և ուղղորդիր past-lateness event-ները side-output/DLQ, անհետացնելու փոխարեն։
4. **Սխալ window տեսակ** → վերաբխեցրու պահանջից․ count-once → tumbling. հատվող շարժվող aggregate → sliding. inactivity-bounded → session. նշի՛ր size/step/gap-ը բացահայտ։
5. **Schema drift-ը կոտրում է consumer-ներին** → գործարկիր registry compatibility check-ը, classify արա change-ը, գրիր consumer-ները և կա՛մ bump արա version-ը (BACKWARD/FORWARD/FULL), կա՛մ գործարկիր versioned migration՝ rollback-ով։
6. **Schemaless / խառը format-ներ** → pin արա format և registry հիմա (Avro՝ streaming evolution-ի, Protobuf՝ typed cross-language-ի), սահմանիր compatibility mode-ը և դադարիր unschema'd record ընդունել։
7. **Query-based CDC-ն բաց է թողնում delete-ները** → ավելացրու hard-delete մշակում (tombstone / log-based source), overlap window, monotonic cursor և պարբերական source-to-target reconciliation՝ divergence բռնելու։
8. **Poison message-ը սպանում է կամ կորում է** → ավելացրու DLQ՝ լրիվ diagnostic context-ով, բաժանիր transient retry-ները poison routing-ից, alert արա quarantine rate-ի վրա և փաստաթղթավորիր fix-and-replay path-ը idempotent ingest-ով։
9. **Backfill-ը history-ն overwrite է անում տեղում** → ուղղորդիր այն versioned/partitioned output, reconcile արա count/sum-ը, հետո swap արա serving pointer-ը. դարձրու idempotent ըստ partition-ի, որ rerun-ները ապահով լինեն։
10. **Freshness-ը սահմանված dashboard load time-ով** → փոխարինիր contract-ով․ expected arrival, allowed lateness, completeness threshold, owner, alert route. alert արա arrival + completeness-ի վրա, ոչ chart render-ի։
11. **Data-quality gate չկա** → տեղադրիր blocking assertion-ներ (freshness/volume/schema/uniqueness/null/reconciliation) source-ի և serving-ի միջև. fail-եղած assertion-ը պետք է կանգնեցնի promotion-ը, ոչ թե warn-and-continue։
12. **«Done» green DAG-ի վրա** → փակելուց առաջ ստուգիր իրական downstream metric-ը/contract-ը․ data-ն fresh, complete, deduplicated և source-ի դեմ reconciled է՞։ Green run-ը անհրաժեշտ է, ոչ բավարար։

### Worked ELT pipeline (mechanism walkthrough)

Կառուցիր **ELT** order-events pipeline, որ սնում է warehouse, ծայրից ծայր․

1. **Extract / ingest (E + L)։** Stream արա order event-ները source-ից **log-based CDC**-ով (պահում է order-ը, բռնում delete-երը) դեպի landing topic, serialize-ված որպես **Avro** schema registry-ի դեմ **BACKWARD** compatibility mode-ով, որ consumer-ները նախ upgrade-վեն։ Land արա raw record-ները ingest date-ով partition-ված warehouse-ի raw zone — *դեռ transform չկա*. սա պահում է լրիվ lineage և թույլ է տալիս հետո replay անել transform-ները։ Bad/չ-parse-վող record-ները ուղղորդվում են **DLQ** topic՝ payload + error + offset-ով. transient source error-ը retry է backoff-ով։
2. **Idempotency landing-ին։** Գրիր raw-ը idempotency key-ով `order_id + source_updated_at` MERGE-ով, որ CDC replay-ը կամ consumer retry-ն չկարողանա duplicate land-ված row անել։
3. **Transform (T, in-warehouse)։** Գործարկիր cleaning/conforming/aggregation-ը որպես SQL/transform model *warehouse-ի ներսում* raw zone-ի դեմ — version-ավորված և replayable։ Քանի որ transform-ները կարդում են immutable raw partition-ից, logic fix-ը re-run է, ոչ re-extract։
4. **Streaming aggregate (եթե live metric է պետք)։** Near-real-time orders-per-hour metric-ի համար օգտագործիր **tumbling** 1-ժամանոց event-time window՝ watermark-ով և, ասենք, 15-րոպեանոց allowed-lateness-ով. ուշ-բայց-allowed event-ները ուղղում են window-ը, past-lateness event-ները գնում side-output/DLQ — count-ները երբեք լուռ սխալ չեն։
5. **Quality gate։** Transform-ված model-ը serving promote անելուց առաջ գործարկիր blocking assertion-ներ․ row-count ընդդեմ source-ի tolerance-ի ներսում, uniqueness `order_id`-ի վրա, null-rate սահման required field-երի վրա, և source-to-target **revenue reconciliation** (`amount`-ի sum-ը համընկնում է source-ին tolerance-ի ներսում)։ Fail-ը block է անում promotion-ը։
6. **Backfill (երբ transform logic-ը փոխվում է)։** Reprocess արա `orders_fact_backfill_YYYYMMDD`-ի մեջ immutable raw zone-ից, գործարկիր նույն quality+reconciliation gate-ը, հետո **atomic swap** արա serving view-ը backfill output-ին — rollback-ը view-ի re-point-ն է։ Idempotent ըստ partition-ի։
7. **Freshness contract & verify-live։** Contract․ source close 02:00 UTC, expected serving availability 02:30, allowed lateness 20 րոպե, completeness ≥ 99%, owner = DE on-call, alert breach-ի վրա։ Done-ը նշանակում է, որ **reconciliation-ը անցավ և freshness/completeness-ը բավարարվեց running warehouse-ում** — ոչ թե DAG-ը green դարձավ։

Սա ELT է (load raw, transform in-warehouse) հենց այն պատճառով, որ ուզում ենք immutable raw lineage և replayable transform. ETL design-ը transform կաներ նախքան land-ը և կկորցներ էժան re-run-ը։
