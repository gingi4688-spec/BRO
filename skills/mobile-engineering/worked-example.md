# Mobile Engineering worked examples

## English

### Example A — offline-sync architecture

**Prompt.** Field technicians fill in inspection forms in buildings with no signal, then sync when they get back online. Design the mobile architecture.

**Senior answer.** The hard fact is that the network is absent at the moment of work and present later, so this is a sync contract, not a cache. **Local store:** an on-device database is the working truth while offline; sensitive inspection data is encrypted at rest with the key in the keystore (Keychain / KeyStore), with a retention rule that purges synced records after N days. **Operation log:** every edit and submission is an ordered, append-only intent with an **idempotency key**, so a flaky-network retry cannot create a duplicate record. **Authority & conflict policy fit to data risk:** a *draft* edit is low-risk and merges by field (two techs rarely touch the same draft); a *submitted* record is high-value, so the server is the authority and a divergence requires explicit **reviewer resolution**, never silent last-write-wins. **Sync engine:** retry with exponential backoff, and the UI shows a per-record **queued / syncing / synced / conflict** status so the tech is never guessing. **Lifecycle:** the form persists at each field change (save boundary), so an OS kill mid-inspection loses nothing and the screen restores from saved state, not memory. **Release:** the new sync engine ships behind a remote flag, rolls out 5% → 25% → 100% gated on a sync-failure and crash-free guardrail, with a remote kill switch back to the old engine. **Verify:** run it on a real mid-tier device in airplane mode, force-kill mid-form, submit the same record twice, and create a deliberate conflict — confirm no duplicate, no lost data, correct conflict state.

**Why this passes.** It names the actual failure mode — that "offline cache" with last-write-wins silently destroys a submitted inspection — and replaces it with a contract: an idempotent operation log (so retries can't duplicate), authority split by data risk (drafts merge, submissions need a reviewer), and a visible per-record status so the tech trusts the queue. It ties lifecycle to the save boundary so a process-death kill mid-form loses nothing, which is the realistic on-site failure, not the happy path. Security is concrete (encrypted at rest, key in the keystore, retention rule), the release is reversible without a store round-trip (remote flag + kill switch), and the verification is on a real device exercising airplane mode, force-kill, duplicate submit, and a conflict — the four conditions that actually break offline apps.

### Example B — native vs cross-platform decision

**Prompt.** A 4-engineer team (all strong in TypeScript/React, no native iOS/Android experience) is building a consumer delivery app. It needs maps with live driver tracking, push notifications, camera for proof-of-delivery, and it must ship to both platforms in three months. Native, cross-platform, or hybrid?

**Senior answer.** Decide by requirement, not familiarity. **Map the hard native dependencies:** maps/live location, push, and camera are all well-supported by mature cross-platform plugins — none is a platform-exclusive API or a performance floor that only native can hit. There is no AR, no on-device ML, no sustained-60fps game loop, no deep OS integration here, so the requirement does not force native. **Weigh the team and velocity:** four engineers strong in TypeScript/React with no native experience, shipping to both platforms in three months — a cross-platform framework lets them reuse one codebase and their existing skill, where two native codebases would mean learning two new toolchains under a hard deadline (the larger risk). **Name the maintenance tradeoff:** cross-platform carries a bridging cost and a dependency on the framework's plugin ecosystem; flag that live driver tracking should be load-tested on the cross-platform map layer on a low-tier device, since smooth real-time map updates are the one place a cross-platform ceiling could bite. **Recommendation:** cross-platform, with a documented **escape hatch** — if live tracking janks on the low tier, drop a **native module** for just the map/location screen rather than rewriting the app. **What would flip this:** if the app later needs on-device ML or AR, re-run the decision for that feature and add a native module, do not rewrite.

**Why this passes.** It refuses to pick the stack by what the team already knows and instead scores the requirement: it checks each feature (maps, push, camera) against whether it is a hard native dependency and finds none, so native is not forced. It treats "two unfamiliar native toolchains under a three-month deadline" as the real risk that the cross-platform choice removes, and it does not pretend cross-platform is free — it names the bridging cost and the one performance risk (real-time map tracking on a low-tier device) with a concrete test for it. The recommendation carries an honest escape hatch (a native module for the one hard screen) rather than an all-or-nothing rewrite, and it states the future condition (on-device ML/AR) that would change the answer — so the decision is reversible and requirement-driven, not a permanent bet on a fashion.

### Example C — performance triage

**Prompt.** Users report the app "lags and feels janky" when scrolling the feed, and a few report it crashing on older phones. Triage it.

**Senior answer.** Get on-device numbers before touching code. **Reproduce on the right hardware:** the report is "older phones," so profile on a representative low/mid-tier device, not a flagship — the flagship may hide the problem entirely. **Frame budget:** the target is ~16ms per frame at 60fps; profile the scroll and find which frames blow the budget. The usual culprits in a feed are **image decode on the main thread**, synchronous JSON parsing of the page, and over-eager layout passes. **Fix structurally:** move image decode and JSON parse to a background thread, cache decoded images, and recycle row views so layout is not rebuilt per scroll. **The crash on old phones is almost certainly memory:** older devices have far less RAM, full-resolution images are held in memory, and the app likely ignores the memory-pressure callback — so the OS kills it (an OOM that surfaces as a crash). Fix: downsample images to the display size, release off-screen images, and respond to `didReceiveMemoryWarning` / `onTrimMemory` by dropping caches. Check for a **retain cycle / Context leak** (memory that climbs across navigations and never drops) with a leak tool. **Re-measure on the low tier:** p95 frame time back under budget, memory flat across scrolling, no OOM kill on the old device. **Verify on real hardware,** not the simulator — the simulator has desktop RAM and will not reproduce the OOM.

**Why this passes.** It starts where mobile performance lives — on a representative low/mid-tier device, not a flagship — because the bug report is "older phones," and it reasons against the explicit ~16ms frame budget rather than the vague "feels janky." It separates the two symptoms correctly: jank is a main-thread budget problem (image decode / JSON parse / layout on the UI thread), while the crash on old phones is a memory problem (full-res images + an ignored memory-pressure callback = an OS OOM kill), and it prescribes the structural fix for each (off-thread work and view recycling for jank; downsampling, releasing off-screen images, and honoring the pressure callback for memory), plus a leak-tool check for a retain cycle. It closes with re-measurement on the low tier and a real-device verification, refusing the simulator that would hide the OOM — so the triage is evidence-driven end to end.

### Example D — a breaking API change with clients you cannot force-update

**Prompt.** The backend team wants to change the `/checkout` response: rename a field and change `price` from a float to integer cents. Mobile says "you can't just change it." Design the migration and the app rollout, given that old app versions stay installed for months.

**Senior answer.** The mobile constraint that changes everything: **you cannot force-update installed clients.** A user on last quarter's app version keeps calling the old contract for months (some never update), so a breaking server change instantly crashes or corrupts every un-updated install. The discipline is the same expand/contract as a database migration — but the "old readers you can't redeploy" are **apps in the wild**, and the contract is the API:

1. **Expand the API additively — never mutate in place.** The server adds the new fields (`total_cents` as int) *alongside* the old (`price` as float) and returns both. Old clients read `price`; new clients read `total_cents`. A rename becomes add-new + keep-old, not rename. (If truly unavoidable, version the endpoint — `/v2/checkout` — and keep `/v1` alive.)
2. **Ship the new app that reads the new fields**, but assume slow, partial adoption. Client parsing is defensive: read `total_cents`, fall back to `price` if absent, and never crash on an unknown extra field (forward-compatible parsing).
3. **Staged (phased) rollout of the new app with real halt-thresholds**, not "ship to 100%": 1% → 5% → 20% → 50% → 100% over days, watching per-stage guardrails vs the prior baseline. **Filled halt recipe (calibrate to your Play/Store-vitals baseline):** halt/rollback if at any stage **crash-free sessions < 99.5%**, or **ANR rate > 0.47%** (Play vitals bad-behavior threshold), or checkout **success rate drops > 1 pt**, or a **P0/P1 spike**. Put a **remote kill switch / feature flag** in front of the new checkout path so it can be disabled server-side without a new release — mobile cannot hotfix in minutes (store review latency), so the flag is the real rollback.
4. **Contract only when the old version has drained.** Measure the share of traffic still on old-contract clients; keep the old fields until that share falls below an agreed floor (e.g. < 1–2%, often 2–3 months), optionally force the long tail with a minimum-supported-version gate, *then* remove the old fields. The removal is the one irreversible step — last, evidence-gated on adoption telemetry.

**Why this passes.** It leads with the mobile-defining constraint — **installed clients cannot be force-updated**, so old app versions call the old contract for months — and therefore makes the server change **additive (expand), never a mutating rename**, with old and new fields coexisting and forward-compatible client parsing. It runs a **staged rollout with concrete, filled halt-thresholds** (crash-free < 99.5%, ANR > 0.47%, checkout −1 pt) instead of "ship it," and puts a **remote kill switch** in front because mobile cannot hotfix in minutes (store review), so the flag is the true rollback. It contracts (removes old fields) only after **adoption telemetry** shows the old-contract tail has drained below a floor — the irreversible step last and evidence-gated, exactly the reversibility discipline the rubric wants for the un-updatable-client case.

## Հայերեն

### Օրինակ A — offline-sync ճարտարապետություն

**Prompt.** Field technician-ները լրացնում են inspection form-եր առանց signal-ի շենքերում, հետո sync են անում, երբ նորից online են լինում։ Նախագծիր mobile ճարտարապետությունը։

**Senior պատասխան.** Կոշտ փաստն այն է, որ network-ը բացակա է աշխատանքի պահին և ներկա է ավելի ուշ, ուստի սա sync contract է, ոչ cache։ **Local store․** on-device database-ն աշխատանքային truth-ն է offline-ի ժամանակ. sensitive inspection data-ն encrypt-ված է at-rest՝ key-ը keystore-ում (Keychain / KeyStore), retention rule-ով, որ purge է անում synced record-ները N օրից հետո։ **Operation log․** ամեն edit և submission ordered, append-only intent է **idempotency key**-ով, ուստի անկայուն-network retry-ն չի կարող կրկնակի record ստեղծել։ **Authority & conflict policy՝ data risk-ին համապատասխան․** *draft* edit-ը low-risk է և merge է լինում field-ով (երկու tech-ը հազվադեպ են նույն draft-ին դիպչում). *submitted* record-ը high-value է, ուստի server-ը authority է, և շեղումը պահանջում է բացահայտ **reviewer resolution**, երբեք լուռ last-write-wins։ **Sync engine․** retry՝ exponential backoff-ով, և UI-ն ցույց է տալիս per-record **queued / syncing / synced / conflict** status, ուստի tech-ը երբեք չի գուշակում։ **Lifecycle․** form-ը պահպանվում է ամեն field-ի փոփոխությանը (save boundary), ուստի OS kill-ը inspection-ի կեսին ոչինչ չի կորցնում, և screen-ը restore է լինում saved state-ից, ոչ memory-ից։ **Release․** նոր sync engine-ը ship է լինում remote flag-ի հետևում, roll out 5% → 25% → 100%՝ gated sync-failure և crash-free guardrail-ի վրա, remote kill switch-ով հին engine-ին։ **Verify․** գործարկիր այն իրական mid-tier device-ի վրա airplane mode-ում, force-kill արա form-ի կեսին, submit արա նույն record-ը երկու անգամ, և ստեղծիր միտումնավոր conflict — հաստատիր ոչ duplicate, ոչ կորած data, ճիշտ conflict state։

**Ինչու է անցնում gate-ը.** Այն անվանում է իրական failure mode-ը — որ «offline cache»-ը last-write-wins-ով լուռ ոչնչացնում է submitted inspection-ը — և փոխարինում է contract-ով․ idempotent operation log (որ retry-ները չ-duplicate անեն), authority՝ բաժանված data risk-ով (draft-երը merge, submission-ները reviewer են ուզում), և տեսանելի per-record status, որ tech-ը վստահի queue-ին։ Այն կապում է lifecycle-ը save boundary-ի հետ, որ process-death kill-ը form-ի կեսին ոչինչ չկորցնի, որը ռեալիստ on-site failure-ն է, ոչ happy path-ը։ Security-ն կոնկրետ է (encrypt-ված at-rest, key-ը keystore-ում, retention rule), release-ը հետշրջելի է առանց store round-trip-ի (remote flag + kill switch), և verification-ը իրական device-ի վրա է՝ վարժեցնելով airplane mode, force-kill, duplicate submit և conflict — այն չորս պայմանը, որ իրականում կոտրում են offline app-երը։

### Օրինակ B — native ընդդեմ cross-platform որոշում

**Prompt.** 4 engineer-անոց թիմ (բոլորը ուժեղ TypeScript/React-ում, native iOS/Android փորձ չունեն) կառուցում է consumer delivery app։ Պետք են map՝ live driver tracking-ով, push notification, camera՝ proof-of-delivery-ի համար, և պետք է ship լինի երկու platform-ին երեք ամսում։ Native, cross-platform, թե hybrid։

**Senior պատասխան.** Որոշիր պահանջով, ոչ ծանոթությամբ։ **Քարտեզագրիր կոշտ native dependency-ները․** map/live location-ը, push-ը և camera-ն բոլորը լավ support-ված են հասուն cross-platform plugin-ներով — ոչ մեկը platform-exclusive API չէ կամ performance floor, որ միայն native-ը կարող է հասնել։ Այստեղ AR չկա, on-device ML չկա, sustained-60fps game loop չկա, խորը OS integration չկա, ուստի պահանջը չի ստիպում native։ **Կշռիր թիմը և velocity-ն․** չորս engineer ուժեղ TypeScript/React-ում՝ առանց native փորձի, ship երկու platform-ին երեք ամսում — cross-platform framework-ը թույլ է տալիս վերաօգտագործել մեկ codebase և իրենց եղած skill-ը, մինչ երկու native codebase-ը կնշանակեր երկու նոր toolchain սովորել կոշտ deadline-ի տակ (ավելի մեծ risk-ը)։ **Անվանի՛ր maintenance tradeoff-ը․** cross-platform-ը կրում է bridging cost և կախվածություն framework-ի plugin ecosystem-ից. flag արա, որ live driver tracking-ը պետք է load-test արվի cross-platform map layer-ի վրա low-tier device-ով, քանի որ smooth real-time map update-ը այն մի տեղն է, որտեղ cross-platform ceiling-ը կարող է խայթել։ **Recommendation․** cross-platform, փաստաթղթավորված **escape hatch**-ով — եթե live tracking-ը janks է անում low tier-ի վրա, drop արա **native module** միայն map/location screen-ի համար՝ app-ը վերագրելու փոխարեն։ **Ինչը կշրջեր սա․** եթե app-ին հետո պետք լինի on-device ML կամ AR, վերագործարկիր որոշումը այդ feature-ի համար և ավելացրու native module, մի՛ վերագրիր։

**Ինչու է անցնում gate-ը.** Այն հրաժարվում է stack-ն ընտրել նրանով, ինչ թիմը արդեն գիտի, և փոխարենը գնահատում է պահանջը․ ստուգում է ամեն feature-ը (map, push, camera) ընդդեմ նրա, թե արդյոք կոշտ native dependency է, և ոչ մեկը չի գտնում, ուստի native-ը ստիպված չէ։ Այն համարում է «երկու անծանոթ native toolchain երեք-ամսյա deadline-ի տակ»-ը իրական risk-ը, որ cross-platform ընտրությունը հանում է, և չի ձևացնում, թե cross-platform-ը անվճար է — անվանում է bridging cost-ը և մեկ performance risk-ը (real-time map tracking low-tier device-ի վրա)՝ դրա համար կոնկրետ test-ով։ Recommendation-ը կրում է ազնիվ escape hatch (native module մեկ կոշտ screen-ի համար), ոչ all-or-nothing վերագրում, և նշում է ապագա պայմանը (on-device ML/AR), որ կփոխեր պատասխանը — ուստի որոշումը հետշրջելի է և պահանջով driven, ոչ մշտական խաղադրույք նորաձևության վրա։

### Օրինակ C — performance triage

**Prompt.** User-ները հաղորդում են, որ app-ը «lag և janky է զգացվում» feed-ը scroll անելիս, և մի քանիսը հաղորդում են, որ այն crash է լինում հին հեռախոսների վրա։ Triage արա այն։

**Senior պատասխան.** Ստացիր on-device թվեր մինչև code-ին դիպչելը։ **Reproduce արա ճիշտ hardware-ի վրա․** report-ը «հին հեռախոս» է, ուստի profile արա representative low/mid-tier device-ի վրա, ոչ flagship-ի — flagship-ը կարող է խնդիրը լրիվ թաքցնել։ **Frame budget․** target-ը ~16ms per frame է 60fps-ի դեպքում. profile արա scroll-ը և գտիր, որ frame-երն են պայթեցնում budget-ը։ Feed-ում սովորական մեղավորները՝ **image decode main thread-ի վրա**, page-ի սինխրոն JSON parsing, և չափից շատ layout pass։ **Ուղղիր կառուցվածքային․** image decode-ը և JSON parse-ը տեղափոխիր background thread, cache արա decode-ված image-ները, և recycle արա row view-ները, որ layout-ը scroll-ի ընթացքում չ-rebuild լինի։ **Հին հեռախոսի crash-ը գրեթե անկասկած memory է․** հին device-ները շատ ավելի քիչ RAM ունեն, full-resolution image-ները պահվում են memory-ում, և app-ը հավանաբար անտեսում է memory-pressure callback-ը — ուստի OS-ը սպանում է այն (OOM, որ երևում է որպես crash)։ Fix․ downsample արա image-ները display size-ին, ազատիր off-screen image-ները, և արձագանքիր `didReceiveMemoryWarning` / `onTrimMemory`-ին՝ drop անելով cache-երը։ Ստուգիր **retain cycle / Context leak**-ի համար (memory, որ բարձրանում է navigation-ների ընթացքում և երբեք չի իջնում) leak tool-ով։ **Վերաչափիր low tier-ի վրա․** p95 frame time-ը կրկին budget-ից ցածր, memory-ն հարթ scroll-ի ընթացքում, OOM kill չկա հին device-ի վրա։ **Verify արա իրական hardware-ի վրա,** ոչ simulator-ում — simulator-ը desktop RAM ունի և OOM-ը չի վերարտադրի։

**Ինչու է անցնում gate-ը.** Այն սկսում է այնտեղ, որտեղ բջջային performance-ն ապրում է — representative low/mid-tier device-ի վրա, ոչ flagship-ի — որովհետև bug report-ը «հին հեռախոս» է, և դատում է բացահայտ ~16ms frame budget-ի դեմ, ոչ թե vague «feels janky»-ի։ Այն ճիշտ բաժանում է երկու symptom-ը․ jank-ը main-thread budget-ի խնդիր է (image decode / JSON parse / layout UI thread-ի վրա), իսկ հին հեռախոսի crash-ը memory-ի խնդիր է (full-res image + անտեսված memory-pressure callback = OS OOM kill), և նշանակում է կառուցվածքային fix ամեն մեկին (off-thread work և view recycling jank-ի համար. downsampling, off-screen image-ների ազատում և pressure callback-ի հարգում memory-ի համար), plus leak-tool ստուգում retain cycle-ի համար։ Այն փակում է վերաչափմամբ low tier-ի վրա և իրական-device verification-ով՝ հրաժարվելով simulator-ից, որ կթաքցներ OOM-ը — ուստի triage-ը evidence-driven է ծայրից ծայր։

### Օրինակ D — breaking API change client-ներով, որ չես կարող force-update անել

**Prompt.** Backend team-ը ուզում է փոխել `/checkout` response-ը․ rename անել field և `price`-ը float-ից դարձնել integer cents։ Mobile-ը ասում է «չես կարող պարզապես փոխել»։ Նախագծիր migration-ը և app rollout-ը, հաշվի առնելով, որ հին app version-ները ամիսներ մնում են installed։

**Senior պատասխան.** Mobile-ի constraint-ը, որ ամեն ինչ փոխում է․ **չես կարող force-update անել installed client-ները։** Անցյալ եռամսյակի app version-ի user-ը ամիսներ շարունակում է կանչել հին contract-ը (ոմանք երբեք չեն update անում), ուստի breaking server change-ը ակնթարթորեն crash կամ corrupt է անում ամեն չ-update-ված install։ Discipline-ը նույն expand/contract-ն է, ինչ database migration-ը — բայց «հին reader-ները, որ չես կարող redeploy անել» **apps in the wild** են, և contract-ը API-ն է․

1. **Expand արա API-ն additive — երբեք մի՛ mutate արա in place։** Server-ը ավելացնում է նոր field-երը (`total_cents` որպես int) հին-ի *կողքին* (`price` որպես float) և վերադարձնում երկուսն էլ։ Հին client-ները կարդում են `price`. նոր client-ները՝ `total_cents`։ Rename-ը դառնում է add-new + keep-old, ոչ rename։ (Եթե իսկապես անխուսափելի է, version արա endpoint-ը — `/v2/checkout` — և `/v1`-ը վեր պահիր։)
2. **Ship արա նոր app-ը, որ կարդում է նոր field-երը**, բայց ենթադրիր դանդաղ, մասնակի adoption։ Client parsing-ը defensive է․ կարդա `total_cents`, fall back արա `price`-ի, եթե բացակա է, և երբեք մի՛ crash արա unknown extra field-ի վրա (forward-compatible parsing)։
3. **Staged (phased) rollout նոր app-ի իրական halt-threshold-ներով**, ոչ «ship 100%»․ 1% → 5% → 20% → 50% → 100% օրերի ընթացքում, հետևելով per-stage guardrail-ներին նախորդ baseline-ի դեմ։ **Filled halt recipe (calibrate արա քո Play/Store-vitals baseline-ին)․** halt/rollback արա, եթե որևէ stage-ում **crash-free session < 99.5%**, կամ **ANR rate > 0.47%** (Play vitals bad-behavior threshold), կամ checkout **success rate ընկնում է > 1 կետ**, կամ **P0/P1 spike**։ Դիր **remote kill switch / feature flag** նոր checkout path-ի առջև, որ այն կարողանա disable լինել server-side առանց նոր release-ի — mobile-ը չի կարող hotfix անել րոպեներում (store review latency), ուստի flag-ը իրական rollback-ն է։
4. **Contract արա միայն, երբ հին version-ը drain է եղել։** Չափիր traffic-ի share-ը, որ դեռ հին-contract client-ների վրա է. պահիր հին field-երը, մինչ այդ share-ը ընկնի համաձայնեցված floor-ից ցածր (օր.՝ < 1–2%, հաճախ 2–3 ամիս), ընտրովի ստիպիր long tail-ը minimum-supported-version gate-ով, *հետո* հանիր հին field-երը։ Հեռացումը միակ irreversible քայլն է — վերջինը, evidence-gated adoption telemetry-ի վրա։

**Ինչու է անցնում gate-ը.** Այն սկսում է mobile-ը սահմանող constraint-ից — **installed client-ները չեն կարող force-update լինել**, ուստի հին app version-ները ամիսներ կանչում են հին contract-ը — և հետևաբար server change-ը դարձնում է **additive (expand), երբեք mutating rename**, հին ու նոր field-երը coexist, forward-compatible client parsing-ով։ Այն գործարկում է **staged rollout կոնկրետ, filled halt-threshold-ներով** (crash-free < 99.5%, ANR > 0.47%, checkout −1 կետ)՝ «ship it»-ի փոխարեն, և դնում **remote kill switch** առջևում, որովհետև mobile-ը չի կարող hotfix անել րոպեներում (store review), ուստի flag-ը իրական rollback-ն է։ Այն contract է անում (հանում հին field-երը) միայն այն բանից հետո, երբ **adoption telemetry**-ն ցույց է տալիս, որ հին-contract tail-ը drain է եղել floor-ից ցածր — irreversible քայլը վերջինը և evidence-gated, հենց reversibility discipline-ը, որ rubric-ը ուզում է un-updatable-client դեպքի համար։
