# Cybersecurity Operations and SOC manual

## English

### Operating principle

Senior SOC and incident-response work is decision-grade only when it converts raw signal into an evidence-grounded decision and pairs every claim with an auditable mechanism. The deliverable is one of a few shapes: an alert triage note, a deployable detection rule, an incident-response plan, a severity call, a log-source/collection map, or a post-incident review. Two disciplines govern all of them. First, **confidence is earned from corroboration, not from how alarming the signal sounds** — severity is impact multiplied by confidence, scored separately, and destructive action waits for the second and third log source. Second, **the response must not destroy what it is trying to protect**: containment that wipes a host before capturing it erases the evidence, and containment that loudly swats one foothold warns an adversary who still holds others. The work is not "respond fast"; it is respond in the right order — preserve, contain quietly, eradicate to the full scope of stolen credentials and persistence, recover from known-good state, and ship a detection so the same intrusion cannot recur unseen. Throughout, attribution stays a caveated hypothesis, the legal/breach-notification clock is a counsel decision you feed rather than pre-empt, and a technique you cannot see in the logs is a collection gap to fix, not a verdict to guess.

### Mechanism reference

- **MITRE ATT&CK** — ATT&CK maps observed behavior to tactic and technique so the SOC reasons about adversary intent, not tool names. Example: repeated failed logins followed by a success from an unusual ASN maps to Credential Access / Brute Force (T1110) and Valid Accounts (T1078); if the session then enumerates shares or directory objects, add Discovery, and a new inbox-forwarding rule adds Collection / persistence. The map is useful only when it changes collection, detection, or response — otherwise it is decoration. Use it to derive the data sources that confirm the technique and the expected *next* behavior to hunt for.
- **Detection rule logic** — A deployable rule needs logic, a threshold, the data source it runs on, a true-positive case, an expected false-positive case, and a tuning dimension. Impossible-travel as a Sigma/KQL rule needs IdP login events (user, source country/ASN, timestamp) and a velocity threshold; true positive: New York then Paris in 20 minutes with no VPN baseline; false positive: a corporate VPN egress change or a roaming mobile carrier. Prefer durable behavior (TTPs) over brittle indicators (specific IPs/hashes the adversary rotates in minutes). Ship a new rule **silent/log-only** until its false-positive rate is measured, then promote it to a page.
- **Severity = impact × confidence** — Impact weighs asset criticality, privilege level, data exposure, and lateral spread; confidence weighs signal quality, corroborating logs, and known-benign explanations. The two are scored separately so panic cannot inflate a verdict: a high-impact / low-confidence alert earns investigation priority but not destructive containment. The matrix then drives a response tier (monitor → investigate → contain → declare incident) with an owner and the next evidence to collect.
- **SOC metrics** — Operational feedback, not vanity numbers. MTTD = detection time − estimated compromise/start time; MTTR = containment-or-recovery time − detection time; dwell time = how long the adversary was present; false-positive rate = benign alerts / total alerts. Segment every metric **by detection type**, or noisy rules hide critical misses inside a healthy-looking average.
- **Log-source taxonomy and collection** — Detection and investigation are bounded by what you collect and how long you keep it. A working SOC needs EDR (process, file, registry), IdP/auth, DNS, web proxy, cloud audit (control-plane), network flow, and email/mail-audit telemetry — and retention long enough to cover realistic dwell time. A technique with no collecting log source is undetectable and uninvestigable; the first deliverable there is a collection/retention gap request, not a confident verdict.

#### Incident response — the full lifecycle and eradication depth

IR runs in order: **detection → containment → eradication → recovery → post-incident review**, with evidence preservation threaded through. The dangerous, often-shortchanged stage is **eradication** — removing the adversary's access and persistence completely, not just the malware you happened to find.

- **Containment before destruction.** Capture volatile evidence (memory, network connections, running processes) and a forensic disk image *before* you wipe or reboot a host — a reboot erases memory-resident implants and the proof of what happened. The exception is active, ongoing harm (live exfiltration, encryption in progress) where stopping the bleeding outranks evidence; say so explicitly when you make that trade. Prefer **scoped, quiet containment** (network-isolate the host, disable the specific session) over loud actions that warn an adversary still holding other footholds.
- **Credential and token rotation scope.** Assume every credential, secret, session token, and API key reachable from a compromised host is exposed. Rotate in *scope*, not just the obviously-stolen account: local and domain accounts that logged into the host, service accounts whose secrets were on disk, cached cloud/API tokens, and any password reused elsewhere. Cached Kerberos tickets and pass-the-hash material mean a single foothold can yield credentials far beyond it.
- **Active Directory tier-0 reset.** When a Domain Admin or any tier-0 identity (DCs, the directory itself, the PKI/CA, anything that can grant domain control) is compromised, treat the whole identity tier as owned. Reset tier-0 account passwords, audit and reset trusts, and rebuild domain controllers from trusted media. Critically, rotate the **`krbtgt` account password twice**, allowing Active Directory replication to complete between the two resets — `krbtgt` signs all Kerberos tickets, so a single reset still leaves valid forged **golden tickets** for one password generation; the second reset invalidates them. Skipping the double reset leaves silent domain-wide persistence that survives every host rebuild.
- **Reimaging versus cleaning.** Reimage a compromised host from a known-good image rather than "cleaning" it. Removing the malware you found does not remove the implant you didn't, the dropped tool you missed, or the backdoored config you can't see. Cleaning is acceptable only for low-privilege, low-confidence, fully-understood cases with an owner's sign-off; for anything privileged or uncertain, rebuild.
- **Firmware and bootkit persistence.** Some implants live below the operating system and survive a disk wipe: UEFI/bootkit firmware, the baseboard management controller (BMC/IPMI), and network-device firmware (routers, switches, VPN appliances). If below-OS persistence is suspected or confirmed, an OS reimage is not enough — require a firmware re-flash from a trusted source or hardware replacement, or treat the device as permanently untrusted and remove it from sensitive segments.
- **Persistence hunt before "clean."** Before declaring eradication complete, hunt the standard persistence mechanisms: scheduled tasks/cron, new or modified services and daemons, registry run-keys and WMI subscriptions, startup folders, mailbox/inbox-forwarding rules, OAuth app grants and token persistence, new local/cloud accounts, and modified trust relationships. Persistence missed here is the adversary's return ticket.
- **Recovery and review.** Recover from clean backups validated against the compromise timeline (a backup taken after the initial access may itself be poisoned). Then run a blameless post-incident review that ships at least one detection or control change per contributing factor — an incident closed with no detection update leaves the same door open.

#### CTI operationalization — from report to deployable detection

Threat intelligence earns its cost only when it changes a rule, a hunt, or a block. Reading and filing a report changes nothing. Operationalize in this order: (1) extract the **behavior and TTPs**, not just atomic indicators — IPs, domains, and hashes rotate in hours, while the technique persists; (2) check it against **your collection** — can the relevant log source even see this behavior? if not, the output is a collection gap, not a rule; (3) express it as a **detection rule or hunt query** (Sigma for portability, then translate to your platform's query language such as KQL/SPL) with logic, threshold, a TP and an FP case; (4) **bake silent/log-only**, measure the false-positive rate against your real estate, and tune; (5) **block the durable indicators** at the perimeter and **promote** the tuned rule to a page; (6) record the **coverage delta** — which ATT&CK techniques this report did and did not improve — so intelligence value is measurable, not assumed.

#### Ransomware incident response — the high-tempo case

Ransomware compresses the lifecycle and adds extortion dynamics, so the order and the gates matter even more.

- **Triage and scope first.** Identify the strain/behavior, the entry vector, and the blast radius (which hosts and shares are encrypting). Determine whether it is **double extortion** — data was exfiltrated before encryption — because that changes everything downstream (it is a data breach, not only an availability event).
- **Contain to stop spread, preserving evidence where the trade allows.** Network-isolate encrypting and adjacent hosts and disable the propagation path (compromised account, exposed RDP/VPN, the lateral-movement protocol). Because encryption is active ongoing harm, speed can outrank a full forensic image on the *encrypting* hosts — but still preserve memory and logs on patient-zero and a representative sample, and capture the ransom note and any C2/exfil indicators.
- **Eradicate to full scope.** Apply the eradication depth above — credential rotation in scope, AD tier-0 reset with the double `krbtgt` rotation if domain identity was used to push the payload, reimage rather than clean, and a persistence hunt — because ransomware actors routinely leave backdoors to return.
- **Recover from validated, offline/immutable backups.** Restore only from backups proven clean against the compromise timeline; verify the backups were not themselves encrypted or deleted (a common pre-encryption step) and were immutable/offline. Do not restore onto an estate that has not been eradicated, or you re-encrypt.
- **Route the decisions that are not yours.** The **ransom-payment** decision belongs to leadership with legal counsel (it carries sanctions-screening and legal exposure and is never a SOC call); the **breach-notification** clock and disclosures belong to legal/privacy counsel — feed them the exfiltration evidence and timeline early. Do not negotiate, pay, or declare "not a breach" on your own authority.

### Decision rules

1. Map the alert to ATT&CK tactic/technique, its confirming data sources, and the expected next behavior before reacting; if no mapping changes collection/detection/response, lower its priority.
2. Score severity as impact × confidence with the two reasoned separately; a high-impact/low-confidence alert gets investigation priority, not destructive containment.
3. On low confidence, collect the second and third corroborating log source before any reset, block, or wipe.
4. Make every detection rule state logic, fields, threshold, log source, a TP case, an FP case, and a tuning dimension; ship new rules silent/log-only until the FP rate is known.
5. Operationalize a CTI report into a detection or hunt against logs you actually collect — TTPs over rotatable indicators — or it changed nothing.
6. Sequence IR as detection → containment → eradication → recovery → review, and preserve volatile evidence and a forensic image before destructive containment unless active harm makes speed the higher duty.
7. Scope eradication to all reachable credentials/tokens and a persistence hunt, not just the entry host; reimage rather than clean for anything privileged or uncertain.
8. On tier-0/Domain-Admin compromise, do a full AD reset including a double `krbtgt` rotation (replication between resets) and DC rebuild; on suspected firmware/bootkit persistence, require firmware re-flash or hardware replacement, not just an OS reimage.
9. When telemetry to confirm/refute a technique is uncollected or out of retention, deliver a collection/retention gap request, not a confident verdict.
10. Engage IR and evidence preservation immediately, but loop legal/privacy-counsel and IR-command into the breach-notification decision early; never declare "not a breach" to dodge the clock, and never destroy state legal must preserve.
11. Keep attribution a caveated hypothesis; drive action from behavior, not from an uncorroborated actor name.
12. Report MTTD/MTTR/dwell/FP-rate segmented by detection type; close every incident with at least one shipped detection or control change.

### Failure-repair playbook

1. **Alert is just "suspicious login"** → map it to ATT&CK (T1110 → T1078 …), name the confirming data sources and the expected next behavior, and set priority by whether the map changes the response.
2. **Severity set by how scary it sounds** → re-score as impact × confidence separately; route a high-impact/low-confidence alert to investigation, not to destructive containment.
3. **Destructive action on one uncorroborated signal** → block it until the second/third log source corroborates; pull the corroboration first.
4. **Detection rule is vague suspiciousness** → add logic, fields, threshold, the log source it runs on, a TP and an FP case, and a tuning dimension; deploy it silent/log-only first.
5. **CTI report read and filed** → extract TTPs, check them against your collection, write a Sigma/KQL rule or hunt query, bake and tune it, block durable indicators, and record the coverage delta.
6. **Host wiped before evidence capture** → for the next host, capture memory and a forensic image before any reboot/reimage; reconstruct the timeline from the logs you still have and fix the collection gap that lost the rest.
7. **Containment warned the adversary** → switch to scoped, quiet containment, assume burned persistence, and hunt the other footholds before the next visible action.
8. **Eradication cleaned only the entry host** → rotate all reachable credentials/tokens in scope, hunt persistence (tasks, services, run-keys, mailbox rules, OAuth grants), and reimage rather than clean.
9. **Domain-Admin incident closed without krbtgt/tier-0 reset** → treat tier-0 as owned: double-rotate `krbtgt` with replication between resets, reset tier-0 accounts/trusts, and rebuild DCs before declaring recovery.
10. **OS reimaged but firmware/bootkit persistence suspected** → escalate below-OS: re-flash UEFI/BMC/network-device firmware from trusted media or replace the hardware, or quarantine the device as untrusted.
11. **Remediation racing ahead of legal** → pause destructive steps that aren't stopping active harm, preserve evidence, and loop legal/privacy-counsel and IR-command into the breach-notification call with the timeline.
12. **Incident closed with no detection update** → before closing, ship at least one detection or control change per contributing factor and verify the new rule fires on the TP case and is quiet on the benign case in the running estate.

## Հայերեն

### Գործառնական սկզբունք

Ավագ SOC-ի և incident-response-ի աշխատանքը decision-grade է միայն այն ժամանակ, երբ raw signal-ը վերածում է ապացույցով հիմնավորված որոշման և ամեն պնդում զուգում auditable mechanism-ի հետ։ Deliverable-ը մի քանի ձևից մեկն է՝ alert triage note, deploy-ելի detection rule, incident-response plan, severity call, log-source/collection map կամ post-incident review։ Բոլորը կառավարվում են երկու discipline-ով․ Առաջին՝ **confidence-ը վաստակվում է corroboration-ից, ոչ թե signal-ի վախեցնող հնչողությունից** — severity-ն impact բազմապատկած confidence-ով է, առանձին score-ված, և destructive action-ը սպասում է երկրորդ ու երրորդ log source-ին։ Երկրորդ՝ **response-ը չպետք է ոչնչացնի այն, ինչ փորձում է պաշտպանել**․ containment-ը, որ wipe է անում host-ը մինչ capture-ը, ջնջում է ապացույցը, իսկ containment-ը, որ բարձր ձայնով հարվածում է մեկ foothold-ի, զգուշացնում է adversary-ին, որ դեռ ուրիշներ ունի։ Աշխատանքը «արագ արձագանքել» չէ. այն ճիշտ հերթականությամբ արձագանքելն է — պահպանի՛ր, contain արա լուռ, eradicate արա գողացված credential-ների և persistence-ի ողջ scope-ով, recover արա known-good state-ից, և ship արա detection, որ նույն ներխուժումը աննկատ չկրկնվի։ Ողջ ընթացքում attribution-ը մնում է caveat-ով hypothesis, legal/breach-notification-ի ժամացույցը counsel-ի որոշում է, որ դու սնում ես, ոչ թե կանխորոշում, և technique, որ չես տեսնում log-երում, collection gap է՝ ուղղելու, ոչ verdict՝ գուշակելու։

### Մեխանիզմների տեղեկագիր

- **MITRE ATT&CK** — ATT&CK-ը դիտված behavior-ը կապում է tactic-ի և technique-ի հետ, որ SOC-ը մտածի adversary-ի նպատակի մասին, ոչ tool-ի անունով։ Օրինակ՝ կրկնվող failed login-ներ, հետո success unusual ASN-ից՝ Credential Access / Brute Force (T1110) և Valid Accounts (T1078). եթե session-ը հետո enumerate է անում share-եր կամ directory object-եր, ավելացիր Discovery, իսկ նոր inbox-forwarding rule-ը ավելացնում է Collection / persistence։ Map-ը արժեք ունի միայն, երբ փոխում է collection, detection կամ response — այլապես դեկորացիա է։ Օգտագործիր այն technique-ը հաստատող data source-ները և սպասվող *հաջորդ* behavior-ը բխեցնելու համար։
- **Detection rule-ի logic** — Deploy-ելի rule-ին պետք է logic, threshold, log source-ը, որի վրա run է, true-positive case, սպասվող false-positive case և tuning dimension։ Impossible-travel-ը որպես Sigma/KQL rule պահանջում է IdP login event-եր (user, source country/ASN, timestamp) և velocity threshold. true positive՝ New York, հետո Paris 20 րոպեում առանց VPN baseline-ի. false positive՝ corporate VPN egress change կամ roaming mobile carrier։ Նախընտրիր durable behavior (TTP) brittle indicator-ից (կոնկրետ IP/hash, որ adversary-ն րոպեներում rotate է անում)։ Նոր rule-ը ship արա **silent/log-only**, մինչ false-positive rate-ը չափվի, հետո promote արա page-ի։
- **Severity = impact × confidence** — Impact-ը կշռում է asset criticality, privilege level, data exposure և lateral spread. confidence-ը՝ signal quality, corroborating logs և known-benign explanation-ներ։ Երկուսը առանձին են score-վում, որ խուճապը չուռճացնի verdict-ը․ high-impact / low-confidence alert-ը ստանում է investigation priority, ոչ destructive containment։ Matrix-ը հետո շարժում է response tier (monitor → investigate → contain → declare incident)՝ owner-ով և հավաքելու հաջորդ ապացույցով։
- **SOC metric-ներ** — Operational feedback, ոչ vanity թվեր։ MTTD = detection time − գնահատված compromise/start time. MTTR = containment-կամ-recovery time − detection time. dwell time = որքան էր adversary-ն ներկա. false-positive rate = benign alerts / total alerts։ Ամեն metric segment արա **detection type-ով**, թե չէ noisy rule-ները critical miss-երը թաքցնում են առողջ-տեսք average-ի ներսում։
- **Log-source taxonomy և collection** — Detection-ը և investigation-ը սահմանափակված են նրանով, ինչ հավաքում ես և որքան ես պահում։ Աշխատող SOC-ին պետք է EDR (process, file, registry), IdP/auth, DNS, web proxy, cloud audit (control-plane), network flow, և email/mail-audit telemetry — և retention բավական երկար՝ իրատեսական dwell time-ը ծածկելու։ Technique, որ հավաքող log source չունի, undetectable և uninvestigable է. այնտեղ առաջին deliverable-ը collection/retention gap-ի request-ն է, ոչ վստահ verdict։

#### Incident response — ողջ lifecycle-ը և eradication-ի խորությունը

IR-ը գնում է հերթականությամբ՝ **detection → containment → eradication → recovery → post-incident review**, ապացույցի պահպանումը՝ ողջ ընթացքում հյուսված։ Վտանգավոր, հաճախ թերակատարված փուլը **eradication**-ն է — adversary-ի access-ի և persistence-ի լրիվ հեռացումը, ոչ միայն այն malware-ի, որ պատահաբար գտար։

- **Containment՝ մինչ ոչնչացումը։** Capture արա volatile evidence-ը (memory, network connection, running process) և forensic disk image-ը *մինչ* host-ը wipe կամ reboot անելը — reboot-ը ջնջում է memory-resident implant-ները և կատարվածի ապացույցը։ Բացառությունը active, ընթացիկ վնասն է (live exfiltration, ընթացքի մեջ encryption), որտեղ արյունահոսությունը կանգնեցնելը գերակա է ապացույցից. ասա՛ դա բացահայտ, երբ այդ trade-ն ես անում։ Նախընտրիր **scoped, լուռ containment** (host-ի network-isolate, կոնկրետ session-ի անջատում) բարձր action-ից, որ զգուշացնում է դեռ ուրիշ foothold ունեցող adversary-ին։
- **Credential-ի և token-ի rotation scope-ը։** Ենթադրիր, որ compromised host-ից հասանելի ամեն credential, secret, session token և API key exposed է։ Rotate արա *scope*-ում, ոչ միայն ակնհայտ-գողացված հաշիվը․ local և domain հաշիվներ, որ login արել են host-ին, service account-ներ, որոնց secret-ը disk-ի վրա էր, cached cloud/API token-ներ, և ցանկացած password, որ reuse արված է այլուր։ Cached Kerberos ticket-ները և pass-the-hash material-ը նշանակում են, որ մեկ foothold-ը կարող է credential տալ իրենից շատ ավելի հեռու։
- **Active Directory tier-0 reset։** Երբ Domain Admin-ը կամ ցանկացած tier-0 identity (DC-ներ, ինքը directory-ն, PKI/CA-ն, այն ամենը, ինչ կարող է domain control տալ) compromised է, ողջ identity tier-ը համարիր owned։ Reset արա tier-0 հաշիվների password-ները, audit և reset արա trust-երը, և rebuild արա domain controller-ները trusted media-ից։ Կրիտիկորեն՝ rotate արա **`krbtgt` account-ի password-ը երկու անգամ**՝ թույլ տալով, որ Active Directory replication-ը ավարտվի երկու reset-երի միջև — `krbtgt`-ն ստորագրում է բոլոր Kerberos ticket-ները, ուստի մեկ reset-ը դեռ թողնում է վավեր forged **golden ticket**-ներ մեկ password generation-ի համար. երկրորդ reset-ը invalidate է անում դրանք։ Double reset-ը բաց թողնելը թողնում է լուռ, domain-wide persistence, որ վերապրում է ամեն host rebuild։
- **Reimaging ընդդեմ cleaning-ի։** Compromised host-ը reimage արա known-good image-ից, ոչ թե «մաքրիր» այն։ Գտածդ malware-ը հանելը չի հանում այն implant-ը, որ չգտար, բաց թողած dropped tool-ը կամ չտեսնվող backdoored config-ը։ Cleaning-ը ընդունելի է միայն low-privilege, low-confidence, լրիվ հասկացված դեպքերի համար՝ owner-ի sign-off-ով. privileged կամ անորոշ ամեն ինչի համար՝ rebuild։
- **Firmware և bootkit persistence։** Որոշ implant-ներ ապրում են OS-ից ներքև և վերապրում disk wipe-ը․ UEFI/bootkit firmware, baseboard management controller (BMC/IPMI), և network-device firmware (router, switch, VPN appliance)։ Եթե below-OS persistence-ը կասկածվում կամ հաստատվում է, OS-ի reimage-ը բավարար չէ — պահանջիր firmware re-flash trusted source-ից կամ hardware-ի փոխարինում, կամ device-ը համարիր մշտապես untrusted և հանիր sensitive segment-ներից։
- **Persistence hunt՝ մինչ «clean»-ը։** Eradication-ը ավարտված հայտարարելուց առաջ hunt արա ստանդարտ persistence mechanism-ները․ scheduled task/cron, նոր կամ փոփոխված service/daemon, registry run-key և WMI subscription, startup folder, mailbox/inbox-forwarding rule, OAuth app grant և token persistence, նոր local/cloud հաշիվ, և փոփոխված trust relationship։ Այստեղ բաց թողած persistence-ը adversary-ի վերադարձի տոմսն է։
- **Recovery և review։** Recover արա clean backup-ից, որ validate-ված է compromise timeline-ի դեմ (initial access-ից հետո վերցված backup-ը կարող է ինքը poisoned լինել)։ Հետո վարիր blameless post-incident review, որ ship է անում առնվազն մեկ detection կամ control փոփոխություն ամեն contributing factor-ի համար — incident, որ փակվում է առանց detection update-ի, թողնում է նույն դուռը բաց։

#### CTI operationalization — report-ից մինչ deploy-ելի detection

Threat intelligence-ը իր ծախսն արդարացնում է միայն, երբ փոխում է rule, hunt կամ block։ Report կարդալն ու file անելը ոչինչ չի փոխում։ Operationalize արա այս հերթականությամբ․ (1) քաշիր **behavior-ը և TTP-ները**, ոչ միայն atomic indicator-ները — IP, domain և hash-երը rotate են լինում ժամերում, մինչ technique-ը պահպանվում է. (2) ստուգիր այն **քո collection**-ի դեմ — կարո՞ղ է առնչվող log source-ը այս behavior-ը տեսնել. եթե ոչ, output-ը collection gap է, ոչ rule. (3) արտահայտիր այն որպես **detection rule կամ hunt query** (Sigma՝ portability-ի, հետո translate քո platform-ի query language-ին, օրինակ՝ KQL/SPL) logic-ով, threshold-ով, TP և FP case-ով. (4) **bake արա silent/log-only**, չափիր false-positive rate-ը քո իրական estate-ի դեմ, և tune արա. (5) **block արա durable indicator-ները** perimeter-ում և **promote** արա tuned rule-ը page-ի. (6) գրանցիր **coverage delta**-ն — որ ATT&CK technique-ները այս report-ը բարելավեց և որ ոչ — որ intelligence-ի արժեքը չափելի լինի, ոչ ենթադրված։

#### Ransomware incident response — high-tempo դեպքը

Ransomware-ը սեղմում է lifecycle-ը և ավելացնում extortion dynamics, ուստի հերթականությունն ու gate-երը ավելի են կարևորվում։

- **Triage և scope՝ նախ։** Հստակեցրու strain/behavior-ը, entry vector-ը և blast radius-ը (որ host-երն ու share-երն են encrypt լինում)։ Որոշիր՝ արդյո՞ք **double extortion** է — data exfiltrate-վեց մինչ encryption-ը — որովհետև դա փոխում է ամեն ինչ ներքևում (դա data breach է, ոչ միայն availability event)։
- **Contain արա spread-ը կանգնեցնելու, ապացույց պահպանելով, որտեղ trade-ն թույլ է տալիս։** Network-isolate արա encrypting և հարակից host-երը և անջատիր propagation path-ը (compromised հաշիվ, exposed RDP/VPN, lateral-movement protocol-ը)։ Քանի որ encryption-ը active ընթացիկ վնաս է, արագությունը կարող է գերակա լինել լրիվ forensic image-ից *encrypting* host-երի վրա — բայց դեռ պահպանիր memory-ն ու log-երը patient-zero-ի և representative sample-ի վրա, և capture արա ransom note-ը և ցանկացած C2/exfil indicator։
- **Eradicate արա լրիվ scope-ով։** Կիրառիր վերևի eradication-ի խորությունը — credential rotation scope-ում, AD tier-0 reset double `krbtgt` rotation-ով, եթե domain identity օգտագործվել է payload-ը push անելու, reimage՝ ոչ clean, և persistence hunt — որովհետև ransomware actor-ները սովորաբար backdoor են թողնում վերադառնալու համար։
- **Recover արա validate-ված, offline/immutable backup-ից։** Restore արա միայն backup-ից, որ ապացուցված clean է compromise timeline-ի դեմ. ստուգիր, որ backup-ները իրենք encrypt կամ ջնջված չէին (հաճախ pre-encryption քայլ) և immutable/offline էին։ Մի՛ restore արա estate-ի վրա, որ eradicate-ված չէ, թե չէ կրկին encrypt կլինես։
- **Ուղղորդիր այն որոշումները, որ քոնը չեն։** **Ransom-payment**-ի որոշումը leadership-ինն է legal counsel-ի հետ (այն ունի sanctions-screening և legal exposure և երբեք SOC call չէ). **breach-notification**-ի ժամացույցը և disclosure-ները legal/privacy counsel-ինն են — սնիր նրանց exfiltration-ի ապացույցով և timeline-ով վաղ։ Մի՛ բանակցիր, վճարիր կամ հայտարարիր «breach չէ» սեփական լիազորությամբ։

### Որոշման կանոններ

1. Map արա alert-ը ATT&CK tactic/technique-ին, այն հաստատող data source-ներին և սպասվող հաջորդ behavior-ին՝ մինչ արձագանքը. եթե ոչ մի mapping չի փոխում collection/detection/response, priority-ն իջեցրու։
2. Score արա severity-ն որպես impact × confidence՝ երկուսը առանձին դատելով. high-impact/low-confidence alert-ը ստանում է investigation priority, ոչ destructive containment։
3. Ցածր confidence-ի դեպքում հավաքիր երկրորդ ու երրորդ corroborating log source-ը՝ մինչ ցանկացած reset, block կամ wipe։
4. Ստիպիր, որ ամեն detection rule նշի logic, fields, threshold, log source, TP case, FP case և tuning dimension. նոր rule-ները ship արա silent/log-only, մինչ FP rate-ը հայտնի լինի։
5. Operationalize արա CTI report-ը detection-ի կամ hunt-ի այն log-ների դեմ, որ իսկապես հավաքում ես — TTP՝ rotatable indicator-ից վեր — կամ ոչինչ չփոխեց։
6. Հերթականացրու IR-ը՝ detection → containment → eradication → recovery → review, և պահպանիր volatile evidence-ը և forensic image-ը մինչ destructive containment-ը, եթե active վնասը արագությունը ավելի բարձր պարտք չի դարձնում։
7. Scope արա eradication-ը բոլոր հասանելի credential/token-ներին և persistence hunt-ին, ոչ միայն entry host-ին. reimage՝ ոչ clean, privileged կամ անորոշ ամեն ինչի համար։
8. Tier-0/Domain-Admin compromise-ի դեպքում արա լրիվ AD reset՝ ներառյալ double `krbtgt` rotation (replication reset-երի միջև) և DC rebuild. կասկածելի firmware/bootkit persistence-ի դեպքում պահանջիր firmware re-flash կամ hardware-ի փոխարինում, ոչ միայն OS reimage։
9. Երբ technique-ը հաստատող/հերքող telemetry-ն չհավաքված է կամ retention-ից դուրս, deliver արա collection/retention gap-ի request, ոչ վստահ verdict։
10. Engage արա IR-ը և ապացույցի պահպանումը անմիջապես, բայց legal/privacy-counsel-ը և IR-command-ը վաղ ներգրավիր breach-notification-ի որոշման մեջ. երբեք «breach չէ» մի՛ հայտարարիր ժամացույցը խույս տալու, և երբեք մի՛ ոչնչացրու state, որ legal-ը պետք է պահպանի։
11. Պահիր attribution-ը caveat-ով hypothesis. շարժիր action-ը behavior-ից, ոչ uncorroborated actor-ի անունից։
12. Հաշվետու եղիր MTTD/MTTR/dwell/FP-rate՝ segment-ված detection type-ով. փակիր ամեն incident առնվազն մեկ ship արված detection կամ control փոփոխությամբ։

### Վերականգնման խաղագիրք

1. **Alert-ը պարզապես «suspicious login» է** → map արա այն ATT&CK-ին (T1110 → T1078 …), անվանի՛ր հաստատող data source-ները և սպասվող հաջորդ behavior-ը, և priority սահմանիր ըստ նրա՝ map-ը փոխո՞ւմ է response-ը։
2. **Severity-ն սահմանված է վախեցնող հնչողությամբ** → re-score արա որպես impact × confidence առանձին. high-impact/low-confidence alert-ը ուղղորդիր investigation, ոչ destructive containment։
3. **Destructive action մեկ uncorroborated signal-ի վրա** → block արա այն, մինչ երկրորդ/երրորդ log source-ը corroborate անի. նախ քաշիր corroboration-ը։
4. **Detection rule-ը vague suspiciousness է** → ավելացրու logic, fields, threshold, log source-ը, որի վրա run է, TP և FP case, և tuning dimension. deploy արա silent/log-only նախ։
5. **CTI report-ը կարդացված և file արված** → քաշիր TTP-ները, ստուգիր քո collection-ի դեմ, գրիր Sigma/KQL rule կամ hunt query, bake և tune արա, block արա durable indicator-ները, և գրանցիր coverage delta-ն։
6. **Host-ը wipe-ված մինչ ապացույցի capture-ը** → հաջորդ host-ի համար capture արա memory-ն և forensic image-ը մինչ ցանկացած reboot/reimage. timeline-ը reconstruct արա դեռ ունեցած log-երից և ուղղիր collection gap-ը, որ կորցրեց մնացածը։
7. **Containment-ը զգուշացրեց adversary-ին** → անցիր scoped, լուռ containment-ի, ենթադրիր burned persistence, և hunt արա մյուս foothold-ները՝ մինչ հաջորդ տեսանելի action-ը։
8. **Eradication-ը մաքրեց միայն entry host-ը** → rotate արա բոլոր հասանելի credential/token-ները scope-ում, hunt արա persistence (task, service, run-key, mailbox rule, OAuth grant), և reimage՝ ոչ clean։
9. **Domain-Admin incident փակված առանց krbtgt/tier-0 reset-ի** → tier-0-ը համարիր owned. double-rotate արա `krbtgt`-ն replication-ով reset-երի միջև, reset արա tier-0 հաշիվներ/trust-եր, և rebuild արա DC-ները՝ մինչ recovery հայտարարելը։
10. **OS-ը reimage-ված, բայց firmware/bootkit persistence կասկածվում է** → escalate արա below-OS․ re-flash արա UEFI/BMC/network-device firmware-ը trusted media-ից կամ փոխարինիր hardware-ը, կամ quarantine արա device-ը որպես untrusted։
11. **Remediation-ը վազում է legal-ից առաջ** → կանգնեցրու destructive քայլերը, որ active վնաս չեն կանգնեցնում, պահպանիր ապացույցը, և legal/privacy-counsel-ը ու IR-command-ը ներգրավիր breach-notification call-ում՝ timeline-ով։
12. **Incident փակված առանց detection update-ի** → փակելուց առաջ ship արա առնվազն մեկ detection կամ control փոփոխություն ամեն contributing factor-ին և ստուգիր, որ նոր rule-ը կրակում է TP case-ի վրա և լուռ է benign case-ի վրա running estate-ում։
