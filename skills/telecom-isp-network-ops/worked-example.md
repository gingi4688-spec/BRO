# Telecom, ISP, and Network Operations worked examples

## English

### Example A — PON outage triage + SLA report

**Prompt.** After a maintenance window, ~40% of customers on one OLT report total loss. The maintenance was a "splitter cleanup." What now, and what does the customer report need?

**Senior answer.** First fix blast radius and last change: the impact is contained to one OLT/PON shelf (a shared element, not scattered), and the last change was the splitter cleanup — so this is almost certainly change-induced shared plant, not 40% of customers simultaneously buying bad routers. Descend from the physical layer: the OLT shows optical alarms; BGP and core reachability are normal, so do not touch routing. Pull per-ONU Rx power across the PON — multiple ONUs read low Rx together, which is the shared-plant signature; a single bad ONT would be one low reading, not a correlated set.

Build the optical budget to confirm: splitter insertion loss for a 1:32 split is ≈ 17–18 dB, plus fiber attenuation (~0.3–0.35 dB/km) and connector/splice loss; against the **Class B+ budget of 28 dB** there should be margin. If the cleanup left a connector loose, dirty, or a fiber bent, the added loss eats the margin and pushes the link marginal — which matches the symptom. Action: do not roll trucks to swap ONTs; inspect the splitter and the connectors touched during cleanup, reseat/clean and **remeasure Rx**, confirm levels are back inside budget, and keep a NOC update to affected customers every 30 minutes. Rule out a rogue ONU only if levels look fine but service still flaps.

SLA report: if the outage lasted **52 minutes** in a 30-day month, the affected-service availability for that month is (43,200 − 52) / 43,200 = **99.88%**, which is below a **99.9% SLA** whose monthly budget is **43.2 minutes** — so the 52-minute outage breached the budget by ~8.8 minutes for the affected customers. The report needs: the measured downtime window, the affected services and customer count, root cause as contributing factors (cleanup disturbed a connector; no post-cleanup Rx remeasure caught it before customers did), remediation (reseat + remeasure), and prevention (a mandatory post-maintenance Rx check inside the MOP). Do not invent a credit figure — state the breach and route the credit to the contract.

**Why this passes.** It anchors on blast radius and the last change before touching anything, so the splitter cleanup is identified as the change-induced cause instead of 40% of customers being blamed. It refuses to debug BGP because core reachability is normal and the OLT is alarming — the fault is found at the physical layer where it lives. The shared-plant call is evidence-based (correlated low Rx across many ONUs, not one bad ONT) and it reads Rx before dispatching a truck, so no ONT is swapped on a shared-plant symptom. The optical budget is summed against the real B+ number (28 dB), not asserted, and the cleanup-loose-connector hypothesis is tied to the measured margin loss. The SLA section computes availability from uptime/measured-time (99.88% from a 52-minute outage against the 43.2-minute budget) and explicitly refuses to invent a credit, routing it to the contract — measurement, not apology.

### Example B — BGP route-leak change MOP

**Prompt.** We're adding a new transit provider and want to start announcing our customer prefixes to them today. Write the change so we don't cause an incident.

**Senior answer.** This is a routing-policy change, so it ships only as a MOP — and the dominant risk is a **route leak** (accidentally re-announcing the new transit's or a peer's routes back out, or leaking more of our own/customers' space than intended) or a **blackhole** (a next-hop that cannot forward). 

Pre-check (capture current state): record the current advertised prefix-count to existing transits, the count we intend to announce to the new one (our aggregates + customer prefixes only), the new peer's expected received-count, and current best-path selection so we can compare after.

Change: (1) Build an **export filter** that permits only our aggregate prefixes and our customer-cone prefixes toward the new transit — never peer or other-transit routes (that is the leak). (2) Build an **import filter** with a **max-prefix** cap sized to the provider's expected full/partial table (so a misconfig on their side cannot flood us). (3) Tag announcements with the **communities/local-pref/MED** intent (e.g. local-pref so the new transit is primary/backup as designed). (4) Verify **next-hop reachability** to the new peer before trusting any received path. (5) Bring the session up but keep it **shut/filtered to a tiny announcement first** if the platform allows, expanding after validation.

Validation (compare to expected): confirm the **advertised count to the new transit equals the intended count** (our aggregates + customers, nothing more), the **received count is under max-prefix and sane**, no peer/other-transit prefix appears in what we send them, traffic is taking the intended path, and there is no reachability loss on existing services. Monitoring: watch route-count, session state, and customer-facing reachability through the bake period.

Rollback trigger + command: if the advertised count exceeds the intended set, if max-prefix trips, or if any existing reachability drops, **shut the new session / withdraw the announcement** (tested command, captured in pre-check) and return to the known-good state. Comms: notify the NOC and the new transit's peering contact of the window and the rollback condition; honor any change-freeze.

**Why this passes.** It names the two real failure modes of this exact change — leak and blackhole — and designs each one out rather than hoping: the export filter is scoped to aggregates + customer cone (the leak guard), max-prefix caps the import (the flood guard), and next-hop reachability is verified before any path is trusted (the blackhole guard). It carries an **expected route-count** to validate against, so "did it work" is a comparison, not a feeling, and validation explicitly checks that no peer/other-transit prefix is in what we announce. The rollback trigger is a named condition with a tested command captured in pre-check, not "we'll revert if it breaks," and comms plus the freeze-window check make it a real change window. Every number is a count or a reachability check on the running session — verified live, not on a clean parse.

### Example C — subscriber session control (BNG/BRAS + RADIUS CoA)

**Prompt.** A subscriber upgrades from 100 Mbps to 500 Mbps mid-billing-cycle and wants it live now, without reconnecting. Separately, an account flagged for non-payment must be moved to a walled-garden captive portal. Design both on the BNG/RADIUS control plane — no truck roll, no session drop.

**Senior answer.** Both are live **session re-authorization**, which is exactly what RADIUS **CoA (Change-of-Authorization, RFC 5176)** exists for — mutate the active session's policy in place instead of tearing it down.

**1. Speed upgrade (CoA-Request).** The policy server sends a **CoA-Request** to the BNG (the NAS), identifying the exact session by an unambiguous key (`Acct-Session-Id` + `NAS-IP-Address`, or framed IP / username), carrying the new rate-limit policy (a new QoS profile / service name via the vendor VSA or a named policy). The BNG applies the new shaper to the live session and returns **CoA-ACK**; on failure it returns **CoA-NAK** with an error cause (session-not-found, unsupported-attribute), and the automation must treat NAK as "not applied," log it, and **not** report success. Verify **on the running session**: the subscriber's active QoS profile on the BNG now shows 500 Mbps and a speed test reflects it — not "the CoA was sent."

**2. Non-payment → walled garden.** Send a **CoA-Request** that swaps the session's policy to the captive-portal service (redirect ACL + DNS to the payment portal) — *not* a Disconnect. CoA keeps the session up so the customer lands on "please pay" instead of a dead link; a **Disconnect-Message (DM)** would drop the PPPoE/IPoE session and the CPE would just retry into the same state. Reserve **Disconnect-Message** for when you actually want the session gone (confirmed fraud, or a forced re-auth to pick up a fresh profile at reconnect). On restore-after-payment, another CoA swaps the full-service policy back.

**Guardrails.** CoA/DM packets are authenticated by the shared secret and source-filtered to the policy server; the session identifier must be exact — a wrong key re-authorizes the *wrong* subscriber (a real blast-radius risk); every CoA is safe to retry (re-applying the same profile is a no-op); each action is logged with actor + session id + before/after policy for dispute/audit. Assumption to label: the exact VSAs/attributes are BNG-vendor-specific and **verify-before-use** against the platform dictionary, not asserted.

**Why this passes.** It maps both requests to the correct control-plane primitive — **CoA for in-place re-authorization, Disconnect only when the session should actually die** — and explains *why* CoA (not DM) is right for both the upgrade and the walled-garden case (a DM to a non-payer just bounces the CPE back into the same state). It handles the **CoA-ACK/NAK** result honestly (NAK = not applied, don't report success), pins the session with an **unambiguous identifier** and names the blast-radius risk of a wrong key, secures the CoA path (shared secret + source filter), and verifies **on the running session** (active QoS profile + speed test), not on the fact that a packet was sent. It flags vendor-specific VSAs as verify-before-use instead of inventing attribute names.

## Հայերեն

### Օրինակ A — PON outage triage + SLA report

**Prompt.** Maintenance window-ից հետո մեկ OLT-ի customer-ների ~40%-ը total loss է report անում։ Maintenance-ը «splitter cleanup» էր։ Հիմա ի՞նչ, և ի՞նչ է պետք customer report-ին։

**Senior պատասխան.** Նախ ֆիքսիր blast radius-ը և last change-ը․ impact-ը պահված է մեկ OLT/PON shelf-ում (shared element, ոչ ցրված), և last change-ը splitter cleanup-ն էր — ուստի սա գրեթե հաստատ change-induced shared plant է, ոչ թե customer-ների 40%-ը միաժամանակ վատ router է գնել։ Իջիր physical layer-ից․ OLT-ն optical alarm է ցույց տալիս. BGP-ն և core reachability-ն normal են, ուստի routing-ին մի՛ դիպչիր։ Քաշիր per-ONU Rx power-ը ողջ PON-ի վրա — բազմաթիվ ONU միասին low Rx են ցույց տալիս, ինչը shared-plant-ի ստորագրությունն է. մեկ վատ ONT-ն մեկ low reading կլիներ, ոչ correlated set։

Կառուցիր optical budget-ը հաստատելու համար․ 1:32 split-ի splitter insertion loss-ը ≈ 17–18 dB է, plus fiber attenuation (~0.3–0.35 dB/km) և connector/splice loss. **Class B+ budget-ի՝ 28 dB**-ի դեմ պետք է margin լինի։ Եթե cleanup-ը connector-ը թողել է թույլ, կեղտոտ կամ fiber-ը bent, ավելացած loss-ը ուտում է margin-ը և link-ը հրում marginal — ինչը համընկնում է symptom-ին։ Action․ truck մի՛ ուղարկիր ONT փոխելու. ստուգիր splitter-ը և cleanup-ի ժամանակ դիպած connector-ները, reseat/clean արա և **remeasure Rx**, հաստատիր, որ level-ները հետ են budget-ի ներսում, և պահիր NOC update ազդակիր customer-ներին յուրաքանչյուր 30 րոպե։ Rogue ONU-ն բացառիր միայն, եթե level-ները լավ են, բայց service-ը դեռ flap է անում։

SLA report․ եթե outage-ը տևեց **52 րոպե** 30-օրյա ամսում, ազդակիր service-ի availability-ն այդ ամսվա համար (43,200 − 52) / 43,200 = **99.88%** է, ինչը ցածր է **99.9% SLA**-ից, որի monthly budget-ը **43.2 րոպե** է — ուստի 52-րոպեանոց outage-ը խախտեց budget-ը ~8.8 րոպեով ազդակիր customer-ների համար։ Report-ին պետք է․ չափված downtime window-ը, ազդակիր service-ները և customer count-ը, root cause-ը որպես contributing factor (cleanup-ը disturb արեց connector. cleanup-ից հետո Rx remeasure չկար, որ բռներ customer-ներից առաջ), remediation-ը (reseat + remeasure), և prevention-ը (պարտադիր post-maintenance Rx check MOP-ի ներսում)։ Մի՛ հորինիր credit թիվ — նշիր breach-ը և credit-ը ուղղորդիր contract-ին։

**Ինչու է անցնում gate-ը.** Այն խարսխվում է blast radius-ի և last change-ի վրա մինչև որևէ բանի դիպչելը, ուստի splitter cleanup-ը նույնականացվում է որպես change-induced պատճառ՝ customer-ների 40%-ին մեղադրելու փոխարեն։ Այն հրաժարվում է BGP debug անելուց, որովհետև core reachability-ն normal է, և OLT-ն alarm է — fault-ը գտնված է physical layer-ում, որտեղ ապրում է։ Shared-plant կոչումը evidence-based է (correlated low Rx շատ ONU-ների վրա, ոչ մեկ վատ ONT), և Rx-ը կարդացվում է truck ուղարկելուց առաջ, ուստի ոչ մի ONT չի փոխվում shared-plant symptom-ի վրա։ Optical budget-ը գումարված է իրական B+ թվի դեմ (28 dB), ոչ պնդված, և cleanup-loose-connector վարկածը կապված է չափված margin loss-ի հետ։ SLA բաժինը հաշվում է availability-ն uptime/measured-time-ից (99.88% 52-րոպեանոց outage-ից 43.2-րոպեանոց budget-ի դեմ) և բացահայտ հրաժարվում credit հորինելուց՝ ուղղորդելով contract-ին — measurement, ոչ apology։

### Օրինակ B — BGP route-leak change MOP

**Prompt.** Նոր transit provider ենք ավելացնում և ուզում ենք այսօր սկսել մեր customer prefix-ները announce անել նրանց։ Գրիր change-ը, որ incident չառաջացնենք։

**Senior պատասխան.** Սա routing-policy change է, ուստի ship-վում է միայն MOP-ով — և գերիշխող risk-ը **route leak**-ն է (պատահաբար նոր transit-ի կամ peer-ի route-երը հետ re-announce անելը, կամ մեր/customer-ների space-ից ավելին leak անելը, քան մտադրված է) կամ **blackhole**-ը (next-hop, որ չի կարող forward անել)։

Pre-check (capture current state)․ գրանցիր ընթացիկ advertised prefix-count-ը գործող transit-ներին, count-ը, որ մտադիր ենք announce անել նորին (մեր aggregate-ները + customer prefix-ները միայն), նոր peer-ի սպասվող received-count-ը, և ընթացիկ best-path selection-ը, որ հետո համեմատենք։

Change․ (1) Կառուցիր **export filter**, որ թույլ է տալիս միայն մեր aggregate prefix-ները և մեր customer-cone prefix-ները նոր transit-ի ուղղությամբ — երբեք peer կամ այլ-transit route (դա leak-ն է)։ (2) Կառուցիր **import filter** **max-prefix** cap-ով՝ size-ված provider-ի սպասվող full/partial table-ին (որ նրանց կողմի misconfig-ը մեզ չ-flood անի)։ (3) Tag արա announcement-ները **communities/local-pref/MED** intent-ով (օր.՝ local-pref, որ նոր transit-ը primary/backup լինի ըստ design-ի)։ (4) Ստուգիր **next-hop reachability**-ն նոր peer-ին մինչև որևէ received path-ի վստահելը։ (5) Բարձրացրու session-ը, բայց պահիր **shut/filtered տիրով announcement-ի** սկզբում, եթե platform-ը թույլ է տալիս, ընդլայնելով validation-ից հետո։

Validation (համեմատիր expected-ի հետ)․ հաստատիր, որ **advertised count-ը նոր transit-ին հավասար է մտադրված count-ին** (մեր aggregate-ները + customer-ները, ոչ ավելին), **received count-ը max-prefix-ից ներքև է և sane**, ոչ մի peer/այլ-transit prefix չի երևում նրանց ուղարկածում, traffic-ը մտադրված path-ն է վերցնում, և գործող service-ների վրա reachability loss չկա։ Monitoring․ հետևիր route-count-ին, session state-ին և customer-facing reachability-ին bake period-ի ընթացքում։

Rollback trigger + command․ եթե advertised count-ը գերազանցում է մտադրված set-ը, եթե max-prefix trip է լինում, կամ եթե որևէ գործող reachability ընկնում է, **shut արա նոր session-ը / withdraw արա announcement-ը** (ստուգված command, capture-ված pre-check-ում) և վերադարձիր known-good state-ին։ Comms․ notify արա NOC-ին և նոր transit-ի peering contact-ին window-ի և rollback condition-ի մասին. հարգիր ցանկացած change-freeze։

**Ինչու է անցնում gate-ը.** Այն անվանում է այս ճիշտ change-ի երկու իրական failure mode-ը — leak և blackhole — և ամեն մեկը design-out է անում՝ հույս դնելու փոխարեն․ export filter-ը scope-ված է aggregate + customer cone-ին (leak guard-ը), max-prefix-ը cap է անում import-ը (flood guard-ը), և next-hop reachability-ն ստուգված է մինչև որևէ path-ի վստահելը (blackhole guard-ը)։ Այն կրում է **սպասվող route-count**, որի դեմ validate անել, ուստի «աշխատե՞ց» համեմատություն է, ոչ զգացում, և validation-ը բացահայտ ստուգում է, որ ոչ մի peer/այլ-transit prefix չկա մեր announce-ածում։ Rollback trigger-ը անվանված պայման է՝ ստուգված command-ով, capture-ված pre-check-ում, ոչ «կկոտրվի՝ հետ կգլորենք», և comms-ը plus freeze-window check-ը այն դարձնում են իրական change window։ Ամեն թիվ count է կամ reachability check running session-ի վրա — verified live, ոչ մաքուր parse-ի վրա։

### Օրինակ C — subscriber session control (BNG/BRAS + RADIUS CoA)

**Prompt.** Subscriber-ը billing-cycle-ի կեսին upgrade է անում 100 Mbps-ից 500 Mbps և ուզում է հիմա live, առանց reconnect-ի։ Առանձին, non-payment-ի համար flag-ված account-ը պետք է տեղափոխվի walled-garden captive portal։ Նախագծիր երկուսն էլ BNG/RADIUS control plane-ի վրա — ոչ truck roll, ոչ session drop։

**Senior պատասխան.** Երկուսն էլ live **session re-authorization** են, ինչի համար հենց գոյություն ունի RADIUS **CoA (Change-of-Authorization, RFC 5176)** — mutate արա active session-ի policy-ն in place՝ քանդելու փոխարեն։

**1. Speed upgrade (CoA-Request).** Policy server-ը ուղարկում է **CoA-Request** BNG-ին (NAS-ին)՝ նույնականացնելով ճշգրիտ session-ը unambiguous key-ով (`Acct-Session-Id` + `NAS-IP-Address`, կամ framed IP / username), կրելով նոր rate-limit policy-ն (նոր QoS profile / service name՝ vendor VSA-ով կամ named policy-ով)։ BNG-ն կիրառում է նոր shaper-ը live session-ին և վերադարձնում **CoA-ACK**. failure-ի դեպքում վերադարձնում է **CoA-NAK** error cause-ով (session-not-found, unsupported-attribute), և automation-ը պետք է NAK-ը համարի «not applied», log անի և **չ**-report անի success։ Verify արա **running session-ի վրա**․ subscriber-ի active QoS profile-ը BNG-ի վրա հիմա ցույց է տալիս 500 Mbps, և speed test-ը արտացոլում է այն — ոչ «CoA-ն ուղարկվեց»։

**2. Non-payment → walled garden.** Ուղարկիր **CoA-Request**, որ swap է անում session-ի policy-ն captive-portal service-ի (redirect ACL + DNS payment portal-ին) — *ոչ* Disconnect։ CoA-ն session-ը վեր է պահում, որ customer-ը հայտնվի «please pay»-ի վրա, ոչ մեռած link-ի. **Disconnect-Message (DM)**-ը կգցեր PPPoE/IPoE session-ը, և CPE-ն պարզապես retry կաներ նույն state-ի մեջ։ Պահիր **Disconnect-Message**-ը այն դեպքի համար, երբ իսկապես ուզում ես session-ը չքանա (հաստատված fraud, կամ forced re-auth՝ reconnect-ին fresh profile վերցնելու)։ Payment-ից հետո restore-ին, մեկ այլ CoA հետ է swap անում full-service policy-ն։

**Guardrail-ներ.** CoA/DM packet-ները authenticated են shared secret-ով և source-filtered policy server-ին. session identifier-ը պետք է ճշգրիտ լինի — սխալ key-ը re-authorize է անում *սխալ* subscriber-ին (իրական blast-radius ռիսկ). ամեն CoA անվտանգ է retry անել (նույն profile-ը կրկին կիրառելը no-op է). ամեն action log-վում է actor + session id + before/after policy-ով dispute/audit-ի համար։ Label-ելու assumption՝ ճշգրիտ VSA-ները/attribute-ները BNG-vendor-specific են և **verify-before-use** platform dictionary-ի դեմ, ոչ պնդված։

**Ինչու է անցնում gate-ը.** Այն map է անում երկու request-ն էլ ճիշտ control-plane primitive-ին — **CoA in-place re-authorization-ի, Disconnect միայն երբ session-ը պետք է իսկապես մեռնի** — և բացատրում է *ինչու* է CoA-ն (ոչ DM-ը) ճիշտ երկուսի համար էլ (non-payer-ին DM-ը պարզապես CPE-ն հետ է շպրտում նույն state)։ Այն ազնվորեն մշակում է **CoA-ACK/NAK** result-ը (NAK = not applied, մի՛ report անի success), pin է անում session-ը **unambiguous identifier**-ով և անվանում սխալ key-ի blast-radius ռիսկը, secure է անում CoA path-ը (shared secret + source filter), և verify անում **running session-ի վրա** (active QoS profile + speed test), ոչ այն փաստի, որ packet ուղարկվեց։ Այն flag է անում vendor-specific VSA-ները որպես verify-before-use՝ attribute անուն հորինելու փոխարեն։
