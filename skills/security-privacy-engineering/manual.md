# Security and Privacy Engineering manual

## English

### Operating principle

Senior security and privacy engineering is decision-grade only when it converts a vague "make it secure" into explicit trust boundaries, an enforced authorization model, secrets that cannot leak silently, and privacy choices designed into the data flow — and pairs every control with the detection that proves it is actually working. The deliverable is one of a few shapes: a threat model, an auth/authorization review, a privacy data-flow map, a supply-chain control plan, a cloud-hardening review, or a detection/incident-response design. The single discipline that governs all of them is the separation of authentication from authorization: a system can authenticate everyone perfectly and still leak every record if it never checks that *this* actor may touch *this* resource. So the first move on any access path is to ask not "is the user logged in" but "is the user authorized for this exact object and this exact function, checked server-side." Security is not the absence of a known bug; it is abuse paths closed by enforced controls, each with a detection that fires when the control is bypassed or fails. This skill is dual-use, so the boundary is fixed before anything else: defensive, authorized design only — the inline `SKILL.md` gate is extended, never replaced.

### Mechanism reference

- **STRIDE threat modeling** — STRIDE maps six threat classes to components and trust boundaries: **S**poofing (identity), **T**ampering (integrity), **R**epudiation (deniability), **I**nformation disclosure (confidentiality), **D**enial of service (availability), **E**levation of privilege (authorization). The mechanism is a flow, not a checklist: diagram the system → list assets → draw trust boundaries (where data crosses a privilege level) → enumerate STRIDE per boundary → assign a mitigation per threat → name a residual-risk owner for what remains. Do it before build, where it can still change the design; a STRIDE table produced after launch to satisfy a checkbox changes no decision and is paperwork.
- **AuthN vs AuthZ, IDOR/BOLA, function-level authz** — **Authentication** proves *who* the actor is; **authorization** decides *what* that actor may do. Conflating them is the most common high-impact flaw. **Broken Object-Level Authorization (IDOR/BOLA)**: an endpoint takes an id from the request (`/orders/{id}`) and returns the object without verifying the caller owns it, so iterating ids walks other tenants' data — the fix is an owner/tenant check at the data layer, on every object access, never client-side hiding. **Broken Function-Level Authorization**: a privileged endpoint is "protected" only by not showing the button; calling it directly succeeds — the fix is a per-action role/permission check on the endpoint itself. The rule: every object access and every privileged function carries a server-side check against *this* actor and *this* resource.
- **OAuth/OIDC and PKCE** — OAuth delegates **authorization** via scoped tokens; OIDC adds **identity** via ID tokens. For a public client (SPA, mobile, anything that cannot keep a secret), use the **authorization code flow with PKCE**, never the implicit flow. The failures PKCE and its companions prevent: authorization-code interception (PKCE code_verifier/challenge), open-redirect token theft (strict redirect-URI allowlist), CSRF on the callback (`state`), ID-token replay (`nonce`), tokens accepted by the wrong service (validate **audience**), and stale-token abuse (**expiry**, rotation, revocation). Scope tokens to least privilege. AuthN proves who; AuthZ still decides what — a valid token is not a blank check.
- **Cryptography (misuse-resistance, not algorithm invention)** — The decision is never "which cipher is strongest"; it is misuse-resistance and key lifecycle. Use a vetted library; never roll your own. For confidentiality + integrity use **authenticated encryption (AEAD)** (e.g. AES-GCM or ChaCha20-Poly1305) with a **unique nonce per message** — a reused or zero nonce breaks the construction; never ECB. For passwords use a **slow, salted password KDF** (e.g. Argon2, scrypt, or bcrypt), never a fast hash (MD5/SHA-1/raw SHA-256) and never unsalted. Manage the **key lifecycle**: generated by a CSPRNG, stored in a KMS/secret manager (not in code or config), separated from the data it protects, and rotated on a schedule and on suspected exposure. "We encrypt it" with no AEAD, no KDF, and no key lifecycle named is not a crypto design. The named primitives are current-but-dated guidance, not constants — before finalizing, re-confirm the chosen AEAD/KDF and the "avoid" list against current cryptographic guidance (the relevant standards body / OWASP), treating them as verify-before-use rather than timeless.
- **Privacy engineering (data-flow first)** — Privacy starts with a **data-flow map**, not a policy paragraph: for each personal-data field — data subject, purpose, collection point, controller/processor, storage, transfer (and destination/jurisdiction), retention, deletion, access, and the rights workflow (access/rectify/erase/export). Then **minimize**: a field with no purpose is removed, not stored "in case." Separate **consent from necessity** — data required to deliver the service is not the same as data the user opted into. Log access to sensitive data, but **pseudonymize** in those logs so the audit trail does not become the new leak. The legal sufficiency of a basis or a transfer is flagged to legal, not invented here.
- **Supply-chain security (SBOM/SCA, provenance)** — You cannot defend what you cannot inventory. Generate a **Software Bill of Materials (SBOM)** of direct and transitive dependencies; run **Software Composition Analysis (SCA)** against known-vulnerable and yanked versions in CI and fail the build on an unreviewed critical. **Pin** versions and **verify provenance/signatures** so a dependency cannot be silently swapped (typosquat, dependency-confusion, compromised maintainer). Isolate the build, restrict who can publish, and verify the artifact you ship is the artifact you built. No SBOM and no SCA gate is supply-chain blindness — an unmonitored door into production.

### Cloud security (IAM and storage/bucket hardening)

Cloud posture is where misconfiguration, not exotic exploitation, causes most exposure. The discipline is **default-deny, least-privilege, and no unproven public access.**

- **IAM least-privilege.** Grant the minimum action on the minimum resource. Wildcards (`Action: "*"`, `Resource: "*"`) are standing over-grant; scope to the specific actions and ARNs/resources a workload needs. Prefer **roles assumed by workloads** over **long-lived access keys**; long-lived keys are the cloud equivalent of a static CI secret — replace them with short-lived federated credentials (workload identity / OIDC). Require **MFA** on human privileged access, separate duties so no single role can both grant access and use it, and review grants so permissions do not accrete unowned. A privileged action with no approval and no expiry is a standing breach.
- **Storage / bucket misconfiguration.** Public object storage is the classic data-leak. Treat every bucket as private by default: enable account- and bucket-level **block-public-access**, verify object **ACLs and bucket policies** do not grant `AllUsers`/`AuthenticatedUsers` read, and prove a "needs to be public" case before opening it (and then only the specific prefix, ideally fronted by a CDN, not the raw bucket). Encrypt at rest with a managed key, enable access logging, and version + lifecycle-expire objects so a deletion or ransom event is recoverable. The tell of trouble is a bucket "opened for now to test" that never gets closed.
- **Network and boundary.** Default-deny security groups / firewall rules; expose only the ports a service needs; keep data stores off the public internet behind private networking. Guard the **confused-deputy / SSRF** path: a server that fetches a user-supplied URL or reaches internal metadata endpoints can be turned into a pivot — restrict egress, block link-local/metadata addresses, and require authentication on internal services.

### Detection engineering (logging, SIEM, alerting, incident response)

Every control needs a detection that proves it fires; a control with no log/alert degrades silently and is unverifiable. The discipline is **log the security-relevant events, centralize them, alert on the conditions that matter, and design the response before the incident.**

- **What to log.** Authentication success and failure, authorization **denials** (a spike of 403s on object endpoints is an IDOR probe), privilege and role changes, secret/key access, data exports and bulk reads, configuration and IAM changes, and admin actions. Logs must be **tamper-evident** (append-only / shipped off the host), carry enough context to investigate (who, what, when, from where, on which resource), and be **retained** long enough to detect slow campaigns — but **pseudonymize PII** so the log store is not itself a privacy liability.
- **SIEM and correlation.** Centralize logs into a SIEM so events across services correlate: a failed-auth burst followed by a success and a data export is a credential-stuffing-into-exfiltration story no single service log shows. Build detections for the abuse paths the threat model named, not just generic noise.
- **Alerting.** Alert on the conditions that indicate a control was bypassed or an abuse path is active — repeated authz denials, impossible-travel logins, a new public bucket, a secret-scanner hit, a dependency flagged critical, an unexpected privilege escalation. Each alert names a severity and an owner who is paged; an alert no one owns is noise. Tune to reduce false positives so the real one is not buried.
- **Incident response (designed up front).** A real IR plan defines: **roles** (incident commander, comms, scribe), **severity** by data-sensitivity and blast radius (not by who noticed), the order of **containment → eradication → recovery**, **evidence preservation** (snapshot before you wipe, or you destroy the forensic trail), and the **disclosure decision path** (who decides if/when to notify, with legal owning the obligation). Rotate credentials and revoke sessions as containment; do the blameless review after recovery and ship a control per contributing factor. "We'll figure it out during the incident" loses time and evidence exactly when both are scarce.

### Decision rules

1. New trust boundary or sensitive action → STRIDE the boundary first (diagram → assets → boundaries → threats → mitigations → residual-risk owner); a model with no diagram is a checklist.
2. Keep authentication and authorization distinct; a logged-in user is not an authorized user — every privileged path needs a server-side authz check.
3. Any access that takes an id from the request → verify ownership/tenant at the data layer (IDOR/BOLA); client-side hiding is not a control.
4. Any privileged endpoint → enforce a per-action role/permission check on the endpoint, not by hiding the UI (function-level authz).
5. OAuth/OIDC public client → authorization code with PKCE; validate redirect URI, state, nonce, token audience, and expiry; scope least-privilege; never implicit flow.
6. Crypto → vetted library, AEAD with a unique nonce, a slow salted password KDF, and a managed/rotated key lifecycle; never invent an algorithm, reuse a nonce, or fast-hash a password.
7. Secret in source, build artifact, image layer, or CI log → treat as compromised, rotate now, then add pre-commit + CI scanning and move to a secret manager / OIDC; scan artifacts and logs, not only the repo.
8. Adding a dependency or shipping a build → generate an SBOM, gate on SCA, pin and verify provenance/signatures, fail the build on an unreviewed critical.
9. Collecting personal data → map the data-flow and minimize to a purpose before designing storage; separate consent from necessity; never log raw sensitive values; flag the legal-basis question to legal.
10. Cloud resource → default-deny least-privilege IAM (no wildcards, no long-lived keys, MFA on privileged), no public storage unless proven and scoped, encryption at rest, access logging.
11. Every control → pair it with a detection (event to log, alert condition, owner paged); a control with no detection is a control on paper.
12. Detection design → log auth/authz/privilege/export/config events, tamper-evident and centralized to a SIEM, retained to catch slow campaigns, with PII pseudonymized.
13. Incident response → design roles, severity-by-impact, containment→eradication→recovery, evidence preservation, and the disclosure path before the incident; preserve evidence before you wipe.
14. Irreversible/production/dual-use/data-exposing step → produce the plan and rollback, then route to a human owner; do not self-authorize disabling auth, opening a firewall, or exporting data.
15. Never treat "documented as enabled" as verified; confirm in the running system — the non-owner gets 403, the scanner blocks, the alert fires — before declaring the control done.

### Failure-repair playbook

1. **Session check used as the authz control (IDOR/BOLA)** → add a server-side owner/tenant check at the data layer on every object access; test it by requesting another actor's id and confirming a 403, not a 200.
2. **Admin function protected only by a hidden UI control** → add a per-action role/permission check on the endpoint; call the route directly as a non-admin and confirm it is denied.
3. **Implicit OAuth flow or unvalidated audience** → move the public client to authorization code with PKCE; enforce redirect-URI allowlist, state, nonce, and audience validation, and reject tokens minted for another service.
4. **Home-rolled or misused crypto** → replace with a vetted library and AEAD with a unique nonce; switch passwords to a slow salted KDF; move keys into a KMS, separate them from the data, and define rotation.
5. **Secret committed or baked into an artifact** → rotate it immediately (treat as leaked), then add pre-commit and CI secret scanning that also covers build artifacts, images, and logs, and migrate to a secret manager or OIDC.
6. **Dependencies trusted blindly** → generate an SBOM, add an SCA gate to CI that fails on unreviewed criticals, pin versions, and verify provenance/signatures to stop typosquat and dependency-confusion.
7. **Data-flow over-collects and logs PII** → remove fields with no purpose, set retention and a deletion path, separate consent from necessity, and pseudonymize PII in logs so the audit trail is not the leak.
8. **Cloud IAM wildcards and a public bucket** → scope policies to specific actions/resources, replace long-lived keys with short-lived federated credentials, enable block-public-access, fix object ACLs/policies, and add access logging.
9. **Controls with no detection** → for each mitigation in the threat model, add the log event, the alert condition, and the owner; a mitigation with no detection is unverifiable and silently degrades.
10. **SSRF / confused-deputy path** → validate and allowlist outbound URLs, block link-local/metadata addresses, restrict egress, and require authentication on internal services the deputy can reach.
11. **Incident handled ad hoc** → write the IR runbook now (roles, severity, containment→eradication→recovery, evidence preservation, disclosure path); in the live incident, snapshot evidence before wiping and route the disclosure decision to the owner.
12. **"Secure" asserted but never verified** → before closing, prove it in the running system: the IDOR returns 403, the scanner blocks the secret, the alert fires, the bucket is not publicly readable — a documented control is necessary, not sufficient.

### Verify live, not "documented as enabled"

A documented authorization check, an "enabled" WAF rule, a "configured" secret scanner, and a "least-privilege" IAM policy can all be wrong in the running system: the check is on the wrong layer, the rule is in count-only mode, the scanner excludes the path the secret is on, the policy still has a wildcard. Before calling a security control done, observe it live: request another user's object and confirm a 403, plant a test secret and confirm the scanner blocks the commit, trigger the abuse condition and confirm the alert pages, try to read the bucket anonymously and confirm it is denied. Treating "documented as enabled" as "verified" is how a control that exists on paper still leaves the abuse path open.

## Հայերեն

### Գործառնական սկզբունք

Ավագ security և privacy engineering-ը decision-grade է միայն այն ժամանակ, երբ անորոշ «դարձրու այն secure»-ը վերածում է հստակ trust boundary-ների, enforce-ված authorization model-ի, secret-ների, որ չեն կարող լուռ արտահոսել, և privacy ընտրությունների, որ նախագծված են հենց data flow-ի մեջ — և ամեն control զուգում է այն detection-ի հետ, որ ապացուցում է, որ այն իրականում աշխատում է։ Deliverable-ը մի քանի ձևից մեկն է․ threat model, auth/authorization review, privacy data-flow map, supply-chain control plan, cloud-hardening review կամ detection/incident-response դիզայն։ Բոլորը կառավարող միակ կարգապահությունը authentication-ը authorization-ից բաժանելն է․ համակարգը կարող է բոլորին կատարյալ authenticate անել և միևնույն է արտահոսել ամեն record, եթե երբեք չստուգի, որ *այս* actor-ը կարող է դիպչել *այս* resource-ին։ Ուստի ցանկացած access path-ի առաջին քայլը ոչ թե «logged-in է՞ user-ը» հարցնելն է, այլ «authorized է՞ user-ը հենց այս object-ի և հենց այս function-ի համար, ստուգված server-side»։ Security-ն հայտնի bug-ի բացակայությունը չէ. այն abuse path-եր են՝ փակված enforce-ված control-ներով, ամեն մեկը detection-ով, որ կրակում է, երբ control-ը bypass-վում կամ fail է լինում։ Այս skill-ը երկակի օգտագործման է, ուստի սահմանը ֆիքսվում է ամեն ինչից առաջ․ միայն defensive, authorized դիզայն — inline `SKILL.md` gate-ը ընդլայնվում է, երբեք չի փոխարինվում։

### Մեխանիզմների տեղեկագիր

- **STRIDE threat modeling** — STRIDE-ը վեց threat class քարտեզագրում է component-ների և trust boundary-ների վրա․ **S**poofing (identity), **T**ampering (integrity), **R**epudiation (deniability), **I**nformation disclosure (confidentiality), **D**enial of service (availability), **E**levation of privilege (authorization)։ Մեխանիզմը flow է, ոչ checklist․ նկարիր համակարգը → թվարկիր asset-ները → գծիր trust boundary-ները (որտեղ data-ն հատում է privilege level) → enumerate արա STRIDE ամեն boundary-ի համար → նշանակիր mitigation ամեն threat-ի → անվանիր residual-risk owner մնացածի համար։ Արա այն build-ից առաջ, որտեղ դեռ կարող է փոխել design-ը. launch-ից հետո checkbox-ի համար արված STRIDE table-ը ոչ մի որոշում չի փոխում և թղթաբանություն է։
- **AuthN ընդդեմ AuthZ, IDOR/BOLA, function-level authz** — **Authentication**-ը հաստատում է *ով* է actor-ը. **authorization**-ը որոշում է *ինչ* կարող է անել այդ actor-ը։ Դրանք շփոթելը ամենատարածված high-impact թերությունն է։ **Broken Object-Level Authorization (IDOR/BOLA)**․ endpoint-ը id է վերցնում request-ից (`/orders/{id}`) և վերադարձնում object-ը՝ առանց ստուգելու, որ caller-ը տիրում է դրան, ուստի id-ները iterate անելը անցնում է ուրիշ tenant-ների data-ի վրայով — fix-ը owner/tenant check է data layer-ում, ամեն object access-ի վրա, երբեք client-side թաքցնելով։ **Broken Function-Level Authorization**․ privileged endpoint-ը «պաշտպանված» է միայն button-ը չցուցադրելով. ուղիղ կանչելը հաջողվում է — fix-ը per-action role/permission check է հենց endpoint-ի վրա։ Կանոնը․ ամեն object access և ամեն privileged function կրում է server-side check *այս* actor-ի և *այս* resource-ի դեմ։
- **OAuth/OIDC և PKCE** — OAuth-ը delegate է անում **authorization**-ը scoped token-ներով. OIDC-ը ավելացնում է **identity** ID token-ով։ Public client-ի համար (SPA, mobile, ամեն ինչ, որ secret չի կարող պահել) օգտագործիր **authorization code flow PKCE-ով**, երբեք implicit flow։ Ձախողումները, որ PKCE-ն և իր ուղեկիցները կանխում են․ authorization-code interception (PKCE code_verifier/challenge), open-redirect token theft (խիստ redirect-URI allowlist), CSRF callback-ի վրա (`state`), ID-token replay (`nonce`), token-ներ ընդունված սխալ service-ի կողմից (validate **audience**) և stale-token abuse (**expiry**, rotation, revocation)։ Scope արա token-ները least privilege-ի։ AuthN-ը հաստատում է ով. AuthZ-ը դեռ որոշում է ինչ — վավեր token-ը դատարկ չեկ չէ։
- **Cryptography (misuse-resistance, ոչ algorithm-ի հորինում)** — Որոշումը երբեք «որ cipher-ն է ամենաուժեղը» չէ. այն misuse-resistance-ն ու key lifecycle-ն է։ Օգտագործիր vetted library. երբեք քո սեփականը մի՛ սարքիր։ Confidentiality + integrity-ի համար օգտագործիր **authenticated encryption (AEAD)** (օր.՝ AES-GCM կամ ChaCha20-Poly1305)՝ **unique nonce ամեն message-ի համար** — reused կամ zero nonce-ը կոտրում է construction-ը. երբեք ECB։ Password-ների համար օգտագործիր **slow, salted password KDF** (օր.՝ Argon2, scrypt կամ bcrypt), երբեք fast hash (MD5/SHA-1/raw SHA-256) և երբեք unsalted։ Կառավարիր **key lifecycle**-ը․ generated CSPRNG-ով, stored KMS/secret manager-ում (ոչ code կամ config-ում), separated այն data-ից, որ պաշտպանում է, և rotated՝ ըստ ժամանակացույցի և կասկածելի exposure-ի դեպքում։ «Encrypt ենք անում»՝ առանց AEAD-ի, KDF-ի և անվանված key lifecycle-ի, crypto design չէ։ Անվանված primitive-ները ընթացիկ-բայց-dated ուղեցույց են, ոչ հաստատուն — վերջնականացնելուց առաջ վերահաստատիր ընտրած AEAD/KDF-ն ու «խուսափելու» ցանկը ընթացիկ cryptographic guidance-ի դեմ (համապատասխան standards body / OWASP)՝ դրանք համարելով verify-before-use, ոչ հավերժական։
- **Privacy engineering (նախ data-flow)** — Privacy-ն սկսում է **data-flow map**-ից, ոչ policy պարբերությունից․ ամեն personal-data field-ի համար — data subject, purpose, collection point, controller/processor, storage, transfer (և destination/jurisdiction), retention, deletion, access և rights workflow (access/rectify/erase/export)։ Հետո **minimize** արա․ purpose չունեցող field-ը հանվում է, ոչ պահվում «եթե պետք լինի»։ Բաժանիր **consent-ը necessity-ից** — service մատուցելու համար պահանջվող data-ն նույնը չէ, ինչ data-ն, որ user-ը opt-in է արել։ Log արա sensitive data-ի access-ը, բայց **pseudonymize** արա այդ log-երում, որ audit trail-ը չդառնա նոր leak-ը։ Basis-ի կամ transfer-ի իրավական բավարարությունը flag-վում է legal-ին, ոչ հորինվում այստեղ։
- **Supply-chain security (SBOM/SCA, provenance)** — Չես կարող պաշտպանել, ինչ չես կարող inventory անել։ Generate արա **Software Bill of Materials (SBOM)** direct և transitive dependency-ների. վազեցրու **Software Composition Analysis (SCA)** known-vulnerable և yanked version-ների դեմ CI-ում և fail արա build-ը չ-review-ված critical-ի վրա։ **Pin** արա version-ները և **verify** արա provenance/signature-ները, որ dependency-ն չկարողանա լուռ swap-վել (typosquat, dependency-confusion, compromised maintainer)։ Մեկուսացրու build-ը, սահմանափակիր ով կարող է publish անել, և verify արա, որ ship արածդ artifact-ը build արածդ artifact-ն է։ Ոչ SBOM, ոչ SCA gate-ը supply-chain blindness է — չհսկվող դուռ դեպի production։

### Cloud security (IAM և storage/bucket hardening)

Cloud posture-ն այնտեղ է, որտեղ misconfiguration-ը, ոչ exotic exploitation-ը, պատճառում է exposure-ի մեծ մասը։ Կարգապահությունը՝ **default-deny, least-privilege և ոչ չ-ապացուցված public access։**

- **IAM least-privilege.** Տուր նվազագույն action-ը նվազագույն resource-ի վրա։ Wildcard-ները (`Action: "*"`, `Resource: "*"`) standing over-grant են. scope արա կոնկրետ action-ների և ARN/resource-ների, որ workload-ին պետք են։ Նախընտրիր **workload-ների assume արած role-եր** ընդդեմ **long-lived access key-երի**. long-lived key-երը static CI secret-ի cloud համարժեքն են — փոխարինիր short-lived federated credential-ով (workload identity / OIDC)։ Պահանջիր **MFA** human privileged access-ի վրա, separate արա duty-ները, որ ոչ մի role չկարողանա և access տալ, և օգտագործել, և review արա grant-ները, որ permission-ները unowned չաճեն։ Privileged action առանց approval-ի և expiry-ի standing breach է։
- **Storage / bucket misconfiguration.** Public object storage-ը classic data-leak-ն է։ Ամեն bucket համարիր private by default․ enable արա account- և bucket-level **block-public-access**, verify արա object **ACL-ները և bucket policy-ները**, որ չտան `AllUsers`/`AuthenticatedUsers` read, և ապացուցիր «պետք է public լինի» case-ը մինչև բացելը (և ապա միայն կոնկրետ prefix-ը, իդեալում CDN-ով առջևից, ոչ raw bucket-ը)։ Encrypt արա at rest managed key-ով, enable արա access logging, և version + lifecycle-expire արա object-ները, որ deletion կամ ransom event-ը recoverable լինի։ Խնդրի tell-ը bucket է, որ «առայժմ test-ի համար բացված» երբեք չի փակվում։
- **Network և boundary.** Default-deny security group / firewall rule-եր. expose արա միայն այն port-ները, որ service-ին պետք են. պահիր data store-ները public internet-ից դուրս՝ private networking-ի հետևում։ Պաշտպանիր **confused-deputy / SSRF** path-ը․ server, որ fetch է անում user-supplied URL կամ հասնում internal metadata endpoint-ների, կարող է վերածվել pivot-ի — սահմանափակիր egress-ը, block արա link-local/metadata հասցեները և պահանջիր authentication internal service-ների վրա։

### Detection engineering (logging, SIEM, alerting, incident response)

Ամեն control-ի պետք է detection, որ ապացուցում է, որ այն կրակում է. control առանց log/alert-ի լուռ degrade է լինում և անստուգելի է։ Կարգապահությունը՝ **log արա security-relevant event-ները, centralize արա, alert արա կարևոր պայմանների վրա և նախագծիր response-ը incident-ից առաջ։**

- **Ինչ log անել.** Authentication success և failure, authorization **denial**-ներ (object endpoint-ների վրա 403-ների spike-ը IDOR probe է), privilege և role change-եր, secret/key access, data export և bulk read, configuration և IAM change-եր, և admin action-ներ։ Log-երը պետք է լինեն **tamper-evident** (append-only / host-ից դուրս ուղարկված), կրեն հետաքննելու բավարար context (ով, ինչ, երբ, որտեղից, որ resource-ի վրա) և **retained** լինեն դանդաղ campaign-ները բռնելու չափ — բայց **pseudonymize** արա PII-ն, որ log store-ն ինքը privacy liability չլինի։
- **SIEM և correlation.** Centralize արա log-երը SIEM-ում, որ service-ների event-ները correlate լինեն․ failed-auth burst-ին հաջորդող success և data export-ը credential-stuffing-into-exfiltration պատմություն է, որ ոչ մի առանձին service log չի ցույց տալիս։ Կառուցիր detection-ներ այն abuse path-երի համար, որ threat model-ն անվանեց, ոչ միայն generic noise-ի։
- **Alerting.** Alert արա այն պայմանների վրա, որ ցույց են տալիս, որ control-ը bypass-վեց կամ abuse path-ը active է — կրկնվող authz denial, impossible-travel login, նոր public bucket, secret-scanner hit, critical flag-ված dependency, անսպասելի privilege escalation։ Ամեն alert անվանում է severity և owner, որ page-վում է. alert, որ ոչ ոք չի տիրում, noise է։ Tune արա false positive-ները նվազեցնելու, որ իրականը չթաղվի։
- **Incident response (նախապես նախագծված).** Իրական IR plan-ը սահմանում է․ **role**-եր (incident commander, comms, scribe), **severity** ըստ data-sensitivity-ի և blast radius-ի (ոչ ըստ ով նկատեց), **containment → eradication → recovery**-ի հերթականություն, **evidence preservation** (snapshot արա մինչև wipe-ը, այլապես քանդում ես forensic trail-ը) և **disclosure decision path**-ը (ով է որոշում՝ notify անել, թե երբ, որտեղ legal-ը տիրում է պարտավորությանը)։ Rotate արա credential-ները և revoke արա session-ները որպես containment. blameless review-ն արա recovery-ից հետո և ship արա control ամեն contributing factor-ի համար։ «Incident-ի ընթացքում կհասկանանք»-ը ժամանակ և evidence է կորցնում հենց այն ժամանակ, երբ երկուսն էլ սակավ են։

### Որոշման կանոններ

1. Նոր trust boundary կամ sensitive action → նախ STRIDE արա boundary-ն (diagram → assets → boundaries → threats → mitigations → residual-risk owner). model առանց diagram-ի checklist է։
2. Պահիր authentication-ն ու authorization-ը առանձին. logged-in user-ը authorized user չէ — ամեն privileged path-ի պետք server-side authz check։
3. Ցանկացած access, որ id է վերցնում request-ից → verify արա ownership/tenant-ը data layer-ում (IDOR/BOLA). client-side թաքցնելը control չէ։
4. Ցանկացած privileged endpoint → enforce արա per-action role/permission check endpoint-ի վրա, ոչ UI-ն թաքցնելով (function-level authz)։
5. OAuth/OIDC public client → authorization code PKCE-ով. validate արա redirect URI, state, nonce, token audience և expiry. scope least-privilege. երբեք implicit flow։
6. Crypto → vetted library, AEAD unique nonce-ով, slow salted password KDF և managed/rotated key lifecycle. երբեք algorithm մի՛ հորինիր, nonce մի՛ reuse արա, password fast-hash մի՛ արա։
7. Secret source-ում, build artifact-ում, image layer-ում կամ CI log-ում → համարիր compromised, rotate արա հիմա, հետո ավելացրու pre-commit + CI scanning և անցիր secret manager / OIDC. scan արա artifact-ները և log-երը, ոչ միայն repo-ն։
8. Dependency ավելացնելիս կամ build ship անելիս → generate արա SBOM, gate արա SCA-ով, pin և verify արա provenance/signature-ները, fail արա build-ը չ-review-ված critical-ի վրա։
9. Personal data հավաքելիս → map արա data-flow-ը և minimize արա purpose-ի մինչև storage-ը նախագծելը. բաժանիր consent-ը necessity-ից. երբեք raw sensitive value մի՛ log արա. flag արա legal-basis-ի հարցը legal-ին։
10. Cloud resource → default-deny least-privilege IAM (ոչ wildcard, ոչ long-lived key, MFA privileged-ի վրա), ոչ public storage, քանի դեռ ապացուցված և scoped չէ, encryption at rest, access logging։
11. Ամեն control → զուգիր detection-ի հետ (log-ելու event, alert-ի պայման, page-վող owner). control առանց detection-ի թղթի վրա control է։
12. Detection design → log արա auth/authz/privilege/export/config event-ները, tamper-evident և SIEM-ում centralized, retained դանդաղ campaign բռնելու չափ, PII-ն pseudonymize-ված։
13. Incident response → նախագծիր role-եր, severity-by-impact, containment→eradication→recovery, evidence preservation և disclosure path incident-ից առաջ. preserve արա evidence-ը մինչև wipe-ը։
14. Անդառնալի/production/dual-use/data-exposing քայլ → արտադրի՛ր պլանն ու rollback-ը, հետո ուղղորդիր մարդ-owner-ի. ինքդ մի՛ authorize արա auth-ի անջատում, firewall-ի բացում կամ data-ի export։
15. Երբեք «documented as enabled»-ը verified մի՛ համարիր. հաստատի՛ր running system-ում — non-owner-ը ստանում է 403, scanner-ը block է անում, alert-ը կրակում է — մինչև control-ը done հայտարարելը։

### Վերականգնման խաղագիրք

1. **Session check-ը օգտագործված որպես authz control (IDOR/BOLA)** → ավելացրու server-side owner/tenant check data layer-ում ամեն object access-ի վրա. test արա ուրիշ actor-ի id հարցնելով և 403 հաստատելով, ոչ 200։
2. **Admin function-ը պաշտպանված միայն թաքնված UI control-ով** → ավելացրու per-action role/permission check endpoint-ի վրա. կանչիր route-ը ուղիղ որպես non-admin և հաստատիր, որ deny է լինում։
3. **Implicit OAuth flow կամ չ-validate-ված audience** → տեղափոխիր public client-ը authorization code PKCE-ով. enforce արա redirect-URI allowlist, state, nonce և audience validation, և reject արա ուրիշ service-ի համար minted token-ները։
4. **Home-rolled կամ misused crypto** → փոխարինիր vetted library-ով և AEAD-ով՝ unique nonce-ով. password-ները փոխիր slow salted KDF-ի. տեղափոխիր key-երը KMS, separate արա data-ից և սահմանիր rotation։
5. **Secret commit-ված կամ baked artifact-ում** → rotate արա անմիջապես (համարիր leaked), հետո ավելացրու pre-commit և CI secret scanning, որ ծածկում է նաև build artifact, image և log, և migrate արա secret manager-ի կամ OIDC-ի։
6. **Dependency-ները blind trusted** → generate արա SBOM, ավելացրու SCA gate CI-ում, որ fail է անում չ-review-ված critical-ի վրա, pin արա version-ները և verify արա provenance/signature-ները՝ typosquat-ը և dependency-confusion-ը կանգնեցնելու։
7. **Data-flow-ը over-collect է անում և PII log է անում** → հանիր purpose չունեցող field-երը, դիր retention և deletion path, բաժանիր consent-ը necessity-ից, և pseudonymize արա PII-ն log-երում, որ audit trail-ը leak-ը չլինի։
8. **Cloud IAM wildcard-ներ և public bucket** → scope արա policy-ները կոնկրետ action/resource-ների, փոխարինիր long-lived key-երը short-lived federated credential-ով, enable արա block-public-access, ուղղիր object ACL/policy-ները և ավելացրու access logging։
9. **Control-ներ առանց detection-ի** → threat model-ի ամեն mitigation-ի համար ավելացրու log event-ը, alert-ի պայմանը և owner-ը. detection չունեցող mitigation-ը անստուգելի է և լուռ degrade է լինում։
10. **SSRF / confused-deputy path** → validate և allowlist արա outbound URL-ները, block արա link-local/metadata հասցեները, սահմանափակիր egress-ը և պահանջիր authentication internal service-ների վրա, որ deputy-ն կարող է հասնել։
11. **Incident handled ad hoc** → գրիր IR runbook-ը հիմա (role-եր, severity, containment→eradication→recovery, evidence preservation, disclosure path). live incident-ում snapshot արա evidence-ը մինչև wipe-ը և ուղղորդիր disclosure-ի որոշումը owner-ին։
12. **«Secure» պնդված, բայց երբեք verify չարված** → փակելուց առաջ ապացուցիր running system-ում․ IDOR-ը 403 է վերադարձնում, scanner-ը block է անում secret-ը, alert-ը կրակում է, bucket-ը public-ից չի կարդացվում — documented control-ը անհրաժեշտ է, ոչ բավարար։

### Verify live, ոչ «documented as enabled»

Փաստաթղթավորված authorization check-ը, «enabled» WAF rule-ը, «configured» secret scanner-ը և «least-privilege» IAM policy-ն կարող են բոլորն էլ սխալ լինել running system-ում․ check-ը սխալ layer-ի վրա է, rule-ը count-only mode-ում է, scanner-ը բացառում է այն path-ը, որի վրա secret-ն է, policy-ն դեռ wildcard ունի։ Security control-ը done հայտարարելուց առաջ դիտի՛ր այն live․ հարցրու ուրիշ user-ի object-ը և հաստատիր 403, տնկիր test secret և հաստատիր, որ scanner-ը block է անում commit-ը, գործարկիր abuse պայմանը և հաստատիր, որ alert-ը page է անում, փորձիր կարդալ bucket-ը անանուն և հաստատիր, որ deny է։ «Documented as enabled»-ը «verified» համարելն այն ճանապարհն է, որով թղթի վրա գոյություն ունեցող control-ը միևնույն է բաց է թողնում abuse path-ը։
