# Software Systems Architecture manual

## English

### Operating principle

Senior software systems architecture is decision-grade only when it starts from an invariant rather than a technology, and pairs every structural choice with an auditable mechanism. The deliverable is one of a few shapes: an architecture decision record, an integration or event-driven design (saga / choreography vs orchestration), a resilience plan, a data-consistency decision, or an API/event contract. The single guardrail that governs all of them is the invariant: the thing that must always be true (an order is never confirmed without authorized payment and reserved inventory; money is never double-charged; a permission revocation is never ignored). If the invariant is unnamed, every downstream choice — which pattern, which consistency model, whether to retry, where the trust boundary sits — is a guess. So the first move is always to write the invariant, the load shape, the failure mode, and the data ownership; then derive the structure from them. Architecture is not the absence of coupling; it is coupling placed deliberately, with seams where the next change is cheap and a clear answer to "what breaks, who owns it, and how do we know."

### Mechanism reference

- **Idempotency and sagas** — Idempotency means the same request can be applied more than once with the same final effect; use idempotency keys on payment/order/transfer commands and store the request hash plus the result so a duplicate returns the first result instead of re-applying. Sagas coordinate distributed work through local transactions and compensating actions; use them when two-phase commit (2PC) is unavailable or too brittle (e.g. an external payment provider that cannot join a distributed transaction). For each saga step define the local transaction, the emitted event, the compensation, the timeout, the owner, and the user-visible state. CQRS separates the write model from the read model when query shape and command invariants pull in different directions; it earns its complexity only when reads and writes genuinely diverge.
- **Resilience patterns and thresholds** — Resilience is only real with thresholds: a timeout per dependency (never unbounded), retry only on retryable errors with jitter and a retry budget, a circuit breaker that opens after a failure ratio and probes in half-open, and bulkheads that isolate resource pools so one slow dependency cannot exhaust all threads. Backpressure rejects or slows work before queues collapse; it is safer than infinite buffering, which only delays the failure and makes it bigger. A retry without a timeout and a budget is not resilience — it is a load amplifier that converts a slow dependency into an outage.
- **Consistency models** — Consistency models shape the user promise, and the invariant picks the model: strong consistency for money, permissions, and inventory; read-your-writes for confirmation pages (a user must see their own just-written change); monotonic reads for sessions (time must not appear to go backward); eventual consistency for feeds, history, and analytics. State the invariant, the acceptable stale window in concrete units, and the action that is unsafe on a stale read (e.g. "granting access on a stale permission read is unsafe; charging on a stale balance is unsafe").
- **API and event as a contract** — An API or event is a contract with consumers, not just code: it has a versioning policy, pagination, idempotency semantics, an error model (codes and shapes), rate limits, an auth scope, and a backward-compatibility rule. Prefer additive (expand/contract) evolution; a breaking change shipped without a deprecation window and a consumer-migration plan is an outage disguised as cleanup. The contract needs an owner; an unowned cross-team contract drifts until it breaks silently.
- **Choreography vs orchestration** — A multi-service workflow is run one of two ways. **Orchestration** uses a central coordinator (an orchestrator or an orchestration-style saga) that calls each step, holds the workflow state, enforces ordering, and runs compensation centrally — choose it when you need end-to-end visibility, enforced sequencing, or a single owner of the end-state. **Choreography** has each service react to events and emit its own, with no central brain — choose it when steps are autonomous and you want loose coupling and independent evolution. The trap is choreography with no owner of the end-state: events fly, nothing tracks whether the workflow ever completes, and orphaned/stuck workflows accumulate. If you choreograph, you still need a way to detect and recover incomplete workflows (a timeout/sweeper, a process manager, or an audit on the event log).
- **Time, ordering, and identity** — In a distributed system you cannot trust wall-clock time or delivery order. Separate two questions: *"has this been applied already?"* (idempotency) is answered by a stable **idempotency key** plus a dedup store; *"in what order did these happen?"* (ordering) is answered by an **ordering/sequence key**, a per-entity partition (so all events for one entity are serialized), or a version/sequence number on the entity. When concurrent writers must be detected, use **logical clocks** (a monotonically increasing counter — Lamport-style — gives a total-ish order) or **vector clocks** (one counter per actor — detects true concurrency and conflicts that a single counter hides). Every request and event carries a **correlation id** (the same id across the whole chain, so a distributed trace can be reconstructed) and a **causation id** (which message caused this one). Generate ids at the edge, propagate them through every hop and event, and log them — without them, a distributed failure is undebuggable.
- **Application-security architecture** — Security here is *placement*, not control implementation (that routes to security). Place a **trust boundary**: authenticate and authorize at the boundary, and treat everything inside as needing its own check rather than blanket trust. Scope each service's credentials to **least privilege** so a compromise is contained; design for **blast-radius minimization** so one stolen token or one popped service does not unlock the whole system. Keep **secrets out of code and repos** (inject at runtime from a secret store; treat any committed secret as compromised and rotate it). Decide **where authz lives** (at the gateway, in each service, or both) and make it consistent — an authz check that is sometimes deep inside and sometimes missing is a hole. Validate and treat all cross-boundary input (including events and internal calls) as untrusted. The architecture owns *where the boundary is and how far a compromise spreads*; the concrete controls, threat model, and crypto choices belong to security.
- **Right-sizing the architecture** — Match structure to the invariant and the team, not to fashion. Default to a modular monolith with clear module seams and explicit internal contracts; it gives you most of the decomposition benefit with a fraction of the operational tax. Split into services, adopt event sourcing, or introduce CQRS only when a real invariant demands it: independent scaling of one component, an audit/replay requirement, divergent read/write models, or independent team deployment. Premature microservices buy you a distributed monolith — all the cost of distribution, none of the independence.

### Decision rules

1. Write the invariant, load shape, failure mode, and data ownership before choosing any pattern; a pattern picked before the invariant is preference dressed as architecture.
2. An ADR must reject at least one plausible alternative and state the tradeoff it loses; without that it documents a conclusion, not a decision.
3. Never retry a non-idempotent write without an idempotency key plus a request-hash→result store; a retried charge/order/transfer is a duplicate applied to production.
4. Distinguish idempotency from ordering: an idempotency key answers "applied already?", an ordering/sequence key (or per-entity partition) answers "in what order?"; a system that dedups but reorders still corrupts state.
5. Choose choreography vs orchestration on coupling and visibility: orchestrate for end-to-end visibility, enforced ordering, or central compensation; choreograph for autonomous, loosely coupled steps — and never leave the workflow with no owner of its end-state.
6. When 2PC is unavailable or brittle, use a saga: per step define local transaction, emitted event, compensation, timeout, owner, and user-visible state; an uncompensatable step goes last or is gated by human review.
7. Pick the consistency model from the invariant (strong for money/permissions, read-your-writes for confirmations, monotonic for sessions, eventual for feeds) and always state the stale window in concrete units plus the unsafe-on-stale action.
8. Two services sharing one writable table are integrating through the database; give each an owned API or event contract instead of a hidden, unversioned shared schema.
9. Ship no breaking API/event change without a versioning policy, a deprecation window, and a consumer-migration plan; prefer additive expand/contract evolution.
10. For a flaky dependency set the full resilience set — timeout, retry-on-retryable-with-jitter-and-budget, circuit breaker, bulkhead, fallback, backpressure — not a bare retry that amplifies the outage.
11. Propagate a correlation id (and causation id) through every cross-service request and event; generate at the edge, log everywhere, or distributed failures are undebuggable.
12. Make ordering explicit when the transport does not guarantee it: per-entity partition/sequence, version numbers, or logical/vector clocks to detect concurrent writes.
13. Place the trust boundary and minimize blast radius: authenticate/authorize at the boundary, least-privilege each service's credentials, keep secrets out of repos; route control design and the threat model to security.
14. Right-size down: default to a modular monolith and adopt services/event-sourcing/CQRS only when a concrete invariant (scaling, audit/replay, divergent models, independent deploy) requires it.
15. Verify the load-bearing claim in the running system — duplicate-delivery idempotency, ordering under concurrency, the consistency promise under lag, and the compensation path — not just that tests pass.

### Failure-repair playbook

1. **Pattern chosen before the invariant** → stop; write the invariant, load shape, failure mode, and data ownership, then re-derive the pattern from them. Discard any choice the invariant does not justify.
2. **ADR with no rejected alternative** → add the strongest plausible option you did not pick and the tradeoff it loses; a decision record with one option is a conclusion, not a decision.
3. **Retry on a non-idempotent write** → add an idempotency key and a request-hash→result store so a duplicate returns the first result; until then, do not retry that write.
4. **Idempotency and ordering conflated** → separate them: keep the idempotency key for dedup, add a per-entity ordering/sequence (or partition) for sequence, and reject or reorder out-of-sequence events explicitly.
5. **Multi-service workflow with no end-state owner** → declare choreography or orchestration; if choreography, add a process manager / timeout sweeper / event-log audit that detects and recovers incomplete workflows.
6. **Saga with an uncompensatable step in the middle** → reorder so the irreversible step is last, or gate it behind human review / a confirmation token; never place "send money / send email" before a step that can still fail.
7. **"Eventual" used to dodge the invariant** → name the invariant, pick the model it requires, and state the stale window plus the unsafe-on-stale action; if the data is money/permissions/inventory, it is probably not eventual.
8. **Resilience theater (retries, no thresholds)** → add a per-dependency timeout, jitter and a retry budget, a circuit breaker, a bulkhead, and backpressure; a retry without a timeout and budget is a load amplifier, not resilience.
9. **Unowned / unversioned contract** → assign an owner, add a versioning policy and error model, list consumers, and require a deprecation window + migration plan before any breaking change.
10. **No correlation id across the chain** → generate a correlation id at the edge, propagate it through every call and event, and log it; add a causation id where you need to reconstruct cause.
11. **Diffused security boundary / unbounded blast radius** → place an explicit trust boundary, make the authz check consistent, scope each service to least privilege, pull secrets out of the repo and rotate them, and route the threat model and controls to security.
12. **Architecture astronautics** → propose the right-sized modular-monolith path, name the invariant that would (and does not currently) justify the complexity, and quantify the operational tax being removed.

### Choreography vs orchestration (how to choose)

When a workflow spans services, decide explicitly: **orchestration** (a central coordinator holds the workflow state, calls each step, enforces order, and runs compensation centrally) or **choreography** (each service reacts to events and emits its own, no central brain). Orchestrate when you need end-to-end visibility, enforced sequencing, central compensation, or a single owner who can answer "where is this workflow and did it finish." Choreograph when steps are autonomous, you want loose coupling and independent evolution, and the order between steps is naturally enforced by data dependencies. The decisive failure mode is choreography with no owner of the end-state: events fly, nothing tracks completion, and stuck/orphaned workflows accumulate silently. If you choreograph, you still owe a recovery mechanism — a timeout sweeper, a process manager, or an audit over the event log — so an incomplete workflow is detected and compensated rather than lost.

### Time, ordering, and identity (the distributed-systems gate)

You cannot trust wall-clock time or delivery order across services, so make identity and order explicit. Keep three things distinct: an **idempotency key** ("has this exact request been applied?") backed by a dedup store; an **ordering/sequence key** ("in what order did these happen?") via a per-entity partition or a version/sequence number; and **clocks for concurrency detection** — a logical (Lamport) clock for a total-ish order, or vector clocks when you must detect true concurrent writes and conflicts a single counter would hide. Thread a **correlation id** through every request and event so a distributed trace can be reconstructed, and a **causation id** to record which message caused which. The common, expensive mistake is using one idempotency key to mean both "don't apply twice" and "apply in order" — it does the first and not the second, so duplicates are caught while a reordered "cancel before create" still corrupts state.

### Application-security architecture (placement, not control implementation)

Architecture decides *where the trust boundary sits and how far a compromise spreads*; the concrete controls, threat model, and crypto choices belong to security. Authenticate and authorize at the boundary and make the authz check consistent — an authz gate that is sometimes at the gateway, sometimes deep inside, and sometimes missing is a hole. Scope every service's credentials to **least privilege** so a popped service cannot reach what it never needed, and design for **blast-radius minimization** so one stolen token does not unlock the system. Keep **secrets out of code and repositories** — inject them at runtime from a secret store, and treat any committed secret as compromised and rotate it regardless of cause. Treat all cross-boundary input as untrusted, including internal calls and events. The deliverable from architecture is the boundary placement, the privilege scoping, the secret-handling design, and the blast-radius analysis — handed to security for the control catalogue and threat model.

### Verify in the running system, not "tests pass"

Passing tests prove the cases that exist behaved; they do not prove the architecture holds under reality. Before declaring a structural change done, exercise the load-bearing claim in the running system: send a duplicate delivery and confirm idempotency dedups it; force concurrent/out-of-order events and confirm ordering and conflict handling; introduce replication lag and confirm the consistency promise still holds; fail a saga step and confirm the compensation actually runs and the user-visible state is correct. "It compiles and tests pass" is necessary, not sufficient — the seam has to survive duplicate delivery, reordering, lag, and partial failure.

## Հայերեն

### Գործառնական սկզբունք

Ավագ software systems architecture-ը decision-grade է միայն այն ժամանակ, երբ սկսում է invariant-ից, ոչ technology-ից, և ամեն կառուցվածքային ընտրություն զուգում է auditable mechanism-ի հետ։ Deliverable-ը մի քանի ձևից մեկն է՝ architecture decision record, integration կամ event-driven design (saga / choreography ընդդեմ orchestration), resilience plan, data-consistency որոշում, կամ API/event contract։ Բոլորը կառավարող միակ guardrail-ը invariant-ն է՝ այն, ինչ պետք է միշտ ճիշտ լինի (order-ը երբեք confirmed չի դառնում առանց authorized payment-ի և reserved inventory-ի. փողը երբեք double-charge չի լինում. permission-ի revocation-ը երբեք չի անտեսվում)։ Եթե invariant-ը անանուն է, ապա ամեն հետընթաց ընտրություն՝ որ pattern, որ consistency model, retry անել թե ոչ, որտեղ է trust boundary-ն, գուշակություն է։ Ուստի առաջին քայլը միշտ invariant-ը, load shape-ը, failure mode-ը և data ownership-ը գրելն է. հետո դրանցից բխեցնելը։ Architecture-ը coupling-ի բացակայությունը չէ. այն գիտակցորեն տեղադրված coupling է՝ կարերով, որտեղ հաջորդ փոփոխությունը էժան է, և հստակ պատասխանով «ինչն է կոտրվում, ով է տիրում, ու ոնց ենք իմանում»։

### Մեխանիզմների տեղեկագիր

- **Idempotency և saga** — Idempotency նշանակում է, որ նույն request-ը կարող է մի քանի անգամ կիրառվել նույն final effect-ով. payment/order/transfer command-ի վրա օգտագործիր idempotency key և պահիր request hash-ը plus result-ը, որ duplicate-ը վերադարձնի առաջին result-ը, ոչ թե կրկին կիրառի։ Saga-ն distributed work-ը կապում է local transaction-ներով և compensating action-ներով. օգտագործիր այն, երբ two-phase commit (2PC)-ն անհասանելի կամ չափազանց brittle է (օր.՝ external payment provider, որ չի կարող join անել distributed transaction-ին)։ Ամեն saga step-ի համար սահմանիր local transaction-ը, emitted event-ը, compensation-ը, timeout-ը, owner-ը և user-visible state-ը։ CQRS-ը բաժանում է write model-ը read model-ից, երբ query shape-ը և command invariant-ները հակառակ ուղղություններով են քաշում. այն արդարացնում է իր complexity-ն միայն, երբ read-ն ու write-ը իսկապես շեղվում են։
- **Resilience pattern և threshold** — Resilience-ն իրական է միայն threshold-ով․ timeout ամեն dependency-ի (երբեք unbounded), retry միայն retryable error-ի վրա՝ jitter-ով և retry budget-ով, circuit breaker, որ բացվում է failure ratio-ից հետո և half-open-ում probe է անում, և bulkhead-ներ, որ մեկուսացնում են resource pool-երը, որ մեկ դանդաղ dependency-ն չսպառի բոլոր thread-երը։ Backpressure-ը reject կամ slow է անում work-ը նախքան queue-ի collapse-ը. այն ավելի ապահով է, քան infinite buffering-ը, որ միայն հետաձգում է failure-ը և մեծացնում։ Retry առանց timeout-ի և budget-ի resilience չէ. այն load amplifier է, որ դանդաղ dependency-ն վերածում է outage-ի։
- **Consistency model-ներ** — Consistency model-ները ձևավորում են user promise-ը, և invariant-ն է ընտրում model-ը․ strong consistency՝ money-ի, permissions-ի և inventory-ի. read-your-writes՝ confirmation page-ի (user-ը պետք է տեսնի իր նոր գրած փոփոխությունը). monotonic reads՝ session-ի (ժամանակը չպետք է երևա հետընթաց). eventual consistency՝ feed-ի, history-ի և analytics-ի։ Նշիր invariant-ը, ընդունելի stale window-ը կոնկրետ միավորով, և այն action-ը, որ stale read-ի դեպքում unsafe է (օր.՝ «stale permission read-ով access տալը unsafe է. stale balance-ով charge անելը unsafe է»)։
- **API և event՝ որպես contract** — API-ն կամ event-ը contract է consumer-ների հետ, ոչ միայն code․ ունի versioning policy, pagination, idempotency semantics, error model (code-եր և shape-եր), rate limit, auth scope և backward-compatibility rule։ Նախընտրիր additive (expand/contract) evolution. breaking change, որ ship է առանց deprecation window-ի և consumer-migration plan-ի, outage է՝ cleanup-ի քողի տակ։ Contract-ին պետք է owner. անտեր cross-team contract-ը drift է անում, մինչև լուռ կոտրվում է։
- **Choreography ընդդեմ orchestration** — Multi-service workflow-ը վարվում է երկու ձևից մեկով։ **Orchestration**-ը օգտագործում է կենտրոնական coordinator (orchestrator կամ orchestration-ոճի saga), որ կանչում է ամեն step, պահում workflow state-ը, enforce է անում ordering-ը և կենտրոնացված run է անում compensation-ը — ընտրիր այն, երբ պետք է ծայրից-ծայր visibility, enforced sequencing կամ end-state-ի մեկ owner։ **Choreography**-ում ամեն service react է անում event-ներին և emit իրենը՝ առանց կենտրոնական ուղեղի — ընտրիր այն, երբ step-երը autonomous են, և ուզում ես loose coupling ու անկախ evolution։ Թակարդը choreography-ն է՝ առանց end-state-ի տիրոջ․ event-ները թռչում են, ոչինչ չի հետևում, թե workflow-ն երբևէ ավարտվու՞մ է, և orphaned/խրված workflow-ները կուտակվում են։ Եթե choreograph ես անում, միևնույն է պետք է recovery mechanism՝ timeout/sweeper, process manager, կամ audit event log-ի վրա, որ incomplete workflow-ն հայտնաբերվի և compensate-վի, ոչ կորչի։
- **Time, ordering և identity** — Distributed system-ում չես կարող վստահել wall-clock time-ին կամ delivery order-ին։ Բաժանիր երկու հարց․ *«սա արդեն կիրառվա՞ծ է»* (idempotency)՝ պատասխանվում է կայուն **idempotency key**-ով plus dedup store-ով. *«ինչ հերթականությամբ են սրանք եղել»* (ordering)՝ պատասխանվում է **ordering/sequence key**-ով, per-entity partition-ով (որ մեկ entity-ի բոլոր event-ները serialize-վեն), կամ entity-ի վրա version/sequence number-ով։ Երբ պետք է concurrent writer-ները հայտնաբերել, օգտագործիր **logical clock**-եր (monotonic աճող counter՝ Lamport-ոճ՝ տալիս է total-ish order) կամ **vector clock**-եր (մեկ counter ամեն actor-ի՝ հայտնաբերում է իրական concurrency և conflict, որ մեկ counter-ը թաքցնում է)։ Ամեն request և event կրում է **correlation id** (նույն id-ն ողջ շղթայով, որ distributed trace-ը կարողանա վերականգնվել) և **causation id** (որ message-ը պատճառեց սա)։ Generate արա id-ները edge-ին, propagate արա ամեն hop-ով և event-ով, և log արա. առանց դրանց distributed failure-ն undebuggable է։
- **Application-security architecture** — Security-ն այստեղ *տեղադրում* է, ոչ control-ի իրականացում (դա ուղղորդվում է security-ին)։ Տեղադրիր **trust boundary**․ authenticate և authorize արա boundary-ին, և ներսի ամեն ինչ համարիր որպես իր check-ը պահանջող, ոչ թե blanket trust։ Ամեն service-ի credential-ը scope արա **least privilege**-ի, որ compromise-ը պարունակվի. design արա **blast-radius minimization**-ի, որ մեկ գողացված token-ը կամ մեկ popped service-ը ողջ համակարգը չբացի։ Secret-ները պահիր **code-ից և repo-ից դուրս** (inject արա runtime-ին secret store-ից. ցանկացած commit-ված secret համարիր compromised և rotate արա)։ Որոշիր, թե **որտեղ է ապրում authz-ը** (gateway-ում, ամեն service-ում, թե երկուսում) և դարձրու հետևողական — authz check, որ երբեմն խորքում է, երբեմն բացակա, անցք է։ Validate և համարիր ամեն cross-boundary input (ներառյալ event-ները և internal call-երը) untrusted։ Architecture-ը տիրում է *որտեղ է boundary-ն և որքան հեռու է տարածվում compromise-ը*. կոնկրետ control-ները, threat model-ը և crypto ընտրությունները security-ինն են։
- **Architecture-ի right-sizing** — Համապատասխանեցրու կառուցվածքը invariant-ին և թիմին, ոչ նորաձևությանը։ Լռելյայն ընտրիր modular monolith՝ պարզ module-կարերով և հստակ internal contract-ներով. այն տալիս է decomposition-ի օգուտի մեծ մասը operational tax-ի փոքր մասով։ Service-ների բաժանիր, event sourcing ընդունիր, կամ CQRS ներմուծիր միայն, երբ իրական invariant է պահանջում՝ մեկ component-ի անկախ scaling, audit/replay պահանջ, շեղվող read/write model, կամ թիմի անկախ deploy։ Վաղաժամ microservices-ը քեզ տալիս է distributed monolith՝ distribution-ի ողջ ծախսը, ոչ մի independence։

### Որոշման կանոններ

1. Գրիր invariant-ը, load shape-ը, failure mode-ը և data ownership-ը նախքան որևէ pattern ընտրելը. invariant-ից առաջ ընտրված pattern-ը preference է architecture-ի հագուստով։
2. ADR-ը պետք է մերժի առնվազն մեկ plausible alternative և նշի tradeoff-ը, որ կորցնում է. առանց դրա այն եզրակացություն է փաստագրում, ոչ որոշում։
3. Երբեք մի՛ retry արա non-idempotent write առանց idempotency key-ի plus request-hash→result store-ի. retry-ված charge/order/transfer-ը duplicate է, կիրառված production-ի վրա։
4. Տարբերիր idempotency-ն ordering-ից․ idempotency key-ը պատասխանում է «արդեն կիրառվա՞ծ է», ordering/sequence key-ը (կամ per-entity partition)՝ «ինչ հերթականությամբ». համակարգ, որ dedup է անում, բայց reorder՝ միևնույն է corrupt է անում state-ը։
5. Ընտրիր choreography ընդդեմ orchestration՝ coupling-ով և visibility-ով․ orchestrate արա ծայրից-ծայր visibility-ի, enforced ordering-ի կամ կենտրոնական compensation-ի համար. choreograph արա autonomous, loosely coupled step-երի համար — և երբեք մի՛ թող workflow-ն առանց իր end-state-ի տիրոջ։
6. Երբ 2PC-ն անհասանելի կամ brittle է, օգտագործիր saga․ ամեն step-ի համար սահմանիր local transaction, emitted event, compensation, timeout, owner և user-visible state. չ-compensate-վող step-ը դիր վերջում կամ gate արա մարդկային review-ով։
7. Consistency model-ը ընտրիր invariant-ից (strong՝ money/permissions, read-your-writes՝ confirmation, monotonic՝ session, eventual՝ feed) և միշտ նշիր stale window-ը կոնկրետ միավորով plus unsafe-on-stale action-ը։
8. Երկու service՝ մեկ writable table կիսելով, integrate են անում database-ով. ամեն մեկին տուր սեփական API կամ event contract, ոչ թե թաքնված, unversioned կիսված schema։
9. Ship մի՛ արա breaking API/event change առանց versioning policy-ի, deprecation window-ի և consumer-migration plan-ի. նախընտրիր additive expand/contract evolution։
10. Flaky dependency-ի համար դիր ամբողջ resilience set-ը՝ timeout, retry-on-retryable-jitter-ով-և-budget-ով, circuit breaker, bulkhead, fallback, backpressure — ոչ մերկ retry, որ ուժեղացնում է outage-ը։
11. Propagate արա correlation id (և causation id) ամեն cross-service request-ով և event-ով. generate արա edge-ին, log արա ամենուր, այլապես distributed failure-ները undebuggable են։
12. Ordering-ը դարձրու հստակ, երբ transport-ը չի երաշխավորում․ per-entity partition/sequence, version number, կամ logical/vector clock՝ concurrent write-երը հայտնաբերելու։
13. Տեղադրիր trust boundary-ն և նվազեցրու blast radius-ը․ authenticate/authorize արա boundary-ին, least-privilege արա ամեն service-ի credential-ը, secret-ները պահիր repo-ից դուրս. control-ի դիզայնը և threat model-ը ուղղորդիր security-ին։
14. Right-size արա ներքև․ լռելյայն ընտրիր modular monolith և ընդունիր service/event-sourcing/CQRS միայն, երբ կոնկրետ invariant (scaling, audit/replay, շեղվող model, անկախ deploy) պահանջում է։
15. Ստուգիր load-bearing պնդումը running system-ում՝ duplicate-delivery idempotency, ordering concurrency-ի տակ, consistency promise lag-ի տակ, և compensation path — ոչ միայն, որ test-երն անցան։

### Վերականգնման խաղագիրք

1. **Pattern ընտրված invariant-ից առաջ** → կանգնիր. գրիր invariant-ը, load shape-ը, failure mode-ը և data ownership-ը, հետո վերաբխեցրու pattern-ը դրանցից։ Դեն նետիր ամեն ընտրություն, որ invariant-ը չի արդարացնում։
2. **ADR առանց մերժված alternative-ի** → ավելացրու ամենաուժեղ plausible option-ը, որ չընտրեցիր, և tradeoff-ը, որ կորցնում է. մեկ option-ով որոշման գրառումը եզրակացություն է, ոչ որոշում։
3. **Retry non-idempotent write-ի վրա** → ավելացրու idempotency key և request-hash→result store, որ duplicate-ը վերադարձնի առաջին result-ը. մինչ այդ՝ մի՛ retry արա այդ write-ը։
4. **Idempotency-ն ու ordering-ը շփոթված** → բաժանիր դրանք․ idempotency key-ը պահիր dedup-ի, ավելացրու per-entity ordering/sequence (կամ partition) sequence-ի համար, և reject կամ reorder արա out-of-sequence event-ները բացահայտ։
5. **Multi-service workflow՝ առանց end-state-ի տիրոջ** → հայտարարիր choreography կամ orchestration. եթե choreography, ավելացրու process manager / timeout sweeper / event-log audit, որ հայտնաբերի և վերականգնի incomplete workflow-ները։
6. **Saga՝ չ-compensate-վող step-ով մեջտեղում** → վերադասավորիր, որ անդառնալի step-ը լինի վերջում, կամ gate արա մարդկային review-ով / confirmation token-ով. երբեք մի՛ դիր «փող ուղարկել / email ուղարկել» step-ից առաջ, որ դեռ կարող է fail անել։
7. **«Eventual»՝ invariant-ից խուսափելու համար** → անվանի՛ր invariant-ը, ընտրիր model-ը, որ պահանջում է, և նշիր stale window-ը plus unsafe-on-stale action-ը. եթե data-ն money/permissions/inventory է, հավանաբար eventual չէ։
8. **Resilience theater (retry, առանց threshold-ի)** → ավելացրու per-dependency timeout, jitter և retry budget, circuit breaker, bulkhead և backpressure. retry առանց timeout-ի և budget-ի load amplifier է, ոչ resilience։
9. **Անտեր / unversioned contract** → նշանակիր owner, ավելացրու versioning policy և error model, թվարկիր consumer-ները, և պահանջիր deprecation window + migration plan ցանկացած breaking change-ից առաջ։
10. **Շղթայով correlation id չկա** → generate արա correlation id edge-ին, propagate արա ամեն call-ով և event-ով, և log արա. ավելացրու causation id, որտեղ պետք է cause-ը վերականգնել։
11. **Ցրված security boundary / անսահման blast radius** → տեղադրիր հստակ trust boundary, դարձրու authz check-ը հետևողական, ամեն service-ը scope արա least privilege-ի, secret-ները հանիր repo-ից և rotate արա, և threat model-ն ու control-ները ուղղորդիր security-ին։
12. **Architecture astronautics** → առաջարկիր right-sized modular-monolith ճանապարհը, անվանի՛ր invariant-ը, որ կարդարացներ (և ներկայումս չի արդարացնում) complexity-ն, և քանակացրու հանվող operational tax-ը։

### Choreography ընդդեմ orchestration (ոնց ընտրել)

Երբ workflow-ն անցնում է service-ներ, որոշիր բացահայտ․ **orchestration** (կենտրոնական coordinator-ը պահում է workflow state-ը, կանչում ամեն step, enforce է անում order-ը և կենտրոնացված run է անում compensation-ը) թե **choreography** (ամեն service react է անում event-ներին և emit իրենը՝ առանց կենտրոնական ուղեղի)։ Orchestrate արա, երբ պետք է ծայրից-ծայր visibility, enforced sequencing, կենտրոնական compensation, կամ մեկ owner, որ կարող է պատասխանել «որտեղ է այս workflow-ն, և ավարտվե՞ց»։ Choreograph արա, երբ step-երը autonomous են, ուզում ես loose coupling ու անկախ evolution, և step-երի միջև order-ը բնականաբար enforce-վում է data-կախվածությամբ։ Որոշիչ failure mode-ը choreography-ն է՝ առանց end-state-ի տիրոջ․ event-ները թռչում են, ոչինչ չի հետևում completion-ին, և խրված/orphaned workflow-ները լուռ կուտակվում են։ Եթե choreograph ես անում, միևնույն է պարտք ես recovery mechanism՝ timeout sweeper, process manager, կամ audit event log-ի վրա, որ incomplete workflow-ն հայտնաբերվի և compensate-վի, ոչ կորչի։

### Time, ordering և identity (distributed-systems gate)

Չես կարող վստահել wall-clock time-ին կամ delivery order-ին service-ների միջև, ուստի identity-ն և order-ը դարձրու հստակ։ Պահիր երեք բան տարբեր․ **idempotency key** («այս նույն request-ը կիրառվա՞ծ է») dedup store-ով. **ordering/sequence key** («ինչ հերթականությամբ են եղել») per-entity partition-ով կամ version/sequence number-ով. և **clock-եր concurrency-ի հայտնաբերման համար** — logical (Lamport) clock՝ total-ish order-ի, կամ vector clock, երբ պետք է հայտնաբերել իրական concurrent write և conflict, որ մեկ counter-ը կթաքցներ։ Անցկացրու **correlation id** ամեն request-ով և event-ով, որ distributed trace-ը կարողանա վերականգնվել, և **causation id**՝ գրանցելու, թե որ message-ն է որին պատճառել։ Տարածված, թանկ սխալը մեկ idempotency key օգտագործելն է և՛ «երկու անգամ մի՛ կիրառիր», և՛ «կիրառիր հերթականությամբ» իմաստով — այն անում է առաջինը, ոչ երկրորդը, ուստի duplicate-ները բռնվում են, մինչ reorder-ված «cancel create-ից առաջ»-ը միևնույն է corrupt է անում state-ը։

### Application-security architecture (տեղադրում, ոչ control-ի իրականացում)

Architecture-ը որոշում է *որտեղ է trust boundary-ն և որքան հեռու է տարածվում compromise-ը*. կոնկրետ control-ները, threat model-ը և crypto ընտրությունները security-ինն են։ Authenticate և authorize արա boundary-ին և դարձրու authz check-ը հետևողական — authz gate, որ երբեմն gateway-ում է, երբեմն խորքում, երբեմն բացակա, անցք է։ Ամեն service-ի credential-ը scope արա **least privilege**-ի, որ popped service-ը չհասնի այն, ինչ երբեք պետք չէր, և design արա **blast-radius minimization**-ի, որ մեկ գողացված token-ը համակարգը չբացի։ Secret-ները պահիր **code-ից և repository-ից դուրս** — inject արա runtime-ին secret store-ից, և ցանկացած commit-ված secret համարիր compromised և rotate արա անկախ պատճառից։ Ամեն cross-boundary input համարիր untrusted, ներառյալ internal call-երը և event-ները։ Architecture-ի deliverable-ը boundary-ի տեղադրումն է, privilege-ի scoping-ը, secret-handling design-ը և blast-radius analysis-ը — հանձնված security-ին control-ի catalogue-ի և threat model-ի համար։

### Ստուգիր running system-ում, ոչ «test-երն անցան»

Անցնող test-երն ապացուցում են, որ եղած case-երը վարվեցին. չեն ապացուցում, որ architecture-ը դիմանում է իրականության տակ։ Կառուցվածքային փոփոխությունը done հայտարարելուց առաջ exercise արա load-bearing պնդումը running system-ում․ ուղարկիր duplicate delivery և հաստատիր, որ idempotency-ն dedup է անում. force արա concurrent/out-of-order event-ներ և հաստատիր ordering-ն ու conflict handling-ը. ներմուծիր replication lag և հաստատիր, որ consistency promise-ը դեռ դիմանում է. fail արա saga step և հաստատիր, որ compensation-ը իրականում run է լինում և user-visible state-ը ճիշտ է։ «Compile է լինում և test-երն անցան»-ը անհրաժեշտ է, ոչ բավարար — կարը պետք է դիմանա duplicate delivery-ին, reordering-ին, lag-ին և partial failure-ին։
