# Software Systems Architecture worked examples

## English

### Example A — order-workflow ADR (saga + consistency + resilience)

**Prompt.** Design the order workflow across cart, payment, inventory, and fulfillment. Write the senior-quality ADR.

**Senior answer.** **Invariant:** an order is never confirmed unless payment is authorized *and* inventory is reserved; money is never double-charged. **Load/failure shape:** the external payment provider is a third party that cannot join a distributed transaction and occasionally times out; inventory is internal. So 2PC is off the table — the ADR rejects it explicitly because the payment provider cannot enlist in it.

**Structure — orchestrated saga:** (1) create a *pending* order (local transaction); (2) authorize payment with an **idempotency key** (request hash → result stored, so a retry returns the first authorization instead of charging twice); (3) reserve inventory; (4) confirm. **Compensation:** if a later step fails, release the inventory reservation and void the payment authorization; the confirm step is last so nothing irreversible runs before a step that can still fail. **Why orchestration, not choreography:** the workflow needs a single owner of the end-state and enforced ordering (you cannot reserve-then-authorize safely), and someone must answer "where is this order and did it finish" — so a central coordinator holds the saga state, with a timeout sweeper to recover orders stuck in `pending`.

**Resilience on payment:** timeout per call; retry only on retryable errors (network/5xx, not "card declined") with jitter and a budget; circuit breaker on the provider with a fallback to a `payment-pending` state rather than a hard failure. **Consistency:** the confirmation page is **read-your-writes** (the buyer must see their own just-placed order); order history may lag up to ~30s (eventual) — the unsafe-on-stale action (confirming/charging) is on the strong path, history is not. **Contract:** the `order-confirmed` event is versioned and additive-only; consumers (fulfillment, analytics) are listed, and any breaking change needs a deprecation window.

**Why this passes.** The invariant is named *first* and it drives every choice: 2PC is rejected for a concrete reason (the payment provider cannot enlist), the saga step order is justified by the invariant (confirm last so no irreversible step precedes a failable one), and the consistency split is tied to the invariant (read-your-writes where the user must see their write, eventual only where a stale read is safe). Retry is gated by an idempotency key on the one non-idempotent write (payment), so a retry cannot double-charge — the domain's hard guardrail is satisfied, not just mentioned. It chooses orchestration with a stated reason (single end-state owner + enforced ordering) and closes the choreography failure mode with a timeout sweeper for stuck `pending` orders. The contract is versioned, additive, and owned, so a downstream consumer is not broken by "cleanup." Nothing is asserted that is not derived from the invariant or a stated failure mode.

### Example B — event-ordering and idempotency design (time/ordering/identity)

**Prompt.** Two services exchange domain events over a broker that can duplicate and reorder messages. We are seeing occasional corrupted state — sometimes a "cancel" is applied before the matching "create," and sometimes an event is processed twice. Design the fix.

**Senior answer.** Separate the two distinct problems, because one key cannot solve both. **Duplication ("applied already?")** → give each event a stable **idempotency key** (e.g. the producer's event id) and a dedup store on the consumer; on receipt, if the key is already recorded, return the stored result and do not re-apply. This stops the double-processing. **Reordering ("in what order?")** → the idempotency key does *not* fix this, so add an ordering mechanism: partition events by entity id (a per-entity **ordering key**) so all events for one order are delivered in sequence to one consumer, and stamp each event with a monotonic **version/sequence number** on the entity. The consumer applies an event only if its sequence is the expected next one; an out-of-sequence event is buffered or rejected, never applied blindly. For concurrent producers where true concurrency must be detected (not just a single sequence), use a **vector clock** so a genuine conflict is surfaced instead of silently lost. **Observability:** thread a **correlation id** through the whole chain (and a **causation id** recording which event caused which) so a corrupted-state incident can be traced end to end.

**Why this passes.** It refuses to conflate idempotency with ordering — the exact mistake that produced the bug — and assigns a separate, correct mechanism to each: an idempotency key + dedup store for "applied already?", and a per-entity ordering key plus a sequence number for "in what order?". It explains *why* the idempotency key alone fails ("cancel before create" survives dedup), which is the precise failure the prompt reported. It escalates to vector clocks only where true concurrent writers must be detected, rather than reaching for them by default, and it adds correlation/causation ids so the next occurrence is debuggable instead of a mystery. Every element maps to a named failure in the prompt (double-processing, reordering), and nothing is invented.

### Example C — CQRS / event-sourcing right-sizing (rule 14)

**Prompt.** A team wants to "add CQRS and event sourcing" to a CRUD admin module because reads feel slow. Is that the right call? Give the decision.

**Senior answer.** CQRS (separate write model and read model) and event sourcing (persist the event log as the source of truth, derive state from it) are **two independent choices**, and neither is a default — each buys a specific capability at a real, permanent cost (eventual consistency between write and read, projection-rebuild machinery, extra operational surface). Decide by the invariant and the read/write shape, not by "reads feel slow."

- **When plain CRUD + an index/cache is the answer (the likely case here):** the read is slow because of a missing index or an N+1, not because the model is wrong. Fix the query first. Bolting CQRS onto a CRUD admin screen imports eventual consistency and a projection to maintain in exchange for nothing the workload needed. Right-size **down**.
- **When CQRS earns itself:** the read and write shapes genuinely diverge — writes are simple per-entity commands but reads are heavy cross-entity aggregations/search at much higher volume, and you must scale or shape them independently (a denormalized read model, a search projection). Then split *reads* from *writes*, accept read-model lag, and state the staleness bound the UI tolerates.
- **When event sourcing earns itself (a higher bar):** you need the full history as a first-class asset — auditability of every state transition, temporal queries ("what did this look like on date X"), or the ability to rebuild/replay projections after a bug. If you only need current state, event sourcing is cost without payoff.

**The right-sizing test (the invariant).** Write the invariant as an executable check and ask which model is required to *hold* it, not to feel modern. If the invariant is "an account balance never goes negative," a strongly-consistent write model must enforce it at command time; a CQRS read model that is eventually consistent must **never** be the thing that authorizes the debit — authorizing off a stale read is exactly how you oversell/overdraw. So: enforce invariants on the **write side, synchronously**; use the read model only for display/query. If a proposed design would authorize a state-changing decision off the eventually-consistent read side, that is the tell it is mis-applied.

**Decision here:** no CQRS / event sourcing. Add the missing index (and a cache if reads dominate), measure, and reserve CQRS for the module where read/write shapes actually diverge, and event sourcing for where history is a required capability — each with its staleness bound and projection-rebuild plan stated.

**Why this passes.** It treats CQRS and event sourcing as **two separate, cost-bearing choices** rather than one buzzword, and right-sizes *down* for the CRUD case where the real defect is a missing index — refusing complexity the workload does not need. It gives a concrete earns-itself bar for each (divergent read/write shapes for CQRS; history-as-a-capability for event sourcing) and anchors the whole call on the **invariant**, with the load-bearing rule that invariants are enforced synchronously on the write side and the eventually-consistent read model must never authorize a state change — the exact failure mode (authorize off a stale read → oversell/overdraw) the pattern invites when mis-applied. The output is a decision with staleness bounds and a rebuild plan, not "let's add CQRS."

## Հայերեն

### Օրինակ A — order-workflow ADR (saga + consistency + resilience)

**Prompt.** Նախագծիր order workflow-ն cart, payment, inventory և fulfillment service-երով։ Գրիր senior-quality ADR-ը։

**Senior պատասխան.** **Invariant․** order-ը երբեք confirmed չի դառնում, մինչև payment-ը authorized *և* inventory-ն reserved չլինեն. փողը երբեք double-charge չի լինում։ **Load/failure shape․** external payment provider-ը երրորդ կողմ է, որ չի կարող join անել distributed transaction-ին և երբեմն timeout է անում. inventory-ն internal է։ Ուստի 2PC-ն բացառվում է — ADR-ը մերժում է այն բացահայտ, որովհետև payment provider-ը չի կարող enlist լինել։

**Կառուցվածք — orchestrated saga․** (1) ստեղծիր *pending* order (local transaction). (2) authorize արա payment-ը **idempotency key**-ով (request hash → result պահված, որ retry-ն վերադարձնի առաջին authorization-ը, ոչ թե երկու անգամ charge անի). (3) reserve արա inventory. (4) confirm։ **Compensation․** եթե հետագա step fail է անում, release արա inventory reservation-ը և void արա payment authorization-ը. confirm step-ը վերջում է, որ ոչ մի անդառնալի բան չ-run լինի մինչև step, որ դեռ կարող է fail անել։ **Ինչու orchestration, ոչ choreography․** workflow-ին պետք է end-state-ի մեկ owner և enforced ordering (չես կարող reserve-հետո-authorize անել ապահով), և ինչ-որ մեկը պետք է պատասխանի «որտեղ է այս order-ը և ավարտվե՞ց» — ուստի կենտրոնական coordinator-ը պահում է saga state-ը, timeout sweeper-ով՝ `pending`-ում խրված order-ները վերականգնելու։

**Resilience payment-ի վրա․** timeout ամեն call-ի. retry միայն retryable error-ի վրա (network/5xx, ոչ «card declined») jitter-ով և budget-ով. circuit breaker provider-ի վրա՝ fallback-ով դեպի `payment-pending` state, ոչ hard failure։ **Consistency․** confirmation page-ը **read-your-writes** է (գնորդը պետք է տեսնի իր նոր դրած order-ը). order history-ն կարող է մինչև ~30 վրկ lag ունենալ (eventual) — unsafe-on-stale action-ը (confirm/charge) strong path-ի վրա է, history-ն՝ ոչ։ **Contract․** `order-confirmed` event-ը versioned է և additive-only. consumer-ները (fulfillment, analytics) թվարկված են, և ցանկացած breaking change-ին պետք է deprecation window։

**Ինչու է անցնում gate-ը.** Invariant-ը անվանված է *առաջինը*, և այն driving է ամեն ընտրություն․ 2PC-ն մերժված է կոնկրետ պատճառով (payment provider-ը չի կարող enlist լինել), saga step-ի order-ը արդարացված է invariant-ով (confirm վերջում, որ անդառնալի step չնախորդի failable-ին), և consistency-ի բաժանումը կապված է invariant-ին (read-your-writes, որտեղ user-ը պետք է տեսնի իր write-ը, eventual միայն, որտեղ stale read-ը ապահով է)։ Retry-ն gated է idempotency key-ով այն մեկ non-idempotent write-ի վրա (payment), ուստի retry-ն չի կարող double-charge անել — domain-ի կոշտ guardrail-ը բավարարված է, ոչ միայն հիշատակված։ Այն ընտրում է orchestration՝ նշված պատճառով (end-state-ի մեկ owner + enforced ordering) և փակում է choreography-ի failure mode-ը timeout sweeper-ով՝ խրված `pending` order-ների համար։ Contract-ը versioned, additive և սեփականատեր ունեցող է, ուստի downstream consumer-ը չի կոտրվում «cleanup»-ից։ Ոչինչ չի պնդվում, որ չի բխեցվում invariant-ից կամ նշված failure mode-ից։

### Օրինակ B — event-ordering և idempotency design (time/ordering/identity)

**Prompt.** Երկու service domain event են փոխանակում broker-ով, որ կարող է duplicate և reorder անել message-ները։ Տեսնում ենք երբեմն corrupt-ված state — երբեմն «cancel»-ը կիրառվում է համապատասխան «create»-ից առաջ, և երբեմն event-ը մշակվում է երկու անգամ։ Նախագծիր fix-ը։

**Senior պատասխան.** Բաժանիր երկու տարբեր խնդիրը, որովհետև մեկ key-ը չի կարող երկուսն էլ լուծել։ **Duplication («արդեն կիրառվա՞ծ է»)** → ամեն event-ի տուր կայուն **idempotency key** (օր.՝ producer-ի event id-ն) և dedup store consumer-ի վրա. ստանալիս, եթե key-ն արդեն գրանցված է, վերադարձրու պահված result-ը և մի՛ կրկին կիրառիր։ Սա կանգնեցնում է double-processing-ը։ **Reordering («ինչ հերթականությա՞մբ»)** → idempotency key-ը սա *չի* ուղղում, ուստի ավելացրու ordering mechanism․ partition արա event-ները entity id-ով (per-entity **ordering key**), որ մեկ order-ի բոլոր event-ները հերթականությամբ հասցվեն մեկ consumer-ի, և stamp արա ամեն event-ը monotonic **version/sequence number**-ով entity-ի վրա։ Consumer-ը կիրառում է event-ը միայն, եթե նրա sequence-ը սպասվող հաջորդն է. out-of-sequence event-ը buffer-վում կամ reject-վում է, երբեք կույր չի կիրառվում։ Concurrent producer-ների համար, որտեղ պետք է իրական concurrency հայտնաբերել (ոչ միայն մեկ sequence), օգտագործիր **vector clock**, որ իրական conflict-ը երևա, ոչ թե լուռ կորչի։ **Observability․** անցկացրու **correlation id** ողջ շղթայով (և **causation id**՝ գրանցելու, թե որ event-ն է որին պատճառել), որ corrupt-ված state-ի incident-ը կարողանա trace լինել ծայրից ծայր։

**Ինչու է անցնում gate-ը.** Այն հրաժարվում է idempotency-ն ու ordering-ը շփոթելուց — հենց այն սխալը, որ bug-ը արտադրեց — և ամեն մեկին տալիս առանձին, ճիշտ mechanism․ idempotency key + dedup store «արդեն կիրառվա՞ծ է»-ի, և per-entity ordering key plus sequence number «ինչ հերթականությա՞մբ»-ի համար։ Այն բացատրում է, թե *ինչու* է idempotency key-ը մենակ ձախողվում («cancel create-ից առաջ»-ը գոյատևում է dedup-ից), որը հենց prompt-ի հաղորդած failure-ն է։ Այն escalate է անում vector clock-ի միայն այնտեղ, որտեղ պետք է իրական concurrent writer-ներ հայտնաբերել, ոչ թե լռելյայն դրան ձեռք մեկնում, և ավելացնում correlation/causation id, որ հաջորդ դեպքը debuggable լինի, ոչ առեղծված։ Ամեն տարր map է անում prompt-ի անվանված failure-ին (double-processing, reordering), և ոչինչ չի հորինված։

### Օրինակ C — CQRS / event-sourcing right-sizing (rule 14)

**Prompt.** Թիմը ուզում է «ավելացնել CQRS և event sourcing» CRUD admin module-ին, որովհետև read-երը slow են զգացվում։ Դա ճի՞շտ որոշում է։ Տուր որոշումը։

**Senior պատասխան.** CQRS-ը (առանձին write model և read model) և event sourcing-ը (event log-ը պահել որպես source of truth, state-ը դրանից բխեցնել) **երկու անկախ ընտրություն** են, և ոչ մեկը default չէ — ամեն մեկը գնում է կոնկրետ capability՝ իրական, մշտական գնով (eventual consistency write-ի ու read-ի միջև, projection-rebuild մեխանիզմ, լրացուցիչ operational surface)։ Որոշիր ըստ invariant-ի և read/write shape-ի, ոչ ըստ «read-երը slow են զգացվում»-ի։

- **Երբ պարզ CRUD + index/cache-ն է պատասխանը (այստեղ ամենահավանական դեպքը)․** read-ը slow է բացակայող index-ի կամ N+1-ի պատճառով, ոչ թե որովհետև model-ը սխալ է։ Նախ ուղղիր query-ն։ CQRS-ը CRUD admin էկրանին պտուտակելը ներմուծում է eventual consistency և պահպանվող projection՝ փոխարենը ոչինչ, ինչ workload-ին պետք էր։ Right-size արա **ներքև**։
- **Երբ CQRS-ը վաստակում է իրեն․** read-ի և write-ի shape-երը իսկապես տարբերվում են — write-երը պարզ per-entity command են, բայց read-երը ծանր cross-entity aggregation/search են շատ ավելի բարձր volume-ով, և պետք է scale կամ shape անես դրանք independently (denormalized read model, search projection)։ Այդ դեպքում բաժանիր *read*-երը *write*-երից, ընդունիր read-model lag-ը և ասա staleness bound-ը, որ UI-ն հանդուրժում է։
- **Երբ event sourcing-ը վաստակում է իրեն (ավելի բարձր շեմ)․** պետք է ամբողջ history-ն որպես first-class asset — ամեն state transition-ի auditability, temporal query («ինչ տեսք ուներ X ամսաթվին»), կամ bug-ից հետո projection-ները rebuild/replay անելու հնարավորություն։ Եթե պետք է միայն ընթացիկ state, event sourcing-ը cost է առանց payoff-ի։

**Right-sizing test-ը (invariant-ը).** Գրիր invariant-ը որպես executable check և հարցրու՝ որ model-ն է պահանջվում այն *պահելու*, ոչ թե modern զգալու համար։ Եթե invariant-ը «account balance-ը երբեք բացասական չի դառնում» է, strongly-consistent write model-ը պետք է enforce անի այն command-ի պահին. CQRS read model, որ eventually consistent է, պետք է **երբեք** չլինի այն, ինչ authorize է անում debit-ը — stale read-ից authorize անելը հենց այն է, ինչով oversell/overdraw ես անում։ Ուստի՝ invariant-ները enforce արա **write side-ում, synchronously**. read model-ը օգտագործիր միայն display/query-ի։ Եթե առաջարկվող design-ը state-փոխող որոշում authorize աներ eventually-consistent read side-ից, դա tell-ն է, որ սխալ է կիրառված։

**Որոշում այստեղ․** ոչ CQRS / event sourcing։ Ավելացրու բացակայող index-ը (և cache, եթե read-երը գերակշռում են), չափիր, և CQRS-ը պահիր այն module-ի համար, որտեղ read/write shape-երը իսկապես տարբերվում են, իսկ event sourcing-ը՝ որտեղ history-ն պահանջվող capability է — ամեն մեկը իր staleness bound-ով և projection-rebuild plan-ով նշված։

**Ինչու է անցնում gate-ը.** Այն վերաբերվում է CQRS-ին և event sourcing-ին որպես **երկու առանձին, cost-կրող ընտրություն**, ոչ մեկ buzzword, և right-size է անում *ներքև* CRUD դեպքի համար, որտեղ իրական defect-ը բացակայող index-ն է — մերժելով complexity, որ workload-ին պետք չէ։ Այն տալիս է կոնկրետ «վաստակում է իրեն» շեմ ամեն մեկի համար (տարբերվող read/write shape CQRS-ի. history-as-capability event sourcing-ի) և ամբողջ որոշումը խարսխում է **invariant**-ի վրա, load-bearing կանոնով, որ invariant-ները enforce են լինում synchronously write side-ում, և eventually-consistent read model-ը երբեք չի authorize անում state-փոխ — հենց այն failure mode-ը (stale read-ից authorize → oversell/overdraw), որ pattern-ը հրավիրում է սխալ կիրառելիս։ Output-ը որոշում է՝ staleness bound-ով և rebuild plan-ով, ոչ «եկեք ավելացնենք CQRS»։
