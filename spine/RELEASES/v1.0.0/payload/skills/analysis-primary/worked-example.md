# Analysis — Primary Lens worked examples

## English

### Example A — Diagnosis (issue tree + Fermi + Bayesian update)

**Prompt.** Activation fell 12% week-over-week. Why, and what should we look at first?

**Senior answer.** *Frame:* the decision is not "write a story about activation" but "where do we spend the next investigation hour so the fix is aimed right" — counterfactual: if we guess wrong, we ship onboarding-copy changes that do nothing. *Decompose* into a two-level issue tree: (1) traffic mix, (2) product funnel, (3) measurement. Product funnel splits into signup completion → email verification → first key action (MECE-enough: each user passes them in order, no leaf shares a metric). *Fermi sizing of the funnel:* 50,000 weekly visitors × 40% signup × 70% verification × 60% first action = **8,400 activated/week** baseline. If verification alone drops 70% → 55%: 50,000 × 40% × 55% × 60% = **6,600**, a **21.4%** hit on that path — so a measured 12% total fall is plausible if roughly half the traffic hit a verification bug. *Interrogate with a Bayesian update:* prior that this is an instrumentation (measurement) bug, not a real drop, = 15% → prior odds 0.15/0.85 = **0.176**. Evidence: backend (server-side) events are stable while frontend events fell — that points to measurement, LR ≈ 4 → posterior odds 0.176 × 4 = **0.705** → posterior = 0.705/1.705 ≈ **41%**. *Observation/inference/judgment:* the 12% is an observation; "verification is the driver" is an inference (not yet confirmed); "investigate measurement before onboarding" is the judgment. *Falsifier / next test:* compare server-side verification completions by browser/version — if they are flat, the measurement hypothesis is wrong and the funnel hypothesis stands. *Dispatch:* hand the instrumentation check to `data-science-analytics`; do not rewrite onboarding copy until the server-side numbers are observed.

**Why this passes.** It refuses to narrate; it frames the real decision (where to spend the next hour) and its counterfactual before touching causes. The Fermi is shown and correct — 50,000 × 0.40 × 0.70 × 0.60 = 8,400, and the 70→55 case gives 6,600, a 21.4% path hit — so the 12% is sized against a mechanism, not asserted. The Bayesian update derives odds from the prior (0.15 → 0.176), applies a defensible LR (frontend fell, backend stable → 4), and lands at ~41% — explicitly *not* certainty, a rank-order for investigation, with the conclusion kept out of the likelihood. It separates observation, inference, and judgment by name, and it ends with a falsifier (flat server-side completions would kill the measurement hypothesis) plus a dispatch that verifies in the data before any copy is changed. Every number traces to a formula; nothing volatile is invented.

### Example B — Dispatch-and-verify (the always-on lens catching a trust failure)

**Prompt.** "I asked the devops agent to fix the latency regression, it came back and said the canary passed and CI is green. Mark it done and close the ticket?"

**Senior answer.** *Frame:* the decision is "is this safe to close", and the real risk is not the fix — it is **closing on trust**. Counterfactual: if we close and it is not actually fixed, the regression ships to 100% under a green badge. *Interrogate the claim with the observation/inference/judgment split:* "CI is green" is an observation about the *tests that exist*; "the latency regression is fixed" is an *inference* that no test on its own proves; "close the ticket" is the *judgment* riding on that inference. The gap between them is exactly the dispatch-and-trust failure mode. *What's missing:* the canary "passed" — against which guardrails? A canary that watched only the mean can pass while p99 (the metric the regression lives in) is still hot. *Verification before closing (in the running system):* (1) read the **live p99 latency** for the affected endpoint over the canary window, not a CI artifact; (2) confirm the guardrail set included p99 and saturation, not just the average; (3) confirm the rollback was rehearsed, not just documented. *Dispatch back:* return to devops with one question — "show the live p99 for the endpoint over the bake window" — and do not close until that real metric is observed. *Falsifier:* if live p99 is back to baseline and held through the full traffic ramp, the fix is real and the ticket can close; if it cannot be shown, it is not done.

**Why this passes.** It is the lens doing its always-on job: an "is it done?" hand-off arrives and the lens *frames the trust risk* instead of rubber-stamping. It names dispatch-and-trust explicitly and dismantles it with the observation/inference/judgment split — green CI is an observation about existing tests, "fixed" is an unproven inference, and the judgment to close is riding on the gap. It demands the live p99 in the running system (the exact metric the regression inhabits, where a mean-only canary would hide it), refuses "function-tested / CI green" as verification, and gives a concrete falsifier that decides the close. It dispatches the verification back to the owner with one sharp question rather than re-doing devops's work itself — the lens owns the reasoning shape, not the specialist content.

### Example C — Decision brief (expected value + flip condition)

**Prompt.** "Should we build the custom analytics pipeline ourselves or buy the vendor product?"

**Senior answer.** *Frame:* the decision is build-vs-buy for the analytics pipeline; counterfactual is "buy" (the reversible default); stop rule is "decide once the EV gap is larger than its uncertainty". *Decompose the build case into EV:* probability the in-house build lands on time and meets needs = 30%, payoff if it does (control + saved licensing over 3 years) ≈ **$2.0M**; probability it overruns/underdelivers = 70%, cost of that (rework, opportunity, delayed roadmap) ≈ **$400K**. EV(build) = 0.30 × $2.0M − 0.70 × $400K = $600K − $280K = **+$320K**. *Interrogate:* the dominant uncertain driver is the 30% success prior — survivorship bias makes in-house builds look better than the reference class (most custom-pipeline builds overrun). Steelman of "buy": the vendor removes the 70% downside entirely and frees the team for product work; its weakness is lock-in and per-seat cost growth. *Observation/inference/judgment:* the license quote is an observation; "we can build it in two quarters" is an inference (check it against the reference class); "build is worth +$320K" is a judgment contingent on the 30% holding. *Flip condition:* if the success prior is actually 20% (closer to the industry base rate for custom builds), EV(build) = 0.20 × $2.0M − 0.80 × $400K = $400K − $320K = **+$80K** — barely positive and inside the noise, so the reversible "buy" wins. *Dispatch:* hand the cost and lock-in modeling to `business-strategy-operations`; this lens supplies the EV frame and the flip condition.

**Why this passes.** It states the decision, the reversible default, and a stop rule before computing anything. The EV is shown and correct (0.30 × 2.0M − 0.70 × 0.40M = +$320K), and — critically — it stress-tests the *dominant* driver: re-running at a 20% prior gives +$80K, inside the noise, which flips the recommendation to "buy". That flip condition is the whole point: the call is not "build" but "build *only if* the success prior survives a base-rate check". It names survivorship bias by mechanism, steelmans the opposite, separates the quote (observation) from the timeline claim (inference) from the EV verdict (judgment), and dispatches the detailed modeling to the owning skill instead of inventing vendor prices.

## Հայերեն

### Օրինակ A — Diagnosis (issue tree + Fermi + Bayesian update)

**Prompt.** Activation-ը շաբաթից շաբաթ ընկավ 12%։ Ինչու՞, և ինչի՞ն նայենք առաջինը։

**Senior պատասխան.** *Frame.* որոշումը «activation-ի մասին story գրելը» չէ, այլ «որտեղ ծախսենք հաջորդ investigation ժամը, որ fix-ը ճիշտ նշանառվի» — counterfactual․ եթե սխալ գուշակենք, ship ենք անում onboarding-copy փոփոխություններ, որ ոչինչ չեն անում։ *Decompose* երկմակարդակ issue tree-ի․ (1) traffic mix, (2) product funnel, (3) measurement։ Product funnel-ը բաժանվում է signup completion → email verification → first key action (MECE-ին մոտ․ ամեն user հերթով անցնում է դրանք, ոչ մի leaf չի կիսում metric)։ *Funnel-ի Fermi sizing.* շաբաթական 50,000 visitor × 40% signup × 70% verification × 60% first action = **8,400 activated/շաբաթ** baseline։ Եթե միայն verification-ն ընկնի 70% → 55%․ 50,000 × 40% × 55% × 60% = **6,600**, **21.4%** հարված այդ path-ին — ուստի measured 12% ընդհանուր անկումը plausible է, եթե traffic-ի մոտ կեսը հանդիպել է verification bug-ի։ *Interrogate Bayesian update-ով.* prior, որ սա instrumentation (measurement) bug է, ոչ իրական անկում, = 15% → prior odds 0.15/0.85 = **0.176**։ Evidence․ backend (server-side) event-երը stable են, մինչ frontend event-երն ընկել են — դա մատնացույց է measurement-ի, LR ≈ 4 → posterior odds 0.176 × 4 = **0.705** → posterior = 0.705/1.705 ≈ **41%**։ *Observation/inference/judgment.* 12%-ը observation է. «verification-ն է driver-ը»՝ inference (դեռ չհաստատված). «measurement-ը հետազոտիր onboarding-ից առաջ»՝ judgment։ *Falsifier / next test.* համեմատիր server-side verification completion-ները browser/version-ով — եթե դրանք հարթ են, measurement hypothesis-ը սխալ է, և funnel hypothesis-ը մնում է։ *Dispatch.* instrumentation check-ը հանձնիր `data-science-analytics`-ին. onboarding copy մի՛ վերագրիր, մինչև server-side թվերը դիտվեն։

**Ինչու է անցնում gate-ը.** Այն հրաժարվում է narrate անելուց. շրջանակում է իրական որոշումը (որտեղ ծախսել հաջորդ ժամը) և դրա counterfactual-ը նախքան cause-ին դիպչելը։ Fermi-ն ցույց է տրված և ճիշտ է — 50,000 × 0.40 × 0.70 × 0.60 = 8,400, և 70→55 դեպքը տալիս է 6,600, 21.4% path հարված — ուստի 12%-ը չափված է mechanism-ի դեմ, ոչ պնդված։ Bayesian update-ը odds-ը բխեցնում է prior-ից (0.15 → 0.176), կիրառում պաշտպանելի LR (frontend ընկավ, backend stable → 4) և վայրէջք է կատարում ~41%-ի — բացահայտ *ոչ* certainty, investigation-ի rank-order, conclusion-ը likelihood-ից դուրս պահված։ Այն անվանով բաժանում է observation, inference և judgment, և ավարտվում falsifier-ով (հարթ server-side completion-ը կսպաներ measurement hypothesis-ը) plus dispatch, որ ստուգում է data-ում նախքան որևէ copy փոխելը։ Ամեն թիվ հետ է գնում formula-ի. ոչ մի volatile բան չի հորինված։

### Օրինակ B — Dispatch-and-verify (մշտապես-միացած ոսպնյակը բռնում է trust failure-ը)

**Prompt.** «Devops agent-ին խնդրեցի latency regression-ը fix անել, վերադարձավ ու ասաց canary-ն անցավ ու CI green է։ Done նշե՞մ ու ticket-ը փակեմ»։

**Senior պատասխան.** *Frame.* որոշումը «սա ապահո՞վ է փակել»-ն է, և իրական ռիսկը fix-ը չէ — այն **վստահությամբ փակելն է**։ Counterfactual․ եթե փակենք ու իրականում fix չլինի, regression-ը ship է անում 100%-ի՝ green badge-ի տակ։ *Interrogate պնդումը observation/inference/judgment բաժանումով.* «CI green է»-ն observation է *եղած test-երի* մասին. «latency regression-ը fix-ված է»-ն *inference* է, որ ոչ մի test ինքնին չի ապացուցում. «ticket-ը փակիր»-ը *judgment* է, որ նստած է այդ inference-ի վրա։ Նրանց միջև բացը հենց dispatch-and-trust ձախողման ձևն է։ *Ինչ է բացակայում.* canary-ն «անցավ» — ո՞ր guardrail-ների դեմ։ Canary, որ միայն mean էր նայում, կարող է անցնել, մինչ p99-ը (այն metric-ը, որտեղ regression-ն ապրում է) դեռ տաք է։ *Verification նախքան փակելը (աշխատող համակարգում).* (1) կարդա **live p99 latency**-ն ազդակիր endpoint-ի համար canary window-ի ընթացքում, ոչ CI artifact. (2) հաստատիր, որ guardrail set-ը ներառում էր p99 և saturation, ոչ միայն average. (3) հաստատիր, որ rollback-ը rehearsed էր, ոչ միայն documented։ *Dispatch հետ.* վերադարձիր devops-ին մեկ հարցով — «ցույց տուր live p99-ը endpoint-ի համար bake window-ի ընթացքում» — և մի՛ փակիր, մինչև այդ իրական metric-ը դիտվի։ *Falsifier.* եթե live p99-ը վերադարձել է baseline և պահվել ողջ traffic ramp-ի ընթացքում, fix-ը իրական է, և ticket-ը կարող է փակվել. եթե այն չի կարող ցույց տրվել, done չէ։

**Ինչու է անցնում gate-ը.** Սա ոսպնյակն է իր մշտապես-միացած գործն անելիս․ «արվա՞ծ է» hand-off է գալիս, և ոսպնյակը *շրջանակում է trust ռիսկը*՝ rubber-stamp-ի փոխարեն։ Այն բացահայտ անվանում է dispatch-and-trust-ը և քանդում observation/inference/judgment բաժանումով — green CI-ն observation է եղած test-երի մասին, «fixed»-ը չապացուցված inference է, և փակելու judgment-ը նստած է բացի վրա։ Այն պահանջում է live p99 աշխատող համակարգում (հենց այն metric-ը, որտեղ regression-ն ապրում է, որտեղ mean-only canary-ն կթաքցներ այն), մերժում է «function-tested / CI green»-ը որպես verification և տալիս կոնկրետ falsifier, որ որոշում է փակումը։ Այն verification-ը dispatch է անում հետ owner-ին մեկ սուր հարցով՝ devops-ի աշխատանքը ինքը վերա-անելու փոխարեն — ոսպնյակը տիրում է դատողության ձևին, ոչ specialist-ի բովանդակությանը։

### Օրինակ C — Decision brief (expected value + flip condition)

**Prompt.** «Analytics pipeline-ը ինքնե՞րս կառուցենք, թե vendor product գնենք»։

**Senior պատասխան.** *Frame.* որոշումը build-vs-buy է analytics pipeline-ի համար. counterfactual-ը «buy»-ն է (հետշրջելի default-ը). stop rule-ը՝ «որոշիր, երբ EV gap-ը մեծ է իր uncertainty-ից»։ *Decompose build case-ը EV-ի.* հավանականությունը, որ in-house build-ը կժամանի ժամանակին և կբավարարի կարիքները = 30%, payoff եթե այո (control + 3 տարվա խնայված licensing) ≈ **$2.0M**. հավանականությունը, որ այն կուշանա/թերակատարի = 70%, դրա cost-ը (rework, opportunity, ուշացած roadmap) ≈ **$400K**։ EV(build) = 0.30 × $2.0M − 0.70 × $400K = $600K − $280K = **+$320K**։ *Interrogate.* dominant uncertain driver-ը 30% success prior-ն է — survivorship bias-ը in-house build-երը դարձնում է reference class-ից ավելի լավ տեսք (custom-pipeline build-երի մեծ մասը ուշանում է)։ «Buy»-ի steelman․ vendor-ը հանում է 70% downside-ն ամբողջությամբ և ազատում թիմը product աշխատանքի համար. դրա թուլությունը lock-in-ն ու per-seat cost-ի աճն է։ *Observation/inference/judgment.* license quote-ը observation է. «երկու quarter-ում կկառուցենք»-ը inference է (ստուգիր reference class-ի դեմ). «build-ն արժե +$320K»-ը judgment է, որ կախված է 30%-ի պահելուց։ *Flip condition.* եթե success prior-ը իրականում 20% է (industry base rate-ին ավելի մոտ custom build-երի համար), EV(build) = 0.20 × $2.0M − 0.80 × $400K = $400K − $320K = **+$80K** — հազիվ դրական և noise-ի ներսում, ուստի հետշրջելի «buy»-ն հաղթում է։ *Dispatch.* cost-ի և lock-in-ի modeling-ը հանձնիր `business-strategy-operations`-ին. այս ոսպնյակը տալիս է EV շրջանակն ու flip condition-ը։

**Ինչու է անցնում gate-ը.** Այն ասում է որոշումը, հետշրջելի default-ը և stop rule-ը նախքան որևէ բան հաշվելը։ EV-ն ցույց է տրված և ճիշտ է (0.30 × 2.0M − 0.70 × 0.40M = +$320K), և — կրիտիկորեն — stress-test է անում *dominant* driver-ը․ 20% prior-ով վերագործարկելը տալիս է +$80K, noise-ի ներսում, որ flip է անում recommendation-ը դեպի «buy»։ Այդ flip condition-ն ամբողջ իմաստն է․ call-ը «build» չէ, այլ «build *միայն եթե* success prior-ը դիմանա base-rate ստուգմանը»։ Այն անվանում է survivorship bias-ը mechanism-ով, steelman է անում հակառակը, բաժանում quote-ը (observation), timeline պնդումը (inference) և EV verdict-ը (judgment), և dispatch է անում մանրամասն modeling-ը owning skill-ին՝ vendor price հորինելու փոխարեն։
