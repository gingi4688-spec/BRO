# DevOps, Platform, and SRE worked examples

## English

### Example A — SLO / error-budget + canary

**Prompt.** A checkout service has a 99.9% availability SLO over 30 days. Over the last hour it is returning 1.44% errors. Design the alerting and a safe rollout for the fix.

**Senior answer.** Budget = (1 − 0.999) × 43,200 min = **43.2 minutes / 30 days**. Allowed error rate is 0.1%; observed is 1.44%, so burn rate = 1.44 / 0.1 = **14.4×**. At 14.4× a full hour consumes ~2% of the monthly budget — that warrants a **page** (fast window). Add a slower window: a sustained **6× burn** (0.6% errors) over 6 hours spends ~5% of budget and warrants a **ticket**, not a page. So the alert policy is multi-window: fast page at ~14.4× over a short window, slow ticket at ~6× over a long window.

Rollout for the fix: **canary** — 5% traffic for 30 min, then 25%, then 50%, then 100%. Guardrails per step: p99 latency must not rise >20% vs baseline, error-budget burn must stay <2× for 10 min, queue saturation <80%, and checkout conversion must not drop. **Automatic abort** the moment any guardrail is crossed; rollback path is the previous known-good revision, and it has been run in staging so the rollback itself is verified. Because the fix touches no schema, a percentage canary is valid (no atomic cutover needed).

**Why this passes.** The budget is computed, not asserted: 43.2 min comes from `(1 − SLO) × window`, and 14.4× comes from `observed / allowed` — both shown, both correct. The alert is a multi-window burn-rate policy (page at 14.4×, ticket at 6×), not a raw-count alarm, so it catches the cliff and the slow leak without flapping. The canary carries the four guardrails this domain requires — p99 (not the mean), saturation as the leading indicator, error-budget burn, and one business metric — plus an automatic abort and a rollback that was actually rehearsed. It states why a percentage canary is valid here (no schema cutover), showing the expand/contract rule was considered, not forgotten.

### Example B — IaC state and drift

**Prompt.** Someone fixed a production outage by editing a load-balancer rule directly in the cloud console. The infra is managed by Terraform. What now?

**Senior answer.** The console edit created **drift**: live state no longer matches the IaC source of truth, and the next `terraform apply` would silently revert the fix and re-break production. Treat the IaC as the source of truth and reconcile in this order: (1) Run a **plan** to see exactly what diverged — confirm the console change is the only drift. (2) **Codify** the fix into the Terraform config (or `import` the changed resource if it was created out-of-band) so the desired state now includes it. (3) Re-run plan; it must show **no changes** — that proves config and live state agree. (4) Ensure remote **state is locked** (state backend with locking) so two applies cannot corrupt it concurrently. (5) Add **drift detection** (a scheduled plan that alerts on non-zero diff) so the next console hot-fix is caught in hours, not at the next deploy. Contributing-factor for the postmortem: the outage runbook allowed a console edit with no path back into IaC — the control is "emergency changes must be codified within X hours, enforced by drift detection."

**Why this passes.** It names the actual failure mode — drift that the next apply silently reverts — rather than just saying "don't edit the console." The reconcile sequence is concrete and ordered (plan → codify/import → plan shows zero diff → lock state → drift detection), and the "plan shows no changes" step is the verification gate, not a green-CI assumption. It locks state to prevent concurrent corruption and closes the loop with a control change for the postmortem, so the same hot-fix cannot silently rot again.

### Example C — blameless postmortem

**Prompt.** A deploy took the API down for 38 minutes. An engineer pushed a config change that pointed the service at the wrong database; the on-call rolled back. Write the postmortem.

**Senior answer.** **Impact & severity:** API 5xx for 38 min; severity set by user impact (full API outage), not by who pushed. **Timeline:** deploy at T0 → error rate crossed page threshold at T0+4 (4 min detection) → on-call diagnosed wrong DB target at T0+22 (18 min diagnosis — the slow leg) → rollback to previous revision at T0+30 → recovery confirmed at T0+38. **Contributing factors (not a single root cause):** (1) the config allowed an invalid DB target to deploy — no validation gate; (2) detection took 4 min because alerting was on raw 5xx count, not on error-budget burn; (3) diagnosis took 18 min because the config diff was not surfaced in the deploy log; (4) the wrong-target config had no pre-deploy connectivity check. **Controls shipped:** (a) schema-validate config and add a pre-deploy connectivity check to the wrong target (blocks the class of failure); (b) move alerting to multi-window burn rate (faster, fewer false pages); (c) surface the config diff in the deploy annotation (cuts diagnosis time); (d) the rollback worked and was already rehearsed — keep it. **No individual is named as the cause**; the failure was a missing validation control, and that control now exists.

**Why this passes.** Severity is set by user impact, and the timeline isolates the slow leg (18 min diagnosis) so the controls target where time was actually lost. The "root cause" is reframed as a contributing-factors map — missing validation, raw-count alerting, hidden config diff — and each factor ships a specific control, not a reprimand. It explicitly refuses to name the engineer; the fix is the validation gate that makes the same mistake un-shippable. It even credits what worked (a rehearsed rollback), which keeps the review honest rather than purely punitive.

## Հայերեն

### Օրինակ A — SLO / error-budget + canary

**Prompt.** Checkout service-ն ունի 99.9% availability SLO 30 օրվա համար։ Վերջին ժամին այն վերադարձնում է 1.44% error։ Նախագծիր alerting-ը և անվտանգ rollout fix-ի համար։

**Senior պատասխան.** Budget = (1 − 0.999) × 43,200 min = **43.2 minute / 30 օր**։ Allowed error rate-ը 0.1% է. observed-ը՝ 1.44%, ուստի burn rate = 1.44 / 0.1 = **14.4×**։ 14.4×-ի դեպքում մի ամբողջ ժամ սպառում է monthly budget-ի ~2%-ը — դա արժանի է **page**-ի (fast window)։ Ավելացրու դանդաղ window․ կայուն **6× burn** (0.6% error) 6 ժամում ծախսում է budget-ի ~5%-ը և արժանի է **ticket**-ի, ոչ page-ի։ Ուստի alert policy-ն multi-window է․ fast page ~14.4×-ով կարճ window-ում, slow ticket ~6×-ով երկար window-ում։

Rollout fix-ի համար․ **canary** — 5% traffic 30 րոպե, հետո 25%, հետո 50%, հետո 100%։ Guardrail-ներ յուրաքանչյուր step-ին․ p99 latency-ն չպետք է բարձրանա >20% baseline-ից, error-budget burn-ը պետք է մնա <2× 10 րոպե, queue saturation-ը <80%, և checkout conversion-ը չպետք է ընկնի։ **Automatic abort** ցանկացած guardrail-ի անցման պահին. rollback path-ը նախորդ known-good revision-ն է, և այն գործարկվել է staging-ում, ուստի rollback-ն ինքը verified է։ Քանի որ fix-ը schema չի դիպչում, percentage canary-ն վավեր է (atomic cutover պետք չէ)։

**Ինչու է անցնում gate-ը.** Budget-ը հաշված է, ոչ պնդված․ 43.2 min-ը գալիս է `(1 − SLO) × window`-ից, իսկ 14.4×-ը՝ `observed / allowed`-ից, երկուսն էլ ցույց տրված, երկուսն էլ ճիշտ։ Alert-ը multi-window burn-rate policy է (page 14.4×-ով, ticket 6×-ով), ոչ raw-count alarm, ուստի բռնում է և՛ կտրուկ անկումը, և՛ դանդաղ արտահոսքը՝ առանց flapping-ի։ Canary-ն կրում է այս domain-ի պահանջած չորս guardrail-ը՝ p99 (ոչ mean), saturation՝ որպես leading indicator, error-budget burn և մեկ business metric, plus automatic abort և rollback, որ իրականում փորձարկվել է։ Այն ասում է, թե ինչու է percentage canary-ն այստեղ վավեր (schema cutover չկա)՝ ցույց տալով, որ expand/contract կանոնը դիտարկվել է, ոչ մոռացվել։

### Օրինակ B — IaC state և drift

**Prompt.** Ինչ-որ մեկը production outage-ը շտկեց՝ ուղղակիորեն cloud console-ում load-balancer rule խմբագրելով։ Infra-ն կառավարվում է Terraform-ով։ Հիմա ի՞նչ։

**Senior պատասխան.** Console-ի խմբագրումը ստեղծեց **drift**․ live state-ն այլևս չի համընկնում IaC source of truth-ի հետ, և հաջորդ `terraform apply`-ը լուռ հետ կգլորի fix-ը և կրկին կկոտրի production-ը։ IaC-ն համարիր source of truth և reconcile արա այս հերթականությամբ․ (1) Գործարկիր **plan**, որ տեսնես հստակ ինչ շեղվեց — հաստատիր, որ console-ի փոփոխությունը միակ drift-ն է։ (2) **Codify** արա fix-ը Terraform config-ում (կամ `import` արա փոխված resource-ը, եթե այն ստեղծվել է out-of-band), որ desired state-ն այժմ ներառի այն։ (3) Վերագործարկիր plan-ը. այն պետք է ցույց տա **no changes** — դա ապացուցում է, որ config-ն ու live state-ը համընկնում են։ (4) Համոզվիր, որ remote **state-ը locked է** (state backend՝ locking-ով), որ երկու apply չկարողանան զուգահեռ corrupt անել։ (5) Ավելացրու **drift detection** (scheduled plan, որ alert է անում non-zero diff-ի վրա), որ հաջորդ console hot-fix-ը բռնվի ժամերում, ոչ հաջորդ deploy-ին։ Postmortem-ի contributing-factor․ outage runbook-ը թույլ տվեց console խմբագրում՝ առանց IaC վերադարձի path-ի — control-ը «emergency փոփոխությունները պետք է codify-վեն X ժամում, enforce-ված drift detection-ով»։

**Ինչու է անցնում gate-ը.** Այն անվանում է իրական failure mode-ը — drift, որ հաջորդ apply-ը լուռ հետ է գլորում, ոչ թե պարզապես «մի՛ խմբագրիր console-ը»։ Reconcile հերթականությունը կոնկրետ է և ordered (plan → codify/import → plan ցույց է տալիս zero diff → lock state → drift detection), և «plan ցույց է տալիս no changes» քայլը verification gate-ն է, ոչ green-CI ենթադրություն։ Այն lock է անում state-ը՝ զուգահեռ corruption-ը կանխելու, և փակում է loop-ը postmortem-ի control փոփոխությամբ, որ նույն hot-fix-ը չկարողանա կրկին լուռ փտել։

### Օրինակ C — blameless postmortem

**Prompt.** Deploy-ը API-ն 38 րոպե գցեց։ Engineer-ը push արեց config փոփոխություն, որ service-ը ուղղեց սխալ database-ի. on-call-ը rollback արեց։ Գրիր postmortem-ը։

**Senior պատասխան.** **Impact & severity․** API 5xx 38 րոպե. severity-ն սահմանված user impact-ով (ամբողջական API outage), ոչ նրանով, ով push արեց։ **Timeline․** deploy T0-ին → error rate-ը հատեց page threshold-ը T0+4-ին (4 րոպե detection) → on-call-ը diagnose արեց սխալ DB target-ը T0+22-ին (18 րոպե diagnosis — դանդաղ հատվածը) → rollback նախորդ revision-ին T0+30-ին → recovery հաստատված T0+38-ին։ **Contributing factors (ոչ մեկ root cause)․** (1) config-ը թույլ տվեց invalid DB target-ի deploy — validation gate չկար. (2) detection-ը 4 րոպե տևեց, որովհետև alerting-ը raw 5xx count-ի վրա էր, ոչ error-budget burn-ի. (3) diagnosis-ը 18 րոպե տևեց, որովհետև config diff-ը չէր երևում deploy log-ում. (4) սխալ-target config-ը pre-deploy connectivity check չուներ։ **Ship արված control-ներ․** (ա) schema-validate արա config-ը և ավելացրու pre-deploy connectivity check սխալ target-ին (block է անում failure-ի դասը). (բ) alerting-ը տեղափոխիր multi-window burn rate (ավելի արագ, ավելի քիչ false page). (գ) config diff-ը երևացրու deploy annotation-ում (կտրում է diagnosis-ի ժամանակը). (դ) rollback-ն աշխատեց և արդեն rehearsed էր — պահիր այն։ **Ոչ մի անհատ չի անվանվում որպես cause**․ ձախողումը բացակայող validation control էր, և այդ control-ն այժմ կա։

**Ինչու է անցնում gate-ը.** Severity-ն սահմանված է user impact-ով, և timeline-ն առանձնացնում է դանդաղ հատվածը (18 րոպե diagnosis), որ control-ները թիրախավորեն, որտեղ ժամանակն իրականում կորավ։ «Root cause»-ը reframe-ված է որպես contributing-factors քարտեզ — բացակայող validation, raw-count alerting, թաքնված config diff — և ամեն factor ship է անում կոնկրետ control, ոչ նկատողություն։ Այն բացահայտ հրաժարվում է engineer-ին անվանելուց. fix-ը validation gate-ն է, որ նույն սխալը դարձնում է un-shippable։ Այն նույնիսկ վարկ է տալիս աշխատածին (rehearsed rollback), որ review-ն ազնիվ պահի, ոչ զուտ պատժիչ։
