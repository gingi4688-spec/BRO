# Frontend, UX, and Product Design / Frontend, UX և Product Design

## English

**Scope.** In: the four joined interface roles — (1) **UX research** (do we understand the user, the job, and the real problem before we draw — Norman, Nielsen's heuristics, Krug, JTBD, and which method answers which question); (2) **laws-of-UX and interaction/product design** (visual hierarchy, the mandatory states, microcopy, error prevention/recovery, purposeful motion, Fitts/Hick/Miller/Jakob/Tesler/Gestalt); (3) **design systems** (semantic vs primitive tokens, atomic design, component-API design, theming, governance, accessibility as a system property); (4) **frontend engineering** (component architecture, state ownership, rendering models, Core Web Vitals, and WCAG 2.2 / WAI-ARIA accessibility implementation — verified, never claimed). Out: page-level structure, information architecture, page-maps, the per-page state matrix, role-gated view layout, and developer handoff (those route to `ui-page-structure-design`); product prioritization, roadmap, and PRD scope (`product-project-management`); native-mobile lifecycle, memory, and app-store concerns (`mobile-engineering`). This skill turns a validated problem into a usable, fast, accessible interface, with a reason for every element and a verified rendered result.

**Leads / Supports.** Lead when the central deliverable is design craft or implemented interface quality: a component-API spec, a design-token set, a UX-research plan, a states/microcopy pass, a performance budget, an accessibility implementation, or a critique of any of these. Support when another skill owns the artifact and design craft is one input — e.g. `ui-page-structure-design` owns the page structure and you supply the component tokens, states, and a11y implementation; `product-project-management` owns the roadmap and you supply the research method and the usability evidence.

Conflict rules:
- **Page structure / IA / page-map / state-matrix → defer to `ui-page-structure-design`.** That skill owns the page job, section order, role-gated view layout, the per-page state matrix, responsive priority, and developer handoff. This skill owns the craft inside the structure — component APIs, tokens, hierarchy, microcopy, motion, performance, and the accessibility implementation. When the question is "what sections and in what order on this page," route there; when it is "how is this component built, tokenized, and rendered correctly," it is here. Do not re-teach the page-structure operating sequence.
- **Roadmap / PRD / prioritization → defer to `product-project-management`.** You own the research *methods* that produce design-ready evidence (interviews, usability tests, JTBD). The decision of *what to build next* and the spec/priority belong to product management; surface the usability evidence, do not set the roadmap.
- **Native-mobile lifecycle → defer to `mobile-engineering`.** Responsive web, touch targets, and mobile-first layout are yours. App lifecycle, memory, background execution, and store submission route to `mobile-engineering`.
- **Copywriting voice/brand → coordinate with `communication-writing-negotiation` and `language-mastery`.** Microcopy as an interaction and accessibility surface is yours; the persuasion craft and the native-Armenian engine are theirs.

Apply `../shared/OPERATING_PROTOCOL.md` before answering: route first, separate facts from assumptions, keep safety boundaries, make the output executable, write equal-depth bilingual, verify before finalizing.

### Decision rules / Որոշման կանոններ

1. **Before designing anything → confirm we understand the user and the real problem.** If it is assumption, not evidence, run discovery first (interview past behavior, watch the real task, test the problem) — solving the wrong problem beautifully is the most expensive mistake.
2. **Pick the research method by the question.** What/why and mental models → generative interviews + contextual inquiry; "does our design work" → usability test (5 users surface ~80% of issues), heuristic evaluation, analytics; findability of a nav → tree test *before* building screens. Watch what users do, not only what they say.
3. **Add an element to a surface only if it serves that surface's one job for this user.** If you cannot say why it belongs here specifically, cut it, hide it behind progressive disclosure, or move it. Hierarchy is the message: one primary action per view, everything else visibly subordinate.
4. **Design every state up front, not just the happy "full" one.** Empty (first-run vs filtered-to-zero are different), loading (skeleton over spinner for layout-stable content), error (what happened + what to do + retry, never a raw stack trace), success, permission-denied, offline/stale, too-much-data. The unhappy path *is* the product.
5. **Token or hardcode → always token.** Components consume **semantic** tokens (`color-text-primary`), never primitives (`gray-700`); no value is missing → if there is no token, you found a gap, add it. Theming (light/dark, density, brand) is a semantic-token swap, not a refactor.
6. **Reuse + extend a system component before inventing one.** Genuinely novel → build it *into* the system (tokens, full state set, docs, a11y), not as a one-off. A component ships its full states: default/hover/active/focus-visible/disabled/loading/error/selected — without focus and disabled it is half-built.
7. **Design the component API as a contract.** Minimal, composable, predictable props; controlled vs uncontrolled is a deliberate choice; prefer slots/children and compound components over a forest of boolean props (composition over configuration); encode ARIA role, keyboard model, and focus inside the component so consumers cannot get it wrong.
8. **Manage state by data ownership.** Local UI state → component; server-fetched data → a query/cache layer (not a global store — treating server data as client state is the #1 mess); cross-cutting session/theme → a small deliberate global store; shareable/back-button state (filters, tabs, pagination) → the URL; form state → a form library.
9. **Pick the rendering model by content × interactivity × SEO × scale.** Rich app behind auth → CSR; dynamic + SEO + fast first paint → SSR; content/marketing, cacheable at the edge → SSG; static shell + dynamic islands, stream and hydrate selectively → streaming SSR / RSC. Not by framework fashion.
10. **Measure performance against Core Web Vitals with field data, then optimize the real hotspot.** LCP < 2.5s (size and prioritize the LCP image), CLS < 0.1 (reserve space, set dimensions), INP < 200ms (break up long tasks, yield to the main thread). Budget it and gate it in CI. The cheapest byte is the one you do not send; premature memoization is noise.
11. **Confirm, undo, or just do.** Reversible → just do (with a way back); reversible-but-noticeable → an undo toast; destructive + irreversible → confirm naming the consequence and the object ("Delete 3 invoices"). Do not confirm the harmless — confirmation fatigue trains the user to click through the one that mattered. Prefer reversible (undo) to preventive (confirm).
12. **Animate only if it communicates.** State change, spatial continuity, causality, or hierarchy of attention — otherwise cut it. Keep UI transitions ~150–300ms (snappy beats smooth for frequent interactions). Always honor `prefers-reduced-motion` with a reduced/none alternative — it is accessibility, not a preference to ignore.
13. **Never encode meaning by color alone.** Pair color with icon, text, or shape; status must survive deuteranopia. Contrast is a hard floor, not taste: body ≥ 4.5:1, large text / UI components ≥ 3:1 (WCAG AA) — test it, do not eyeball it, and check it on disabled/placeholder/focus states too.
14. **Semantic HTML first; ARIA only to fill gaps.** A real `<button>`/`<nav>`/`<label>` brings keyboard, focus, and role for free; the first rule of ARIA is do not use ARIA if a native element exists. Visible `:focus-visible`; trap and restore focus in modals; everything operable keyboard-only.
15. **Not done until verified rendered in the running app.** View every state, representative roles for role UIs, the smallest and a large viewport, a keyboard-only pass, a screen-reader spot-check, dark mode if supported, and the CWV numbers. "It compiles" and "the tests pass" are not "it looks right" and are not "it is accessible" — accessibility and rendered reality are verified, never claimed.

### Failure modes to prevent / Ձախողման ձևեր

1. **Solving the wrong problem beautifully.** A polished surface nobody needed because the problem was assumed, not validated. Tell: no discovery, no usability evidence, design started at the pixel.
2. **Flat hierarchy.** Everything the same size/weight/color, so the eye has no entry point and no primary action stands out. Tell: the squint test fails — blur the screen and nothing pops.
3. **Happy-path-only UI.** Only the full-data state exists; empty, loading, error, and permission-denied break on contact with reality. Tell: a demo that crashes or shows a raw error the moment data is missing or slow.
4. **Hardcoded values instead of tokens.** Eyedropper one-off colors and pixel literals scattered in components; dark mode and density become a rewrite. Tell: raw hex/px inside a component, five button styles, no semantic-token layer.
5. **Server-data-as-client-state.** Fetched data shoved into a global store with manual sync, stale reads, and refetch bugs. Tell: a mega-store holding API responses, no query/cache layer, view state not in the URL.
6. **Accessibility claimed, not verified.** "WCAG compliant" asserted with no keyboard pass, no screen-reader check, `outline:none` with no replacement, `<div onClick>` instead of `<button>`. Tell: an a11y claim with only an automated scan (which catches ~30–40%) or none at all.
7. **Color-only meaning.** Status conveyed by hue alone, failing color-blind users and contrast floors. Tell: red/green dots with no icon, text, or shape; contrast not tested on states.
8. **Placeholder-as-label.** The label is the placeholder, so it vanishes on focus and fails memory and a screen reader. Tell: forms with no persistent label above the field; an error that wipes the half-filled form (form hostility).
9. **Component without its full state set or its a11y baked in.** A button with no focus-visible/disabled/loading, a custom combobox re-derived instead of using a proven APG pattern. Tell: a component spec missing states, or ARIA bolted on after the fact.
10. **Performance guessed, not measured.** `memo` everywhere as ritual, huge JS shipped "to be fast," 10k DOM rows un-virtualized, layout shift on load. Tell: no CWV/field numbers, no budget in CI, optimization with no profiler evidence.
11. **Motion as decoration / reduced-motion ignored.** Animations that delay the task, teleporting UI with no spatial continuity, no `prefers-reduced-motion` path. Tell: long decorative transitions, motion that communicates nothing, no reduced alternative.
12. **Done-on-compile.** A UI called finished because the build is green, never opened in the running app across its states, roles, and viewports. Tell: "done" with no rendered observation, no keyboard pass, no a11y spot-check.

### Acceptance criteria / Ընդունման չափանիշ

- The artifact matches the deliverable (component-API spec / design-token set / UX-research plan / states+microcopy pass / performance budget / a11y implementation), not generic advice.
- Research claims trace to a method and observed user behavior, not assumption; the research method fits the question asked.
- Every element on a surface has a stated reason for this user/job; one primary action per view; hierarchy is explicit and passes the squint test.
- All applicable states are designed (empty/loading/error/success/permission/offline/too-much-data), not just the full state.
- Values are tokens (semantic, not primitive), not hardcodes; components ship their full state set with ARIA/keyboard/focus encoded.
- Performance is measured against Core Web Vitals (LCP/INP/CLS) with field data and a CI budget; optimization targets a measured hotspot.
- Accessibility is implemented to WCAG 2.2 / WAI-ARIA APG and **verified** (keyboard pass + screen-reader spot-check + tested contrast); no untested "WCAG compliant" claim is asserted, and no benchmark/price/model name is invented.
- **Verify in the running UI, never assume** — every state, representative roles, smallest + large viewport, keyboard-only once, a11y spot-check, dark mode if supported, and a glance at the CWV numbers, before the work is called done.
- Bilingual EN + native HY at equal depth; assumptions and unknowns labeled.

### Domain quality bar / Որակի նշաձող

Scored on five dimensions (mirror `domain-rubric.md`): **research validity** (right method for the question, behavior over opinion, problem validated before design) · **interaction design** (hierarchy, all states, microcopy, error prevention/recovery, purposeful motion, the right laws applied) · **design-system rigor** (semantic tokens, atomic composition, component-API contract, theming, governance) · **frontend implementation** (component architecture, correct state ownership, rendering model, Core Web Vitals measured) · **accessibility — verified** (semantic HTML, keyboard/focus, contrast, ARIA APG, tested not claimed).

## Հայերեն

**Շրջանակ։** Ներսում՝ interface-ի չորս միացյալ role-ը — (1) **UX research** (հասկանո՞ւմ ենք user-ին, job-ը և իրական problem-ը նախքան նկարելը — Norman, Nielsen-ի heuristics, Krug, JTBD, և որ մեթոդն է որ հարցին պատասխանում). (2) **laws-of-UX և interaction/product design** (visual hierarchy, պարտադիր state-երը, microcopy, error-ի կանխում/վերականգնում, իմաստալից motion, Fitts/Hick/Miller/Jakob/Tesler/Gestalt). (3) **design system** (semantic ընդդեմ primitive token, atomic design, component-API-ի դիզայն, theming, governance, accessibility՝ որպես system-ի հատկություն). (4) **frontend engineering** (component architecture, state-ի ownership, rendering model, Core Web Vitals, և WCAG 2.2 / WAI-ARIA accessibility-ի իրականացում՝ ստուգված, ոչ պնդված)։ Դուրս՝ էջի մակարդակի structure-ը, information architecture-ը, page-map-ը, per-page state matrix-ը, role-gated view-ի layout-ը և developer handoff-ը (դրանք ուղղորդվում են `ui-page-structure-design`-ին). product-ի prioritization-ը, roadmap-ը և PRD scope-ը (`product-project-management`). native-mobile-ի lifecycle-ը, memory-ն և app-store-ի հարցերը (`mobile-engineering`)։ Այս skill-ը validated problem-ը դարձնում է usable, արագ, accessible interface՝ ամեն element-ի համար պատճառով և ստուգված rendered արդյունքով։

**Առաջատար / Աջակից։** Առաջատար, երբ կենտրոնական deliverable-ը design craft է կամ իրականացված interface-ի որակ՝ component-API spec, design-token set, UX-research plan, states+microcopy pass, performance budget, accessibility-ի իրականացում, կամ դրանցից մեկի քննադատություն։ Աջակից, երբ artifact-ի տերը այլ skill է, իսկ design craft-ը մեկ input է. օրինակ՝ `ui-page-structure-design`-ը տիրում է էջի structure-ին, դու տալիս ես component-ի token-ները, state-երը և a11y-ի իրականացումը. `product-project-management`-ը տիրում է roadmap-ին, դու տալիս ես research մեթոդը և usability evidence-ը։

Կոնֆլիկտի կանոններ․
- **Էջի structure / IA / page-map / state-matrix → զիջիր `ui-page-structure-design`-ին։** Այն skill-ը տիրում է էջի գործին, բաժինների հերթականությանը, role-gated view-ի layout-ին, per-page state matrix-ին, responsive priority-ին և developer handoff-ին։ Այս skill-ը տիրում է structure-ի *ներսի* craft-ին՝ component API, token, hierarchy, microcopy, motion, performance և accessibility-ի իրականացում։ Երբ հարցը «ինչ բաժիններ և ինչ հերթականությամբ այս էջում» է, ուղղորդիր այնտեղ. երբ «ինչպես է այս component-ը կառուցված, tokenized և ճիշտ render-ված», այստեղ է։ Page-structure-ի աշխատանքային հերթականությունը մի՛ վերաուսուցանիր։
- **Roadmap / PRD / prioritization → զիջիր `product-project-management`-ին։** Դու տիրում ես research *մեթոդներին*, որ design-ready evidence են արտադրում (interview, usability test, JTBD)։ *Ինչ կառուցել հաջորդը* որոշումը և spec/priority-ն product management-ինն են. ցույց տուր usability evidence-ը, roadmap-ը մի՛ սահմանիր։
- **Native-mobile lifecycle → զիջիր `mobile-engineering`-ին։** Responsive web-ը, touch target-ները և mobile-first layout-ը քոնն են։ App lifecycle, memory, background execution և store submission ուղղորդվում են `mobile-engineering`-ին։
- **Copywriting voice/brand → համակարգիր `communication-writing-negotiation`-ի և `language-mastery`-ի հետ։** Microcopy-ն՝ որպես interaction և accessibility surface, քոնն է. համոզման craft-ը և native-հայերենի շարժիչը՝ նրանցը։

### Որոշման կանոններ

1. **Նախքան որևէ բան նախագծելը → հաստատիր, որ հասկանում ենք user-ին և իրական problem-ը։** Եթե ենթադրություն է, ոչ evidence, նախ discovery արա (interview անցյալ վարքի մասին, դիտիր իրական task-ը, թեստավորիր problem-ը) — սխալ problem-ը գեղեցիկ լուծելը ամենաթանկ սխալն է։
2. **Ընտրիր research մեթոդը ըստ հարցի։** Ինչ/ինչու և mental model → generative interview + contextual inquiry. «մեր design-ը աշխատո՞ւմ է» → usability test (5 user-ը բացում է problem-ների ~80%-ը), heuristic evaluation, analytics. nav-ի findability → tree test՝ *նախքան* էկրան կառուցելը։ Դիտիր ինչ են user-երը ԱՆՈՒՄ, ոչ միայն ինչ են ԱՍՈՒՄ։
3. **Element ավելացրու surface-ին միայն, եթե այն ծառայում է այդ surface-ի մեկ job-ին այս user-ի համար։** Եթե չես կարող ասել, թե ինչու է այստեղ կոնկրետ, կտրիր, թաքցրու progressive disclosure-ի տակ, կամ տեղափոխիր։ Hierarchy-ն message-ն է. մեկ primary action ամեն view-ում, մնացածը visually ստորադաս։
4. **Նախագծիր ամեն state-ը նախապես, ոչ միայն happy «full»-ը։** Empty (first-run vs filtered-to-zero տարբեր են), loading (skeleton > spinner layout-stable-ի համար), error (ինչ եղավ + ինչ անել + retry, երբեք raw stack trace), success, permission-denied, offline/stale, too-much-data։ Unhappy path-ը *է* product-ը։
5. **Token թե hardcode → միշտ token։** Component-ը սպառում է **semantic** token (`color-text-primary`), երբեք primitive (`gray-700`). token չկա → gap ես գտել, ավելացրու։ Theming-ը (light/dark, density, brand) semantic-token swap է, ոչ refactor։
6. **Reuse + extend system-ի component-ը նախքան հորինելը։** Իսկապես novel → կառուցիր այն system-ի *մեջ* (token, ամբողջ state set, docs, a11y), ոչ one-off։ Component-ը բերում է իր ամբողջ state-ը՝ default/hover/active/focus-visible/disabled/loading/error/selected. առանց focus-ի և disabled-ի կիսատ է։
7. **Նախագծիր component-ի API-ն որպես contract։** Minimal, composable, կանխատեսելի props. controlled vs uncontrolled՝ գիտակցված ընտրություն. նախընտրիր slot/children և compound component՝ boolean prop-երի անտառի փոխարեն (composition over configuration). կոդավորիր ARIA role-ը, keyboard model-ը և focus-ը component-ի ներսում, որ consumer-ը չսխալվի։
8. **Կառավարիր state-ը ըստ data-ի ownership-ի։** Local UI state → component. server-fetched data → query/cache layer (ոչ global store — server data-ն client state համարելը #1 խառնաշփոթն է). cross-cutting session/theme → փոքր գիտակցված global store. shareable/back-button state (filter, tab, pagination) → URL. form state → form library։
9. **Ընտրիր rendering model-ը ըստ content × interactivity × SEO × scale-ի։** Rich app auth-ի հետևում → CSR. dynamic + SEO + արագ first paint → SSR. content/marketing, edge-cacheable → SSG. static shell + dynamic island, stream և selective hydrate → streaming SSR / RSC։ Ոչ framework-ի նորաձևությամբ։
10. **Չափիր performance-ը Core Web Vitals-ով field data-ով, հետո optimize արա իրական hotspot-ը։** LCP < 2.5s (size և prioritize արա LCP image-ը), CLS < 0.1 (ռեզերվ արա տեղ, set արա չափ), INP < 200ms (կտրիր երկար task-ը, yield արա main thread-ին)։ Budget արա և gate արա CI-ում։ Ամենաէժան byte-ը այն է, որ չես ուղարկում. վաղաժամ memoization-ը noise է։
11. **Confirm, undo, թե just-do։** Reversible → արա (հետ-գնալու ճանապարհով). նկատելի-բայց-reversible → undo toast. destructive + irreversible → confirm՝ consequence-ը և object-ը անվանելով («Delete 3 invoices»)։ Անվնասը մի՛ confirm արա — confirmation fatigue-ը սովորեցնում է click անել այն մեկի վրայով, որ կարևոր էր։ Նախընտրիր reversible (undo) > preventive (confirm)։
12. **Animate արա միայն, եթե հաղորդում է։** State change, spatial continuity, causality, կամ attention-ի hierarchy — այլապես կտրիր։ UI transition պահիր ~150–300ms (snappy > smooth հաճախակի interaction-ի համար)։ Միշտ հարգիր `prefers-reduced-motion`-ը՝ reduced/none այլընտրանքով — դա accessibility է, ոչ անտեսելի preference։
13. **Երբեք meaning միայն color-ով։** Զուգիր color-ը icon-ի, text-ի կամ shape-ի հետ. status-ը պետք է դիմանա deuteranopia-ին։ Contrast-ը կոշտ հատակ է, ոչ ճաշակ՝ body ≥ 4.5:1, large/UI ≥ 3:1 (WCAG AA) — թեստավորիր, մի՛ աչքաչափիր, և ստուգիր disabled/placeholder/focus state-երին էլ։
14. **Semantic HTML նախ. ARIA միայն բացերի համար։** Իրական `<button>`/`<nav>`/`<label>`-ը keyboard, focus և role ձրի է բերում. ARIA-ի առաջին կանոնը՝ մի՛ օգտագործիր ARIA, եթե native element կա։ Տեսանելի `:focus-visible`. modal-ում focus trap և restore. ամեն ինչ keyboard-only operable։
15. **Done չէ, քանի դեռ rendered-ում չես ստուգել running app-ում։** Դիտիր ամեն state-ը, role UI-ի representative role-երը, ամենափոքր ու մեծ viewport-ը, keyboard-only pass, screen-reader spot-check, dark mode եթե կա, և CWV թվերը։ «Compile է լինում» ու «test-երն անցան» ≠ «ճիշտ տեսք ունի» և ≠ «accessible է» — accessibility-ն ու rendered իրականությունը verified են, ոչ պնդված։

### Ձախողման ձևեր

1. **Սխալ problem-ը գեղեցիկ լուծել։** Հղկված surface, որ ոչ ոքի պետք չէր, որովհետև problem-ը ենթադրվեց, ոչ validate-վեց։ Tell՝ discovery չկա, usability evidence չկա, design-ը սկսվեց pixel-ից։
2. **Հարթ hierarchy։** Ամեն ինչ նույն size/weight/color, ուստի աչքը entry point չունի և ոչ մի primary action չի առանձնանում։ Tell՝ squint test-ը fail է — լղոզիր էկրանը, ոչինչ չի դուրս ցցվում։
3. **Միայն-happy-path UI։** Միայն full-data state-ը կա. empty, loading, error և permission-denied կոտրվում են իրականության հետ շփման պահին։ Tell՝ demo, որ crash է անում կամ raw error ցույց տալիս, հենց data-ն բացակայում կամ դանդաղ է։
4. **Hardcode token-ի փոխարեն։** Eyedropper one-off color և pixel literal՝ ցրված component-ներում. dark mode-ն ու density-ն դառնում են rewrite։ Tell՝ raw hex/px component-ի ներսում, հինգ button style, semantic-token շերտ չկա։
5. **Server-data-as-client-state։** Fetch արված data՝ խցկված global store-ում ձեռքով sync-ով, stale read և refetch bug-ով։ Tell՝ mega-store, որ API response է պահում, query/cache layer չկա, view state-ը URL-ում չէ։
6. **Accessibility պնդված, ոչ ստուգված։** «WCAG compliant» պնդված առանց keyboard pass-ի, առանց screen-reader ստուգման, `outline:none` առանց փոխարինման, `<div onClick>`՝ `<button>`-ի փոխարեն։ Tell՝ a11y claim միայն automated scan-ով (որ բռնում է ~30–40%) կամ ընդհանրապես առանց։
7. **Color-only meaning։** Status հաղորդված միայն hue-ով, ձախողելով գունակույր user-ին և contrast հատակը։ Tell՝ red/green dot առանց icon-ի, text-ի կամ shape-ի. contrast-ը state-երին չտեստավորված։
8. **Placeholder-as-label։** Label-ը placeholder է, ուստի անհետանում է focus-ին և ձախողում հիշողությունն ու screen reader-ը։ Tell՝ form առանց field-ից վերև մշտական label-ի. error, որ սրբում է կիսատ form-ը (form hostility)։
9. **Component առանց ամբողջ state set-ի կամ ներսի a11y-ի։** Button առանց focus-visible/disabled/loading-ի, custom combobox՝ վերածնված ապացուցված APG pattern-ի փոխարեն։ Tell՝ component spec, որ state է բացակայում, կամ ARIA՝ հետո կպցրած։
10. **Performance գուշակված, ոչ չափված։** `memo` ամենուր որպես ծես, հսկայական JS ship արված «արագ լինելու համար», 10k DOM row առանց virtualize-ի, layout shift load-ին։ Tell՝ CWV/field թիվ չկա, CI-ում budget չկա, optimization առանց profiler evidence-ի։
11. **Motion որպես դեկոր / reduced-motion անտեսված։** Animation, որ ուշացնում է task-ը, teleport-վող UI առանց spatial continuity-ի, `prefers-reduced-motion` path չկա։ Tell՝ երկար դեկորատիվ transition, motion, որ ոչինչ չի հաղորդում, reduced այլընտրանք չկա։
12. **Done-on-compile։** UI հայտարարված ավարտված, որովհետև build-ը green է, երբեք բացված running app-ում իր state-երով, role-երով ու viewport-ներով։ Tell՝ «done» առանց rendered observation-ի, առանց keyboard pass-ի, առանց a11y spot-check-ի։

### Ընդունման չափանիշ

- Artifact-ը համապատասխանում է deliverable-ին (component-API spec / design-token set / UX-research plan / states+microcopy pass / performance budget / a11y իրականացում), ոչ generic advice։
- Research-ի պնդումները հետ են գնում մեթոդի և observed user behavior-ի, ոչ ենթադրության. research մեթոդը համապատասխանում է տրված հարցին։
- Surface-ի ամեն element-ը ունի նշված պատճառ այս user-ի/job-ի համար. մեկ primary action ամեն view-ում. hierarchy-ն հստակ է և անցնում է squint test-ը։
- Բոլոր կիրառելի state-երը նախագծված են (empty/loading/error/success/permission/offline/too-much-data), ոչ միայն full state-ը։
- Արժեքները token են (semantic, ոչ primitive), ոչ hardcode. component-ները բերում են իրենց ամբողջ state set-ը ARIA/keyboard/focus կոդավորմամբ։
- Performance-ը չափված է Core Web Vitals-ով (LCP/INP/CLS) field data-ով և CI budget-ով. optimization-ը թիրախավորում է չափված hotspot։
- Accessibility-ն իրականացված է WCAG 2.2 / WAI-ARIA APG-ով և **ստուգված** (keyboard pass + screen-reader spot-check + թեստավորված contrast). ոչ մի չ-test-ված «WCAG compliant» claim չի պնդվում, և ոչ մի benchmark/price/model name չի հորինվում։
- **Ստուգի՛ր running UI-ում, երբեք մի՛ ենթադրիր** — ամեն state-ը, representative role-երը, ամենափոքր + մեծ viewport-ը, keyboard-only մեկ անգամ, a11y spot-check, dark mode եթե կա, և հայացք CWV թվերին, մինչև done ասելը։
- Երկլեզու EN + native HY հավասար խորությամբ. assumption-ները և unknown-ները label-ված։
