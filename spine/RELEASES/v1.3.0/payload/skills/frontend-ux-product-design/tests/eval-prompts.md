# Frontend, UX, and Product Design eval prompts

## English

Run these after changes. Each prompt has its own pass check — passing requires mechanism-level reasoning and a concrete artifact, not vocabulary. Do not reuse one check for another prompt.

1. **Research method by question.** "We want to redesign onboarding. Where do we start?" — Pass only if it validates the problem before drawing: picks the method by the open question (generative interviews about past behavior / contextual inquiry for what-and-why; usability test for "does the current flow work"), watches behavior over stated preference, and does not jump to screens. Fail if it starts at the pixel.
2. **Hierarchy & states.** "Design the layout for an invoices list view." — Pass only if it establishes one primary action and explicit hierarchy (squint-test) and designs all applicable states (empty first-run vs filtered-to-zero, loading skeleton, error with recovery, permission-denied, too-much-data → virtualize), not just the full table.
3. **Design tokens & theming.** "We have five button styles and dark mode is broken. Fix it." — Pass only if it defines three-tier tokens (primitive → semantic → component), makes components consume semantic only, and treats dark mode as a token-value swap — not a sixth style or a CSS fork.
4. **Component-API design.** "Design the API for a reusable Select/Combobox." — Pass only if props are a contract (enums/slots over boolean forests, deliberate controlled/uncontrolled, compound/`asChild`), the full state set is present (incl. focus-visible and disabled), and ARIA role/keyboard/focus come from a native element or the APG, not bolted on.
5. **State management.** "Where should filters, fetched rows, auth, and a form's dirty state live?" — Pass only if it assigns by data ownership: fetched rows → query/cache layer (not a global store), filters/tabs/pagination → URL, auth/theme → small global store, form dirty/validation → form library, local UI → component.
6. **Rendering model.** "Should this marketing site and this in-app dashboard use SSR, SSG, or CSR?" — Pass only if it chooses by content × interactivity × SEO × scale (marketing → SSG/edge-cacheable; dashboard behind auth → CSR or streaming), not by framework fashion, and names the tradeoff.
7. **Core Web Vitals.** "The app feels slow. What do we measure and fix?" — Pass only if it names LCP (<2.5s), INP (<200ms), CLS (<0.1) with what moves each (prioritize LCP image; break up long INP tasks; reserve space for CLS), insists on field/RUM data over lab feel, and budgets it in CI. Fail if it optimizes by guess or memoizes as ritual.
8. **Accessibility — verified not claimed.** "Our PM wants us to put 'WCAG 2.2 AA compliant' on the site. Can we?" — Pass only if it refuses to claim conformance without running the manual passes (keyboard, screen-reader spot-check, tested contrast on states), explains automated tools catch ~30–40%, and replaces the claim with the verified result. Fail if it green-lights the badge from an automated scan.
9. **Delegation boundary.** "Design the full structure and section order of the new settings page, with the role-gated views and state matrix." — Pass only if it routes the page structure / IA / role-gated layout / per-page state matrix to `ui-page-structure-design` and keeps for itself the component tokens, microcopy, motion, performance, and a11y implementation; it must not re-teach the page-structure operating sequence. (Also: roadmap/PRD → `product-project-management`; native-mobile lifecycle → `mobile-engineering`.)
10. **Verify in the running UI.** "It compiles and the tests pass — are we done?" — Pass only if it says a green build is necessary but not sufficient and requires observing the running app: every state, representative roles, smallest + large viewport, a keyboard pass, a screen-reader spot-check, dark mode if supported, and the CWV numbers — before "done."
11. **Armenian equal-depth.** Ask any of prompts 1–10 in Armenian. — Pass only if the Armenian is native, equal-depth (same mechanism, same numbers, same artifact), and punctuation-clean (correct `․`/`։`/«», no homoglyphs); tech tokens in English (LCP, INP, CLS, ARIA, token) are fine.

Regression checks (run alongside):

- **No invented facts.** Ask for a specific Lighthouse score benchmark or a named library's exact bundle size. — Pass only if it refuses to invent it or marks it verify-before-use with a measurement method, not a fabricated number.
- **No thin label answer.** Ask "just give me the UX best practices." — Pass only if it expands into mechanism (a law applied, a token tier, a state designed, a CWV moved), not a list of names.

## Հայերեն

Գործարկիր սրանք փոփոխություններից հետո։ Ամեն prompt ունի իր pass check-ը — անցնելը պահանջում է mechanism-level reasoning և concrete artifact, ոչ vocabulary։ Մի՛ կիրառիր մի check-ը մյուս prompt-ի համար։

1. **Research մեթոդ ըստ հարցի.** «Ուզում ենք redesign անել onboarding-ը։ Որտեղի՞ց սկսենք»։ — Անցնում է միայն, եթե validate է անում problem-ը նախքան նկարելը՝ ընտրում է մեթոդը ըստ բաց հարցի (generative interview անցյալ վարքի մասին / contextual inquiry՝ ինչ-ու-ինչու. usability test՝ «ընթացիկ flow-ն աշխատո՞ւմ է»), դիտում է վարք ասված preference-ից առաջ, և չի թռչում էկրաններին։ Fail՝ եթե սկսում է pixel-ից։
2. **Hierarchy & states.** «Նախագծիր invoices list view-ի layout-ը»։ — Անցնում է միայն, եթե հաստատում է մեկ primary action ու հստակ hierarchy (squint-test) և նախագծում ամեն կիրառելի state (empty first-run vs filtered-to-zero, loading skeleton, error recovery-ով, permission-denied, too-much-data → virtualize), ոչ միայն full table-ը։
3. **Design token & theming.** «Ունենք հինգ button style, dark mode-ը կոտրված է։ Ուղղիր»։ — Անցնում է միայն, եթե սահմանում է երեք-շերտ token (primitive → semantic → component), component-ները դարձնում միայն semantic սպառող, և dark mode-ը համարում token-արժեքի swap — ոչ վեցերորդ style կամ CSS fork։
4. **Component-API design.** «Նախագծիր reusable Select/Combobox-ի API-ն»։ — Անցնում է միայն, եթե props-ը contract է (enum/slot՝ boolean անտառի փոխարեն, գիտակցված controlled/uncontrolled, compound/`asChild`), ամբողջ state set-ը կա (ներառյալ focus-visible և disabled), և ARIA role/keyboard/focus-ը գալիս է native element-ից կամ APG-ից, ոչ կպցրած։
5. **State management.** «Որտեղ պետք է ապրեն filter-ները, fetch արված row-երը, auth-ը և form-ի dirty state-ը»։ — Անցնում է միայն, եթե նշանակում է ըստ data-ի ownership-ի՝ fetch արված row → query/cache layer (ոչ global store), filter/tab/pagination → URL, auth/theme → փոքր global store, form dirty/validation → form library, local UI → component։
6. **Rendering model.** «Այս marketing site-ը և այս in-app dashboard-ը SSR, SSG, թե CSR օգտագործե՞ն»։ — Անցնում է միայն, եթե ընտրում է ըստ content × interactivity × SEO × scale-ի (marketing → SSG/edge-cacheable. dashboard auth-ի հետևում → CSR կամ streaming), ոչ framework-ի նորաձևությամբ, և անվանում է tradeoff-ը։
7. **Core Web Vitals.** «App-ը դանդաղ է զգացվում։ Ինչ չափենք ու ուղղենք»։ — Անցնում է միայն, եթե անվանում է LCP (<2.5s), INP (<200ms), CLS (<0.1) ինչն է ամեն մեկը շարժում (prioritize արա LCP image-ը. կտրիր երկար INP task-ը. ռեզերվ արա տեղ CLS-ի համար), պնդում է field/RUM data lab զգացումից առաջ, և budget անում CI-ում։ Fail՝ եթե optimize է անում գուշակությամբ կամ memoize որպես ծես։
8. **Accessibility — verified ոչ պնդված.** «Մեր PM-ը ուզում է site-ին դնել «WCAG 2.2 AA compliant»։ Կարո՞ղ ենք»։ — Անցնում է միայն, եթե հրաժարվում է conformance պնդելուց առանց ձեռքի pass-երի (keyboard, screen-reader spot-check, թեստավորված contrast state-երին), բացատրում է, որ automated tool-ը բռնում է ~30–40%, և claim-ը փոխարինում verified արդյունքով։ Fail՝ եթե green-light է տալիս badge-ին automated scan-ից։
9. **Delegation boundary.** «Նախագծիր նոր settings էջի ամբողջ structure-ը ու բաժինների հերթականությունը՝ role-gated view-երով ու state matrix-ով»։ — Անցնում է միայն, եթե էջի structure / IA / role-gated layout / per-page state matrix-ը ուղղորդում է `ui-page-structure-design`-ին և իրեն պահում component-ի token-ները, microcopy-ն, motion-ը, performance-ը և a11y-ի իրականացումը. չպետք է վերաուսուցանի page-structure-ի աշխատանքային հերթականությունը։ (Նաև՝ roadmap/PRD → `product-project-management`. native-mobile lifecycle → `mobile-engineering`։)
10. **Verify running UI-ում.** «Compile է լինում ու test-երն անցնում են — done ե՞նք»։ — Անցնում է միայն, եթե ասում է, որ green build-ը անհրաժեշտ է, բայց ոչ բավարար, և պահանջում է դիտել running app-ը՝ ամեն state, representative role, ամենափոքր + մեծ viewport, keyboard pass, screen-reader spot-check, dark mode եթե կա, և CWV թվերը — նախքան «done»-ը։
11. **Հայերեն equal-depth.** Հարցրու 1–10-ից որևէ մեկը հայերեն։ — Անցնում է միայն, եթե հայերենը native է, equal-depth (նույն mechanism-ը, նույն թվերը, նույն artifact-ը) և punctuation-clean (ճիշտ `․`/`։`/«», առանց homoglyph-ի). անգլերեն tech token-ները (LCP, INP, CLS, ARIA, token) նորմալ են։

Regression check-եր (գործարկիր կողքից)․

- **Ոչ մի հորինված fact.** Հարցրու կոնկրետ Lighthouse score benchmark կամ named library-ի ճշգրիտ bundle size։ — Անցնում է միայն, եթե հրաժարվում է հորինելուց կամ նշում verify-before-use՝ չափման մեթոդով, ոչ հորինված թվով։
- **Ոչ բարակ label պատասխան.** Հարցրու «պարզապես տուր UX best practice-ները»։ — Անցնում է միայն, եթե դառնում է mechanism (կիրառված law, token tier, նախագծված state, շարժված CWV), ոչ անունների ցուցակ։
