# Mobile Engineering manual

## English

### Operating principle

Senior mobile work is decision-grade only when it designs for a runtime that is actively hostile and a client you cannot patch on demand. A backend you own; a mobile process you merely rent from the OS — it can be paused, backgrounded, throttled, or killed at any moment, the network can vanish mid-operation, the device may have a tenth of a flagship's RAM, and once a binary ships, fixing it means a store review measured in days while the broken version stays in users' hands for months. So every mobile deliverable starts from four non-negotiables: state survives process death, work that exceeds the 16ms frame budget leaves the main thread, sensitive data is encrypted at rest, and risky behavior is reversible without a store release. The deliverable is one of five shapes — a mobile architecture plan, an offline-sync design, a performance-triage report, a release/rollout plan, or a native-vs-cross-platform decision — and each is judged not by the names it uses but by whether it holds up under app-switch, low memory, a dead network, an old installed client, and a low-tier device. Mobile is not a small server; treating it like one is the root of most of its failures.

### Mechanism reference

- **Mobile lifecycle is hostile** — Apps pause, resume, lose network, hit background-execution limits, and get killed by the OS with no warning under memory pressure. State must be persisted at the right save boundary (on backgrounding, on field change for a draft), and navigation must restore from saved state or a deep link, never from an in-memory happy path. Process death is the default case to design for, not the exception: a lifecycle bug usually only surfaces under app-switch, low memory, or slow network — exactly the conditions a fast device on Wi-Fi never reproduces.
- **Offline-first sync needs a contract, not a cache** — Real offline requires a local store (the on-device truth), an ordered **operation log** of intents, **idempotency keys** so a retry cannot double-apply, a **conflict policy**, retry with backoff, and a user-visible **queued / synced / conflict** status. Last-write-wins is acceptable only for low-value, single-owner fields; collaborative or money/inventory data needs server authority, field-level merge, or explicit manual resolution. The operation log must be idempotent end to end, because a flaky network guarantees retries, and a non-idempotent retry is a duplicate charge or a duplicate record.
- **Performance and battery are product features — the 16ms/60fps frame budget** — A 60fps target is **~16.7ms per frame** (1000ms ÷ 60); a 120fps display halves that to ~8.3ms. Anything on the main/UI thread that pushes a frame past its budget — JSON parsing, image decode, synchronous disk or DB reads, an expensive layout pass — drops the frame, and a stream of dropped frames is jank. Held long enough, a blocked main thread is an **ANR** ("Application Not Responding," ~5s for input on Android) or an iOS watchdog kill. The fixes are structural: move parse/decode/I/O to a background thread, cache decoded images, batch network calls, and budget cold start. Battery is a product feature too: respect background-execution limits and coalesce wakeups, because needless wakeups and radio use are a measurable defect.
- **Mobile release mechanics — staged rollout because store rollback is slow** — You cannot instantly recall a binary; a fix is a new build through store review (days), not a server rollback (minutes). So risky behavior ships behind a **feature flag / remote config**, releases go out by **staged percentage** (e.g. 1% → 5% → 20% → 50% → 100%) gated on **crash-free sessions** and **ANR rate**, and there is a **remote kill switch** that disables the risky path without a store submission. Migrations must be forward-safe and reversible where possible. The store path is the slow path; the remote path is your real rollback.
- **Mobile security on the device** — Secrets and tokens live in the platform keystore — **Keychain** on iOS, **KeyStore**-backed storage (e.g. EncryptedSharedPreferences / a KeyStore-wrapped key) on Android — never in plain `UserDefaults` / `SharedPreferences` or a clear-text file, with a **retention/purge rule** for when the data is removed. Transport is pinned by hashing the **public key (SPKI)**, not the leaf certificate, with a **backup pin** and a remote path to relax pinning, so a routine cert renewal cannot brick every install. **Biometric** auth (Face ID / fingerprint) gates a *local unlock of a key* with a passcode fallback — it is never the credential itself, and a biometric "yes" is only meaningful when bound to a Keychain/KeyStore key operation. Data-at-rest encryption assumes the device may be lost, rooted, jailbroken, or backed up.
- **On-device memory management** — Mobile memory is small and the OS reclaims it by killing your app. On iOS, ARC frees objects when references drop, so a **retain cycle** (a closure capturing `self` strongly, a strong `delegate`, two objects strongly referencing each other) is a leak; break it with `weak`/`unowned` on the back-reference. On Android, the classic leak is holding an **Activity / Context** past its lifecycle — from a static field, a singleton, a long-lived listener, or a Handler — which pins the whole view tree; use the application context where appropriate, lifecycle-aware components, and clear listeners. Honor the **memory-pressure callbacks** (`didReceiveMemoryWarning` / `onTrimMemory`) by dropping caches and releasing images; the app that ignores them is the one the OS kills first on a low-end device.
- **On-device testing strategy** — The simulator/emulator is fast and convenient and lies about the things that matter: it runs on desktop RAM and CPU, does not thermally throttle, has fast desktop flash, and fakes (or omits) the secure enclave, real biometrics, and real radio behavior. Use it for fast iteration, but verify on **real devices** across a **device-tier matrix** (at least one low/mid-tier device most users carry, not only a flagship), and use a **device farm** for breadth across OS versions and form factors. Security, performance, memory, and biometric behavior must be confirmed on physical hardware before "done."
- **Localization and RTL** — Externalize every user-facing string into resources (no hard-coded text, no naive concatenation that assumes word order). Use locale-aware **dates, numbers, and plural rules**, and design layouts with **leading/trailing** (not left/right) so they **mirror for RTL** locales (Arabic, Hebrew). Allow for text expansion (other languages run longer), and test with a **pseudo-locale** to catch hard-coded strings and truncation before a translator ever sees the build.

### Decision rules

1. Design for process death first: persist state at the save boundary and restore from saved state / a deep link, never from an in-memory happy path — mobile is not a small server.
2. If offline is called a "cache," upgrade it to a sync contract: local store, ordered operation log, idempotency keys, conflict policy, retry/backoff, and a visible queued/synced/conflict status.
3. Allow last-write-wins only for low-value single-owner fields; collaborative or money/inventory data requires server authority, field-level merge, or manual resolution — a conflict policy of "hope" blocks launch.
4. Treat ~16ms as the per-frame budget at 60fps; move JSON parse, image decode, disk/DB I/O, and heavy layout off the main thread, or accept jank and ANR risk.
5. Reject any performance claim with no on-device numbers; require cold start, p95 frame time, and memory measured on a mid/low-tier device, not only a flagship.
6. Store sensitive data in Keychain/KeyStore with at-rest encryption and a retention/purge rule; never plain `UserDefaults`/`SharedPreferences` or a clear-text file.
7. Pin the public key (SPKI hash), not the leaf cert; ship a backup pin and a remote relax path so a cert renewal cannot brick the app.
8. Treat biometrics as a local unlock of a Keychain/KeyStore key with a passcode fallback, bound to a real key operation — never as the credential itself.
9. Before any server-contract change, identify the oldest installed client and keep the change backward-compatible (expand/contract) or gate old clients with a forced-upgrade screen; never break N-2 silently.
10. For a risky release, ship behind a feature flag, roll out by staged percentage gated on crash-free/ANR, and keep a remote kill switch — because store rollback is slow.
11. For a suspected leak, name the ownership: `weak`/`unowned` on iOS back-references; never hold an Activity/Context past its lifecycle on Android; confirm with a leak tool, not a guess.
12. Honor memory-pressure callbacks (`didReceiveMemoryWarning` / `onTrimMemory`) by dropping caches and releasing images, or the OS kills the app first on a low-end device.
13. Build localization and RTL in from the start: externalized strings, locale-aware dates/numbers/plurals, leading/trailing layout that mirrors for RTL, and a pseudo-locale test — not a late translation pass.
14. Never treat "passes in the simulator" as verified; confirm on a representative real device (including a low-tier one) before declaring the change done.

### Failure-repair playbook

1. **Heavy work on the main thread (jank/ANR)** → move parse/decode/I/O to a background thread, cache decoded images, and measure p95 frame time against ~16ms; if the main thread blocks, it is an ANR/watchdog risk, not a cosmetic stutter.
2. **Memory climbs and never drops (leak/retain cycle)** → find the strong reference that should be weak: `weak self` in the offending closure, a `weak` delegate, or an Activity/Context held by a static/singleton/listener on Android; confirm the fix with a leak tool, then add a regression check across navigations.
3. **Offline "cache" with no conflict rule** → replace it with a sync contract — operation log + idempotency keys + a conflict policy fit to data risk (LWW only for low-value fields) + a visible synced/conflict status; block launch until the policy exists.
4. **Server contract change with no oldest-client check** → identify the lowest installed version, make the change additive/expand-contract or gate old clients with a forced upgrade; treat breaking an installed client as an outage you cannot roll back from the server.
5. **Big-bang release with no kill switch** → put the risky path behind a flag/remote config, convert the release to a staged percentage gated on crash-free/ANR, and add a remote disable that needs no store review before shipping.
6. **Secrets in `UserDefaults`/`SharedPreferences` or a plain file** → move them to Keychain/KeyStore with at-rest encryption, add a retention/purge rule, and treat the previously stored secret as exposed (rotate it).
7. **Leaf-cert pin with no backup** → switch to an SPKI public-key pin, add a backup pin and a remote relax/kill path, and verify the renewal path so the next cert rotation does not hard-fail every install.
8. **Biometric used as the credential** → re-bind it to a key operation in Keychain/KeyStore (the biometric unlocks the key, the key authenticates), and add a passcode fallback so a biometric failure does not lock the user out.
9. **Lifecycle bug only seen on the happy path** → add explicit tests for app-switch, process death, low memory, and network loss; restore from saved state / deep link and assert the screen rebuilds correctly, not from in-memory state.
10. **Performance tuned on a flagship only** → re-measure on the mid/low-tier device most users carry, build a device-tier matrix, and address the cold start / OOM / jank that only the low tier reveals.
11. **Localization/RTL retrofit breaking layout** → externalize strings, switch constraints to leading/trailing, mirror for RTL, use locale-aware dates/plurals, and run a pseudo-locale pass to catch hard-coded text and truncation.
12. **"Done" because the simulator passed** → run on a representative physical device (and a low-tier one); confirm real memory, thermal, flash, secure-enclave, and biometric behavior before closing — the simulator hides exactly these.

### Mobile security on the device (detail)

Threat model the client as a device that can be lost, rooted, jailbroken, or have its backup read. (1) **Secure storage** — secrets, tokens, and keys go in the platform keystore (Keychain / KeyStore-backed), never in `UserDefaults` / `SharedPreferences` / a clear-text file; set the right accessibility class (e.g. only-when-unlocked, this-device-only) so a backup or a locked device does not leak them, and define a retention/purge rule. (2) **At-rest encryption** — encrypt sensitive on-device data; let the key live in the keystore/secure enclave, not in the binary. (3) **Certificate / public-key pinning** — pin the **SPKI public-key hash** (survives cert renewal when the key is reused), carry a **backup pin**, and keep a remote path to relax/disable pinning so a misconfigured pin is not a permanent, un-rollbackable outage. (4) **Biometric auth** — Face ID / Touch ID / fingerprint is a *local unlock* of a keystore-protected secret with a passcode fallback; bind "success" to an actual key operation, never trust a bare boolean, and degrade gracefully when biometry is unavailable or fails. Key-management policy, server-side authz, and the full threat model route to `security-privacy-engineering`; this skill owns the on-device hygiene.

### On-device memory management (detail)

(1) **Retain cycles & weak references (iOS/ARC)** — ARC reclaims an object when its strong references reach zero, so a cycle leaks: a closure capturing `self` strongly, a strong `delegate`, a parent⇄child strong pair, or a timer retaining its target. Break the back-edge with `weak self` (re-checked inside the closure) or `unowned` when the lifetime is guaranteed. (2) **Android Context/lifecycle leaks** — holding an `Activity`/`Context` past its lifecycle pins the entire view hierarchy: a static reference, a singleton, a long-lived listener/observer, an inner-class Handler, or a thread that outlives the screen. Use the application context where a UI context is not required, prefer lifecycle-aware components (ViewModel, lifecycle-scoped coroutines), unregister listeners in the matching teardown, and avoid non-static inner classes holding the outer Activity. (3) **Memory-pressure callbacks** — respond to `didReceiveMemoryWarning` (iOS) and `onTrimMemory` / `onLowMemory` (Android) by dropping caches, releasing decoded images and off-screen state, and shrinking in-memory buffers; an app that ignores these is the first the OS evicts on a low-RAM device, which users experience as "it reloads every time I switch back."

### On-device testing strategy (detail)

Use the **emulator/simulator** for fast inner-loop iteration; use **real devices** for anything where the simulator lies. The simulator runs on desktop RAM/CPU, never thermally throttles, has fast desktop storage, and fakes or omits the secure enclave, real biometrics, GPS/sensors, and real radio/network behavior — so memory limits, cold-start time, jank under thermal load, biometric flows, and pinning all need a physical device. Maintain a **device-tier matrix** (at least one low/mid-tier device representative of your actual users, plus current and oldest-supported OS versions), and use a **device farm** for breadth across OS versions, screen sizes, and OEM skins you cannot keep on a desk. The gate: security, performance, memory, and biometric behavior are confirmed on physical hardware before a change is called done.

### Localization and RTL (detail)

Localization is structural, not a final translation pass. Externalize every user-facing string into resource files; never concatenate sentence fragments (word order differs by language) and never hard-code text in code or layout. Use locale-aware formatting for **dates, times, numbers, currencies, and plural rules** (plural categories vary — one/few/many/other). Design layout with **leading/trailing** rather than left/right so it **mirrors automatically for RTL** locales (Arabic, Hebrew): the back button, list chevrons, and progress direction all flip. Allow **text expansion** — translations often run 30–40% longer, so fixed-width labels truncate. Validate early with a **pseudo-locale** (accented, lengthened text) to surface hard-coded strings, clipping, and layout breaks before real translations arrive.

## Հայերեն

### Գործառնական սկզբունք

Ավագ բջջային աշխատանքը decision-grade է միայն այն ժամանակ, երբ նախագծում է runtime-ի համար, որ ակտիվորեն թշնամական է, և client-ի համար, որ չես կարող ըստ պահանջի patch անել։ Backend-ը քոնն է. բջջային process-ը պարզապես վարձում ես OS-ից — այն կարող է ցանկացած պահի pause, background, throttle կամ kill լինել, network-ը կարող է operation-ի կեսին անհետանալ, device-ը կարող է flagship-ի RAM-ի մեկ տասներորդն ունենալ, և երբ binary-ն ship է լինում, այն շտկելը նշանակում է store review՝ օրերով չափվող, մինչ կոտրված version-ը ամիսներով մնում է user-ների ձեռքին։ Ուստի ամեն բջջային deliverable սկսվում է չորս չ-բանակցելի կետից․ state-ը գերապրում է process death-ին, 16ms frame budget-ը գերազանցող work-ը հեռանում է main thread-ից, sensitive data-ն encrypt-ված է at-rest, և risky behavior-ը հետշրջելի է առանց store release-ի։ Deliverable-ը հինգ ձևից մեկն է՝ mobile architecture plan, offline-sync design, performance-triage report, release/rollout plan կամ native-vs-cross-platform որոշում, և ամեն մեկը դատվում է ոչ թե իր օգտագործած անուններով, այլ նրանով, թե արդյոք դիմանում է app-switch-ի, low memory-ի, մեռած network-ի, հին տեղադրված client-ի և low-tier device-ի տակ։ Mobile-ը փոքր server չէ. այն այդպես վերաբերվելը նրա ձախողումների մեծ մասի արմատն է։

### Մեխանիզմների տեղեկագիր

- **Բջջային lifecycle-ը թշնամական է** — App-երը pause/resume են լինում, network են կորցնում, background-execution limit են ստանում և memory pressure-ի տակ OS-ի կողմից առանց զգուշացման kill են լինում։ State-ը պետք է պահպանվի ճիշտ save boundary-ում (background-ի անցնելիս, draft-ի field փոխվելիս), և navigation-ը պետք է restore լինի saved state-ից կամ deep link-ից, երբեք in-memory happy path-ից։ Process death-ը նախագծելու լռելյայն դեպքն է, ոչ բացառությունը․ lifecycle bug-ը սովորաբար երևում է միայն app-switch-ի, low memory-ի կամ slow network-ի տակ — հենց այն պայմանները, որ Wi-Fi-ի վրա արագ device-ը երբեք չի վերարտադրում։
- **Offline-first sync-ին պետք է contract, ոչ cache** — Իրական offline-ին պետք են local store (device-ի truth-ը), intent-ների ordered **operation log**, **idempotency key**-եր, որ retry-ն չկարողանա կրկնակի կիրառել, **conflict policy**, retry՝ backoff-ով, և user-տեսանելի **queued / synced / conflict** status։ Last-write-wins-ը ընդունելի է միայն low-value, single-owner field-երի համար. collaborative կամ money/inventory data-ին պետք է server authority, field-level merge կամ բացահայտ manual resolution։ Operation log-ը պետք է idempotent լինի ծայրից ծայր, որովհետև անկայուն network-ը երաշխավորում է retry-ներ, և ոչ-idempotent retry-ն կրկնակի charge կամ կրկնակի record է։
- **Performance-ը և battery-ն product feature են — 16ms/60fps frame budget-ը** — 60fps target-ը **~16.7ms per frame** է (1000ms ÷ 60). 120fps display-ը կիսում է այն մինչև ~8.3ms։ Main/UI thread-ի ամեն ինչ, որ frame-ը իր budget-ից այն կողմ է հրում — JSON parsing, image decode, սինխրոն disk կամ DB read, թանկ layout pass — drop է անում frame-ը, և drop-ված frame-ների հոսքը jank է։ Բավական երկար պահված, block-ված main thread-ը **ANR** է («Application Not Responding», Android-ում input-ի համար ~5վ) կամ iOS watchdog kill։ Ուղղումները կառուցվածքային են․ parse/decode/I/O-ն տեղափոխիր background thread, cache արա decode-ված image-ները, batch արա network call-երը, և budget արա cold start-ը։ Battery-ն նույնպես product feature է․ հարգիր background-execution limit-ները և coalesce արա wakeup-ները, որովհետև ավելորդ wakeup-ները և radio-ի օգտագործումը չափելի defect են։
- **Բջջային release մեխանիկա — staged rollout, որովհետև store rollback-ը դանդաղ է** — Չես կարող ակնթարթ հետ կանչել binary-ն. fix-ը store review-ով նոր build է (օրեր), ոչ server rollback (րոպեներ)։ Ուստի risky behavior-ը ship է լինում **feature flag / remote config**-ի հետևում, release-ները դուրս են գալիս **staged percentage**-ով (օր.՝ 1% → 5% → 20% → 50% → 100%)՝ gated **crash-free session**-ի և **ANR rate**-ի վրա, և կա **remote kill switch**, որ անջատում է risky path-ը առանց store submission-ի։ Migration-ները պետք է forward-safe լինեն և, որտեղ հնարավոր է, հետշրջելի։ Store path-ը դանդաղ path-ն է. remote path-ը քո իրական rollback-ն է։
- **Բջջային security device-ի վրա** — Secret-ները և token-ները ապրում են platform keystore-ում — iOS-ում **Keychain**, Android-ում **KeyStore**-ապահովված storage (օր.՝ EncryptedSharedPreferences / KeyStore-փաթաթված key) — երբեք plain `UserDefaults` / `SharedPreferences` կամ clear-text ֆայլում, **retention/purge rule**-ով, թե երբ է data-ն հեռացվում։ Transport-ը pin-վում է **public key (SPKI)** hash-ով, ոչ leaf certificate-ով, **backup pin**-ով և pinning-ը թուլացնելու remote path-ով, որ սովորական cert renewal-ը չկարողանա brick անել ամեն install։ **Biometric** auth-ը (Face ID / fingerprint) gate է անում *key-ի local unlock* passcode fallback-ով — այն երբեք credential-ը ինքը չէ, և biometric «yes»-ը իմաստ ունի միայն, երբ կապված է Keychain/KeyStore key operation-ի հետ։ Data-at-rest encryption-ը ենթադրում է, որ device-ը կարող է կորել, root/jailbreak արվել կամ backup-վել։
- **On-device memory management** — Բջջային memory-ն փոքր է, և OS-ը այն հետ է վերցնում՝ սպանելով քո app-ը։ iOS-ում ARC-ն ազատում է object-ը, երբ reference-ները զրոյանում են, ուստի **retain cycle**-ը (closure, որ `self`-ը strong է բռնում, strong `delegate`, երկու object, որ իրար strong են reference անում) leak է. կոտրիր այն back-reference-ի `weak`/`unowned`-ով։ Android-ում classic leak-ը **Activity / Context**-ը իր lifecycle-ից այն կողմ պահելն է — static field-ից, singleton-ից, երկար ապրող listener-ից, Handler-ից — որ pin է անում ամբողջ view tree-ն. օգտագործիր application context-ը, որտեղ տեղին է, lifecycle-aware component-ներ, և մաքրիր listener-ները։ Հարգիր **memory-pressure callback**-ները (`didReceiveMemoryWarning` / `onTrimMemory`)՝ drop անելով cache-երը և ազատելով image-ները. այն app-ը, որ անտեսում է դրանք, առաջինն է, որ OS-ը սպանում է low-end device-ի վրա։
- **On-device testing strategy** — Simulator/emulator-ը արագ է, հարմար և ստում է կարևոր բաների մասին․ այն աշխատում է desktop RAM/CPU-ի վրա, thermal throttle չի անում, ունի արագ desktop flash, և կեղծում է (կամ բաց է թողնում) secure enclave-ը, իրական biometric-ը և իրական radio վարքը։ Օգտագործիր այն արագ iteration-ի համար, բայց ստուգիր **իրական device**-ների վրա՝ **device-tier matrix**-ով (առնվազն մեկ low/mid-tier device, որ user-ների մեծ մասն ունի, ոչ միայն flagship), և օգտագործիր **device farm**՝ OS version-ների և form factor-ների լայնության համար։ Security-ն, performance-ը, memory-ն և biometric վարքը պետք է հաստատվեն ֆիզիկական hardware-ի վրա մինչև «done»-ը։
- **Localization և RTL** — Externalize արա ամեն user-facing string ռեսուրսների մեջ (ոչ hard-coded text, ոչ naive concatenation, որ word order է ենթադրում)։ Օգտագործիր locale-aware **date, number և plural rule**. և նախագծիր layout-ը **leading/trailing**-ով (ոչ left/right), որ այն **mirror լինի RTL** locale-ների համար (արաբերեն, եբրայերեն)։ Թող տեղ տուր text expansion-ի (այլ լեզուները ավելի երկար են լինում), և test արա **pseudo-locale**-ով, որ բռնես hard-coded string-ը և truncation-ը մինչև translator-ի build տեսնելը։

### Որոշման կանոններ

1. Նախ նախագծիր process death-ի համար․ state-ը պահպանիր save boundary-ում և restore արա saved state-ից / deep link-ից, երբեք in-memory happy path-ից — mobile-ը փոքր server չէ։
2. Եթե offline-ը «cache» է անվանված, բարձրացրու sync contract-ի․ local store, ordered operation log, idempotency key, conflict policy, retry/backoff և տեսանելի queued/synced/conflict status։
3. Թույլ տուր last-write-wins միայն low-value single-owner field-երին. collaborative կամ money/inventory data-ին պետք է server authority, field-level merge կամ manual resolution — «հուսանք» conflict policy-ն block է անում launch-ը։
4. Համարիր ~16ms per-frame budget-ը 60fps-ի դեպքում. JSON parse-ը, image decode-ը, disk/DB I/O-ն և թանկ layout-ը հանիր main thread-ից, կամ ընդունիր jank և ANR risk։
5. Մերժիր ցանկացած performance claim՝ առանց on-device թվերի. պահանջիր cold start, p95 frame time և memory՝ չափված mid/low-tier device-ի վրա, ոչ միայն flagship-ի։
6. Sensitive data-ն պահիր Keychain/KeyStore-ում՝ at-rest encryption-ով և retention/purge rule-ով. երբեք plain `UserDefaults`/`SharedPreferences` կամ clear-text ֆայլ։
7. Pin արա public key-ը (SPKI hash), ոչ leaf cert-ը. ship արա backup pin և remote relax path, որ cert renewal-ը չկարողանա brick անել app-ը։
8. Համարիր biometric-ը Keychain/KeyStore key-ի local unlock passcode fallback-ով, կապված իրական key operation-ի հետ — երբեք որպես credential ինքը։
9. Ցանկացած server-contract փոփոխությունից առաջ պարզիր ամենահին տեղադրված client-ը և պահիր փոփոխությունը backward-compatible (expand/contract) կամ gate արա հին client-ները forced-upgrade screen-ով. երբեք լուռ մի՛ կոտրիր N-2-ը։
10. Risky release-ի համար ship արա feature flag-ի հետևում, roll out արա staged percentage-ով՝ gated crash-free/ANR-ի վրա, և պահիր remote kill switch — որովհետև store rollback-ը դանդաղ է։
11. Կասկածվող leak-ի համար անվանի՛ր ownership-ը․ `weak`/`unowned` iOS-ի back-reference-ների համար. Android-ում երբեք Activity/Context մի՛ պահիր իր lifecycle-ից այն կողմ. հաստատիր leak tool-ով, ոչ գուշակությամբ։
12. Հարգիր memory-pressure callback-ները (`didReceiveMemoryWarning` / `onTrimMemory`)՝ drop անելով cache-երը և ազատելով image-ները, այլապես OS-ը app-ը առաջինն է սպանում low-end device-ի վրա։
13. Localization-ը և RTL-ը կառուցիր սկզբից․ externalized string, locale-aware date/number/plural, leading/trailing layout, որ mirror լինի RTL-ի համար, և pseudo-locale test — ոչ ուշ translation pass։
14. Երբեք «simulator-ում անցնում է»-ը verified մի՛ համարիր. հաստատիր representative իրական device-ի վրա (ներառյալ low-tier-ի) մինչև փոփոխությունը done հայտարարելը։

### Վերականգնման խաղագիրք

1. **Heavy work main thread-ի վրա (jank/ANR)** → parse/decode/I/O-ն տեղափոխիր background thread, cache արա decode-ված image-ները, և չափիր p95 frame time-ը ~16ms-ի դեմ. եթե main thread-ը block-վում է, դա ANR/watchdog risk է, ոչ cosmetic stutter։
2. **Memory բարձրանում է և երբեք չի իջնում (leak/retain cycle)** → գտիր strong reference-ը, որ պետք է weak լինի․ `weak self` մեղավոր closure-ում, `weak` delegate, կամ Activity/Context՝ static/singleton/listener-ից Android-ում. հաստատիր fix-ը leak tool-ով, հետո ավելացրու regression check navigation-ների ընթացքում։
3. **Offline «cache»՝ առանց conflict rule-ի** → փոխարինիր sync contract-ով — operation log + idempotency key + data risk-ին համապատասխան conflict policy (LWW միայն low-value field-երին) + տեսանելի synced/conflict status. block արա launch-ը, մինչև policy-ն գոյություն ունենա։
4. **Server contract փոփոխություն՝ առանց oldest-client ստուգման** → պարզիր ամենացածր տեղադրված version-ը, դարձրու փոփոխությունը additive/expand-contract կամ gate արա հին client-ները forced upgrade-ով. տեղադրված client-ի կոտրումը համարիր outage, որ չես կարող server-ից rollback անել։
5. **Big-bang release՝ առանց kill switch-ի** → risky path-ը դիր flag/remote config-ի հետևում, release-ը վերածիր staged percentage-ի՝ gated crash-free/ANR-ի վրա, և ավելացրու remote disable, որ store review պետք չունի, մինչև ship-ը։
6. **Secret-ներ `UserDefaults`/`SharedPreferences`-ում կամ plain ֆայլում** → տեղափոխիր Keychain/KeyStore՝ at-rest encryption-ով, ավելացրու retention/purge rule, և նախկինում պահված secret-ը համարիր exposed (rotate արա այն)։
7. **Leaf-cert pin՝ առանց backup-ի** → անցիր SPKI public-key pin-ի, ավելացրու backup pin և remote relax/kill path, և ստուգիր renewal path-ը, որ հաջորդ cert rotation-ը չ-hard-fail անի ամեն install։
8. **Biometric-ը օգտագործվում է որպես credential** → վերակապիր այն Keychain/KeyStore-ի key operation-ի հետ (biometric-ը unlock է անում key-ը, key-ը authenticate է անում), և ավելացրու passcode fallback, որ biometric-ի ձախողումը user-ին չկողպի։
9. **Lifecycle bug, որ միայն happy path-ում է երևում** → ավելացրու բացահայտ test-եր app-switch-ի, process death-ի, low memory-ի և network loss-ի համար. restore արա saved state-ից / deep link-ից և assert արա, որ screen-ը ճիշտ է վերակառուցվում, ոչ in-memory state-ից։
10. **Performance՝ tuned միայն flagship-ի վրա** → վերաչափիր mid/low-tier device-ի վրա, որ user-ների մեծ մասն ունի, կառուցիր device-tier matrix, և հասցեագրիր cold start / OOM / jank-ը, որ միայն low tier-ն է բացահայտում։
11. **Localization/RTL retrofit, որ կոտրում է layout-ը** → externalize արա string-երը, անցիր leading/trailing constraint-ի, mirror արա RTL-ի համար, օգտագործիր locale-aware date/plural, և գործարկիր pseudo-locale pass՝ hard-coded text-ը և truncation-ը բռնելու։
12. **«Done», որովհետև simulator-ն անցավ** → գործարկիր representative ֆիզիկական device-ի վրա (և low-tier-ի). հաստատիր իրական memory, thermal, flash, secure-enclave և biometric վարքը մինչև փակելը — simulator-ը հենց սրանք է թաքցնում։

### Բջջային security device-ի վրա (մանրամասն)

Threat model արա client-ը որպես device, որ կարող է կորել, root/jailbreak արվել կամ իր backup-ը կարդացվել։ (1) **Secure storage** — secret, token և key գնում են platform keystore (Keychain / KeyStore-ապահովված), երբեք `UserDefaults` / `SharedPreferences` / clear-text ֆայլ. դիր ճիշտ accessibility class (օր.՝ միայն-unlock-ի-ժամանակ, this-device-only), որ backup-ը կամ կողպված device-ը չ-leak անի դրանք, և սահմանիր retention/purge rule։ (2) **At-rest encryption** — encrypt արա sensitive on-device data-ն. թող key-ը ապրի keystore/secure enclave-ում, ոչ binary-ում։ (3) **Certificate / public-key pinning** — pin արա **SPKI public-key hash**-ը (գերապրում է cert renewal-ին, երբ key-ը վերաօգտագործվում է), կրիր **backup pin**, և պահիր remote path՝ pinning-ը թուլացնելու/անջատելու, որ սխալ configure արված pin-ը մշտական, չ-rollback-վող outage չլինի։ (4) **Biometric auth** — Face ID / Touch ID / fingerprint-ը keystore-պաշտպանված secret-ի *local unlock* է passcode fallback-ով. կապիր «success»-ը իրական key operation-ի հետ, երբեք մի՛ վստահիր մերկ boolean-ի, և graceful degrade արա, երբ biometry-ն անհասանելի է կամ ձախողվում է։ Key-management policy-ն, server կողմի authz-ը և ամբողջական threat model-ը ուղղորդվում են `security-privacy-engineering`-ին. այս skill-ը տիրում է on-device hygiene-ին։

### On-device memory management (մանրամասն)

(1) **Retain cycle և weak reference (iOS/ARC)** — ARC-ն հետ է վերցնում object-ը, երբ նրա strong reference-ները զրոյանում են, ուստի cycle-ը leak է․ closure, որ `self`-ը strong է բռնում, strong `delegate`, parent⇄child strong զույգ, կամ timer, որ իր target-ն է retain անում։ Կոտրիր back-edge-ը `weak self`-ով (closure-ի ներսում վերաստուգված) կամ `unowned`-ով, երբ lifetime-ը երաշխավորված է։ (2) **Android Context/lifecycle leak** — `Activity`/`Context`-ը իր lifecycle-ից այն կողմ պահելը pin է անում ամբողջ view hierarchy-ն․ static reference, singleton, երկար ապրող listener/observer, inner-class Handler, կամ thread, որ գերապրում է screen-ին։ Օգտագործիր application context-ը, որտեղ UI context պետք չէ, նախընտրիր lifecycle-aware component-ներ (ViewModel, lifecycle-scoped coroutine), unregister արա listener-ները համապատասխան teardown-ում, և խուսափիր non-static inner class-ից, որ outer Activity-ն է բռնում։ (3) **Memory-pressure callback** — արձագանքիր `didReceiveMemoryWarning`-ին (iOS) և `onTrimMemory` / `onLowMemory`-ին (Android)՝ drop անելով cache-երը, ազատելով decode-ված image-ները և off-screen state-ը, և փոքրացնելով in-memory buffer-ները. app-ը, որ անտեսում է սրանք, առաջինն է, որ OS-ը evict է անում low-RAM device-ի վրա, որը user-ները զգում են որպես «ամեն անգամ վերադառնալիս նորից է load անում»։

### On-device testing strategy (մանրամասն)

Օգտագործիր **emulator/simulator**-ը արագ inner-loop iteration-ի համար. օգտագործիր **իրական device**-ներ ամեն ինչի համար, որտեղ simulator-ը ստում է։ Simulator-ը աշխատում է desktop RAM/CPU-ի վրա, երբեք thermal throttle չի անում, ունի արագ desktop storage, և կեղծում կամ բաց է թողնում secure enclave-ը, իրական biometric-ը, GPS/sensor-ները և իրական radio/network վարքը — ուստի memory limit-ը, cold-start time-ը, thermal load-ի տակ jank-ը, biometric flow-ները և pinning-ը բոլորին պետք է ֆիզիկական device։ Պահիր **device-tier matrix** (առնվազն մեկ low/mid-tier device՝ քո իրական user-ներին representative, plus ընթացիկ և ամենահին-supported OS version), և օգտագործիր **device farm**՝ OS version-ների, screen size-երի և OEM skin-ների լայնության համար, որ չես կարող սեղանին պահել։ Gate-ը․ security-ն, performance-ը, memory-ն և biometric վարքը հաստատվում են ֆիզիկական hardware-ի վրա մինչև փոփոխությունը done կոչվելը։

### Localization և RTL (մանրամասն)

Localization-ը կառուցվածքային է, ոչ վերջնական translation pass։ Externalize արա ամեն user-facing string ռեսուրս ֆայլերի մեջ. երբեք մի՛ concatenate արա նախադասության հատվածներ (word order-ը լեզվից-լեզու տարբեր է) և երբեք hard-code մի՛ արա text code-ում կամ layout-ում։ Օգտագործիր locale-aware ձևաչափում **date, time, number, currency և plural rule**-ի համար (plural category-ները տարբերվում են՝ one/few/many/other)։ Նախագծիր layout-ը **leading/trailing**-ով, ոչ left/right, որ այն **ավտոմատ mirror լինի RTL** locale-ների համար (արաբերեն, եբրայերեն)․ back button-ը, list chevron-ները և progress-ի ուղղությունը բոլորը շրջվում են։ Թող տեղ տուր **text expansion**-ի — translation-ները հաճախ 30–40% ավելի երկար են, ուստի fixed-width label-ները truncate են լինում։ Validate արա շուտ **pseudo-locale**-ով (accented, երկարացված text)՝ hard-coded string-ը, clipping-ը և layout-ի կոտրումը բացահայտելու համար, մինչև իրական translation-ների գալը։
