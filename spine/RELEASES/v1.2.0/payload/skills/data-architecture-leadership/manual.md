# Data Architecture and Leadership manual

## English

### Operating principle

Senior data-architecture-and-leadership work is decision-grade only when it makes enterprise data trustworthy *before* tools multiply inconsistent truths — by fixing meaning, ownership, lineage, and decision rights, not by buying a platform. The deliverable is one of a few concrete shapes: a platform/storage decision matrix, a data contract, a modeling/grain decision, an MDM rulebook, a governance decision log, or a data-team maturity roadmap. The single discipline that governs all of them is **grain and ownership**: if nobody can say what one row means and who owns each decision, every downstream choice — the storage layer, the model, the metric definition, the contract — inherits that ambiguity. So the first move is always to pin the grain in one sentence and name the owner, then reason from there. Architecture is not a tool list; it is the set of agreements that keep data meaning the same as it moves and changes. And leadership here is sequencing: matching the architecture to the team's maturity (crawl/walk/run) so you do not hand a five-person team a data mesh it cannot run.

Answer in the lens that was asked. The **operating lens** wants a specific decision now (which storage, which model, is this change safe) → produce a matrix or contract. The **full-curriculum lens** wants the mechanisms taught end-to-end → produce the mechanism reference below, not a one-off recommendation. The **operating-data-roles lens** wants to know who owns each decision and how the team matures → keep the architecture decision-rights here and route the people/org design to `operating-data-roles`.

### Mechanism reference

- **Warehouse / lake / lakehouse / mesh** — These solve different failure modes; choose by latency, cost, governance, transaction needs, schema volatility, and domain-ownership maturity. A **warehouse** optimizes governed SQL and schema-on-write (structure enforced at write time; strong for stable, modeled analytics). A **lake** optimizes cheap raw storage and schema-on-read (any format in, structure applied at query time; strong for data science and unmodeled exploration, weak on governance). A **lakehouse** adds open table formats (Iceberg, Delta) on top of lake storage to give ACID transactions, schema evolution, and time travel — warehouse-grade reliability on lake-grade storage. **Mesh** is not a storage layer at all; it is an operating model in which domains own data *products* with contracts, SLAs, and stewards. Picking a lakehouse is a storage decision; "doing mesh" is an ownership decision, and the two must be evaluated separately even when a prompt bundles them as "lakehouse plus mesh."
- **Medallion layering (bronze / silver / gold)** — A layered refinement model on a lake/lakehouse. **Bronze (raw)** is the immutable, append-only landing zone: exactly what arrived, never edited in place — it is the system of record that makes replay and audit possible. **Silver** is cleaned, conformed, deduplicated, joined data. **Gold** is business-level aggregates and marts consumers actually query. The cardinal rule: fixes, dedupe, and corrections happen *forward* into silver/gold; mutating bronze destroys the ability to reprocess history and to prove what the source actually sent. If raw is mutable, lineage and auditability are gone.
- **3NF / Kimball / Data Vault** — These differ by grain and change handling. **3NF** normalizes to protect update integrity in operational/transactional stores (one fact in one place; minimal redundancy). **Kimball dimensional** optimizes analytics: facts at an explicit grain, conformed dimensions shared across facts, and slowly-changing-dimension (SCD) types to handle attribute history — pick it for stable, business-facing reporting. **Data Vault** separates **hubs** (business keys), **links** (relationships), and **satellites** (descriptive, time-stamped attributes) for auditability and many evolving sources — pick it when sources change often and lineage/audit is the priority. In every model the non-negotiable is the **grain**: a fact table with an undefined grain is the single most common warehouse defect, because it makes metrics double-count and joins fan out.
- **Data contracts and schema evolution** — A contract pins a producer's schema, owner, SLA, and compatibility policy so consumers do not break silently. **Backward-compatible**: new consumers can read old data (adding a nullable column). **Forward-compatible**: old consumers survive new data. **Full**: both. A schema registry (Avro/Protobuf) enforces the allowed change set. **Breaking** changes — renaming a field, narrowing a type, dropping a column — require a versioned table/topic, a migration window, and named consumer owners; if the consumers are unknown, the breaking change is frozen until they are.
- **MDM (master data management)** — Builds a golden record through **match → merge → survivorship → stewardship**. Matching combines deterministic keys (exact id) and probabilistic similarity (fuzzy name/address). Merging consolidates the matched records. **Survivorship** decides, *per attribute*, which source wins (e.g. CRM wins legal name, billing wins tax id, support wins contact preference) — without explicit survivorship rules, the "single customer view" silently becomes last-writer-wins. Stewardship is the human workflow that resolves the conflicts the rules cannot. A golden record with no survivorship table is not MDM; it is a guess.
- **Governance, ownership, and decision rights** — Governance is the set of *decisions with owners*, not a tool you install. Each critical object needs one owner and one definition: who can change this schema, who owns this metric's definition, who approves a breaking change, who arbitrates an MDM conflict. A catalog or lineage tool only matters to the extent people use it to make those decisions; a catalog nobody queries is shelfware, and lineage too noisy to answer "if I change X, who breaks?" is decoration. The leadership job is to assign these rights and standards, and to sequence them to the team's maturity.

### Decision rules

1. Pin the **grain** in one sentence before designing any table; an undefined grain is the #1 warehouse bug and makes metrics double-count.
2. Split a "lakehouse plus mesh" request into a storage decision and an ownership decision; evaluate each on its own evidence.
3. Do not endorse mesh without real domain owners, versioned contracts, SLAs, and stewards; recommend central/lakehouse until ownership is real.
4. Choose storage by scoring latency, cost, governance, transactions, schema volatility, and ownership; pick the simplest architecture that meets the hard constraints and name the binding one.
5. Declare the raw/bronze layer immutable and append-only; do fixes and dedupe forward into silver/gold, never by mutating bronze.
6. Classify every schema change as backward/forward/full/breaking before shipping; a breaking change needs a versioned table, a migration window, and named consumer owners.
7. Choose the model by grain, change rate, and audit need — 3NF for transactional integrity, Kimball for stable analytics, Data Vault for many volatile sources with lineage needs — and state the grain in each.
8. Require per-attribute survivorship for any golden record; define match → merge → survivorship → stewardship, or the single customer view becomes last-writer-wins.
9. Treat governance as decisions-with-owners; tie any catalog/lineage tool to a decision people must make, and assign one owner and one definition per metric.
10. Prune lineage to the edges that answer "if I change X, who breaks?"; column-level lineage of everything is unusable.
11. Answer a team-capability question as a crawl → walk → run sequence; never skip a stage, and never hand an immature team mesh/automated contracts/column lineage.
12. Require a jurisdiction and source for any retention/residency/PII claim; never invent a compliance threshold.
13. Gate irreversible data changes (destructive backfill, hard delete, golden-record overwrite) behind an owner, a backup/restore path, and where possible a reversible expand/contract sequence.

### Failure-repair playbook

1. **Grain is undefined** → stop the design; write the grain as one sentence ("one row = one shipped order line"), then rebuild the fact table and re-check every metric for double-counting against it.
2. **Bronze/raw is being mutated** → block the in-place edit; move the fix/dedupe forward into a silver transform, restore bronze as append-only, and confirm history can still be replayed.
3. **Mesh proposed with no ownership** → reframe as a storage decision plus an ownership-maturity gap; recommend central/lakehouse now and a contract+steward path before any domain owns a product.
4. **"Lakehouse plus mesh" bundled** → separate the two decisions; give a storage recommendation on its own evidence and an ownership recommendation on its own, and state that mesh waits for real ownership.
5. **Golden record with no survivorship** → add a per-attribute survivorship table (which source wins each field) and a stewardship workflow for conflicts; until then, label the "single customer view" as last-writer-wins.
6. **Breaking change with unknown consumers** → freeze the breaking change; inventory consumers, assign owners, choose a compatibility class, and define a versioned-table migration window before shipping.
7. **Catalog bought, no adoption** → tie the catalog to a real decision (schema-change approval, metric ownership) so people must use it; an unused catalog is not governance.
8. **Two definitions of one metric** → assign one owner and one canonical definition, point all dashboards at the source of truth, and deprecate the conflicting copy.
9. **Model chosen by preference** → re-derive the choice from grain, change rate, and audit need; if none of those force the chosen model, switch to the one the requirements actually demand.
10. **Lineage too noisy** → prune to impact-relevant edges; keep the lineage that answers "if I change X, who breaks?" and drop the rest to a diagnostic view.
11. **Maturity stage skipped** → reset to the crawl/walk/run sequence; install the missing intermediate stage (governed warehouse + grain before mesh; catalog adoption before automated contracts) rather than the leap.
12. **Invented compliance threshold** → remove the asserted number; require a jurisdiction and a cited source, or mark it verify-before-use with a placeholder.

### Coaching mode — the crawl / walk / run maturity path

When the question is about a *team's* data capability, not a single architecture decision, answer with a sequenced maturity path, not the most advanced pattern. The failure mode here is skipping stages: handing a small or immature team a data mesh, automated contract enforcement, or column-level lineage before it can run one governed warehouse with a defined grain.

- **Crawl** — one governed warehouse (or a single lakehouse), the grain of the core fact explicitly defined, basic data contracts for the few critical producers, and one named owner per critical metric. Goal: a single trustworthy source of truth that people actually use. Do not start mesh here.
- **Walk** — medallion layering (immutable bronze, conformed silver, gold marts), a catalog with *real adoption* tied to decisions, MDM on the top entity (usually customer), and compatibility-classed schema changes with a registry. Goal: refinement, discoverability, and a golden record on the entity that matters most.
- **Run** — domain ownership / mesh where domains genuinely own data products with contracts, SLAs, and stewards; automated contract enforcement in CI; and impact-pruned lineage used for change-impact analysis. Goal: federated ownership without losing consistency. Reach run only when walk is solid.

Match the recommendation to where the team is, and name the *one* next stage — not the destination — as the actionable move. The coaching deliverable is "you are at walk; here is the one thing that gets you toward run," not "here is the end-state mesh diagram."

### Գործառնական սկզբունք

Ավագ data-architecture-and-leadership աշխատանքը decision-grade է միայն այն ժամանակ, երբ կազմակերպության տվյալները վստահելի է դարձնում *նախքան* գործիքները բազմապատկեն անհամապատասխան ճշմարտությունները՝ իմաստ, ownership, lineage և decision rights ամրացնելով, ոչ թե հարթակ գնելով։ Deliverable-ը մի քանի կոնկրետ ձևից մեկն է՝ platform/storage decision matrix, data contract, modeling/grain որոշում, MDM rulebook, governance decision log, կամ թիմի maturity roadmap։ Բոլորը կառավարող միակ կարգապահությունը **grain-ն ու ownership-ն** է․ եթե ոչ ոք չի կարող ասել՝ ինչ է նշանակում մեկ row և ով է տիրում ամեն որոշմանը, ապա ամեն հետընթաց ընտրություն՝ storage layer-ը, model-ը, metric-ի սահմանումը, contract-ը, ժառանգում է այդ երկիմաստությունը։ Ուստի առաջին քայլը միշտ grain-ը մեկ նախադասությամբ ամրացնելն ու owner-ը անվանելն է, հետո՝ դրանից բխեցնելը։ Architecture-ը գործիքների ցուցակ չէ. այն այն համաձայնությունների ամբողջությունն է, որ տվյալի իմաստը պահում են նույնը, երբ այն շարժվում և փոխվում է։ Իսկ leadership-ն այստեղ հերթականացում է․ architecture-ը համապատասխանեցնել թիմի maturity-ին (crawl/walk/run), որ հնգանոց թիմին data mesh չտաս, որը նա չի կարող վարել։

### Մեխանիզմների տեղեկագիր

- **Warehouse / lake / lakehouse / mesh** — Սրանք տարբեր failure mode-եր են լուծում. ընտրությունն արա latency, cost, governance, transaction need, schema volatility և domain-ownership maturity-ով։ **Warehouse**-ը optimize է անում governed SQL-ը և schema-on-write-ը (structure-ը enforce-ված է write-ի պահին. ուժեղ է կայուն, model-ված analytics-ի համար)։ **Lake**-ը optimize է անում cheap raw storage-ը և schema-on-read-ը (ցանկացած format ներս, structure-ը կիրառվում է query-ի պահին. ուժեղ data science-ի և չ-model-ված հետազոտության համար, թույլ՝ governance-ում)։ **Lakehouse**-ը lake storage-ի վրա ավելացնում է open table format-ներ (Iceberg, Delta)՝ տալով ACID transaction, schema evolution և time travel — warehouse-grade հուսալիություն lake-grade storage-ի վրա։ **Mesh**-ը ընդհանրապես storage layer չէ. operating model է, որտեղ domain-ները տիրում են data *product*-ների՝ contract-ով, SLA-ով և steward-ով։ Lakehouse ընտրելը storage որոշում է. «mesh անելը» ownership որոշում է, և երկուսը պետք է առանձին գնահատվեն, նույնիսկ երբ prompt-ը դրանք կապկպում է որպես «lakehouse plus mesh»։
- **Medallion շերտավորում (bronze / silver / gold)** — Շերտավորված զտման model lake/lakehouse-ի վրա։ **Bronze (raw)**-ը immutable, append-only landing zone-ն է․ ճշտիվ ինչ եկավ, երբեք տեղում չ-խմբագրված — այն system of record-ն է, որ replay-ն ու audit-ը հնարավոր է դարձնում։ **Silver**-ը մաքրված, conformed, dedupe-ված, join-ված տվյալն է։ **Gold**-ը business-level aggregate-ներն ու mart-ներն են, որ consumer-ները իրականում query են անում։ Գլխավոր կանոնը․ fix-երը, dedupe-ն ու ուղղումները արվում են *առաջ*՝ silver/gold. bronze-ը mutate անելը ոչնչացնում է history-ն reprocess անելու և ապացուցելու, թե source-ն իրականում ինչ ուղարկեց, հնարավորությունը։ Եթե raw-ը mutable է, lineage-ն ու auditability-ն կորած են։
- **3NF / Kimball / Data Vault** — Սրանք տարբերվում են grain-ով և change handling-ով։ **3NF**-ը normalize է անում՝ operational/transactional store-երում update integrity պաշտպանելու համար (մեկ fact մեկ տեղում. նվազագույն redundancy)։ **Kimball dimensional**-ը optimize է անում analytics-ը․ fact-եր հստակ grain-ով, conformed dimension-ներ՝ fact-երի միջև կիսված, և slowly-changing-dimension (SCD) type-եր՝ attribute-ի history-ն վարելու համար — ընտրիր այն կայուն, business-facing reporting-ի համար։ **Data Vault**-ը բաժանում է **hub**-երը (business key), **link**-երը (relationship) և **satellite**-ները (descriptive, time-stamped attribute)՝ auditability-ի և շատ փոփոխվող source-ների համար — ընտրիր այն, երբ source-ները հաճախ են փոխվում, և lineage/audit-ը priority է։ Ամեն model-ում ոչ-բանակցելին **grain**-ն է․ չ-սահմանված grain-ով fact table-ը warehouse-ի ամենահաճախ հանդիպող defect-ն է, որովհետև metric-ները double-count է անում և join-երը fan-out։
- **Data contract և schema evolution** — Contract-ը ամրացնում է producer-ի schema-ն, owner-ը, SLA-ն և compatibility policy-ն, որ consumer-ները լուռ չկոտրվեն։ **Backward-compatible**․ new consumer-ը կարդում է old data (nullable column ավելացնելը)։ **Forward-compatible**․ old consumer-ը գոյատևում է new data-ից։ **Full**․ երկուսն էլ։ Schema registry-ն (Avro/Protobuf) enforce է անում թույլատրված change set-ը։ **Breaking** change-երը՝ field rename, type narrow, column drop, պահանջում են versioned table/topic, migration window և անվանված consumer owner. եթե consumer-ները անհայտ են, breaking change-ը freeze է, մինչև պարզվեն։
- **MDM (master data management)** — Golden record է կառուցում **match → merge → survivorship → stewardship** քայլերով։ Matching-ը զուգում է deterministic key (ճշգրիտ id) և probabilistic similarity (fuzzy name/address)։ Merge-ը համախմբում է match-ված record-ները։ **Survivorship**-ը որոշում է *ամեն attribute-ի համար*, թե որ source-ն է հաղթում (օր.՝ CRM-ը հաղթում է legal name-ում, billing-ը՝ tax id-ում, support-ը՝ contact preference-ում) — առանց հստակ survivorship rule-ի «single customer view»-ը լուռ դառնում է last-writer-wins։ Stewardship-ը մարդկային workflow-ն է, որ լուծում է այն conflict-ները, որ rule-ները չեն կարող։ Golden record առանց survivorship table-ի MDM չէ. գուշակություն է։
- **Governance, ownership և decision rights** — Governance-ը *owner ունեցող որոշումների* ամբողջությունն է, ոչ գործիք, որ install ես անում։ Ամեն կրիտիկական object-ին պետք է մեկ owner և մեկ սահմանում․ ով կարող է փոխել այս schema-ն, ով է տիրում այս metric-ի սահմանմանը, ով է approve անում breaking change-ը, ով է arbitrate անում MDM conflict-ը։ Catalog կամ lineage գործիքը կարևոր է միայն այնքանով, որքանով մարդիկ այն օգտագործում են այդ որոշումները կայացնելու համար. catalog, որ ոչ ոք չի query անում, shelfware է, և lineage, որ չափազանց աղմկոտ է «եթե X փոխեմ, ո՞վ է կոտրվում» հարցին պատասխանելու համար, դեկորացիա է։ Leadership-ի գործը այս իրավունքներն ու standard-ները նշանակելն է և թիմի maturity-ին համապատասխան հերթականացնելը։

### Որոշման կանոններ

1. Ամրացրու **grain**-ը մեկ նախադասությամբ նախքան որևէ table նախագծելը. չ-սահմանված grain-ը warehouse-ի #1 bug-ն է և metric-ները double-count է անում։
2. «Lakehouse plus mesh» հարցումը բաժանիր storage որոշման և ownership որոշման. ամեն մեկը գնահատիր իր ապացույցով։
3. Mesh մի՛ հաստատիր առանց իրական domain owner-ի, versioned contract-ի, SLA-ի և steward-ի. առաջարկիր central/lakehouse, մինչև ownership-ը իրական է։
4. Storage ընտրիր՝ score անելով latency, cost, governance, transactions, schema volatility և ownership. ընտրիր ամենապարզ architecture-ը, որ բավարարում է hard constraint-ները, և անվանի՛ր binding-ը։
5. Raw/bronze շերտը հայտարարիր immutable և append-only. fix-երն ու dedupe-ն արա առաջ՝ silver/gold, երբեք bronze-ը mutate անելով։
6. Ամեն schema change classify արա backward/forward/full/breaking՝ ship-ից առաջ. breaking change-ը պահանջում է versioned table, migration window և անվանված consumer owner։
7. Model-ը ընտրիր grain-ով, change rate-ով և audit need-ով — 3NF՝ transactional integrity-ի, Kimball՝ կայուն analytics-ի, Data Vault՝ շատ փոփոխվող source-ների lineage need-ով — և grain-ը նշիր ամեն մեկում։
8. Ցանկացած golden record-ի համար պահանջիր per-attribute survivorship. սահմանիր match → merge → survivorship → stewardship, այլապես single customer view-ը դառնում է last-writer-wins։
9. Governance-ը համարիր owner ունեցող որոշումներ. ցանկացած catalog/lineage գործիք կապիր որոշման, որ մարդիկ պետք է կայացնեն, և ամեն metric-ին նշանակիր մեկ owner և մեկ սահմանում։
10. Lineage-ը prune արա այն edge-երին, որ պատասխանում են «եթե X փոխեմ, ո՞վ է կոտրվում». ամեն ինչի column-level lineage-ն անօգտագործելի է։
11. Թիմի կարողության հարցին պատասխանիր crawl → walk → run հերթականությամբ. երբեք stage մի՛ բաց թող, և երբեք անհաս թիմին mesh/ավտոմատ contract/column lineage մի՛ տուր։
12. Ցանկացած retention/residency/PII պնդման համար պահանջիր jurisdiction և source. երբեք compliance threshold մի՛ հորինիր։
13. Անդառնալի data change-երը (destructive backfill, hard delete, golden-record overwrite) gate արա owner-ի, backup/restore path-ի և, որտեղ հնարավոր է, հետշրջելի expand/contract հերթականության հետևում։

### Վերականգնման խաղագիրք

1. **Grain-ը չ-սահմանված է** → կանգնեցրու design-ը. grain-ը գրիր մեկ նախադասությամբ («մեկ row = մեկ shipped order line»), հետո վերակառուցիր fact table-ը և ամեն metric-ը կրկին ստուգիր double-counting-ի համար դրա դեմ։
2. **Bronze/raw-ը mutate է արվում** → block արա տեղում խմբագրումը. fix-ը/dedupe-ն տար առաջ՝ silver transform-ի, վերականգնիր bronze-ը որպես append-only, և հաստատիր, որ history-ն դեռ կարող է replay-վել։
3. **Mesh է առաջարկվում առանց ownership-ի** → reframe արա որպես storage որոշում plus ownership-maturity բաց. առաջարկիր central/lakehouse հիմա և contract+steward path՝ նախքան որևէ domain product-ի owner լինի։
4. **«Lakehouse plus mesh»-ը կապկպած է** → բաժանիր երկու որոշումը. տուր storage recommendation իր ապացույցով և ownership recommendation իրով, և նշիր, որ mesh-ը սպասում է իրական ownership-ի։
5. **Golden record առանց survivorship-ի** → ավելացրու per-attribute survivorship table (որ source-ն է հաղթում ամեն field-ում) և stewardship workflow conflict-ների համար. մինչ այդ՝ «single customer view»-ը label արա որպես last-writer-wins։
6. **Breaking change անհայտ consumer-ներով** → freeze արա breaking change-ը. inventory արա consumer-ները, նշանակիր owner, ընտրիր compatibility class, և սահմանիր versioned-table migration window՝ ship-ից առաջ։
7. **Catalog գնված է, adoption չկա** → catalog-ը կապիր իրական որոշման (schema-change approval, metric ownership), որ մարդիկ ստիպված օգտագործեն. չ-օգտագործված catalog-ը governance չէ։
8. **Մեկ metric-ի երկու սահմանում** → նշանակիր մեկ owner և մեկ canonical սահմանում, բոլոր dashboard-ները ուղղիր source of truth-ին, և deprecate արա հակասող copy-ն։
9. **Model ընտրված է նախասիրությամբ** → ընտրությունը վերա-բխեցրու grain-ից, change rate-ից և audit need-ից. եթե դրանցից ոչ մեկը չի ստիպում ընտրած model-ը, անցիր այն մեկին, որ պահանջը իրականում պահանջում է։
10. **Lineage-ն չափազանց աղմկոտ է** → prune արա impact-relevant edge-երին. պահիր այն lineage-ը, որ պատասխանում է «եթե X փոխեմ, ո՞վ է կոտրվում», մնացածը գցիր diagnostic view։
11. **Maturity stage բաց է թողնված** → reset արա crawl/walk/run հերթականության. install արա բացակայող միջանկյալ stage-ը (governed warehouse + grain՝ նախքան mesh. catalog adoption՝ նախքան ավտոմատ contract), ոչ թռիչքը։
12. **Հորինված compliance threshold** → հանիր պնդված թիվը. պահանջիր jurisdiction և վկայակոչված source, կամ նշիր verify-before-use՝ placeholder-ով։

### Coaching ռեժիմ — crawl / walk / run maturity path-ը

Երբ հարցը *թիմի* տվյալների կարողության մասին է, ոչ մեկ architecture որոշման, պատասխանիր հերթականացված maturity path-ով, ոչ ամենաառաջադեմ pattern-ով։ Failure mode-ն այստեղ stage-երը բաց թողնելն է․ փոքր կամ անհաս թիմին data mesh, ավտոմատ contract enforcement կամ column-level lineage տալը՝ նախքան այն կարող է վարել մեկ governed warehouse՝ սահմանված grain-ով։

- **Crawl** — մեկ governed warehouse (կամ մեկ lakehouse), core fact-ի grain-ը հստակ սահմանված, հիմնական data contract-ներ այն մի քանի կրիտիկական producer-ի համար, և մեկ անվանված owner ամեն կրիտիկական metric-ի։ Նպատակ՝ մեկ վստահելի source of truth, որ մարդիկ իրականում օգտագործում են։ Mesh-ը այստեղ մի՛ սկսիր։
- **Walk** — medallion շերտավորում (immutable bronze, conformed silver, gold mart), catalog՝ *իրական adoption*-ով, որ կապված է որոշումներին, MDM՝ top entity-ի վրա (սովորաբար customer), և compatibility-classed schema change-եր՝ registry-ով։ Նպատակ՝ զտում, discoverability, և golden record այն entity-ի վրա, որ ամենից կարևորն է։
- **Run** — domain ownership / mesh, որտեղ domain-ները իսկապես տիրում են data product-ների՝ contract-ով, SLA-ով և steward-ով. ավտոմատ contract enforcement CI-ում. և impact-pruned lineage՝ change-impact analysis-ի համար։ Նպատակ՝ federated ownership՝ առանց consistency կորցնելու։ Run-ին հասիր միայն, երբ walk-ը ամուր է։

Recommendation-ը համապատասխանեցրու, թե թիմը որտեղ է, և անվանի՛ր *մեկ* հաջորդ stage-ը — ոչ destination-ը — որպես actionable move։ Coaching deliverable-ը «դու walk-ում ես. ահա այն մեկ բանը, որ քեզ run-ի կողմ է տանում» է, ոչ «ահա end-state mesh-ի diagram-ը»։
