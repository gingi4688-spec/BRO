# Databases and Storage Engineering manual

## English

### Operating principle

Senior database and storage work is decision-grade only when it starts from the invariant — the state that must never exist — and pairs every recommendation with an auditable mechanism: a query plan, an isolation-to-anomaly mapping, an amplification or compaction model, a partition behavior, or a recovery procedure. The deliverable is one of a few shapes: a query review, a schema-and-index plan, a consistency/isolation decision, a multi-store data architecture, or a migration/recovery plan. Two guardrails govern all of them. First, never recommend an index without the query shape and EXPLAIN — an index proposed from a column name is a guess. Second, never promise correctness without naming what breaks under concurrency and under partition — isolation chosen by default and consistency claimed as "CA under partition" are the two ways a confident answer is silently wrong. Correctness is not the absence of errors in a demo; it is an invariant that cannot be violated by the concurrency, the partition, the crash, and the migration the system will actually meet.

### Mechanism reference

- **Isolation levels and anomalies** — Isolation levels map to the anomalies they prevent. Read uncommitted permits dirty reads; read committed prevents dirty reads but allows non-repeatable reads; repeatable read stabilizes the rows a transaction has read but may still allow phantoms depending on the engine; serializable behaves as if transactions ran one at a time. MVCC keeps old row versions so readers see a consistent snapshot while writers continue; locking blocks conflicting operations instead. Choose the isolation level from the business invariant, not from the engine default.
- **Snapshot isolation and write skew** — Snapshot isolation (what many engines call "repeatable read") gives each transaction a consistent snapshot taken at start and prevents dirty/non-repeatable reads and lost updates on the same row. But it permits **write skew**: two transactions read the same set, each decides its write is safe against the snapshot, and each writes a *different* row — together violating a multi-row invariant that neither violated alone. The canonical case: two doctors both on call, each transaction checks "at least one other is on call," sees the other, and takes itself off duty — leaving zero. SI sees no write-write conflict because the rows differ. The fixes: `SERIALIZABLE` isolation (which detects the read-write dependency cycle and aborts one), materialize the conflict as a single row both transactions lock `FOR UPDATE`, or enforce the invariant with a database constraint.
- **MVCC garbage, autovacuum, and bloat (Postgres-style)** — Under MVCC an `UPDATE` or `DELETE` does not overwrite in place; it writes a new row version and leaves the old one as a **dead tuple** that is still needed by any older snapshot. Once no snapshot needs it, the dead tuple is garbage. **Autovacuum** reclaims that space for reuse and updates the planner statistics and the visibility map. If autovacuum cannot keep up — because write volume is high, autovacuum is throttled too low, or a **long-running transaction holds an old snapshot** that keeps dead tuples "still needed" — dead tuples accumulate and the table and its indexes **bloat**: they occupy far more pages than the live data, so scans read more pages and slow down. The cure is to fix the cause (kill or shorten the long transaction, tune autovacuum to run more aggressively on hot tables) and reclaim space; throwing hardware at a bloat problem hides it. Vacuum also advances the transaction-id frontier to prevent wraparound.
- **WAL, checkpoints, and crash recovery** — A durable database writes changes to a **write-ahead log (WAL)** before applying them to the data pages: the log record is flushed to disk first, so a committed transaction survives a crash even if its data pages were still in memory. A **checkpoint** periodically flushes dirty data pages to disk and records a log position, bounding how much WAL must be replayed after a crash. On restart, recovery **replays the WAL from the last checkpoint** (redo) to bring data pages forward and rolls back uncommitted transactions (undo). This is also the basis of **point-in-time recovery (PITR)**: a base backup plus the archived WAL replayed to a chosen target time. Tuning trades off: more frequent checkpoints mean shorter recovery but more steady I/O; archived WAL is what makes PITR and physical replication possible. This is the crash-recovery model for in-place engines, distinct from the LSM WAL+SSTable path below.
- **Locking, deadlocks, and queue patterns** — Writers take row/page locks; readers under MVCC usually do not block writers. A **deadlock** is a cycle: transaction 1 holds lock A and waits for B, transaction 2 holds B and waits for A. The engine's **deadlock detector** finds the cycle and aborts one transaction as the victim (the application must retry it). The prevention is **consistent lock ordering** — always acquire locks in the same global order (e.g. by primary key ascending) so a cycle cannot form — plus keeping transactions short so locks are held briefly. `SELECT ... FOR UPDATE` takes an explicit row lock for a read-modify-write so a concurrent transaction cannot change the row underneath you (the lost-update fix). For a **work queue / job table**, `SELECT ... FOR UPDATE SKIP LOCKED` lets each of N workers claim a batch of *unlocked* rows and skip rows another worker already holds: workers pull disjoint jobs without blocking and without double-processing. Plain `SELECT` lets two workers grab the same job; plain `FOR UPDATE` makes the workers queue behind one lock.
- **B-trees and LSM trees** — B-trees update pages in place and give ordered range reads; the cost is page splits and random writes, and the WAL protects each in-place change. LSM trees write to a WAL and an in-memory memtable, flush sorted SSTables, then compact them in the background; this raises write throughput but creates **read amplification** (a key may live in several SSTables) and **space amplification** (overlapping data before compaction), mitigated by bloom filters (skip SSTables that cannot hold the key) and a compaction strategy. Choose B-tree for in-place-update, point-and-range OLTP; consider LSM for write-heavy, high-ingest, range-scan workloads.
- **CAP / PACELC** — During a network **partition** you must choose: refuse some operations to keep **consistency** (CP), or keep serving possibly-stale data for **availability** (AP). You cannot have both during a partition — "CA under partition" is not an option; partition tolerance is not negotiable on a real network. **PACELC** extends it: even with no partition (Else), you still trade **latency** against **consistency** (synchronous replication is consistent but slower; asynchronous is faster but can serve stale reads). A payment ledger chooses CP — refuse rather than double-spend. A social feed usually chooses AP — a slightly stale feed is fine and self-repairs. Wrong-but-fast is unacceptable for money, access control, and legal records.
- **Indexing and query plans** — An index helps only when predicate order and selectivity fit the query. Index column order is **equality predicates → range/inequality → `ORDER BY` column**, so equality narrows first and the order is already satisfied without a sort. A **covering index** (`INCLUDE` the selected columns) answers the query from the index alone, removing the table lookup — e.g. `(user_id, created_at) INCLUDE (status, total)` for recent orders by user. Always read **EXPLAIN** for scan type (seq vs index), estimated vs actual rows (a large gap means stale statistics or skew), join order and method, and any sort/hash that **spills** to disk. The **N+1 problem** is one query per parent row to fetch its children; replace it with a single batched query (`IN (ids)` or a join).

### Decision rules

1. Start from the invariant — the state that must never exist — and choose isolation, indexes, partitioning, and stores to protect it; never start from the schema or the engine.
2. For a slow query, read EXPLAIN (scan type, estimated vs actual rows, join order, sort/hash spill) before proposing any index; an index without the query shape and the plan is a guess.
3. Order index columns equality → range → `ORDER BY`, and use a covering `INCLUDE` to remove the table lookup; the wrong column order makes the index unusable.
4. Replace one-query-per-parent-row (N+1) with a single batched query (`IN (ids)` or a join); the tell is query count scaling with result rows.
5. Fix duplicate/lost updates with `SELECT FOR UPDATE`, an atomic update, an idempotency key, or higher isolation — not with more retries.
6. Under snapshot isolation, guard cross-row invariants against write skew with `SERIALIZABLE`, a single locked conflict row, or a constraint; SI is not "serializable enough."
7. Choose CP vs AP from the invariant (money/access/legal → CP; staleness acceptable and repairable → AP), state the partition behavior and the repair path, and never claim "CA under partition."
8. Route read-your-writes paths (confirmation, profile edit) to the primary or a read-your-writes token; only lag-tolerant reads go to replicas, with a stated lag bound.
9. Choose the storage engine from write/read/space amplification and compaction cost: B-tree for in-place point/range OLTP, LSM for write-heavy high-ingest range scans — not from fashion.
10. When MVCC writes/scans degrade, check dead tuples, autovacuum lag, and any long-running transaction holding an old snapshot before adding hardware; cure the cause and reclaim bloat.
11. Prevent recurring deadlocks by imposing a consistent global lock order and keeping transactions short; treat each deadlock victim as a retry, and analyze which two lock orders collide.
12. Claim work-queue rows with `SELECT FOR UPDATE SKIP LOCKED` so N workers pull disjoint jobs without blocking or double-processing; plain `SELECT` double-processes and plain `FOR UPDATE` serializes.
13. Change a live table with expand/contract (add backward-compatible, dual-write/dual-read, batch backfill, switch reads, drop old), never an atomic destructive cutover with no rollback.
14. Size checkpoint frequency and WAL archiving to the recovery objective: more frequent checkpoints shorten replay; archived WAL enables PITR and physical replication.
15. Treat a backup as untested until a restore has succeeded and the recovery time is measured; gate irreversible/data-loss changes behind explicit owner approval with a stated backup/restore path.

### Failure-repair playbook

1. **Index proposed from a column name** → stop; pull the query and run EXPLAIN, then design the index from equality/range/order and selectivity, and confirm a covering `INCLUDE` is warranted before shipping it.
2. **N+1 or table lookup per row** → batch the children into one query (`IN`/join) and add a covering index so the parent query is answered from the index alone; re-run EXPLAIN to confirm the lookups are gone.
3. **Isolation taken from the default** → name the invariant, map it to the anomaly that would break it, and raise isolation (or add a constraint / explicit lock) to exactly the level the invariant needs.
4. **Write skew under snapshot isolation** → materialize the conflict (lock a single guard row `FOR UPDATE`), or move to `SERIALIZABLE`, or enforce the multi-row rule as a database constraint; do not assume SI is serializable.
5. **Lost update from read-modify-write** → replace the read-then-write with an atomic update, or take `SELECT FOR UPDATE` on the row, or use an optimistic version column that fails the second writer.
6. **"CA under partition" or a consistency promise with no partition story** → restate as CP or AP, describe exactly which operations refuse or which reads go stale during a partition, and name the repair path afterward.
7. **Read-your-writes served from a lagging replica** → route that path to the primary (or a read-your-writes token), and reserve replica reads for lag-tolerant paths with an explicit lag bound.
8. **MVCC bloat and degrading scans** → find and kill/shorten the long transaction pinning the snapshot, tune autovacuum to run aggressively on the hot table, reclaim the bloat, and refresh statistics — before considering more hardware.
9. **Recurring deadlocks** → read the deadlock log to find the two colliding lock orders, impose one consistent global order, shorten the transactions, and make the application retry the aborted victim.
10. **Queue table double-processing or serializing** → switch the claim query to `FOR UPDATE SKIP LOCKED` so workers take disjoint unlocked rows; add a status/lease column so a crashed worker's rows are reclaimed.
11. **Destructive migration with no rollback** → convert it to expand/contract (backward-compatible add, dual-write/dual-read, batched backfill, switch reads, drop later), and stage a tested rollback and backup before touching the live table.
12. **"We have backups"** → run an actual restore into a scratch instance, measure the recovery time against the RTO, and test PITR (base backup + WAL replay to a target time) before trusting the claim.

### MVCC, vacuum, and bloat (operational detail)

Under MVCC, every `UPDATE`/`DELETE` leaves a dead tuple visible until no snapshot needs it. Autovacuum reclaims that space, refreshes planner statistics, and maintains the visibility map (which lets index-only scans skip the heap). Three things break it: write volume outrunning the autovacuum rate, autovacuum throttled too conservatively for a hot table, and — most insidious — a long-running transaction (an open analytics query, an idle-in-transaction connection) that holds an old snapshot so dead tuples stay "still needed" and cannot be reclaimed anywhere in the database. The symptom is a table whose on-disk size and index size grow far past the live row count while scans slow. The fix order is: find the oldest snapshot and end the transaction holding it; tune autovacuum thresholds/cost limits for the hot table; reclaim the bloat; refresh statistics. Adding CPU or RAM treats the symptom, not the garbage.

### Crash recovery: WAL and checkpoints (in-place engines)

The write-ahead rule is that the log record for a change is durably flushed *before* the data page is, so a committed transaction is recoverable even if its data page never reached disk. A checkpoint flushes dirty pages and records a log position; recovery after a crash replays WAL from the last checkpoint (redo) and undoes uncommitted work. The checkpoint interval is a tradeoff: frequent checkpoints shorten recovery time but raise steady write I/O; infrequent checkpoints do the reverse. Archived WAL beyond the live segments is what enables point-in-time recovery and physical replication — without it, the backup is only as fresh as the last base snapshot. This in-place WAL+checkpoint model is the recovery path for B-tree engines; an LSM engine recovers by replaying its own WAL into the memtable and trusting already-flushed SSTables.

## Հայերեն

### Գործառնական սկզբունք

Ավագ database և storage աշխատանքը decision-grade է միայն այն ժամանակ, երբ սկսում է invariant-ից — այն state-ից, որ երբեք չպետք է գոյություն ունենա — և ամեն recommendation զուգում է auditable mechanism-ի հետ՝ query plan, isolation-ից anomaly-ի քարտեզում, amplification կամ compaction model, partition behavior կամ recovery procedure։ Deliverable-ը մի քանի ձևից մեկն է՝ query review, schema-and-index plan, consistency/isolation որոշում, multi-store data architecture կամ migration/recovery plan։ Երկու guardrail կառավարում է բոլորը։ Առաջին՝ երբեք index մի՛ առաջարկիր առանց query shape-ի և EXPLAIN-ի — սյունի անունից առաջարկված index-ը գուշակություն է։ Երկրորդ՝ երբեք correctness մի՛ խոստացիր առանց անվանելու, թե ինչ է կոտրվում concurrency-ի և partition-ի տակ — default-ով ընտրված isolation-ը և «CA under partition» պնդված consistency-ն այն երկու ձևն են, որով վստահ պատասխանը լուռ սխալ է լինում։ Correctness-ը demo-ում error-ների բացակայությունը չէ. այն invariant է, որ չի կարող խախտվել այն concurrency-ով, partition-ով, crash-ով և migration-ով, որ համակարգն իրականում կհանդիպի։

### Մեխանիզմների տեղեկագիր

- **Isolation level-ներ և anomaly-ներ** — Isolation level-ները քարտեզվում են այն anomaly-ներին, որ կանխում են։ Read uncommitted-ը թույլ է տալիս dirty read. read committed-ը կանխում է dirty read-ը, բայց թողնում non-repeatable read. repeatable read-ը կայունացնում է transaction-ի կարդացած row-երը, բայց engine-ից կախված կարող է դեռ թողնել phantom. serializable-ը վարվում է, կարծես transaction-ները մեկ առ մեկ են աշխատել։ MVCC-ն պահում է old row version-ներ, որ reader-ները տեսնեն consistent snapshot, մինչ writer-ները շարունակվում են. locking-ը փոխարենը block է անում conflict operation-ները։ Isolation level-ը ընտրիր business invariant-ից, ոչ engine default-ից։
- **Snapshot isolation և write skew** — Snapshot isolation-ը (որ շատ engine-ներ կոչում են «repeatable read») ամեն transaction-ի տալիս է start-ին վերցված consistent snapshot և կանխում է dirty/non-repeatable read-ը և նույն row-ի lost update-ը։ Բայց այն թույլ է տալիս **write skew**․ երկու transaction կարդում են նույն set-ը, ամեն մեկը որոշում է, որ իր write-ը ապահով է snapshot-ի դեմ, և ամեն մեկը գրում է *տարբեր* row — միասին խախտելով multi-row invariant, որ ոչ մեկը մենակ չէր խախտում։ Canonical դեպքը՝ երկու բժիշկ երկուսն էլ on call, ամեն transaction ստուգում է «առնվազն մեկ ուրիշը on call է», տեսնում է մյուսին և իրեն հանում duty-ից — թողնելով զրո։ SI-ն write-write conflict չի տեսնում, որովհետև row-երը տարբեր են։ Ուղղումները՝ `SERIALIZABLE` isolation (որ հայտնաբերում է read-write dependency cycle-ը և abort անում մեկը), conflict-ը materialize արա որպես մեկ row, որ երկու transaction էլ lock են անում `FOR UPDATE`-ով, կամ invariant-ը enforce արա database constraint-ով։
- **MVCC garbage, autovacuum և bloat (Postgres-style)** — MVCC-ի տակ `UPDATE` կամ `DELETE`-ը տեղում չի վերագրում. գրում է նոր row version և հին-ը թողնում որպես **dead tuple**, որ դեռ պետք է ցանկացած ավելի հին snapshot-ի։ Երբ ոչ մի snapshot-ի պետք չէ, dead tuple-ը garbage է։ **Autovacuum**-ը այդ տարածքը վերադարձնում է վերաօգտագործման, թարմացնում planner statistics-ը և visibility map-ը։ Եթե autovacuum-ը չի հասցնում — որովհետև write volume-ը բարձր է, autovacuum-ը չափազանց ցածր է throttle-ված, կամ **երկար-աշխատող transaction-ը պահում է old snapshot**, որ dead tuple-ները պահում է «դեռ պետք»-ի վիճակում — dead tuple-ները կուտակվում են, և table-ը ու իր index-ները **bloat** են լինում․ զբաղեցնում են շատ ավելի շատ page, քան live data-ն, ուստի scan-ը ավելի շատ page է կարդում և դանդաղում։ Բուժումը՝ ուղղիր պատճառը (kill կամ կարճացրու երկար transaction-ը, tune արա autovacuum-ը hot table-ի վրա ավելի ագրեսիվ աշխատելու) և վերադարձրու տարածքը. bloat խնդրին hardware նետելը թաքցնում է այն։ Vacuum-ը նաև առաջ է տանում transaction-id frontier-ը՝ wraparound-ը կանխելու համար։
- **WAL, checkpoint և crash recovery** — Durable database-ը փոփոխությունները գրում է **write-ahead log (WAL)**-ում մինչ data page-երին կիրառելը․ log record-ը նախ flush է լինում disk, ուստի commit-ած transaction-ը գոյատևում է crash-ին, նույնիսկ եթե իր data page-երը դեռ memory-ում էին։ **Checkpoint**-ը պարբերաբար flush է անում dirty data page-երը disk և գրանցում log position. սահմանափակում է, թե որքան WAL պետք է replay լինի crash-ից հետո։ Restart-ին recovery-ն **replay է անում WAL-ը վերջին checkpoint-ից** (redo)՝ data page-երը առաջ բերելու, և roll back է անում uncommitted transaction-ները (undo)։ Սա նաև **point-in-time recovery (PITR)**-ի հիմքն է․ base backup plus archived WAL՝ replay արած ընտրված target time-ին։ Tuning-ը trade-off է․ ավելի հաճախ checkpoint նշանակում է ավելի կարճ recovery, բայց ավելի շատ steady I/O. archived WAL-ն այն է, ինչ հնարավոր է դարձնում PITR-ը և physical replication-ը։ Սա in-place engine-ների crash-recovery model-ն է, տարբեր ստորև LSM-ի WAL+SSTable path-ից։
- **Locking, deadlock և queue pattern-ներ** — Writer-ները վերցնում են row/page lock. MVCC-ի տակ reader-ները սովորաբար writer չեն block անում։ **Deadlock**-ը cycle է․ transaction 1-ը պահում է lock A և սպասում B-ին, transaction 2-ը պահում է B և սպասում A-ին։ Engine-ի **deadlock detector**-ը գտնում է cycle-ը և abort անում մեկ transaction որպես victim (app-ը պետք է retry անի այն)։ Կանխումը՝ **հետևողական lock ordering** — միշտ lock-երը վերցրու նույն global կարգով (օր.՝ primary key-ով աճման), որ cycle չկարողանա ձևավորվել — plus transaction-ները կարճ պահել, որ lock-երը կարճ ժամանակ պահվեն։ `SELECT ... FOR UPDATE`-ը explicit row lock է վերցնում read-modify-write-ի համար, որ concurrent transaction-ը row-ը քո տակից չփոխի (lost-update-ի ուղղումը)։ **Work queue / job table**-ի համար `SELECT ... FOR UPDATE SKIP LOCKED`-ը թույլ է տալիս N worker-ից ամեն մեկին claim անել *unlocked* row-երի batch և բաց թողնել row-երը, որ ուրիշ worker արդեն պահում է․ worker-ները քաշում են disjoint job-եր՝ առանց block-ի և առանց double-process-ի։ Պարզ `SELECT`-ը թույլ է տալիս երկու worker-ի վերցնել նույն job-ը. պարզ `FOR UPDATE`-ը worker-ներին հերթ է կանգնեցնում մեկ lock-ի հետևում։
- **B-tree և LSM tree** — B-tree-ը page-երը update է անում տեղում և տալիս ordered range read. cost-ը page split-ն ու random write-ն է, և WAL-ը պաշտպանում է ամեն in-place փոփոխությունը։ LSM tree-ն գրում է WAL-ի և in-memory memtable-ի, flush է անում sorted SSTable, հետո background-ում compact է անում. սա բարձրացնում է write throughput-ը, բայց ստեղծում **read amplification** (key-ը կարող է ապրել մի քանի SSTable-ում) և **space amplification** (overlapping data մինչ compaction), որ մեղմվում են bloom filter-ով (բաց թող SSTable-ները, որ չեն կարող key-ը պահել) և compaction strategy-ով։ B-tree ընտրիր in-place-update, point-and-range OLTP-ի համար. LSM դիտարկիր write-heavy, high-ingest, range-scan workload-ի համար։
- **CAP / PACELC** — Network **partition**-ի ժամանակ պետք է ընտրես․ որոշ operation մերժիր՝ **consistency** պահելու (CP), կամ շարունակիր serve անել հնարավոր stale data՝ **availability**-ի համար (AP)։ Partition-ի ժամանակ երկուսն էլ հնարավոր չեն — «CA under partition» option չէ. partition tolerance-ը իրական network-ում բանակցելի չէ։ **PACELC**-ը ընդլայնում է․ նույնիսկ առանց partition-ի (Else), դու դեռ trade-off ունես **latency** ընդդեմ **consistency**-ի (synchronous replication-ը consistent է, բայց դանդաղ. asynchronous-ը արագ է, բայց կարող է stale read serve անել)։ Payment ledger-ը ընտրում է CP — մերժիր, քան double-spend անես։ Social feed-ը սովորաբար ընտրում է AP — մի փոքր stale feed-ը նորմալ է և ինքն իրեն repair է լինում։ Wrong-but-fast-ը անընդունելի է money-ի, access control-ի և legal record-ի համար։
- **Indexing և query plan-ներ** — Index-ը օգնում է միայն, երբ predicate order-ը և selectivity-ն համապատասխանում են query-ին։ Index-ի սյունի կարգը **equality predicate → range/inequality → `ORDER BY` սյուն** է, որ equality-ն նախ narrow անի, և order-ը արդեն բավարարված լինի առանց sort-ի։ **Covering index**-ը (selected սյուները `INCLUDE` արած) query-ին պատասխանում է միայն index-ից՝ հանելով table lookup-ը — օր.՝ `(user_id, created_at) INCLUDE (status, total)` user-ի recent orders-ի համար։ Միշտ EXPLAIN կարդա scan type-ի (seq ընդդեմ index), estimated ընդդեմ actual rows-ի (մեծ բացը նշանակում է stale statistics կամ skew), join order-ի և method-ի, և ցանկացած sort/hash-ի, որ **spill** է անում disk։ **N+1 խնդիրը** ամեն parent row-ի համար մեկ query է իր child-երը բերելու. փոխարինիր մեկ batched query-ով (`IN (ids)` կամ join)։

### Որոշման կանոններ

1. Սկսիր invariant-ից — այն state-ից, որ երբեք չպետք է գոյություն ունենա — և ընտրիր isolation, index, partitioning և store՝ այն պաշտպանելու. երբեք մի՛ սկսիր schema-ից կամ engine-ից։
2. Slow query-ի համար կարդա EXPLAIN (scan type, estimated ընդդեմ actual rows, join order, sort/hash spill) մինչ որևէ index առաջարկելը. index առանց query shape-ի և plan-ի գուշակություն է։
3. Index-ի սյուները դասավորիր equality → range → `ORDER BY`, և օգտագործիր covering `INCLUDE`՝ table lookup-ը հանելու. սխալ սյունի կարգը index-ը դարձնում է անօգտագործելի։
4. One-query-per-parent-row (N+1)-ը փոխարինիր մեկ batched query-ով (`IN (ids)` կամ join). tell-ը՝ query-ների քանակը մեծանում է result row-երի հետ։
5. Duplicate/lost update-ը ուղղիր `SELECT FOR UPDATE`-ով, atomic update-ով, idempotency key-ով կամ ավելի բարձր isolation-ով, ոչ ավելի շատ retry-ով։
6. Snapshot isolation-ի տակ cross-row invariant-ները պաշտպանիր write skew-ից `SERIALIZABLE`-ով, մեկ lock-ված conflict row-ով կամ constraint-ով. SI-ն «serializable-enough» չէ։
7. CP ընդդեմ AP ընտրիր invariant-ից (money/access/legal → CP. staleness acceptable և repairable → AP), նշիր partition behavior-ը և repair path-ը, և երբեք «CA under partition» մի՛ պնդիր։
8. Read-your-writes path-երը (confirmation, profile edit) ուղղորդիր primary-ին կամ read-your-writes token-ին. միայն lag-հանդուրժող read-երը գնում են replica՝ նշված lag bound-ով։
9. Storage engine-ը ընտրիր write/read/space amplification-ից և compaction cost-ից․ B-tree՝ in-place point/range OLTP-ի, LSM՝ write-heavy high-ingest range scan-ի համար, ոչ նորաձևությունից։
10. Երբ MVCC write/scan-ը degrade է անում, ստուգիր dead tuple, autovacuum lag և old snapshot պահող ցանկացած երկար transaction մինչ hardware ավելացնելը. ուղղիր պատճառը և վերադարձրու bloat-ը։
11. Կրկնվող deadlock-ները կանխիր հետևողական global lock order պարտադրելով և transaction-ները կարճ պահելով. ամեն deadlock victim համարիր retry, և վերլուծիր, որ երկու lock order է բախվում։
12. Work-queue row-երը claim արա `SELECT FOR UPDATE SKIP LOCKED`-ով, որ N worker-ը disjoint job քաշի՝ առանց block-ի կամ double-process-ի. պարզ `SELECT`-ը double-process է անում, պարզ `FOR UPDATE`-ը serialize։
13. Live table-ը փոխիր expand/contract-ով (backward-compatible ավելացրու, dual-write/dual-read, batch backfill, switch read-երը, drop հին-ը), ոչ երբեք atomic destructive cutover-ով՝ առանց rollback-ի։
14. Checkpoint-ի հաճախականությունը և WAL archiving-ը size արա recovery objective-ին․ ավելի հաճախ checkpoint-ը կարճացնում է replay-ը. archived WAL-ը հնարավոր է դարձնում PITR-ը և physical replication-ը։
15. Backup-ը համարիր չստուգված, մինչև restore-ը հաջողի և recovery time-ը չափվի. անդառնալի/data-loss change-երը gate արա հստակ owner approval-ի հետևում՝ նշված backup/restore path-ով։

### Վերականգնման խաղագիրք

1. **Index առաջարկված սյունի անունից** → կանգնի՛ր. քաշիր query-ն և գործարկիր EXPLAIN, հետո index-ը նախագծիր equality/range/order-ից և selectivity-ից, և հաստատիր, որ covering `INCLUDE`-ը արդարացված է մինչ ship-ը։
2. **N+1 կամ table lookup ամեն row-ի** → child-երը batch արա մեկ query-ի (`IN`/join) և ավելացրու covering index, որ parent query-ն պատասխանվի միայն index-ից. վերագործարկիր EXPLAIN՝ հաստատելու, որ lookup-ները գնացել են։
3. **Isolation վերցված default-ից** → անվանի՛ր invariant-ը, քարտեզիր այն anomaly-ին, որ կկոտրեր այն, և բարձրացրու isolation-ը (կամ ավելացրու constraint / explicit lock) ճիշտ այն level-ին, որ invariant-ին պետք է։
4. **Write skew snapshot isolation-ի տակ** → materialize արա conflict-ը (lock արա մեկ guard row `FOR UPDATE`-ով), կամ անցիր `SERIALIZABLE`-ի, կամ multi-row rule-ը enforce արա database constraint-ով. մի՛ ենթադրիր, որ SI-ն serializable է։
5. **Lost update read-modify-write-ից** → read-then-write-ը փոխարինիր atomic update-ով, կամ վերցրու `SELECT FOR UPDATE` row-ի վրա, կամ օգտագործիր optimistic version սյուն, որ երկրորդ writer-ին fail անի։
6. **«CA under partition» կամ consistency խոստում առանց partition story-ի** → վերաձևակերպիր որպես CP կամ AP, նկարագրիր հստակ, որ operation-ները մերժվում են կամ որ read-երը stale են լինում partition-ի ժամանակ, և անվանիր repair path-ը հետո։
7. **Read-your-writes serve-ված lagging replica-ից** → այդ path-ը ուղղորդիր primary-ին (կամ read-your-writes token-ին), և replica read-երը պահիր lag-հանդուրժող path-երի համար՝ explicit lag bound-ով։
8. **MVCC bloat և degrade-վող scan** → գտիր և kill/կարճացրու snapshot-ը pin անող երկար transaction-ը, tune արա autovacuum-ը hot table-ի վրա ագրեսիվ աշխատելու, վերադարձրու bloat-ը, և թարմացրու statistics-ը — մինչ ավելի շատ hardware դիտարկելը։
9. **Կրկնվող deadlock-ներ** → կարդա deadlock log-ը՝ գտնելու երկու բախվող lock order-ը, պարտադրիր մեկ հետևողական global order, կարճացրու transaction-ները, և app-ին տուր abort-ված victim-ը retry անելու։
10. **Queue table double-process կամ serialize** → claim query-ն փոխիր `FOR UPDATE SKIP LOCKED`-ի, որ worker-ները disjoint unlocked row վերցնեն. ավելացրու status/lease սյուն, որ crash-ած worker-ի row-երը վերադարձվեն։
11. **Destructive migration առանց rollback-ի** → փոխիր expand/contract-ի (backward-compatible add, dual-write/dual-read, batched backfill, switch read-երը, drop հետո), և stage արա ստուգված rollback և backup մինչ live table-ին դիպչելը։
12. **«Backup ունենք»** → գործարկիր իրական restore scratch instance-ի մեջ, չափիր recovery time-ը RTO-ի դեմ, և test արա PITR (base backup + WAL replay target time-ին) մինչ պնդմանը վստահելը։

### MVCC, vacuum և bloat (operational մանրամասն)

MVCC-ի տակ ամեն `UPDATE`/`DELETE` թողնում է dead tuple, որ տեսանելի է, մինչև ոչ մի snapshot-ի պետք լինի։ Autovacuum-ը վերադարձնում է այդ տարածքը, թարմացնում planner statistics-ը և maintain է անում visibility map-ը (որ index-only scan-ին թույլ է տալիս բաց թողնել heap-ը)։ Երեք բան կոտրում է այն․ write volume-ը գերազանցում է autovacuum-ի rate-ը, autovacuum-ը չափազանց պահպանողական է throttle-ված hot table-ի համար, և — ամենավտանգավորը — երկար-աշխատող transaction-ը (բաց analytics query, idle-in-transaction connection), որ պահում է old snapshot, ուստի dead tuple-ները մնում են «դեռ պետք» և չեն կարող վերադարձվել database-ում ոչ մի տեղ։ Symptom-ը այն table-ն է, որի on-disk size-ը և index size-ը մեծանում են շատ ավելի, քան live row count-ը, մինչ scan-ը դանդաղում է։ Ուղղման կարգը՝ գտիր ամենահին snapshot-ը և ավարտիր այն պահող transaction-ը. tune արա autovacuum threshold/cost limit-ները hot table-ի համար. վերադարձրու bloat-ը. թարմացրու statistics-ը։ CPU կամ RAM ավելացնելը symptom-ն է բուժում, ոչ garbage-ը։

### Crash recovery․ WAL և checkpoint (in-place engine-ներ)

Write-ahead rule-ն այն է, որ փոփոխության log record-ը durably flush է լինում *մինչ* data page-ը, ուստի commit-ած transaction-ը recoverable է, նույնիսկ եթե իր data page-ը երբեք disk չհասավ։ Checkpoint-ը flush է անում dirty page-երը և գրանցում log position. crash-ից հետո recovery-ն replay է անում WAL-ը վերջին checkpoint-ից (redo) և undo է անում uncommitted աշխատանքը։ Checkpoint interval-ը trade-off է․ հաճախ checkpoint-ը կարճացնում է recovery time-ը, բայց բարձրացնում steady write I/O. հազվադեպ checkpoint-ը հակառակը։ Live segment-ներից այն կողմ archived WAL-ն այն է, ինչ հնարավոր է դարձնում point-in-time recovery-ն և physical replication-ը — առանց դրա backup-ը այնքան թարմ է, որքան վերջին base snapshot-ը։ Այս in-place WAL+checkpoint model-ը B-tree engine-ների recovery path-ն է. LSM engine-ը recover է անում՝ replay անելով իր սեփական WAL-ը memtable-ի մեջ և վստահելով արդեն flush արած SSTable-ներին։
