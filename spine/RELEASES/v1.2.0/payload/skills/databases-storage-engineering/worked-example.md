# Databases and Storage Engineering worked examples

## English

### Example A — slow-query diagnosis and index plan

**Prompt.** "Recent orders for one user" is slow. It filters by `user_id`, sorts by `created_at DESC`, returns `status` and `total`, and EXPLAIN shows it scanning ~2M rows. Give a senior query review.

**Senior answer.** First, read the plan, not the symptom. EXPLAIN shows a sequential scan of the orders table with a filter on `user_id` and a separate sort on `created_at DESC`; estimated rows are far above actual for heavy users, which says the planner has no useful index and is also mis-estimating from stale statistics. So two problems: no index for this access pattern, and possibly stale stats.

The access pattern is one equality predicate (`user_id`), an ordering (`created_at DESC`), and two columns read back (`status`, `total`). The index follows equality → range/order → covering: `CREATE INDEX ON orders (user_id, created_at DESC) INCLUDE (status, total)`. The equality on `user_id` narrows to one user's rows immediately; because `created_at DESC` is the second key, the rows come out already ordered, so the sort disappears; and because `status` and `total` are in the `INCLUDE`, the query is answered from the index with no heap lookup. After creating it, re-run EXPLAIN and confirm an index scan with no separate sort node and no seq scan — that is the verification, not "it should be faster."

Second, the N+1. If the page then fetches each order's line items with one query per order, query count scales with the number of orders shown — that is the real latency for a user with many orders. Replace it with a single batched query: `SELECT ... FROM order_lines WHERE order_id IN (:ids)` (or a join), turning N+1 queries into 2.

Third, the consistency note. If reads are served from a replica, a user who just placed an order can hit the list before the replica catches up and not see their own order — a read-your-writes violation on a confirmation path. Route the order-confirmation and immediately-after-write list reads to the primary (or use a read-your-writes token); the older history page can tolerate a short, bounded replica lag. Assumptions to label: the 2M figure is the whole table, not one user; `status` is low-cardinality so it earns `INCLUDE`, not a leading position; statistics may be stale (a heavy user's estimate is off), so an `ANALYZE` may be needed before trusting the planner.

**Why this passes.** It reads EXPLAIN before proposing anything, and it names *two* distinct findings from the plan — the missing index and the stale-statistics mis-estimate — rather than reflexively "adding an index." The index it designs is justified column by column against the equality→order→covering rule: `user_id` first because it is the equality, `created_at DESC` second so the sort node disappears, `status`/`total` in `INCLUDE` so the heap lookup disappears — each clause maps to a specific line of the plan it removes. It closes the loop with the actual verification (re-run EXPLAIN, confirm index scan, no sort, no seq scan), so "done" means the plan changed, not that it feels faster. It catches the N+1 as a separate defect (query count scaling with rows, fixed with one batched `IN` query), and it adds the read-your-writes consistency boundary that a pure index answer would miss — routing the confirmation read to the primary while letting history tolerate bounded lag. Assumptions (table size, cardinality, stale stats) are labeled, not asserted.

### Example B — multi-store architecture with consistency boundaries

**Prompt.** A marketplace needs to handle orders and payments, show a fast product catalog, support full-text product search, and run daily revenue analytics — all on growing traffic. Design the data architecture and be explicit about which store owns what and where consistency boundaries sit.

**Senior answer.** One database cannot be the source of truth, the search index, the hot cache, and the analytics warehouse without one of those roles degrading the others. The move is to pick a **system of record** and treat every other store as a **derived, eventually-consistent projection** of it, with the consistency boundary stated at each hop.

- **OLTP system of record — relational (B-tree, MVCC).** Orders, payments, inventory, accounts. This is the only **strongly consistent** store and the only one allowed to hold the money/inventory invariants. Payment writes run at the isolation the invariant needs: an inventory decrement under concurrency is a lost-update/write-skew risk, so it uses `SELECT ... FOR UPDATE` on the stock row (or a `CHECK (stock >= 0)` constraint) — snapshot isolation alone would let two concurrent buyers each see stock and both decrement past zero. CP under partition: if the database is unreachable, the system refuses the order rather than double-selling. Backups are WAL + base backup with a tested PITR restore and a stated RPO/RTO.
- **Cache — key-value (e.g. an in-memory store).** Hot product/catalog reads and rendered pages. It is a **derived projection**: the OLTP row is the truth; the cache is allowed to be stale within a bounded TTL. Consistency boundary: writes go to OLTP and **invalidate or update** the cache (write-through or explicit invalidation), never the cache alone — a cache that is written without the database is a second, lying source of truth. A user editing their own profile must read-your-writes, so that path bypasses the cache or re-reads the primary.
- **Search — inverted index (search engine).** Full-text product search and faceting, which a relational `LIKE` cannot do well. It is a **derived projection** fed asynchronously from OLTP via change-data-capture or an outbox. Consistency boundary: search is **eventually consistent** — a just-created product may take seconds to appear in search, which is acceptable for discovery; it is never the store that confirms an order. The repair path is a periodic full reindex to correct any missed events.
- **Analytics — columnar warehouse / OLAP.** Daily revenue, cohort, and margin queries that would compete with OLTP for I/O if run on the primary. It is a **derived projection** loaded by a batch/stream ETL from OLTP (owned with `data-engineering-pipelines`). Consistency boundary: analytics is **lag-tolerant** (hours-old is fine) and **read-only** with respect to the source; it never writes back to OLTP, and revenue numbers are reconciled against the OLTP ledger as the authority.

The propagation pattern that keeps the projections honest is the **outbox / change-data-capture** approach: the OLTP transaction writes the business row and an event in the *same* transaction, and a relay ships that event to the cache invalidator, the search indexer, and the analytics loader. This guarantees that if the order committed, the downstream stores will (eventually) reflect it, and if it rolled back, no event leaks — closing the dual-write inconsistency where the database and the search index disagree. Assumptions to label: traffic and data volumes are growing but unstated, so exact sizing/sharding is deferred until the access patterns and cardinalities are measured; the warehouse refresh cadence (daily) is a requirement, not a guess.

**Why this passes.** It refuses the single-store fantasy and names one **system of record** (OLTP) with every other store as an explicitly *derived* projection — so there is exactly one place the money/inventory invariants live, and three places that are allowed to be stale. Each hop carries a stated consistency boundary: cache stale within a TTL and invalidated on write, search eventually consistent via CDC with a reindex repair path, analytics lag-tolerant and read-only with reconciliation against the OLTP ledger. It puts the hardest correctness work where it belongs — the inventory decrement gets `FOR UPDATE` precisely because snapshot isolation permits the two-buyers write skew, and the store is CP under partition because double-selling is unacceptable. It solves the cross-store dual-write trap with the outbox/CDC pattern (business row + event in one transaction) instead of hand-waving "keep them in sync," and it defers sizing/sharding honestly until access patterns are measured rather than inventing capacity numbers. The result is an architecture where each store does the one thing it is good at and no store silently becomes a second source of truth.

### Example C — online schema migration (expand/contract)

**Prompt.** You need to rename a hot `orders.amount` (integer cents) column to `total_cents`, zero downtime, on a 200M-row table serving production traffic. A teammate says "just run `ALTER TABLE ... RENAME COLUMN` on prod now." Why not, and what is the safe sequence?

**Senior answer.** A direct rename is a **breaking, not-reversible-in-place** change: the instant it commits, every running app instance still reading/writing `amount` breaks, and rolling back the deploy does not un-break it because the column is already gone. On a 200M-row hot table it also risks a long lock depending on the engine. The safe path is **expand/contract (parallel-change)** — every step is independently deployable and reversible, and old and new coexist until the switch is proven:

1. **Expand — add the new column, nullable, no backfill yet.** `ALTER TABLE orders ADD COLUMN total_cents bigint` (adding a nullable column is metadata-only on most engines — cheap, no table rewrite). *Reversible:* drop the unused column. App still uses `amount`.
2. **Dual-write.** Deploy app code that writes **both** `amount` and `total_cents` on every insert/update (still reads `amount`). New rows are now correct in both. *Reversible:* revert the deploy; `total_cents` is just unused.
3. **Backfill in batches.** Backfill history `UPDATE ... SET total_cents = amount WHERE total_cents IS NULL` in **bounded batches** (e.g. 5–10k rows by pk range, throttled, a short transaction each) so you never hold a long lock or blow up replication lag. It is resumable and **idempotent** — the `WHERE total_cents IS NULL` guard makes re-runs safe. *Reversible:* stop the backfill; nothing read-facing changed.
4. **Dual-read / verify.** Deploy code that reads `total_cents` but falls back to `amount` when null, plus a metric that asserts they agree. Bake and watch: a mismatch count > 0 is the stop signal. *Reversible:* flip reads back to `amount`.
5. **Switch reads to `total_cents` only** once backfill is 100% and the mismatch metric is flat at zero for a full bake window. *Reversible:* the fallback-to-`amount` code is still deployed, so you flip back instantly.
6. **Contract — stop writing `amount`, then (a release later) drop it.** Only after `total_cents` has been the sole read path in production for a safe window, remove the dual-write, then `ALTER TABLE orders DROP COLUMN amount`. The drop is the one irreversible step, so it is **last, gated on evidence** (zero reads of `amount` in logs/metrics), and a release on its own.

The teammate's "drop/rename on prod now" collapses six reversible steps into one irreversible one taken blind. The refusal is not "never migrate" — it is "expand/contract so every step before the final drop can be rolled back, and the drop happens only after the new column is proven in production."

**Why this passes.** It names the real failure — a direct rename breaks every running instance the moment it commits and cannot be rolled back in place — instead of just running the DDL. It sequences **expand → dual-write → batched idempotent backfill → dual-read verify → switch → contract/drop** and states the **reversibility of each step** explicitly, so the only irreversible action (the drop) is last, evidence-gated, and isolated. The backfill is batched, throttled, and idempotent (guarded by `IS NULL`), protecting the hot table from a long lock and replication-lag blowup, and the switch is gated on a **zero-mismatch bake** — verified in production, not assumed. It explicitly refuses the "drop on prod now" push while still delivering the migration, which is exactly what the skill's top adversarial probe targets.

### Example D — deadlock analysis (read the log, fix the lock order)

**Prompt.** Production throws intermittent `deadlock detected` under load; one transaction is always rolled back. The log shows two transactions each holding a row lock the other wants. Diagnose from the log and fix it.

**Senior answer.** A deadlock is not random — it is two transactions acquiring the **same locks in opposite orders**, so each waits on a lock the other holds (a cycle); the engine breaks it by killing a victim and rolling it back. Read the cycle from the log, then impose a **consistent global lock order** so the cycle cannot form.

Read the log:
- **T1** holds a lock on `accounts` row `A`, waits for row `B`.
- **T2** holds a lock on `accounts` row `B`, waits for row `A`.
- Cycle: T1 → B (held by T2) → A (held by T1). Classic **A-then-B vs B-then-A** conflict — e.g. a "transfer" that locks the *from* account then the *to*, run concurrently in both directions (A→B and B→A).

Fix — a total order on lock acquisition:
1. **Acquire locks in a consistent order everywhere.** Always lock the rows in a deterministic order — e.g. by ascending primary key (`LEAST(from_id, to_id)` first, then the other). Now both A→B and B→A lock the *lower id first*, so they queue instead of deadlocking. This is the root fix: a global order makes a cycle impossible.
2. **Keep transactions short, touch rows in a stable order.** Do reads/validation before opening the write transaction; never interleave user think-time inside a transaction holding locks.
3. **Where a natural order is hard, `SELECT ... FOR UPDATE` with an explicit `ORDER BY`** (or lock a single parent/summary row first as a mutex) so contenders serialize on one gate.
4. **Make the app deadlock-tolerant anyway.** Even with the ordering rule, keep a **bounded retry with backoff** on the deadlock error code — a victim's rollback is safe to retry, turning a rare residual deadlock into a transparent hiccup instead of a user-facing error. Retry is the belt; the lock order is the fix.
5. **Check granularity / missing index.** A `WHERE` with no index can take range/gap locks over more rows than intended and aggravate the deadlock — confirm the update hits an index so it locks the row, not a range.

**Why this passes.** It reads the **cycle straight from the log** (T1 holds A waits B, T2 holds B waits A) and names the mechanism — the same locks acquired in **opposite orders** — instead of calling it random. The root fix is a **consistent global lock order** (ascending id, `LEAST(from,to)` first) so the cycle *cannot form*, not a hopeful "make it faster." It adds the supporting disciplines (short transactions, stable row order, a mutex gate where natural order is hard) and — critically — a **bounded retry with backoff**, because a deadlock victim is safe to retry, so a rare residual becomes a transparent hiccup. It also checks the **granularity / missing-index** angle where an unindexed predicate takes wider gap/range locks. The fix targets the ordering cycle — the actual cause — and makes the system tolerant of the residual.

### Օրինակ A — slow-query diagnosis և index plan

**Prompt.** «Մեկ user-ի recent orders»-ը slow է։ Filter է անում `user_id`-ով, sort `created_at DESC`-ով, վերադարձնում է `status` և `total`, և EXPLAIN-ը ցույց է տալիս ~2M row scan։ Տուր senior query review։

**Senior պատասխան.** Նախ կարդա plan-ը, ոչ symptom-ը։ EXPLAIN-ը ցույց է տալիս orders table-ի sequential scan՝ `user_id`-ի filter-ով և առանձին `created_at DESC` sort-ով. estimated rows-ը heavy user-ների համար շատ ավելի է, քան actual-ը, ինչը ասում է, որ planner-ը օգտակար index չունի և նաև սխալ է estimate անում stale statistics-ից։ Ուստի երկու խնդիր՝ այս access pattern-ի համար index չկա, և հնարավոր է stale stats։

Access pattern-ը մեկ equality predicate է (`user_id`), ordering (`created_at DESC`) և երկու վերադարձվող սյուն (`status`, `total`)։ Index-ը հետևում է equality → range/order → covering-ին․ `CREATE INDEX ON orders (user_id, created_at DESC) INCLUDE (status, total)`։ `user_id`-ի equality-ն անմիջապես narrow է անում մեկ user-ի row-երին. քանի որ `created_at DESC`-ը երկրորդ key-ն է, row-երը դուրս են գալիս արդեն ordered, ուստի sort-ը անհետանում է. և քանի որ `status`-ը և `total`-ը `INCLUDE`-ում են, query-ն պատասխանվում է index-ից առանց heap lookup-ի։ Ստեղծելուց հետո վերագործարկիր EXPLAIN-ը և հաստատիր index scan՝ առանց առանձին sort node-ի և առանց seq scan-ի — դա է verification-ը, ոչ թե «պետք է ավելի արագ լինի»։

Երկրորդ՝ N+1-ը։ Եթե page-ը հետո ամեն order-ի line item-ները բերում է մեկ query-ով ամեն order-ի, query-ների քանակը մեծանում է ցուցադրվող order-ների քանակով — դա է իրական latency-ն շատ order ունեցող user-ի համար։ Փոխարինիր մեկ batched query-ով․ `SELECT ... FROM order_lines WHERE order_id IN (:ids)` (կամ join), N+1 query-ն դարձնելով 2։

Երրորդ՝ consistency note-ը։ Եթե read-երը serve են լինում replica-ից, user-ը, որ հենց նոր order է դրել, կարող է հասնել list-ին մինչ replica-ի հասնելը և չտեսնել իր սեփական order-ը — read-your-writes-ի խախտում confirmation path-ի վրա։ Order-confirmation-ի և write-ից անմիջապես հետո list read-երը ուղղորդիր primary-ին (կամ օգտագործիր read-your-writes token). ավելի հին history page-ը կարող է հանդուրժել կարճ, սահմանափակ replica lag։ Label-ելու assumption-ներ՝ 2M թիվը ամբողջ table-ն է, ոչ մեկ user-ի. `status`-ը low-cardinality է, ուստի վաստակում է `INCLUDE`, ոչ առաջատար դիրք. statistics-ը կարող է stale լինի (heavy user-ի estimate-ը սխալ է), ուստի `ANALYZE` կարող է պետք լինի մինչ planner-ին վստահելը։

**Ինչու է անցնում gate-ը.** Այն կարդում է EXPLAIN-ը մինչ որևէ բան առաջարկելը, և անվանում է plan-ից *երկու* տարբեր գտածո — բացակայող index-ը և stale-statistics mis-estimate-ը — ոչ թե ռեֆլեքսով «index ավելացնում»։ Նախագծած index-ը արդարացված է սյուն առ սյուն equality→order→covering կանոնի դեմ․ `user_id` նախ՝ որովհետև equality-ն է, `created_at DESC` երկրորդ՝ որ sort node-ը անհետանա, `status`/`total` `INCLUDE`-ում՝ որ heap lookup-ը անհետանա — ամեն clause քարտեզվում է plan-ի կոնկրետ տողին, որ հանում է։ Այն փակում է loop-ը իրական verification-ով (վերագործարկիր EXPLAIN, հաստատիր index scan, ոչ sort, ոչ seq scan), ուստի «done» նշանակում է plan-ը փոխվեց, ոչ թե թվում է ավելի արագ։ Այն բռնում է N+1-ը որպես առանձին defect (query count-ը մեծանում է row-երով, ուղղված մեկ batched `IN` query-ով), և ավելացնում է read-your-writes consistency boundary-ն, որ զուտ index պատասխանը բաց կթողներ — confirmation read-ը ուղղորդելով primary-ին, մինչ history-ն հանդուրժում է սահմանափակ lag։ Assumption-ները (table size, cardinality, stale stats) label-ված են, ոչ պնդված։

### Օրինակ B — multi-store architecture՝ consistency boundary-ներով

**Prompt.** Marketplace-ին պետք է մշակել order-եր և payment-ներ, ցույց տալ արագ product catalog, աջակցել full-text product search, և գործարկել daily revenue analytics — ամենն աճող traffic-ի վրա։ Նախագծիր data architecture-ը և եղիր բացահայտ, թե որ store-ն ինչ է տիրում և որտեղ են consistency boundary-ները։

**Senior պատասխան.** Մեկ database չի կարող լինել source of truth-ը, search index-ը, hot cache-ը և analytics warehouse-ը՝ առանց այդ role-երից մեկը մյուսները degrade անելու։ Move-ը՝ ընտրիր **system of record** և ամեն մյուս store համարիր նրա **derived, eventually-consistent projection**՝ ամեն hop-ին նշված consistency boundary-ով։

- **OLTP system of record — relational (B-tree, MVCC).** Order, payment, inventory, account։ Սա միակ **strongly consistent** store-ն է և միակը, որ թույլատրվում է պահել money/inventory invariant-ները։ Payment write-երը աշխատում են invariant-ին պետք isolation-ով․ inventory decrement-ը concurrency-ի տակ lost-update/write-skew risk է, ուստի օգտագործում է `SELECT ... FOR UPDATE` stock row-ի վրա (կամ `CHECK (stock >= 0)` constraint) — միայն snapshot isolation-ը կթողներ, որ երկու concurrent buyer երկուսն էլ տեսնեն stock և երկուսն էլ decrement անեն զրոյից ներքև։ CP partition-ի տակ․ եթե database-ը անհասանելի է, համակարգը մերժում է order-ը՝ double-sell-ի փոխարեն։ Backup-ները WAL + base backup են՝ ստուգված PITR restore-ով և նշված RPO/RTO-ով։
- **Cache — key-value (օր.՝ in-memory store).** Hot product/catalog read-եր և rendered page-եր։ Այն **derived projection** է․ OLTP row-ն է truth-ը. cache-ը թույլատրվում է stale լինել սահմանափակ TTL-ի ներսում։ Consistency boundary․ write-երը գնում են OLTP և **invalidate կամ update** են անում cache-ը (write-through կամ explicit invalidation), երբեք միայն cache-ը — cache, որ գրվում է առանց database-ի, երկրորդ, ստախոս source of truth է։ User-ը, որ խմբագրում է իր սեփական profile-ը, պետք է read-your-writes անի, ուստի այդ path-ը շրջանցում է cache-ը կամ վերակարդում primary-ից։
- **Search — inverted index (search engine).** Full-text product search և faceting, որ relational `LIKE`-ը լավ չի կարող անել։ Այն **derived projection** է, որ OLTP-ից սնվում է asynchronously՝ change-data-capture-ով կամ outbox-ով։ Consistency boundary․ search-ը **eventually consistent** է — հենց նոր ստեղծված product-ը կարող է վայրկյաններ վերցնի search-ում հայտնվելու, որ acceptable է discovery-ի համար. այն երբեք order հաստատող store-ը չէ։ Repair path-ը պարբերական full reindex է՝ բաց թողնված event-ները ուղղելու։
- **Analytics — columnar warehouse / OLAP.** Daily revenue, cohort և margin query, որ primary-ի վրա գործարկելու դեպքում OLTP-ի հետ I/O-ի համար կմրցեին։ Այն **derived projection** է, որ load է լինում batch/stream ETL-ով OLTP-ից (տիրվում է `data-engineering-pipelines`-ի հետ)։ Consistency boundary․ analytics-ը **lag-հանդուրժող** է (ժամեր հին-ը նորմալ է) և **read-only** source-ի նկատմամբ. այն երբեք հետ չի գրում OLTP, և revenue թվերը reconcile են լինում OLTP ledger-ի դեմ որպես authority։

Propagation pattern-ը, որ projection-ները ազնիվ է պահում, **outbox / change-data-capture** մոտեցումն է․ OLTP transaction-ը գրում է business row-ը և event-ը *նույն* transaction-ում, և relay-ն այդ event-ը ship է անում cache invalidator-ին, search indexer-ին և analytics loader-ին։ Սա երաշխավորում է, որ եթե order-ը commit-վեց, downstream store-երը (ի վերջո) կարտացոլեն այն, և եթե roll back-վեց, ոչ մի event չի արտահոսում — փակելով dual-write inconsistency-ն, որտեղ database-ը և search index-ը համաձայն չեն։ Label-ելու assumption-ներ՝ traffic-ը և data volume-ները աճում են, բայց չնշված, ուստի ճշգրիտ sizing/sharding-ը հետաձգվում է, մինչ access pattern-ները և cardinality-ները չափվեն. warehouse-ի refresh cadence-ը (daily) պահանջ է, ոչ գուշակություն։

**Ինչու է անցնում gate-ը.** Այն մերժում է single-store fantasy-ն և անվանում է մեկ **system of record** (OLTP)՝ ամեն մյուս store որպես բացահայտ *derived* projection — ուստի կա ճիշտ մեկ տեղ, որտեղ money/inventory invariant-ները ապրում են, և երեք տեղ, որ թույլատրվում են stale լինել։ Ամեն hop կրում է նշված consistency boundary․ cache stale TTL-ի ներսում և invalidate-ված write-ին, search eventually consistent CDC-ով՝ reindex repair path-ով, analytics lag-հանդուրժող և read-only՝ OLTP ledger-ի դեմ reconciliation-ով։ Այն ամենադժվար correctness աշխատանքը դնում է, որտեղ պետք է — inventory decrement-ը ստանում է `FOR UPDATE` ճշգրիտ, որովհետև snapshot isolation-ը թույլ է տալիս երկու-buyer write skew-ը, և store-ը CP է partition-ի տակ, որովհետև double-selling-ը անընդունելի է։ Այն լուծում է cross-store dual-write trap-ը outbox/CDC pattern-ով (business row + event մեկ transaction-ում)՝ «keep them in sync» ձեռքով թափահարելու փոխարեն, և ազնվորեն հետաձգում է sizing/sharding-ը, մինչ access pattern-ները չափվեն՝ capacity թվեր հորինելու փոխարեն։ Արդյունքը architecture է, որտեղ ամեն store անում է այն մեկ բանը, որում լավն է, և ոչ մի store լուռ չի դառնում երկրորդ source of truth։

### Օրինակ C — online schema migration (expand/contract)

**Prompt.** Պետք է rename անես hot `orders.amount` (integer cents) սյունը `total_cents`-ի, zero downtime, 200M-row table-ի վրա, որ production traffic է serve անում։ Թիմակիցդ ասում է «պարզապես գործարկիր `ALTER TABLE ... RENAME COLUMN` prod-ի վրա հիմա»։ Ինչո՞ւ ոչ, և ո՞րն է անվտանգ հերթականությունը։

**Senior պատասխան.** Ուղիղ rename-ը **breaking, not-reversible-in-place** փոփոխություն է․ հենց commit-վի, ամեն աշխատող app instance, որ դեռ կարդում/գրում է `amount`, կոտրվում է, և deploy-ը հետ գլորելը չի ուղղում, որովհետև սյունն արդեն չկա։ 200M-row hot table-ի վրա այն նաև երկար lock-ի ռիսկ է՝ ըստ engine-ի։ Անվտանգ path-ը **expand/contract (parallel-change)** է — ամեն քայլ independently deployable ու reversible է, և հին ու նոր coexist են, մինչ switch-ը ապացուցվի․

1. **Expand — ավելացրու նոր սյունը, nullable, դեռ առանց backfill-ի.** `ALTER TABLE orders ADD COLUMN total_cents bigint` (nullable սյուն ավելացնելը metadata-only է engine-ների մեծ մասում — էժան, table rewrite չկա)։ *Reversible․* drop արա չօգտագործված սյունը։ App-ը դեռ `amount` է օգտագործում։
2. **Dual-write.** Deploy արա app code, որ գրում է **երկուսն էլ**՝ `amount` և `total_cents`, ամեն insert/update-ին (դեռ կարդում է `amount`)։ Նոր row-երն այժմ ճիշտ են երկուսում։ *Reversible․* revert արա deploy-ը. `total_cents`-ը պարզապես չօգտագործված է։
3. **Backfill batch-երով.** Backfill արա history-ն՝ `UPDATE ... SET total_cents = amount WHERE total_cents IS NULL` **սահմանափակ batch-երով** (օր.՝ 5–10k row ըստ pk range-ի, throttled, ամեն մեկը կարճ transaction), որ երբեք երկար lock չպահես կամ replication lag չպայթեցնես։ Resumable է և **idempotent** — `WHERE total_cents IS NULL` guard-ը re-run-ը անվտանգ է դարձնում։ *Reversible․* կանգնեցրու backfill-ը. read-facing ոչինչ չփոխվեց։
4. **Dual-read / verify.** Deploy արա code, որ կարդում է `total_cents`, բայց fall back է անում `amount`-ի, երբ null է, plus metric, որ պնդում է, թե համաձայն են։ Bake արա և հետևիր․ mismatch count > 0-ը stop signal-ն է։ *Reversible․* read-երը հետ շրջիր `amount`-ի։
5. **Switch արա read-երը միայն `total_cents`-ի**, երբ backfill-ը 100% է, և mismatch metric-ը հարթ զրո է ամբողջ bake window-ի ընթացքում։ *Reversible․* fallback-to-`amount` code-ը դեռ deployed է, ուստի ակնթարթորեն հետ ես շրջում։
6. **Contract — դադարիր գրել `amount`, հետո (մեկ release անց) drop արա այն.** Միայն այն բանից հետո, երբ `total_cents`-ը production-ում եղել է միակ read path-ը անվտանգ window-ի ընթացքում, հանիր dual-write-ը, հետո `ALTER TABLE orders DROP COLUMN amount`։ Drop-ը միակ irreversible քայլն է, ուստի **վերջինն է, evidence-gated** (`amount`-ի զրո read log/metric-ում), և առանձին release։

Թիմակցի «drop/rename prod-ի վրա հիմա»-ն վեց reversible քայլը սեղմում է մեկ irreversible-ի, արված կույր։ Մերժումը «երբեք migrate չանել» չէ — «expand/contract, որ ամեն քայլ մինչ վերջին drop-ը կարողանա հետ գլորվել, և drop-ը լինի միայն այն բանից հետո, երբ նոր սյունը ապացուցվի production-ում»։

**Ինչու է անցնում gate-ը.** Այն անվանում է իրական failure-ը — ուղիղ rename-ը կոտրում է ամեն աշխատող instance հենց commit-ի պահին և չի կարող in-place հետ գլորվել — DDL-ը պարզապես գործարկելու փոխարեն։ Այն sequence է անում **expand → dual-write → batched idempotent backfill → dual-read verify → switch → contract/drop** և բացահայտ ասում է ամեն քայլի **reversibility-ն**, ուստի միակ irreversible action-ը (drop-ը) վերջինն է, evidence-gated և մեկուսացված։ Backfill-ը batched, throttled և idempotent է (`IS NULL`-ով guard-ված)՝ պաշտպանելով hot table-ը երկար lock-ից և replication-lag պայթյունից, և switch-ը gated է **zero-mismatch bake**-ի վրա — verified production-ում, ոչ ենթադրված։ Այն բացահայտ մերժում է «drop prod-ի վրա հիմա» push-ը՝ միևնույն ժամանակ migration-ը մատուցելով, ինչը հենց այն է, ինչ skill-ի top adversarial probe-ը թիրախավորում է։

### Օրինակ D — deadlock analysis (log-ը կարդալ, lock order-ը ուղղել)

**Prompt.** Production-ը load-ի տակ նետում է ընդհատվող `deadlock detected`. մեկ transaction միշտ rollback է լինում։ Log-ը ցույց է տալիս երկու transaction, ամեն մեկը պահում է row lock, որ մյուսն ուզում է։ Ախտորոշիր log-ից և ուղղիր։

**Senior պատասխան.** Deadlock-ը random չէ — երկու transaction ձեռք են բերում **նույն lock-երը հակառակ կարգով**, ուստի ամեն մեկը սպասում է lock-ի, որ մյուսն է պահում (cycle). engine-ը կոտրում է այն՝ victim սպանելով ու rollback անելով։ Կարդա cycle-ը log-ից, հետո պարտադրիր **consistent global lock order**, որ cycle-ը չկարողանա ձևավորվել։

Կարդա log-ը․
- **T1**-ը պահում է lock `accounts` row `A`-ի վրա, սպասում է row `B`-ին։
- **T2**-ը պահում է lock row `B`-ի վրա, սպասում է row `A`-ին։
- Cycle․ T1 → B (պահած T2-ի) → A (պահած T1-ի)։ Classic **A-then-B ընդդեմ B-then-A** conflict — օր.՝ «transfer», որ lock է անում *from* account-ը հետո *to*-ն, գործարկված զուգահեռ երկու ուղղությամբ (A→B և B→A)։

Fix — total order lock acquisition-ի վրա․
1. **Ձեռք բեր lock-երը consistent order-ով ամենուր.** Միշտ lock արա row-երը deterministic order-ով — օր.՝ ascending primary key-ով (`LEAST(from_id, to_id)` նախ, հետո մյուսը)։ Հիմա և՛ A→B, և՛ B→A lock են անում *ցածր id-ն նախ*, ուստի queue են լինում deadlock-ի փոխարեն։ Սա root fix-ն է․ global order-ը cycle-ը անհնար է դարձնում։
2. **Պահիր transaction-ները կարճ, դիպչիր row-երին stable order-ով.** Read/validation արա նախքան write transaction բացելը. երբեք մի՛ interleave արա user think-time lock պահող transaction-ի ներսում։
3. **Որտեղ natural order-ը դժվար է, `SELECT ... FOR UPDATE` explicit `ORDER BY`-ով** (կամ lock արա մեկ parent/summary row նախ որպես mutex), որ contender-ները serialize լինեն մեկ gate-ի վրա։
4. **Դարձրու app-ը deadlock-tolerant միևնույն է.** Նույնիսկ ordering rule-ով, պահիր **bounded retry backoff-ով** deadlock error code-ի վրա — victim-ի rollback-ը ապահով է retry անել, հազվագյուտ residual deadlock-ը դարձնելով transparent hiccup, ոչ user-facing error։ Retry-ն belt-ն է. lock order-ը՝ fix-ը։
5. **Ստուգիր granularity / missing index.** `WHERE` առանց index-ի կարող է range/gap lock վերցնի ավելի շատ row-ի վրա, քան մտադրված, և aggravate անի deadlock-ը — հաստատիր, որ update-ը հարվածում է index-ի, որ row lock անի, ոչ range։

**Ինչու է անցնում gate-ը.** Այն կարդում է **cycle-ը ուղիղ log-ից** (T1 holds A waits B, T2 holds B waits A) և անվանում mechanism-ը — նույն lock-երը **հակառակ կարգով** — random անվանելու փոխարեն։ Root fix-ը **consistent global lock order** է (ascending id, `LEAST(from,to)` նախ), որ cycle-ը *չկարողանա ձևավորվել*, ոչ հուսադրող «ավելի արագ արա»։ Այն ավելացնում է supporting discipline-ները (կարճ transaction, stable row order, mutex gate, որտեղ natural order-ը դժվար է) և — կրիտիկ — **bounded retry backoff-ով**, որովհետև deadlock victim-ը ապահով է retry անել, ուստի հազվագյուտ residual-ը դառնում է transparent hiccup։ Այն նաև ստուգում է **granularity / missing-index** անկյունը, որտեղ unindexed predicate-ը ավելի լայն gap/range lock է վերցնում։ Fix-ը թիրախավորում է ordering cycle-ը — իրական cause-ը — և համակարգը դարձնում tolerant residual-ի նկատմամբ։
