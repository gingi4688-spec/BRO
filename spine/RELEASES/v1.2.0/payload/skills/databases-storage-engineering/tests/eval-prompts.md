# Databases and Storage Engineering eval prompts

## English

Run these after changes. Each prompt has its own pass check — passing requires mechanism-level reasoning and a concrete artifact, not vocabulary. Do not reuse one check for another prompt.

1. **Slow-query / index plan.** "This 'recent orders for a user' query scans 2M rows; make it fast." — Pass only if it reads **EXPLAIN** first (scan type, estimated vs actual rows), designs the index as **equality → range → `ORDER BY` with a covering `INCLUDE`**, catches the **N+1**, and verifies by **re-running EXPLAIN** (index scan, no sort, no seq scan). Fail if it proposes an index from the column name alone.
2. **Isolation by invariant.** "We get occasional double-charges on checkout." — Pass only if it names the **invariant** (no double-charge), identifies the **lost-update / read-modify-write race**, and fixes it with `SELECT FOR UPDATE` / atomic update / idempotency key / higher isolation — not "add a retry." Fail if it accepts the engine default without reasoning.
3. **Write skew under snapshot isolation.** "Under repeatable read, two on-call engineers both managed to go off duty at once, leaving zero on call. Why, and how do we prevent it?" — Pass only if it names **write skew under snapshot isolation** (each transaction reads the set and writes a different row, no write-write conflict), and prescribes **`SERIALIZABLE`, a single locked guard row, or a constraint**. Fail if it just says "use a transaction."
4. **MVCC bloat / autovacuum.** "Writes on our Postgres table have gotten slower and the table is huge on disk though the row count is normal." — Pass only if it names **dead tuples and bloat**, checks **autovacuum lag and a long-running transaction holding an old snapshot**, and cures the cause (end the long transaction, tune autovacuum, reclaim) **before** adding hardware. Fail if it jumps to a bigger instance.
5. **Deadlocks / lock ordering.** "We keep getting deadlocks on two tables under load." — Pass only if it explains the **A→B / B→A cycle and the deadlock detector's victim**, prescribes a **consistent global lock order** plus short transactions, and treats the victim as a **retry**. Fail if it blames load with no lock-order analysis.
6. **Queue / SKIP LOCKED.** "Multiple workers pull jobs from a `jobs` table and sometimes process the same job twice." — Pass only if it diagnoses the plain `SELECT` (or plain `FOR UPDATE`) and prescribes **`SELECT ... FOR UPDATE SKIP LOCKED`** so workers claim disjoint rows, plus a lease/status column for crashed workers. Fail if it adds application-side locking instead.
7. **CAP / consistency.** "Should our payments service be CP or AP, and what about reads from replicas?" — Pass only if it chooses **CP from the money invariant**, states the **partition behavior** (refuse rather than double-spend), never claims "CA under partition," and routes **read-your-writes** off lagging replicas. Bonus: names the **PACELC** latency tradeoff.
8. **Storage-engine choice.** "We have a write-heavy, high-ingest time-series workload — B-tree or LSM?" — Pass only if it reasons from **write/read/space amplification and compaction** (LSM favored for write-heavy ingest, with bloom filters / compaction strategy), not from engine names. Fail if it picks by popularity.
9. **WAL / crash recovery.** "How does our database survive a crash mid-transaction, and what makes point-in-time recovery possible?" — Pass only if it explains the **write-ahead rule (log flushed before data page), checkpoints, and WAL replay (redo) + undo on restart**, and ties **PITR to a base backup + archived WAL replayed to a target time**. Fail if it conflates WAL with backups or omits checkpoints.
10. **Multi-store architecture.** "Design stores for orders/payments, a fast catalog, full-text search, and daily analytics." — Pass only if it names **one system of record (OLTP)** with the others as **derived projections**, states a **consistency boundary per store** (bounded-stale cache, eventually-consistent search via CDC, lag-tolerant read-only analytics), and closes the **dual-write trap with outbox/CDC**. Fail if it makes every store a source of truth.
11. **Armenian equal-depth.** Ask any of prompts 1–10 in Armenian. — Pass only if the Armenian is native, equal-depth (same mechanism, same artifact, same SQL/terms), and punctuation-clean (correct `․`/`։`/«», no homoglyphs); English tech tokens (EXPLAIN, MVCC, WAL, CDC, FOR UPDATE) staying English is correct.

Regression checks (run alongside):

- **No invented facts.** Ask for a specific engine's exact default isolation level, a benchmark number, or a version-specific limit. — Pass only if it refuses to invent it or marks it verify-before-use with the general rule/formula, not a fabricated number.
- **No thin label answer.** Ask "just give me database best practices." — Pass only if it expands into a mechanism, a query plan, an invariant, or a worked micro-example, not a list of buzzwords.

## Հայերեն

Գործարկիր սրանք փոփոխություններից հետո։ Ամեն prompt ունի իր pass check-ը — անցնելը պահանջում է mechanism-level reasoning և concrete artifact, ոչ vocabulary։ Մի՛ կիրառիր մի check-ը մյուս prompt-ի համար։

1. **Slow-query / index plan.** «Այս «user-ի recent orders» query-ն 2M row է scan անում. արագացրու»։ — Անցնում է միայն, եթե նախ կարդում է **EXPLAIN** (scan type, estimated ընդդեմ actual rows), index-ը նախագծում որպես **equality → range → `ORDER BY`՝ covering `INCLUDE`-ով**, բռնում **N+1**-ը, և verify է անում **EXPLAIN-ը վերագործարկելով** (index scan, ոչ sort, ոչ seq scan)։ Fail՝ եթե index է առաջարկում միայն սյունի անունից։
2. **Isolation ըստ invariant-ի.** «Checkout-ին երբեմն double-charge ենք ստանում»։ — Անցնում է միայն, եթե անվանում է **invariant**-ը (ոչ double-charge), հայտնաբերում է **lost-update / read-modify-write race**-ը, և ուղղում `SELECT FOR UPDATE` / atomic update / idempotency key / ավելի բարձր isolation-ով — ոչ «ավելացրու retry»։ Fail՝ եթե ընդունում է engine default-ը առանց reasoning-ի։
3. **Write skew snapshot isolation-ի տակ.** «Repeatable read-ի տակ երկու on-call engineer երկուսն էլ կարողացան միաժամանակ off duty գնալ՝ թողնելով զրո on call։ Ինչու, և ոնց կանխենք»։ — Անցնում է միայն, եթե անվանում է **write skew-ը snapshot isolation-ի տակ** (ամեն transaction կարդում է set-ը և գրում տարբեր row, write-write conflict չկա), և նշանակում **`SERIALIZABLE`, մեկ lock-ված guard row, կամ constraint**։ Fail՝ եթե պարզապես ասում է «transaction օգտագործիր»։
4. **MVCC bloat / autovacuum.** «Մեր Postgres table-ի write-երը դանդաղել են, և table-ը disk-ի վրա հսկայական է, թեև row count-ը նորմալ է»։ — Անցնում է միայն, եթե անվանում է **dead tuple-ները և bloat-ը**, ստուգում է **autovacuum lag-ը և old snapshot պահող երկար transaction**, և բուժում պատճառը (ավարտիր երկար transaction-ը, tune արա autovacuum, վերադարձրու) **մինչ** hardware ավելացնելը։ Fail՝ եթե ցատկում է ավելի մեծ instance-ի։
5. **Deadlock / lock ordering.** «Load-ի տակ երկու table-ի վրա անընդհատ deadlock ենք ստանում»։ — Անցնում է միայն, եթե բացատրում է **A→B / B→A cycle-ը և deadlock detector-ի victim-ը**, նշանակում **հետևողական global lock order** plus կարճ transaction-ներ, և victim-ը համարում **retry**։ Fail՝ եթե load-ը մեղադրում է առանց lock-order վերլուծության։
6. **Queue / SKIP LOCKED.** «Մի քանի worker job են քաշում `jobs` table-ից, և երբեմն նույն job-ը երկու անգամ են մշակում»։ — Անցնում է միայն, եթե diagnose է անում պարզ `SELECT`-ը (կամ պարզ `FOR UPDATE`-ը) և նշանակում **`SELECT ... FOR UPDATE SKIP LOCKED`**, որ worker-ները disjoint row claim անեն, plus lease/status սյուն crash-ած worker-ների համար։ Fail՝ եթե application-side locking է ավելացնում փոխարենը։
7. **CAP / consistency.** «Մեր payments service-ը CP պետք է լինի՞ թե AP, և ինչ կասենք replica-ից read-երի մասին»։ — Անցնում է միայն, եթե ընտրում է **CP՝ money invariant-ից**, նշում **partition behavior-ը** (մերժիր, քան double-spend), երբեք «CA under partition» չի պնդում, և **read-your-writes**-ը հանում lagging replica-ից։ Bonus՝ անվանում է **PACELC** latency trade-off-ը։
8. **Storage-engine ընտրություն.** «Ունենք write-heavy, high-ingest time-series workload — B-tree՞ թե LSM»։ — Անցնում է միայն, եթե reasoning է անում **write/read/space amplification-ից և compaction-ից** (LSM նախընտրելի write-heavy ingest-ի համար՝ bloom filter / compaction strategy-ով), ոչ engine անուններից։ Fail՝ եթե ընտրում է popularity-ով։
9. **WAL / crash recovery.** «Ոնց է մեր database-ը գոյատևում transaction-ի կեսին crash-ին, և ինչն է հնարավոր դարձնում point-in-time recovery-ն»։ — Անցնում է միայն, եթե բացատրում է **write-ahead rule-ը (log flush մինչ data page), checkpoint-ները, և WAL replay (redo) + undo restart-ին**, և կապում **PITR-ը base backup + archived WAL՝ target time-ին replay արած**։ Fail՝ եթե WAL-ը շփոթում է backup-ի հետ կամ բաց թողնում checkpoint-ները։
10. **Multi-store architecture.** «Նախագծիր store-եր order/payment-ի, արագ catalog-ի, full-text search-ի և daily analytics-ի համար»։ — Անցնում է միայն, եթե անվանում է **մեկ system of record (OLTP)**՝ մյուսները որպես **derived projection**, նշում **consistency boundary ամեն store-ի** (bounded-stale cache, eventually-consistent search CDC-ով, lag-հանդուրժող read-only analytics), և փակում **dual-write trap-ը outbox/CDC-ով**։ Fail՝ եթե ամեն store-ը source of truth է դարձնում։
11. **Հայերեն equal-depth.** Հարցրու 1–10-ից որևէ մեկը հայերեն։ — Անցնում է միայն, եթե հայերենը native է, equal-depth (նույն mechanism-ը, նույն artifact-ը, նույն SQL/term-երը) և punctuation-clean (ճիշտ `․`/`։`/«», առանց homoglyph-ի). անգլերեն tech token-ները (EXPLAIN, MVCC, WAL, CDC, FOR UPDATE) անգլերեն մնալը ճիշտ է։

Regression check-եր (գործարկիր կողքից)․

- **Ոչ մի հորինված fact.** Հարցրու կոնկրետ engine-ի ճշգրիտ default isolation level-ը, benchmark թիվ կամ version-specific limit։ — Անցնում է միայն, եթե հրաժարվում է հորինելուց կամ նշում verify-before-use՝ ընդհանուր կանոնով/formula-ով, ոչ հորինված թվով։
- **Ոչ բարակ label պատասխան.** Հարցրու «պարզապես տուր database best practice-ները»։ — Անցնում է միայն, եթե դառնում է mechanism, query plan, invariant կամ worked micro-example, ոչ buzzword-ների ցուցակ։
