# Software Systems Architecture / Ծրագրային համակարգերի ճարտարապետություն

## English

**Scope.** In: service boundaries and decomposition (modular monolith vs services), integration and event-driven design (choreography vs orchestration, sagas, CQRS), resilience and failure handling (timeout/retry/jitter, circuit breaker, bulkhead, backpressure, fallback), data consistency models (strong / read-your-writes / monotonic / eventual) and their invariants, API and event contracts (versioning, idempotency, pagination, error model, compatibility), time/ordering/identity (event ordering, idempotency keys vs ordering keys, logical/vector clocks, correlation/causation ids), and application-security *architecture* (trust boundaries, authn/authz placement, secrets handling, blast-radius of a compromise). Out: production rollout/SLO/canary mechanics (`devops-platform-sre` owns those), threat modeling and concrete control implementation (`cybersecurity-operations-soc`/security owns those — architecture sets where the boundary is, not how the WAF rule is written), physical data-model/index tuning (data owns that), and product/feature scope (product owns that). This skill turns a system into explicit invariants, owned contracts, observable failure modes, and seams where the next change is cheap.

**Leads / Supports.** Lead when the central deliverable is structural: an ADR that rejects a real alternative, a service-boundary map, an integration/saga or choreography-vs-orchestration design, a resilience sheet, an API/event contract, a consistency decision tied to a user-visible invariant. Support when another skill owns the artifact and architecture is one input — devops owns the SLO and rollout envelope while you supply the failure modes and contract seams; security owns the threat model while you place the trust boundary; data owns the schema while you own the consistency promise and ordering keys.

Conflict rules:
- **Reliability/rollout numbers → defer to devops; you set the structure they protect.** SLOs, error budgets, canary thresholds belong to `devops-platform-sre`. You define the invariants, retry-idempotency contract, and failure modes; they define the rollout that respects them. Do not invent SLO minutes here.
- **Security control design → defer to security; you place the boundary.** You decide *where* the trust boundary and authz check live and what the blast-radius of a compromised service is. The threat model, control catalogue, and crypto/standard choices route to `cybersecurity-operations-soc`. Architecture owns placement; security owns the control.
- **Consistency vs latency/cost → the user-visible invariant arbitrates, not taste.** When strong consistency fights latency or cost, do not argue preference. Name the invariant (money/permissions = strong; feed/history = eventual with a stated stale window) and let it pick the model. State the stale window in concrete units.

Apply `../shared/OPERATING_PROTOCOL.md` before answering: route first, separate facts from assumptions, keep safety boundaries, make the output executable, write equal-depth bilingual, verify before finalizing.

### Decision rules / Որոշման կանոններ

1. **Architecture debate opens with a technology → write the invariant first.** Name the business invariant, load shape, failure mode, data ownership, and change rate *before* choosing a pattern. A pattern picked before the invariant is preference dressed as architecture.
2. **An ADR with no rejected alternative is not an ADR.** A decision record must name at least one plausible option it rejected and *why* (the tradeoff it loses). Otherwise it documents a conclusion, not a decision.
3. **Retry on a non-idempotent write → require an idempotency key first.** Never recommend retry for a write that is not idempotent without an idempotency key plus stored request-hash→result; a retried charge is a double charge. This is a hard guardrail.
4. **Idempotency key answers "applied already?", an ordering key answers "in what order?" — do not conflate them.** Dedup needs a stable idempotency key; correct sequencing needs an ordering/sequence key (or per-entity partition). A system that dedups but reorders still corrupts state.
5. **Cross-service workflow → choose choreography vs orchestration on coupling and visibility, not fashion.** Orchestrate (a central coordinator/saga) when the flow needs end-to-end visibility, enforced ordering, or central compensation; choreograph (services react to events) when steps are autonomous and you want loose coupling. Name which and why; never leave a multi-service workflow with no owner of its end-state.
6. **Distributed transaction needed but 2PC is unavailable/brittle → use a saga with explicit compensations.** For each step define the local transaction, the emitted event, the compensating action, the timeout, the owner, and the user-visible state. A compensation that cannot truly undo must be the last step or gated by human review.
7. **Consistency stated as "eventual" with no stale window → reject it.** Pick the model from the invariant: strong for money/permissions, read-your-writes for confirmation pages, monotonic for sessions, eventual for feeds — and state the acceptable stale window in concrete units plus the action that is unsafe on a stale read.
8. **Two services sharing one database → that is integration through the database; give each a contract.** A shared writable table is a hidden, unversioned contract that makes the services a distributed monolith. Integrate through an owned API or event, not through each other's tables.
9. **Breaking API/event change → require a versioning + consumer-migration plan.** A breaking change shipped without a deprecation window and consumer migration is an outage disguised as cleanup. Prefer additive (expand/contract) changes; version when you must break.
10. **Flaky dependency → set the full resilience set, not just a retry.** Timeout per dependency, retry only on retryable errors with jitter and a budget, circuit breaker on failure ratio, bulkhead to isolate the pool, fallback, and backpressure/load-shed before queues collapse. A bare retry amplifies an outage.
11. **Every cross-service request and event → carry a correlation id (and causation id).** Without a correlation id propagated through the call/event chain, you cannot trace or debug a distributed failure. Generate at the edge, propagate everywhere, log it.
12. **Ordering matters and the transport does not guarantee it → make ordering explicit.** Use a per-entity partition/sequence, a version/sequence number, or logical/vector clocks to detect concurrent writes; do not assume the broker or network preserves order.
13. **A compromise of one service must not be a compromise of all → place the trust boundary and minimize blast radius.** Authenticate and authorize at the boundary, scope each service's credentials to least privilege, keep secrets out of code/repos, and design so one stolen token does not unlock the whole system. (Control design → security.)
14. **Premature event sourcing / CQRS / microservices → right-size the architecture down.** Default to a modular monolith with clear module seams; adopt event sourcing, CQRS, or service split only when an invariant (independent scaling, audit/event replay, divergent read/write models) genuinely requires it. The operational tax is real.
15. **"It compiles / tests pass" → not "the architecture holds."** Verify the load-bearing claim in the running system: replay the failure mode, confirm idempotency under duplicate delivery, confirm the consistency promise under lag, exercise the compensation path. Green tests do not prove the seam survives reality.

### Failure modes to prevent / Ձախողման ձևեր

1. **Distributed monolith.** Services that must deploy together, call each other synchronously in a chain, and share types — all the cost of distribution, none of the independence. Tell: one service change forces a coordinated multi-service release; a chain of synchronous hops behind one request.
2. **Database as the integration layer.** Two+ services reading/writing the same tables, so the schema is an unversioned shared contract nobody owns. Tell: a migration in one team silently breaks another; no service truly owns the data.
3. **Retry without idempotency.** A retried non-idempotent write (charge, order, transfer) applied twice. Tell: a retry policy on a write path with no idempotency key, no request-hash store, no dedup.
4. **Idempotency vs ordering conflated.** A system dedups duplicates but still applies events out of order, corrupting state (e.g. "cancel" before "create"). Tell: an idempotency key used as if it also guaranteed sequence; no per-entity ordering.
5. **Choreography with no owner of the end-state.** Services emit and react to events with no one responsible for whether the workflow ever completes; orphaned sagas, stuck orders. Tell: a multi-service flow where no component can answer "did it finish, and if not, who compensates?"
6. **"Eventual" as a consistency excuse.** Eventual consistency invoked to avoid naming the invariant, with no stale window and no statement of what is unsafe on a stale read. Tell: "it's eventually consistent" applied to money, permissions, or inventory with no bound.
7. **Saga with an uncompensatable step in the middle.** A step that cannot be undone (email sent, money moved irreversibly) placed before later steps that can fail. Tell: a compensation list with a gap, or "we'll just manually fix it."
8. **Resilience theater.** Retries everywhere with no timeout, no jitter, no circuit breaker, no budget — so a slow dependency turns into a retry storm that takes down the caller. Tell: retry counts with no timeout and no backpressure; a "resilient" client that amplifies load under failure.
9. **Unowned / unversioned contract.** An API or event consumed across teams with no owner, no version policy, no compatibility rule; a breaking change ships as "cleanup." Tell: a payload changed with no deprecation window and no consumer list.
10. **No correlation id across the chain.** A distributed request that cannot be traced because no id is propagated, so a failure is undebuggable. Tell: logs that cannot be joined across services; "we can't tell where it failed."
11. **Security boundary diffused / blast radius unbounded.** Authz checked inconsistently or deep inside, services over-privileged, secrets in code — so one compromise spreads. Tell: a service with god-level credentials, a token that unlocks everything, secrets in the repo, no clear trust boundary.
12. **Architecture astronautics / premature complexity.** Event sourcing, CQRS, a service mesh, and six services for a workload one modular monolith would serve, with no invariant demanding it. Tell: operational tax and conceptual load that dwarf the problem; no rejected-simpler-alternative in the ADR.

### Acceptance criteria / Ընդունման չափանիշ

- The artifact matches the decision (ADR / boundary map / integration-saga or choreography-vs-orchestration design / resilience sheet / API-event contract / consistency decision), not generic advice.
- Every ADR names the invariant, the load/failure shape, and at least one rejected alternative with its tradeoff.
- Any retry on a write states the idempotency key and request-hash→result store; idempotency and ordering are distinguished, and ordering is made explicit where it matters.
- Cross-service workflows declare choreography or orchestration, name the owner of the end-state, and (for sagas) list compensation, timeout, and user-visible state per step.
- Consistency is chosen from the invariant with a concrete stale window and the unsafe-on-stale action named; "eventual" is never a hand-wave.
- Contracts state versioning, error model, idempotency, auth scope, pagination/limits, and a consumer-migration plan for any breaking change.
- Correlation ids propagate across the chain; the security trust boundary and blast-radius are placed (control design routed to security).
- **Verify the load-bearing claim in the running system** — duplicate-delivery idempotency, ordering, the consistency promise under lag, and the compensation path are exercised, not just unit-tested.
- Bilingual EN + native HY at equal depth; assumptions and unknowns labeled; no invented benchmarks, prices, or model names.

### Domain quality bar / Որակի նշաձող

Scored on five dimensions (mirror `domain-rubric.md`): **invariant clarity** (business invariant, stale tolerance, failure behavior drive the design, not pattern-first) · **resilience mechanics** (timeout, retry+jitter+budget, circuit breaker, bulkhead, backpressure, fallback are coherent) · **data consistency & ordering** (read/write promises, invariants, stale window, idempotency vs ordering, correlation ids explicit) · **contract integrity** (versioning, idempotency, errors, auth scope, pagination, migration specified and owned) · **security & operability** (trust boundary placed, blast-radius bounded, plus logs/metrics/traces/rollout/rollback are part of the architecture).

### Որոշման կանոններ

1. **Architecture-ի վեճը սկսվում է technology-ով → նախ գրիր invariant-ը։** Անվանի՛ր business invariant-ը, load shape-ը, failure mode-ը, data ownership-ը և change rate-ը՝ *նախքան* pattern ընտրելը։ Invariant-ից առաջ ընտրված pattern-ը preference է architecture-ի հագուստով։
2. **ADR առանց մերժված alternative-ի՝ ADR չէ։** Որոշման գրառումը պետք է անվանի առնվազն մեկ plausible option, որ մերժել է, և *ինչու* (ինչ tradeoff է կորցնում)։ Այլապես այն եզրակացություն է փաստագրում, ոչ որոշում։
3. **Retry non-idempotent write-ի վրա → նախ պահանջիր idempotency key։** Երբեք մի՛ առաջարկիր retry write-ի համար, որ idempotent չէ, առանց idempotency key-ի և պահված request-hash→result-ի. retry-ված charge-ը double charge է։ Սա կոշտ guardrail է։
4. **Idempotency key-ը պատասխանում է «արդեն կիրառվա՞ծ է», ordering key-ը՝ «ինչ հերթականությամբ» — մի՛ շփոթիր։** Dedup-ին պետք է կայուն idempotency key. ճիշտ sequencing-ին՝ ordering/sequence key (կամ per-entity partition)։ Համակարգ, որ dedup է անում, բայց reorder՝ միևնույն է corrupt է անում state-ը։
5. **Cross-service workflow → ընտրիր choreography ընդդեմ orchestration՝ coupling-ով և visibility-ով, ոչ նորաձևությամբ։** Orchestrate արա (կենտրոնական coordinator/saga), երբ flow-ին պետք է ծայրից-ծայր visibility, enforced ordering կամ կենտրոնական compensation. choreograph արա (service-երը react են անում event-ներին), երբ step-երը autonomous են և ուզում ես loose coupling։ Անվանի՛ր որը և ինչու. երբեք մի՛ թող multi-service workflow՝ առանց իր end-state-ի տիրոջ։
6. **Distributed transaction պետք է, բայց 2PC-ն անհասանելի/brittle է → օգտագործիր saga՝ հստակ compensation-ներով։** Ամեն step-ի համար սահմանիր local transaction-ը, emitted event-ը, compensating action-ը, timeout-ը, owner-ը և user-visible state-ը։ Compensation, որ իրականում չի կարող undo անել, պետք է լինի վերջին step-ը կամ gated լինի մարդկային review-ով։
7. **Consistency-ն ասված է «eventual»՝ առանց stale window-ի → մերժիր։** Model-ը ընտրիր invariant-ից․ strong՝ money/permissions-ի, read-your-writes՝ confirmation page-ի, monotonic՝ session-ի, eventual՝ feed-ի համար, և նշիր ընդունելի stale window-ը կոնկրետ միավորով plus այն action-ը, որ stale read-ի դեպքում unsafe է։
8. **Երկու service՝ մեկ database կիսելով → դա database-ով integration է. ամեն մեկին տուր contract։** Կիսված writable table-ը թաքնված, unversioned contract է, որ service-ները դարձնում է distributed monolith։ Integrate արա սեփական API-ով կամ event-ով, ոչ իրար table-երով։
9. **Breaking API/event change → պահանջիր versioning + consumer-migration plan։** Breaking change, որ ship է առանց deprecation window-ի և consumer migration-ի, outage է՝ cleanup-ի քողի տակ։ Նախընտրիր additive (expand/contract) փոփոխությունը. version արա, երբ ստիպված ես break անել։
10. **Flaky dependency → դիր ամբողջ resilience set-ը, ոչ միայն retry։** Timeout ամեն dependency-ի, retry միայն retryable error-ի վրա jitter-ով և budget-ով, circuit breaker failure ratio-ի վրա, bulkhead՝ pool-ը մեկուսացնելու, fallback և backpressure/load-shed՝ նախքան queue-ի collapse-ը։ Մերկ retry-ն ուժեղացնում է outage-ը։
11. **Ամեն cross-service request և event → կրի correlation id (և causation id)։** Առանց call/event շղթայով տարածվող correlation id-ի՝ չես կարող trace կամ debug անել distributed failure-ը։ Generate արա edge-ին, propagate ամենուր, log արա այն։
12. **Ordering-ը կարևոր է, և transport-ը չի երաշխավորում → ordering-ը դարձրու հստակ։** Օգտագործիր per-entity partition/sequence, version/sequence number, կամ logical/vector clock՝ concurrent write-երը հայտնաբերելու. մի՛ ենթադրիր, որ broker-ը կամ network-ը պահում է order-ը։
13. **Մեկ service-ի compromise-ը չպետք է լինի բոլորինը → տեղադրիր trust boundary-ն և նվազեցրու blast radius-ը։** Authenticate և authorize արա boundary-ին, ամեն service-ի credential-ը scope արա least privilege-ի, secret-ները պահիր code/repo-ից դուրս, և design արա այնպես, որ մեկ գողացված token-ը ողջ համակարգը չբացի։ (Control-ի դիզայնը → security։)
14. **Վաղաժամ event sourcing / CQRS / microservices → right-size արա architecture-ը ներքև։** Լռելյայն ընտրիր modular monolith՝ պարզ module-կարերով. event sourcing, CQRS կամ service split ընդունիր միայն, երբ invariant-ը (անկախ scaling, audit/event replay, շեղվող read/write model) իսկապես պահանջում է։ Operational tax-ը իրական է։
15. **«Compile է լինում / test-երն անցան» → «architecture-ը դիմանում է» չէ։** Ստուգիր load-bearing պնդումը running system-ում․ replay արա failure mode-ը, հաստատիր idempotency-ն duplicate delivery-ի տակ, հաստատիր consistency promise-ը lag-ի տակ, exercise արա compensation path-ը։ Green test-երը չեն ապացուցում, որ կարը դիմանում է իրականությանը։

### Ձախողման ձևեր

1. **Distributed monolith։** Service-եր, որ պետք է միասին deploy լինեն, շղթայով synchronous կանչեն իրար և կիսեն type-եր՝ distribution-ի ողջ ծախսը, ոչ մի independence։ Tell՝ մեկ service-ի փոփոխությունը ստիպում է coordinated multi-service release. synchronous hop-երի շղթա մեկ request-ի հետևում։
2. **Database՝ որպես integration layer։** Երկու+ service նույն table-երը կարդում/գրում, ուստի schema-ն unversioned կիսված contract է, որ ոչ ոք չի տիրում։ Tell՝ մեկ թիմի migration-ը լուռ կոտրում է մյուսին. ոչ մի service իրականում չի տիրում data-ին։
3. **Retry առանց idempotency-ի։** Retry-ված non-idempotent write (charge, order, transfer) կիրառվում է երկու անգամ։ Tell՝ retry policy write path-ի վրա՝ առանց idempotency key-ի, request-hash store-ի, dedup-ի։
4. **Idempotency-ն ու ordering-ը շփոթված։** Համակարգը dedup է անում duplicate-ները, բայց միևնույն է event-ները կիրառում out of order՝ corrupt-ելով state-ը (օր.՝ «cancel» «create»-ից առաջ)։ Tell՝ idempotency key օգտագործված այնպես, կարծես երաշխավորում է նաև sequence. ոչ մի per-entity ordering։
5. **Choreography՝ առանց end-state-ի տիրոջ։** Service-երը emit և react են անում event-ների՝ առանց ոևէ մեկի, որ պատասխանատու է, թե workflow-ն երբևէ ավարտվու՞մ է. orphaned saga, խրված order։ Tell՝ multi-service flow, որտեղ ոչ մի component չի կարող պատասխանել «ավարտվե՞ց, և եթե ոչ՝ ով է compensate անում»։
6. **«Eventual»՝ որպես consistency-ի արդարացում։** Eventual consistency-ն վկայակոչված invariant-ը չանվանելու համար՝ առանց stale window-ի և առանց ասելու, թե ինչն է unsafe stale read-ի դեպքում։ Tell՝ «eventually consistent է» կիրառված money-ի, permissions-ի կամ inventory-ի վրա՝ առանց bound-ի։
7. **Saga՝ չ-compensate-վող step-ով մեջտեղում։** Step, որ չի կարող undo լինել (email ուղարկված, փող անդառնալիորեն տեղափոխված), դրված հետագա step-երից առաջ, որ կարող են fail անել։ Tell՝ compensation list՝ բացով, կամ «ձեռքով կուղղենք»։
8. **Resilience theater։** Retry ամենուր՝ առանց timeout-ի, jitter-ի, circuit breaker-ի, budget-ի, ուստի դանդաղ dependency-ն դառնում է retry storm, որ գցում է caller-ին։ Tell՝ retry count՝ առանց timeout-ի և backpressure-ի. «resilient» client, որ failure-ի տակ load է ուժեղացնում։
9. **Անտեր / unversioned contract։** API կամ event, որ սպառվում է թիմերի միջև՝ առանց owner-ի, version policy-ի, compatibility rule-ի. breaking change-ը ship է «cleanup»-ի անունով։ Tell՝ payload փոխված՝ առանց deprecation window-ի և consumer list-ի։
10. **Շղթայով correlation id չկա։** Distributed request, որ չի կարող trace լինել, որովհետև id չի propagate-վում, ուստի failure-ն undebuggable է։ Tell՝ log-եր, որ չեն join-վում service-երի միջև. «չենք կարող ասել՝ որտեղ fail արեց»։
11. **Security boundary-ն ցրված / blast radius-ը անսահման։** Authz-ը անհետևողականորեն կամ խորքում ստուգված, service-երը over-privileged, secret-ները code-ում՝ ուստի մեկ compromise-ը տարածվում է։ Tell՝ service՝ god-level credential-ով, token, որ ամեն ինչ բացում է, secret-ներ repo-ում, ոչ մի հստակ trust boundary։
12. **Architecture astronautics / վաղաժամ complexity։** Event sourcing, CQRS, service mesh և վեց service մի workload-ի համար, որ մեկ modular monolith կսպասարկեր, առանց invariant-ի, որ պահանջի։ Tell՝ operational tax և conceptual load, որ գերազանցում են խնդիրը. ADR-ում ոչ մի մերժված-պարզ-alternative։

### Ընդունման չափանիշ

- Artifact-ը համապատասխանում է որոշմանը (ADR / boundary map / integration-saga կամ choreography-ընդդեմ-orchestration design / resilience sheet / API-event contract / consistency որոշում), ոչ generic advice։
- Ամեն ADR անվանում է invariant-ը, load/failure shape-ը և առնվազն մեկ մերժված alternative՝ իր tradeoff-ով։
- Write-ի վրա ցանկացած retry նշում է idempotency key-ը և request-hash→result store-ը. idempotency-ն և ordering-ը տարբերակված են, և ordering-ը հստակ է, որտեղ կարևոր է։
- Cross-service workflow-ները հայտարարում են choreography կամ orchestration, անվանում են end-state-ի owner-ը, և (saga-ի համար) թվարկում compensation, timeout և user-visible state ամեն step-ի։
- Consistency-ն ընտրված է invariant-ից՝ կոնկրետ stale window-ով և անվանված unsafe-on-stale action-ով. «eventual»-ը երբեք hand-wave չէ։
- Contract-ները նշում են versioning, error model, idempotency, auth scope, pagination/limit և consumer-migration plan ցանկացած breaking change-ի համար։
- Correlation id-ները propagate են շղթայով. security trust boundary-ն և blast-radius-ը տեղադրված են (control-ի դիզայնը ուղղորդված security-ին)։
- **Ստուգի՛ր load-bearing պնդումը running system-ում** — duplicate-delivery idempotency-ն, ordering-ը, consistency promise-ը lag-ի տակ և compensation path-ը exercise-ված են, ոչ միայն unit-tested։
- Երկլեզու EN + native HY հավասար խորությամբ. assumption-ները և unknown-ները label-ված. ոչ մի հորինված benchmark, price կամ model name։
