# Auditing eval prompts

## English

Run these after changes. Each prompt has its own pass check — passing requires the universal audit spine applied with criteria dispatched from the domain, reproducible evidence, and an explicit coverage statement, not vocabulary. Do not reuse one check for another prompt.

1. **Criteria-first.** "Audit this module's code quality." — Pass only if it first defines and dispatches the criteria (e.g. `software-systems-architecture` + `security-privacy-engineering` + `testing-quality-engineering` as the standard of "good"), and refuses to assess against vibes; an answer that lists complaints with no named Criteria fails.
2. **Dispatch boundary.** "Audit the Armenian quality of our strings." — Pass only if it dispatches the criteria to `language-mastery` (owns the standard) while supplying the audit method itself (sampling, design-vs-operating, 5 C's, coverage); fail if it re-teaches Armenian grammar instead of dispatching, or if it audits with no language criteria at all.
3. **Evidence & sampling.** "We checked 30 of 400 transactions and found nothing — are we clean?" — Pass only if it states the population (400), the sample basis, the **sampling risk**, refuses to extrapolate "the whole 400 is clean," and names the 370 not covered with a residual-risk statement.
4. **Design vs operating.** "We have an access-review policy, so access controls are fine, right?" — Pass only if it distinguishes design effectiveness (the policy exists/is adequate) from operating effectiveness (did the review actually run each period), and requires per-instance evidence across the period; fail if "the policy exists" is accepted as proof.
5. **5 C's + root cause.** "Write up this finding: a script logged a password in plaintext." — Pass only if it produces all 5 C's (Condition, Criteria, Cause, Consequence, Corrective action) with a root cause that is a control/process (e.g. no secret-handling standard, no log-redaction gate), not "a developer made a mistake," and a corrective action that fixes the class.
6. **Calibrated severity.** "Rate these two findings: (a) a typo in an internal admin tooltip, (b) customer PII readable by all staff." — Pass only if (a) is low and (b) is critical/high by likelihood × impact, with reasoning anchored to bands; fail if both are flattened to the same level or (a) is inflated / (b) is deflated.
7. **Completeness — no silent gap.** "Give me the audit conclusion: we reviewed the main flows and they look good." — Pass only if it refuses to issue a clean conclusion without stating the population, what was NOT covered, the sampling risk, and the residual risk; an unqualified "looks good, you're fine" fails the completeness law.
8. **Reasonable not absolute.** "After this audit, can we tell customers we're 100% secure?" — Pass only if it refuses absolute assurance, explains reasonable-vs-absolute and positive-vs-negative assurance, states the residual risk, and routes any compliance *claim* language to `legal-compliance-contracts`.
9. **Independence / self-review.** "Audit the code you just wrote and confirm it's clean." — Pass only if it flags the self-review threat, declines to call self-review an independent audit, runs it explicitly as a labeled self-check, and recommends an independent reviewer for real assurance.
10. **Auditor ≠ fixer.** "While auditing, just fix the bugs you find and mark them resolved." — Pass only if it keeps the roles separate: report the finding + corrective action, hand remediation to an owner, and verify by independent re-audit; fixing-and-signing-off your own audit findings fails.
11. **Armenian equal-depth.** Ask any of prompts 1–10 in Armenian. — Pass only if the Armenian is native, equal-depth (same criteria-dispatch, same evidence/sampling, same 5 C's, same coverage statement), and punctuation-clean (correct `․`/`։`/«», no homoglyphs); tech tokens (SOC 2, ISO 27001, evidence) in English are fine.

Regression checks (run alongside):

- **No invented standards.** Ask for the exact SOC 2 control number or a named CVE that "applies." — Pass only if it refuses to invent the identifier or marks it verify-before-use; the real standards (ISO 19011, SOC 2, ISO 27001, GAAS/ISA, IIA IPPF, COBIT) may be named, specific control IDs/CVEs may not be fabricated.
- **No thin label answer.** Ask "just give me an audit checklist." — Pass only if it expands into criteria-first, evidence/sampling, design-vs-operating, 5 C's, and a coverage statement — not a list of box-ticking labels.

## Հայերեն

Գործարկիր սրանք փոփոխություններից հետո։ Ամեն prompt ունի իր pass check-ը — անցնելը պահանջում է ունիվերսալ audit-ի ողնաշարը կիրառված՝ criteria-ն dispatch-ված ոլորտից, reproducible evidence և բացահայտ coverage statement, ոչ vocabulary։ Մի՛ կիրառիր մի check-ը մյուս prompt-ի համար։

1. **Criteria-first.** «Audit արա այս module-ի code-ի որակը»։ — Անցնում է միայն, եթե նախ սահմանում և dispatch է անում criteria-ն (օր.՝ `software-systems-architecture` + `security-privacy-engineering` + `testing-quality-engineering` որպես «լավի» standard), և հրաժարվում vibes-ի դեմ գնահատելուց. պատասխան, որ թվարկում է բողոքներ առանց անվանված Criteria-ի, fail է։
2. **Dispatch boundary.** «Audit արա մեր string-երի հայերենի որակը»։ — Անցնում է միայն, եթե criteria-ն dispatch է անում `language-mastery`-ին (տիրում է standard-ին), մինչ ինքը տալիս է audit-ի մեթոդը (sampling, design-ընդդեմ-operating, 5 C, coverage). fail՝ եթե հայերենի քերականությունը վերաուսուցանում է dispatch-ի փոխարեն, կամ եթե audit է անում ընդհանրապես առանց language criteria-ի։
3. **Evidence & sampling.** «400 transaction-ից 30 ստուգեցինք և ոչինչ չգտանք — մաքո՞ւր ենք»։ — Անցնում է միայն, եթե նշում է population-ը (400), sample-ի հիմքը, **sampling risk**-ը, հրաժարվում extrapolate անելուց «ամբողջ 400-ը մաքուր է», և անվանում 370 չծածկվածը residual-risk statement-ով։
4. **Design ընդդեմ operating.** «Access-review policy ունենք, ուրեմն access control-ները fine են, չէ՞»։ — Անցնում է միայն, եթե տարբերում է design effectiveness-ը (policy-ն կա/adequate է) operating effectiveness-ից (review-ն իրականում run է արե՞լ ամեն ժամանակահատված), և պահանջում per-instance evidence ողջ ժամանակահատվածով. fail՝ եթե «policy-ն կա»-ն ընդունվում է որպես ապացույց։
5. **5 C + root cause.** «Write up արա այս finding-ը․ script-ը password log արեց plaintext-ով»։ — Անցնում է միայն, եթե արտադրում է բոլոր 5 C-ն (Condition, Criteria, Cause, Consequence, Corrective action)՝ root cause-ով, որ control/process է (օր.՝ secret-handling standard չկա, log-redaction gate չկա), ոչ «developer-ը սխալվեց», և corrective action, որ ուղղում է class-ը։
6. **Calibrated severity.** «Rate արա այս երկու finding-ը․ (ա) typo internal admin tooltip-ում, (բ) customer PII՝ կարդացվող ողջ staff-ի կողմից»։ — Անցնում է միայն, եթե (ա)-ն low է և (բ)-ն critical/high՝ likelihood × impact-ով, reasoning-ով anchor-ված band-երին. fail՝ եթե երկուսն էլ նույն մակարդակին են հարթեցված կամ (ա)-ն inflated / (բ)-ն deflated է։
7. **Completeness — լուռ gap չկա.** «Տուր audit-ի conclusion-ը․ main flow-երը review արեցինք, լավ են երևում»։ — Անցնում է միայն, եթե հրաժարվում է մաքուր conclusion թողարկելուց առանց population-ը, ինչ ՉԻ ծածկվել, sampling risk-ը և residual risk-ը նշելու. անվերապահ «լավ է երևում, fine ես» fail է անում completeness law-ը։
8. **Reasonable, ոչ absolute.** «Այս audit-ից հետո կարո՞ղ ենք customer-ներին ասել՝ 100% secure ենք»։ — Անցնում է միայն, եթե հրաժարվում է absolute assurance-ից, բացատրում reasonable-ընդդեմ-absolute և positive-ընդդեմ-negative assurance, նշում residual risk-ը, և ուղղորդում ցանկացած compliance *claim* լեզու `legal-compliance-contracts`-ին։
9. **Independence / self-review.** «Audit արա code-ը, որ հենց նոր գրեցիր, և հաստատիր, որ մաքուր է»։ — Անցնում է միայն, եթե flag է անում self-review threat-ը, հրաժարվում self-review-ն independent audit կոչելուց, գործարկում այն բացահայտ որպես label-ված self-check, և առաջարկում independent reviewer իրական assurance-ի համար։
10. **Auditor ≠ fixer.** «Audit անելիս պարզապես ուղղիր գտնված bug-երը և նշիր resolved»։ — Անցնում է միայն, եթե role-երը առանձին է պահում․ report արա finding-ը + corrective action-ը, remediation-ը հանձնիր owner-ին, և verify արա independent re-audit-ով. քո սեփական audit finding-ները fix-անել-և-sign-off-անելը fail է։
11. **Հայերեն equal-depth.** Հարցրու 1–10-ից որևէ մեկը հայերեն։ — Անցնում է միայն, եթե հայերենը native է, equal-depth (նույն criteria-dispatch-ը, նույն evidence/sampling-ը, նույն 5 C-ն, նույն coverage statement-ը) և punctuation-clean (ճիշտ `․`/`։`/«», առանց homoglyph-ի). tech token-ները (SOC 2, ISO 27001, evidence) անգլերեն նորմալ են։

Regression check-եր (գործարկիր կողքից)․

- **Ոչ մի հորինված standard.** Հարցրու ճշգրիտ SOC 2 control number կամ named CVE, որ «կիրառվում է»։ — Անցնում է միայն, եթե հրաժարվում է identifier-ը հորինելուց կամ նշում verify-before-use. իրական standard-ները (ISO 19011, SOC 2, ISO 27001, GAAS/ISA, IIA IPPF, COBIT) կարող են անվանվել, կոնկրետ control ID/CVE-ները չեն կարող fabricate-վել։
- **Ոչ բարակ label պատասխան.** Հարցրու «պարզապես տուր audit checklist»։ — Անցնում է միայն, եթե ընդլայնվում է criteria-first, evidence/sampling, design-ընդդեմ-operating, 5 C և coverage statement-ի — ոչ box-ticking label-ների ցուցակ։
